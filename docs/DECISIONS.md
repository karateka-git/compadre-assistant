# Журнал решений

Записи отражают решения на указанную дату. Ранние ограничения Telegram-only и
отложенный RAG уже пересмотрены последующей реализацией. Для текущего поведения
используйте [ARCHITECTURE.md](ARCHITECTURE.md) и [RUN.md](RUN.md).
Разрешение пересоздавать development-БД не распространяется на production:
его правила заданы в [PRODUCTION.md](PRODUCTION.md).

## 2026-06-07. Форма проекта

Статус: частично пересмотрено решением "Выбор стека для первой реализации" ниже. Docker-first и итеративный подход остаются актуальными; Kotlin-first больше не актуален.

Решение:

- Развивать проект итеративно, под контролем пользователя.
- Использовать Docker-first подход.
- Первоначально считать Kotlin предпочтительным направлением для основного сервиса, пока лёгкое исследование стека не покажет обратное.
- Считать Codex automation обязательным будущим компонентом.
- Оставить Python как fallback или sidecar для извлечения текста статей и RAG.

Причины:

- Docker-first делает локальную разработку ближе к будущему развёртыванию на VPS.
- Kotlin интересен для изучения и подходит для service orchestration, bot polling, доступа к SQLite и HTTP-вызовов к LLM.
- Python может оказаться сильнее на будущих этапах: article extraction, embeddings и RAG. Поэтому границы модулей должны оставаться заменяемыми.
- Codex automation не должна заменять бота. Она должна периодически ревьюить сохранённые статьи и контекст Obsidian.

Последствия:

- Начинаем с планирования и исследования стека внутри папки проекта.
- Не фиксируем подробную RAG-схему слишком рано.
- Проектируем adapters и services так, чтобы Telegram, VK, automation и будущий RAG могли использовать общую логику обработки статей.

## 2026-06-07. Выбор стека для первой реализации

Решение:

- Выбираем Python как основной и единственный стек первой реализации.
- Выбираем Telegram как единственный канал MVP.
- VK откладываем на будущий adapter.
- Выбираем Docker Compose с начала проекта.
- Выбираем `aiogram` для Telegram polling и отправки ответов.
- Выбираем OpenAI-совместимый Python LLM adapter через переменные окружения.
- Выбираем SQLite через stdlib `sqlite3`, простые SQL-миграции и repository layer.
- Выбираем `trafilatura` для извлечения чистого текста статей.

Причины:

- Python быстрее доведёт MVP до работающего Telegram-бота со статьями, LLM-анализом и SQLite.
- Telegram достаточно для первой полезной версии; VK не должен усложнять стартовый конфиг, архитектуру и критерии готовности.
- `aiogram` закрывает polling и базовую bot-инфраструктуру без ручной реализации Telegram Bot API.
- Python сильнее в извлечении текста статей и будущем RAG, поэтому больше не нужен отдельный Python sidecar.
- stdlib `sqlite3` достаточно прост для начальной схемы; SQLAlchemy можно добавить позже, если запросы и модель усложнятся.

Последствия:

- Этап 2 начинается с Python-каркаса, Dockerfile, `docker-compose.yml`, `.env.example` и минимального запуска приложения.
- Минимальный набор локальных инструментов и Docker-зависимостей фиксируется в `docs/SETUP.md`.
- В MVP нет VK token и VK adapter.
- В коде должны рано появиться интерфейсы для article loading, article extraction, LLM analysis и storage.
- Telegram adapter не должен знать о SQL, LLM-клиенте и деталях извлечения статей.
- Внутренняя модель сообщений остаётся достаточно общей, чтобы VK можно было добавить позже без переписывания article pipeline.
- Подробности исследования зафиксированы в `docs/STACK_RESEARCH.md`.

## 2026-06-27. Миграции до первого MVP

Статус: пересмотрено решением "Пересоздание SQLite на этапе разработки" от
2026-07-20 ниже.

Решение:

- Сохранить реализованный механизм SQL-миграций.
- До выхода первого MVP изменять одну начальную миграцию `0001_initial_schema.sql`.
- После изменения начальной схемы удалять локальную `data/app.db` и создавать базу заново.
- Начать добавлять новые миграции `0002`, `0003` и далее после появления реальных данных, которые нельзя пересоздать.

Причины:

- До реального использования базы начальная схема будет часто меняться.
- Поддержка истории каждой промежуточной версии сейчас не приносит практической пользы.
- Готовый механизм миграций понадобится после появления ценных пользовательских данных.

Последствия:

- До первого MVP локальная база считается временной и может быть удалена.
- Изменения `0001_initial_schema.sql` требуют пересоздания локальной базы.
- После появления реальных данных применённые миграции больше не изменяются.

## 2026-07-20. Пересоздание SQLite на этапе разработки

Решение:

- Пока проект находится в активной разработке, не добавлять последовательные
  миграции `0002`, `0003` и далее.
- При изменении схемы обновлять единственный файл
  `0001_initial_schema.sql` так, чтобы он описывал полную актуальную схему.
- Не создавать технического `Legacy user` в новой базе: таблица `app_users` после
  применения схемы пуста, первого пользователя создаёт только `/register`.
- После изменения схемы удалять локальную `data/app.db` и создавать базу заново
  при следующем запуске приложения.
- Механизм применения SQL-миграций сохранить как часть каркаса проекта, но
  историю промежуточных схем пока не вести.
- Перейти к накопительным миграциям только после отдельного решения о том, что
  в базе появились данные, которые требуется сохранять между изменениями схемы.

Причины:

- Текущая база содержит только данные разработки и может быть пересоздана.
- Поддержка переходов между промежуточными схемами сейчас усложняет разработку,
  не защищая ценные пользовательские данные.
- Одна полная начальная схема упрощает проверку структуры базы Этапа 9.

Последствия:

- Изменения схемы GitHub connector и следующих этапов вносятся в
  `0001_initial_schema.sql`.
- Пересоздание `data/app.db` удаляет все локальные статьи, анализы, пользователей,
  привязки каналов, настройки vault и заметки.
- Перед удалением базы не требуется переносить данные, пока это решение остаётся
  действующим.

## 2026-07-22. SQLite-модель Obsidian vault

Решение:

- Хранить разрешённые GitHub App installation IDs отдельно от подключения
  vault; один пользователь может иметь несколько разрешённых installations.
- Ограничить `obsidian_vaults` одной активной записью на `app_user_id`.
- Хранить полный Markdown и frontmatter заметки в `obsidian_notes`.
- Хранить tags и wikilinks в отдельных связанных таблицах с сохранением порядка.
- Дублировать `app_user_id` в пользовательских таблицах vault и защищать связи
  составными внешними ключами, чтобы SQLite контролировал изоляцию данных.
- Координировать будущую синхронизацию Telegram/VK процессов коротким lease в
  SQLite.
- Хранить ожидающее подтверждение замены или отключения vault в SQLite с TTL и
  одной активной записью на пользователя.

Причины:

- Разрешённые installations принадлежат пользователю, а не одному repository.
- Нормализованные tags и wikilinks пригодны для последующего FTS/RAG без
  повторного изменения формы хранения Markdown.
- Составные внешние ключи не позволяют случайно связать заметку или lease с
  vault другого пользователя.
- SQLite lease работает между отдельными контейнерами `tg_catcher` и
  `vk_catcher`, использующими общий файл базы.
- Подтверждение, начатое в одном привязанном канале, доступно общему incoming-flow
  независимо от процесса adapter.

Последствия:

- Замена или удаление vault каскадно удаляет его локальные заметки и lease.
- Отзыв installation удаляет связанный vault, только если installation
  действительно исчезла из разрешённого пользователю набора.
- Access tokens, device codes и приватный PEM-ключ в этих таблицах не хранятся.

## 2026-07-22. GitHub App authentication runtime

Решение:

- Считать GitHub App connector выключенным, если вся группа GitHub-настроек
  отсутствует, и отклонять частично заполненную конфигурацию.
- Использовать Client ID для Device Flow и для claim `iss` App JWT; App ID
  хранить как обязательный идентификатор регистрации.
- Подписывать App JWT алгоритмом RS256 через `PyJWT[crypto]`, с `iat` на минуту в
  прошлом и `exp` через девять минут.
- Использовать GitHub REST API version `2026-03-10` и
  `application/vnd.github+json` для API-запросов.
- Создавать один in-memory Device Flow coordinator на процесс adapter.
- Выполнять polling Device Flow в daemon thread, соблюдая выданный GitHub
  interval и увеличивая его на пять секунд при `slow_down`.
- Хранить device code и user access token только в памяти. После авторизации
  записывать в SQLite публичные GitHub user ID/login и разрешённые installation IDs
  через новое соединение background thread.
- Выпускать installation access token только по короткому App JWT и при
  необходимости ограничивать token одним repository ID.

Причины:

- Device Flow подходит headless Telegram/VK сервису и не требует callback URL
  или Client secret.
- Отдельное соединение SQLite не передаёт connection входящего сообщения между
  потоками после закрытия request scope.
- Короткие App/installation tokens и скрытый `repr` уменьшают риск утечки через
  хранение, диагностику и исключения.

Последствия:

- `/register` является единым onboarding-сценарием: создаёт пользователя, просит
  имя общего профиля, затем ссылку repository и при необходимости запускает
  Device Flow.
- Имя профиля хранится в `app_users.display_name`, общее для Telegram и VK и
  изменяется командой `/name <имя>`. Внутренний `app_user_id` не показывается в
  пользовательских ответах.
- Отдельные пользовательские команды `/github_connect` и `/github_vault`
  отсутствуют. GitHub-аккаунт является внутренней частью подключения vault.
- Installation URL показывается только после авторизации, если App не установлено
  или не имеет доступных repositories. Если App уже установлено, лишний шаг
  установки пропускается.
- У пользователя приложения есть один активный подключённый GitHub-аккаунт;
  SQLite хранит его публичные GitHub user ID и login, но не пользовательский token.
- Короткий claim активной попытки хранится в SQLite по `app_user_id`, поэтому
  Telegram и VK не запускают две параллельные авторизации одного пользователя.
- После Device Flow проверка исходного repository продолжается в background
  thread через отдельное короткое SQLite-соединение.
- Telegram и VK identities, привязанные к одному `app_user_id` через `/link`,
  автоматически используют тот же GitHub-аккаунт и vault без повторной
  авторизации.
- Ответы `да` и `нет` применяются только к существующему pending-подтверждению;
  без него бот сообщает, что подтверждать нечего.
- Перезапуск процесса удаляет незавершённую Device Flow session; пользователь
  повторно присылает ссылку repository.
- Live-подключение требует зарегистрированного GitHub App, включённого Device
  Flow и читаемого локального PEM.

## 2026-07-22. Повторная отправка ответов в Telegram и VK

Решение:

- Использовать общий sync/async retry-каркас presentation-слоя с тремя попытками
  и коротким экспоненциальным backoff `0.5`, `1.0` секунды.
- Повторять только временные сетевые, rate-limit и серверные ошибки; постоянные
  ошибки запроса, доступа и авторизации сразу логировать без повтора.
- Повторять каждый chunk отдельно, не переотправляя уже доставленные части длинного
  сообщения.
- Для Telegram соблюдать `retry_after`, возвращённый API. Учитывать, что Bot API не
  предоставляет idempotency key для `sendMessage`, поэтому после потерянного HTTP-
  ответа небольшой риск дубликата принципиально остаётся.
- Для VK сохранять один `random_id` на все попытки одного chunk, чтобы повтор был
  идемпотентным со стороны VK API.

## 2026-07-22. Подтверждаемая запись в Obsidian vault

Решение:

- GitHub App получает минимальные разрешения `Contents: read and write` и
  `Metadata: read`.
- RAG формирует конкретное предложение `add`, `update` или `skip` и показывает
  его пользователю до изменения vault.
- GitHub изменяется только после явного ответа `да` на текущее ожидающее
  предложение этого `app_user`.
- Подтверждённые `add` и `update` записываются прямым commit в default branch;
  отдельная ветка и pull request не создаются.
- Перед commit повторно проверяются HEAD и target blob SHA. Конфликт отменяет
  запись и требует пересчёта предложения.
- GitHub является source of truth для vault; SQLite хранит локальную копию,
  поисковый индекс и состояние article/review workflow.

Причины:

- Основная цель проекта — не только рекомендовать изменения, но и создавать и
  обновлять Obsidian-заметки после контроля пользователя.
- Явное подтверждение защищает vault от ошибочного автоматического решения LLM.
- Прямой commit проще для личного vault, чем обязательный branch/PR workflow.
- Optimistic concurrency по SHA не позволяет незаметно перезаписать изменения,
  сделанные пользователем после подготовки предложения.

Последствия:

- Прежнее решение оставить GitHub connector read-only отменено.
- Статья остаётся в `needs_obsidian_review`, пока предложение не подтверждено и
  успешно применено либо не подтверждён `skip`.
- `cleaned_text` очищается только после успешного завершения подтверждённого
  review; ошибка GitHub сохраняет данные для безопасного повтора.
- Первая реализация write-back создаёт и обновляет только Markdown внутри vault
  root и не удаляет заметки.

## 2026-07-23. Выбор repository и корня Obsidian vault

Решение:

- Принимать только HTTPS URL вида `github.com/owner/repository`; branch, query,
  fragment и вложенные GitHub-страницы не являются repository URL.
- Для каждого installation ID подключённого `app_user_id` запрашивать token,
  ограниченный конкретным repository и permission `Contents: write`.
- Читать `repository_id`, канонические owner/name и default branch из GitHub API,
  а каталог vault проверять через Contents API.
- Пустой `vault-path` означает корень repository; непустой путь хранится как
  относительный POSIX path.
- Первый vault сохранять сразу. Другой repository или path сначала сохранять как
  предложение замены с TTL 10 минут и применять только после `да`.
- Не начинать загрузку Markdown в сценарии выбора: первая синхронизация является
  отдельным следующим подэтапом с lease и атомарной фиксацией source SHA.

Причины:

- Пользователь не вводит installation ID, repository ID или branch вручную.
- Repository-scoped write token проверяет итоговое требование приложения:
  GitHub App может читать и записывать именно этот repository. Публичная
  доступность только для чтения не считается достаточной.
- Разделение выбора и синхронизации сохраняет простой атомарный контракт каждого
  application-сценария.

## 2026-07-27. Инкрементальная локальная копия GitHub vault

Решение:

- После первого выбора и подтверждённой замены vault сразу запускать
  синхронизацию; при временной ошибке сохранять само подключение и предлагать
  повтор через `/github_sync`.
- Условно читать HEAD выбранной ветки с `If-None-Match`, затем сравнивать SHA
  дерева именно корневой папки vault.
- Получать полный recursive tree этой папки, хранить manifest по path/blob SHA и
  скачивать содержимое только новых и изменённых `.md` blobs.
- Полностью сохранять Markdown и отдельно извлекать title, frontmatter, tags и
  wikilinks. Отсутствующие в удалённом manifest заметки удалять локально.
- Координировать Telegram и VK через существующий SQLite lease на один vault.
- Фиксировать новый commit/tree SHA и `last_synced_at` только после успешного
  сохранения всех заметок и удаления устаревших путей. При частичной ошибке
  source SHA остаётся прежним, поэтому следующий запуск повторяет снимок.

Причины:

- ETag быстро завершает проверку неизменившейся ветки, tree SHA отсекает commits
  вне vault, а blob SHA исключает повторное скачивание заметок.
- Полный удалённый manifest необходим не только для обновлений, но и для
  обнаружения удалённых файлов.
- Локальная копия остаётся пригодной для будущего RAG при временной
  недоступности GitHub.

## 2026-07-23. Единый реестр chat-команд

Решение:

- Описывать каждую slash-команду одним элементом `ChatCommand`: точное имя,
  подсказка аргументов, раздел справки и пользовательское описание.
- Распознавать команды только через общий `ParsedChatCommand`, не используя
  независимые строковые `startswith`-проверки.
- Генерировать `/help` обходом `ChatCommand` по разделам; строковое представление
  элемента отвечает за одну Markdown-строку справки.
- Обычную отправку URL и контекстные ответы `да`/`нет` описывать рядом со списком,
  но не выдавать за slash-команды.

Причины:

- Имя команды, parser и справка больше не расходятся при развитии проекта.
- Новая команда не может обрабатываться вне реестра и автоматически появляется
  в `/help` после добавления metadata.
- Точное распознавание не путает команды с общим prefix, например `/link` и
  `/link_code`.

## 2026-07-30. Подтверждаемое отключение Obsidian vault

Решение:

- `/github_disconnect` только создаёт подтверждение действия с TTL 10 минут.
- Ответ `да` удаляет активный vault и его локальные Markdown/metadata через
  SQLite cascade; ответ `нет` сохраняет подключение.
- Не удалять GitHub account и installation IDs: отключается конкретный vault, а
  не авторизация GitHub.
- Сохранять пользователя, связанные Telegram/VK identities, статьи, анализы и
  историю приложения. Никогда не изменять удалённый GitHub repository при
  отключении.

Причины:

- Локальный каталог можно восстановить повторной синхронизацией, а удаление
  пользовательских данных или содержимого GitHub было бы несоразмерным действию
  «отключить vault».
- Сохранённая GitHub-авторизация позволяет позднее подключить тот же или другой
  разрешённый repository без лишнего Device Flow.

## 2026-07-30. Ленивая шестичасовая проверка vault

Решение:

- Перед обработкой URL статьи сравнивать текущее время с `last_checked_at`
  активного vault.
- Считать локальную копию свежей строго меньше шести часов; на границе шести
  часов запускать существующую инкрементальную синхронизацию.

## 2026-07-30. Гибридная загрузка GitHub snapshot

Решение:

- Сохранять recursive Git tree источником manifest, размеров и blob SHA.
- При 50 или более изменённых Markdown/instruction-файлах загружать ZIP archive
  неизменяемого commit SHA; при меньшем числе скачивать только изменённые blobs.
- Не использовать archive, если Git tree не сообщает размеры всех blobs либо
  суммарный размер vault превышает 100 MiB.
- Если ZIP всего repository превышает 100 MiB из-за содержимого вне вложенного
  vault, безопасно вернуться к точечной загрузке blobs из vault manifest.
- Читать ZIP только в памяти, не извлекать файлы на диск и принимать лишь точные
  vault-relative пути из manifest.
- Ограничить ZIP 100 MiB, суммарный извлечённый текст 64 MiB, Markdown 4 MiB,
  конфигурацию 64 KiB и отдельный instruction-файл 256 KiB.
- Использовать общий connection pool, read timeout 30 секунд и до трёх попыток
  безопасного GET; для HTTP 429/5xx учитывать `Retry-After`.
- Не повторять автоматически будущие запросы записи: retry этого решения
  относится только к безопасным GET.

Причины:

- Отдельный REST-запрос для каждой заметки делал стабильный единичный timeout
  вероятным уже на vault из сотен файлов и плохо масштабировался до тысяч.
- ZIP сокращает первую массовую загрузку до постоянного малого числа HTTP
  запросов, а tree сохраняет SHA для последующих точечных обновлений.
- Пороговый режим не загружает весь repository при обычном изменении одной
  заметки.
- Явные лимиты защищают процесс от чрезмерного archive и decompression bomb.

## 2026-08-04. Linear cosine search и Reciprocal Rank Fusion для MVP

Решение:

- Выполнять FTS5/BM25 и vector similarity как две независимые ранжированные
  ветви по разным compact query Этапа 10.6.
- Для MVP читать float32 vectors текущего vault из SQLite и вычислять cosine
  similarity линейно в application-сервисе. До `embed_query()` проверять
  согласованность chunk/embedding markers, моделей, dimension, IDs и hashes.
- Нормализовать cosine из `[-1, 1]` в `[0, 1]` для диагностики, но не смешивать
  это значение напрямую с BM25 score.
- Объединять до 20 кандидатов каждой ветви через стандартный Reciprocal Rank
  Fusion: `score = sum(1 / (60 + rank))`; возвращать до 10 лучших chunks.
- Сохранять в каждом hybrid hit итоговый score, ranks и исходные scores обеих
  ветвей, чтобы recommendation и диагностика видели происхождение результата.
- Пробрасывать отсутствие/stale embedding index и provider errors из 10.7;
  явный FTS-only режим с признаком fallback реализовать отдельно в 10.8.

Причины и последствия:

- BM25 и cosine имеют разные шкалы, поэтому сложение исходных scores было бы
  нестабильным и зависело бы от конкретной модели и размера corpus.
- RRF устойчив к шкалам и поднимает chunks, подтверждённые обеими ветвями.
- Linear scan имеет сложность `O(chunks × dimension)`, но для текущего личного
  vault остаётся простым и проверяемым решением без нового runtime-компонента.
- Если измерения покажут недостаточную latency на крупных vault, уже записанное
  разделение ports позволяет заменить scan на FAISS или vector database из
  бэклога без изменения hybrid workflow.

Решение:

- Использовать существующий стандартный Python `logging` и console stream
  контейнеров, не вводить отдельные `EmbeddingTelemetryObserver` или
  `StructuredLoggingEmbeddingObserver`.
- Передавать через application port только безопасный `EmbeddingCallContext` с
  `operation_id`, `app_user_id`, vault ID и необязательным article ID. Usage,
  billing и logging metadata не входят в domain `EmbeddingVector`.
- Писать стабильные `event=embedding_*` и `key=value` поля для начала операции,
  каждого окончательного SDK batch, итоговой сводки и FTS fallback. Не писать
  API keys, исходные тексты, compact query и vector values.
- Сохранять штатные retries OpenAI SDK с `max_retries=2`. Adapter измеряет весь
  логический SDK-вызов и окончательный исход, но не подменяет SDK собственным
  retry loop и не обещает per-attempt telemetry, которой SDK не предоставляет.
- Оценивать стоимость только из фактического `response.usage` и полного
  optional тарифного блока: цена миллиона входных токенов, валюта и версия
  тарифа. Кабинет provider остаётся источником истины фактического списания.

Причины и последствия:

- Все operational-события фильтруются и агрегируются одним способом в Docker и
  будущей централизованной системе логов.
- Correlation scope позволяет анализировать сбой индексации или query и связанный
  fallback без синхронной telemetry-записи в рабочую SQLite.
- Изменение цены не требует правки кода; без тарифа embeddings и usage-логи
  продолжают работать, а оценочная стоимость честно остаётся неизвестной.

## 2026-08-04. Сохраняемый proposal и подтверждаемый GitHub write-back

Решение:

- Хранить одно pending Obsidian-предложение на `app_user_id` вместе с article,
  analysis и vault IDs, полным предлагаемым Markdown и commit/tree/blob SHA
  снимка, по которому оно было рассчитано.
- Не изменять GitHub до явного ответа `да`. Ответ `нет` закрывает proposal без
  изменения vault; прочий пользовательский ввод не запускает конкурирующий
  article workflow, пока решение ожидается.
- Координировать ручной sync и write-back одним SQLite lease. Перед записью
  повторно читать HEAD, tree и target blob/content; stale proposal закрывать как
  conflict без перезаписи remote-файла.
- Записывать только `.md` внутри настроенного vault root через repository-scoped
  installation token и Contents API прямым commit в default branch. В первой
  версии разрешены `add` и `update`, но не удаление.
- Не выполнять автоматический retry изменяющего PUT. Если HTTP-ответ commit был
  потерян, следующий явный ответ `да` сравнивает remote Markdown с proposal и
  завершает локальную транзакцию без второго commit.
- После подтверждённого commit одной SQLite-транзакцией обновлять локальную
  заметку и vault SHA, применять proposal, переводить статью в `reviewed`,
  очищать `cleaned_text` и инвалидировать поколения chunk/embedding index.
  Подтверждённый `skip` выполняет ту же финализацию без обращения к GitHub.
- Историю применённых proposals не удалять при замене активного vault. Повторная
  ссылка на `reviewed`-статью возвращает сохранённый анализ и результат без
  загрузки страницы; только `/reanalyze` явно начинает новый цикл.

Причины и последствия:

- Пользователь видит полное предлагаемое изменение до записи, а Telegram и VK
  работают с одним pending-состоянием пользователя.
- Optimistic concurrency защищает ручные и внешние изменения vault от тихой
  перезаписи, а lease исключает гонку sync/write между связанными каналами.
- GitHub остаётся source of truth заметок, но завершение article/review workflow
  атомарно фиксируется в SQLite и пригодно для безопасного повтора после сбоя.

## 2026-08-23. Per-note source state и global markers поискового индекса

Решение:

- Сохранить global chunk/embedding markers как быстрый признак того, что всё
  поколение vault полностью готово и разрешено для FTS/semantic search.
- Не использовать отсутствие global marker как причину безусловно удалять все
  chunks. Рядом с каждой заметкой хранить проиндексированные `source_blob_sha`
  и `index_signature`; их расхождение точно определяет dirty notes.
- После подтверждённого GitHub write-back немедленно запускать общий локальный
  indexing workflow после освобождения lease. Поскольку commit уже обновил
  `last_checked_at`, workflow восстанавливает stale index из SQLite без нового
  GitHub-запроса.
- Для dirty note применять стабильный `chunk_key` diff: сохранять IDs
  неизменившихся chunks, обновлять изменившиеся, добавлять новые и удалять
  исчезнувшие. Embeddings переиспользовать по `chunk_id`, document model и
  `content_hash`.
- Публиковать chunk marker только при отсутствии dirty notes, embedding marker —
  только при полном совместимом наборе vectors. При сбое provider считать
  commit успешным, оставить FTS доступным и повторять только недостающую
  semantic-работу при следующем sync/preflight.

Причины:

- GitHub commit нельзя откатывать или выдавать за неуспешный из-за отдельного
  платного embedding API.
- Прежняя invalidation не сохраняла причину stale-состояния. Добавление одной
  статьи превращалось в полный rebuild, меняло все SQLite `chunk_id`, каскадно
  удаляло совместимые vectors и повторно оплачивало весь corpus.
- Per-note state отвечает на вопрос «что изменить», а global marker — «готово ли
  всё поколение». Такое разделение сохраняет fail-closed поиск без отказа от
  инкрементальности Этапов 10.2 и 10.5.

Последствия:

- Обычный `add`/`update` индексирует только затронутую заметку и её изменённые
  chunks; смена parser/policy логически затрагивает все заметки.
- Ошибка semantic-индексации показывается как post-commit предупреждение и
  записывается на этапе `obsidian_index`, не меняя применённый proposal обратно
  в pending.
- Начальная development-схема получает таблицу per-note states; отдельная
  накопительная миграция до MVP не создаётся, локальная БД пересоздаётся.

## 2026-08-23. Source/FTS readiness не зависит от optional embeddings

Решение:

- Считать GitHub source snapshot готовым после успешной записи Markdown,
  обязательных instruction-файлов, chunks и chunk global marker. После этого
  публиковать commit/tree SHA и только затем обращаться к embedding provider.
- Перехватывать только типизированный `EmbeddingProviderError` как degraded
  semantic mode. Оставлять embedding marker отсутствующим и возвращать
  структурированное предупреждение, сохраняя source/FTS результат успешным.
- Не маскировать локальные invariants, ошибки SQLite и неизвестные runtime
  failures semantic fallback-ом.
- Перед fetch/extraction/LLM статьи разрешать fallback после sync-ошибки или
  занятого lease только при одновременном наличии HEAD SHA, tree SHA и
  актуального chunk marker. Иначе останавливать incoming-flow до платных стадий.
- Не повторять полную сбойную embedding-индексацию из article preflight внутри
  шестичасового freshness-window. Повторять её по явному `/github_sync`, при
  post-commit обновлении dirty chunks или очередной плановой GitHub-проверке.

Причины и последствия:

- Embeddings — восстанавливаемая платная проекция, а не часть GitHub source of
  truth. Их недоступность ухудшает поиск до FTS, но не делает Markdown
  несинхронизированным.
- Наличие строк `obsidian_notes` само по себе не доказывает готовность локальной
  копии: sync мог оборваться между source, chunks и публикацией markers.
- Первая незавершённая синхронизация больше не расходует LLM-токены статьи,
  которая всё равно не сможет пройти safe review; ранее сохранённый проверенный
  snapshot по-прежнему поддерживает offline/failure fallback Этапа 9.10.
- Недоступный embedding provider не умножает стоимость при каждой входящей
  статье: до следующей осмысленной точки повтора semantic search деградирует до
  FTS, а пользователь получает явное предупреждение.

## 2026-09-07. Пересоздание development-БД перед запуском

Статус: временное решение, действующее только на этапе разработки. После
завершения этого этапа от пересоздания с потерей данных отказываемся в пользу
миграций с сохранением данных. Разрешение удалять БД без подтверждения тогда
утрачивает силу; любое удаление требует отдельного явного разрешения пользователя.

Пользователь подтвердил, что проект остаётся в разработке и сохранение
промежуточных данных не требуется. При изменении схемы обновляем `0001`,
останавливаем использующие БД процессы, удаляем локальный SQLite-файл и его
оставшиеся WAL/SHM-файлы, затем запускаем проект с новой базой. Дополнительное
подтверждение, перенос данных и временная копия для этой операции не нужны.
Каталог `data/` и PEM сохраняются. Обычные изменения записей БД или кода без
изменения схемы не требуют очистки.

Это порядок работы перед запуском, а не автоматическая возможность startup:
текущие скрипты несовместимость схемы не определяют и БД не удаляют.
Накопительные миграции и совместимость промежуточных схем откладываются до
отдельного решения о переходе к сохраняемым данным.

## 2026-09-07. Checkpoint-сохранение embedding batches (10.23)

Решение:

- Заменить corpus-контракт `embed_documents` на ленивый
  `iter_document_batches`: adapter выдаёт проверенный пакет, application-indexer
  сохраняет его до возобновления generator и следующего HTTP-запроса.
- Разделить SQLite `save_batch` и `complete_generation`. Каждый batch фиксируется
  отдельной короткой транзакцией. Финализация под write lock проверяет chunk
  signature, полный набор IDs, hashes, document model и размерность vectors.
- При повторе использовать уже сохранённые совместимые checkpoints. При смене
  dimension удалять несовместимые строки в транзакции первого нового пакета,
  чтобы смешанный старый профиль не заставил повторно оплатить новые vectors.
- Проверять владельца и срок sync lease перед запросами и внутри транзакций
  сохранения/публикации. После потери lease прекращать работу; успешные предыдущие
  checkpoints остаются. Ошибки SQLite и runtime не переводить в provider fallback.
- Читать JSON через raw-response интерфейс установленного SDK, сохраняя штатные
  retries. Это позволяет отличать malformed 200 от HTTP/transport errors и
  диагностировать исходные типы без неявного преобразования SDK.
- Логировать только фиксированные поля количества, наличия и типов данных,
  HTTP status, ограниченный request ID и тип глубинной причины. Полный response,
  exception message provider, тексты chunks и секреты не выводить.
- Существующая схема подходит: новые таблицы и пересоздание БД не требуются.

Проверки: сохранение пакетов между SQLite-соединениями и после повторного
открытия БД, retry только недостающих chunks, смена dimension, неполный ответ,
неполное покрытие, потеря lease, локальный storage failure и настоящий SDK
через HTTP mock для malformed JSON, HTTP errors и transport errors.

## 2026-10-06. Три слоя и сохранённый маршрут чата (шаг 2.1)

Общие identity use cases и ports находятся в `core/domain`, конфигурация и
SQLite — в `core/data`, нейтральные события, команды и диспетчер — в
`core/presentation`. Obsidian use cases и ports перенесены из временного
`application` в его `domain`. Domain не импортирует SDK, SQLite или конкретные
слои; YAML parser находится в data. Прежние публичные пути удалены.

Режим адресуется внутренним пользователем, каналом и ID конкретного чата.
В SQLite хранится только ID возможности и время изменения; ожидающие
предметные операции остаются данными Obsidian. Начальная вставка не заменяет
существующий выбор при гонке независимых соединений.

Чтобы шаг 2.1 оставался работоспособным отдельно от 2.2, composition root пока
внедряет один вход и default ID Obsidian. Диспетчер сохраняет его при первом
предметном сообщении. Реестр, команды переключения, новая регистрация и
конфигурация возможностей вводятся следующими шагами roadmap. Это временная
сборка одного входа, без совместимых wrappers прежнего application.

## 2026-10-06. Общие контракты и явный реестр входов (шаг 2.2)

Диспетчер получает проверенный `CapabilityRegistry`, а обработчик —
`HandlerContext` с разрешённым пользователем. Descriptor содержит устойчивый ID,
команду и справку; конфликты ID, команд и общих имён отклоняются при сборке.
Core не знает допустимые предметные ID: список разбирается в config, а конкретные
включённые сборки явно выбирает composition root. Динамический поиск не нужен.

Общие команды и команды входа имеют приоритет перед режимом и прежним rebind.
Сохраняется только успешный длительный enter; одноразовый и ошибочный входы не
меняют прежний выбор. `/exit` и логическое завершение handle очищают только
маршрут этого чата. Обычный текст и URL вне режима не запускают предметный use
case. Сохранённый отключённый ID не теряется и сопровождается понятной подсказкой.

Возможность оформляет предметные результаты до передачи `IncomingResponse` ядру
и каналам. Необязательные адресные действия являются общим контрактом; новый
сценарий подтверждений остаётся в 2.4. `ReplyDeliveryPort` отправляет готовый
последующий ответ по сохранённому адресу. Фоновое продолжение Device Flow в
production-сборке открывает новое короткое соединение и не удерживает исходное.
Telegram сохраняет Bot и адрес, а не исходный Message.

Временное исключение до 2.3: первое сохранение имени продолжает прежний Obsidian
onboarding через отдельный `ProfileSetupPort`; остальные входы уже используют
общий protocol. `/obsidian` принимает только вход без аргумента. Обязательность
credentials и healthcheck сохраняются до 2.5. Схема БД не менялась.

Проверено 457 автономных тестов, включая fake-возможность через TG/VK без
изменений core/адаптеров, перезапуск, изоляцию, отключение без удаления данных,
повторный вход, one-shot/ошибки и фоновый ответ после закрытия исходного соединения.

## 2026-10-06. Независимый профиль и аргумент входа Obsidian (шаг 2.3)

Регистрация завершается созданием профиля и именем. Она не читает vault и не
выбирает режим; общие команды доступны без Obsidian. Временный `ProfileSetupPort`
и общие onboarding-модели удалены, продолжение Device Flow называется
подключением GitHub/vault, а не регистрацией профиля.

Общий `enter(context, event, arguments)` передаёт исходное событие и текст после
команды. Предметный разбор принадлежит Obsidian presentation. Успешный вход
активирует режим данного чата; ошибка аргумента сохраняет прежний выбор. Голые
ссылки вне режима показывают вход, внутри режима сохраняется прежний flow.

Composition root передаёт общие descriptors отключённых команд без сборки
предметных зависимостей. Это позволяет отличать отключённую возможность,
ненастроенный GitHub/LLM-провайдер и невыбранный пользовательский vault без
предметных знаний ядра. Пустая LLM-конфигурация не создаёт LLM adapters в сборке
входа. Полное разделение конфигурации и healthcheck остаётся в 2.5; порядок
подтверждений `да`/`нет` сохраняется до 2.4. Схема SQLite не менялась.

## 2026-10-06. Исходный чат ожидающего действия Obsidian (план шага 2.4)

На момент принятия это решение задавало будущую политику шага 2.4 и пересматривало решение
«SQLite-модель Obsidian vault» от 2026-07-22 в части доступности подтверждения
из связанных каналов, а решение «Сохраняемый proposal и подтверждаемый GitHub
write-back» от 2026-08-04 — в части одного pending proposal на пользователя
и блокирования нового article workflow до его завершения. Общий владелец данных
и межпроцессная координация ресурсов сохраняются. До реализации 2.4
схема допускала один pending proposal на `app_user_id`, обработчик блокировал
новый article flow этим ожиданием и принимал подтверждение из связанного
канала. Реализация и проверки описаны в решении от 2026-10-07 ниже.

Решение:

- Pending-действие принадлежит `app_user_id` и хранит исходный адрес
  `(channel, chat_id)`. Продолжить, подтвердить или отменить действие можно
  только в этом чате; связь другого чата с тем же `app_user` этого не разрешает.
- Другой связанный чат, включая другой чат того же канала, не получает
  содержимое чужого pending и действия подтверждения/отмены и независимо
  выполняет собственные сценарии. Только попытка продолжить, подтвердить или
  отменить чужое действие получает короткий отказ с указанием завершить его
  в исходном чате. Перенос действия между чатами не требуется.
- Разные статьи одного профиля из Telegram/VK независимо проходят fetch,
  analysis и review и могут иметь разные pending proposals одного `app_user_id`.
  Шаг 2.4 удаляет `idx_obsidian_proposals_one_pending_per_user` и глобальное
  блокирование article flow чужим ожиданием, меняет выбор pending в ports,
  repositories и callers. Повторная отправка той же статьи использует dedup
  по пользователю и нормализованному URL без дубликата статьи или proposal
  для того же цикла обработки.
- `/exit` очищает только режим чата, сохраняя pending. Повторный вход
  в исходном чате показывает актуальное ожидание. Общие команды профиля
  доступны из каждого чата; режимы чатов и их переключение независимы.
- Простое `да`/`нет` допустимо только при однозначном pending в текущем
  `(channel, chat_id)` и режиме Obsidian. При нескольких ожиданиях в этом чате
  требуется ID операции; pending других чатов не участвуют в выборе.
- Адресное решение несёт ID возможности, тип операции, устойчивый ID pending
  и выбранное действие. Перед выполнением проверяются владелец, исходный адрес,
  TTL для операций со сроком действия, актуальные статус и версия. Захват
  выполнения и изменение статуса атомарны; повторное подтверждение не применяет
  изменение повторно. Межпроцессная координация Telegram/VK сохраняется.
- Одна активная конфигурация vault на пользователя остаётся общим ресурсом:
  replace/disconnect взаимно исключаются и не подменяют чужое ожидание.
  Конфликтующая операция получает короткое объяснение занятого ресурса без
  содержимого pending. Device Flow сохраняет один SQLite claim на пользователя;
  это не блокирует независимые действия, которым авторизация не нужна.
- Sync и write-back одного vault выполняются последовательно под общим SQLite
  lease с повторным SHA preflight. Два write-back могут независимо ожидать
  подтверждения, но не записываются одновременно. Занятый lease не отменяет
  другое ожидание; устаревший proposal получает `conflict` и требует пересчёта
  с новым явным подтверждением. Универсальная очередь задач не вводится.

Причина: конкретное интерактивное действие завершается в чате, где пользователь
его начал. Привязанные чаты общего профиля независимо выполняют одинаковые
действия, пока нет конфликта за общий ресурс.

Проверки шага 2.4 должны покрыть независимые TG/VK article flows с несколькими
proposals, локальный выбор `да`/`нет` и ID, отказ чужому подтверждению без
раскрытия pending, dedup повторной статьи, взаимоисключение replace/disconnect,
один Device Flow claim, последовательную запись под lease и конфликт
устаревшего proposal. На момент принятия решения эти проверки были запланированы; результаты
реализации зафиксированы ниже.

## 2026-10-07. Адресные ожидания и общие ресурсы (шаг 2.4)

Реализована политика исходного чата из решения от 2026-10-06.
Разные статьи одного профиля имеют независимые proposals с адресом и версией;
unique-индекс ограничивает активный цикл статьи, а не число ожиданий профиля.
SQLite article-flow lease по владельцу и нормализованному URL предотвращает
конкурирующие fetch/analysis/review и `/reanalyze` одной статьи. Повтор не переносит
ожидание в другой чат и не раскрывает его preview. Повторный анализ не заменяет
активный proposal: сначала нужно завершить исходную операцию.

Команда решения имеет форму `/confirm <модуль> <операция> <id> <версия> <yes|no>`.
Obsidian поддерживает `proposal`, `replace`, `disconnect`; core — `identity`.
Ядро проверяет режим для адресных действий возможности; простой `да`/`нет`
выбирает ровно одно ожидание текущего чата внутри Obsidian. При нескольких
локальных ожиданиях требуется адресная команда. Identity ожиданием предметный
ввод не перехватывается. `/exit` сохраняет операции, повторный вход показывает
только локальные актуальные записи.

Proposal перед внешним эффектом атомарно переходит в `executing` с новой версией
и сроком execution claim. Финализация проверяет эту версию. Ошибка записи
возвращает `pending` с новой версией, поэтому старая команда не выполняет retry
неявно; можно использовать новый адресный ответ или локальное `да`.
Истёкший execution claim восстанавливается с актуальной версией под vault lease
и SHA preflight; потерянный ответ GitHub по-прежнему проверяется по remote Markdown.

Ожидания replace/disconnect имеют неизменный ID, TTL, исходный адрес, версию и
ID исходной конфигурации. Единственная активная резервация конфигурации не
перезаписывается другой операцией. Проверка решения, смена/удаление vault и
завершение ожидания составляют одну SQLite-транзакцию, которая проверяет также
отсутствие занятого sync/write lease. Два ожидающих write-back не занимают lease
до подтверждения; запись идёт последовательно, stale SHA завершает второй
proposal как `conflict` с необходимостью нового review.

Device Flow сохраняет общий SQLite claim пользователя. Challenge и callback
остаются в памяти процесса с исходным адресом; другой чат не получает challenge,
даже внутри того же процесса. Не связанные с авторизацией сценарии продолжаются.
Перенос identity, погашение кода и удаление пустого прежнего профиля выполняются
атомарно в core после проверки источника, адреса, TTL, ID, версии и статуса.

Автономные проверки используют настоящие repositories на временных SQLite-БД,
два соединения и управляемые внешние gateways. Проверены независимые TG/VK flows,
локальный выбор/адресные решения, отсутствие раскрытия чужих ожиданий, dedup,
конкурирующие подтверждения, TTL/version CAS, конфликты конфигурации и SHA.
Рабочая БД и production не открывались; real Telegram/VK/GitHub/LLM API в этом
шаге не проверялись. Изменения схемы development требуют пересоздания БД перед
отдельным запуском по `AGENTS.md`.
