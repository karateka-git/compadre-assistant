# Архитектура ядра

Документ описывает маршрутизацию, состояние чата, управление профилем и
канальные адаптеры. Схема модулей — в [общем обзоре](../ARCHITECTURE.md#границы-модулей),
команды и ответы — в [реестре ядра](../user-messages/CORE.md), запуск — в [RUN.md](../RUN.md).

## Как проходит сообщение

Общий `IncomingEvent` несёт источник, внешнюю идентичность и `ReplyAddress`
без `article_id` и полей хранения. `IncomingMessageDispatcher` разрешает identity
и передаёт проверенного пользователя в `HandlerContext`. Общие команды и входы
обрабатываются до обычных сообщений активного режима. Команда
`/confirm core identity <id> <version> <yes|no>` подтверждает перенос identity.
На обычный текст вне режима ядро предлагает доступные входы, включая случай с URL.

`CapabilityRegistry` получает явно собранные обработчики из composition root.
`CapabilityDescriptor` задаёт устойчивый ID, команду входа, справку, начальный
личный выбор и необходимость доверенного доступа. Реестр проверяет конфликты
ID, команд и зарезервированных общих имён при сборке.

Команда из секций справки возможности проходит к обработчику, только если
режим её владельца активен в текущем чате и доступен пользователю. Общий
маршрут выполняет эту проверку и при выборе команды кнопкой.

## Ответ, ошибка и фоновая доставка

Обработчики `enter(context, event, arguments)` и `handle(context, event)` вызывают
предметные сценарии и возвращают `CapabilityResult(IncomingResponse, CapabilityMode)`.
Неожиданное исключение любого из этих входов диспетчер логирует с ID возможности
и преобразует в безопасный общий ответ. Исключение `handle` не очищает режим
и не меняет его ревизию: предметное действие могло уже произвести внешний эффект,
поэтому ядро не повторяет вызов автоматически. Перед ручным повтором пользователь
должен проверить состояние действия. Уже отправленные `BackgroundReply` сохраняют
свой адрес и не отменяются этим ответом.
Предметные модели форматируются внутри presentation возможности. Общий
`IncomingResponse` содержит `MessageContent`, необязательную ошибку, адресные
`ConfirmationAction` и уместные `ReplyAction` для следующего шага. Адресная
команда имеет форму `/confirm <module> <operation> <id> <version> <yes|no>`.
Ядро проверяет выбранный режим для действия возможности, а предметные проверки
выполняет соответствующий обработчик.

Telegram и VK отображают общий ответ, включая полные текстовые команды действий.
Через `ReplyDeliveryPort` возможность отправляет `BackgroundReply` с сохранённым
адресом и уже оформленным ответом. Ранняя квитанция выбранного
обработчика использует ту же общую доставку. Ядро не журналирует каждое
предметное сообщение.

## Структура ответа и вывод в каналы

`core/presentation/message_content.py` задаёт неизменяемые `MessageContent` с
упорядоченными `Paragraph` и `BulletList`; абзацы и `ListItem` состоят из
`TextSpan(text, style)`. Стили `PLAIN`, `EMPHASIS`, `CODE` выражают смысл:
обычный текст, короткий акцент и точное значение для копирования. Presentation
ядра или возможности создаёт эти блоки и выбирает слова. Адаптер оформляет
готовый ответ. Текст пользователя, URL, путь, diff, статья и ответ LLM
остаются буквальными данными, включая похожие на HTML и Markdown символы.

`presentation/message_rendering.py` разворачивает абзацы и списки, добавляет
текстовые строки адресных подтверждений после основного содержания и делит
ответ до сериализации. Сохраняются порядок, пробелы, переносы и типичные
составные Unicode-символы; это не полная реализация Unicode UAX #29. Целый
блок или токен остаётся в одной части, если вмещается; слишком длинное значение
делится без удаления символов. Часть проверяется с учётом лимита канала.
Отправка частей последовательна; неопределённый сетевой результат не даёт
основания пересылать весь ответ в plain-виде.

`presentation/telegram/rendering.py` экранирует каждый span как HTML-текст,
оборачивает `EMPHASIS` в `<b>`, `CODE` в `<code>` и возвращает самостоятельные
части с закрытыми тегами и `parse_mode=HTML`. Лимит 3900 измеряется в UTF-16
единицах уже сериализованного HTML. `presentation/vk/rendering.py` возвращает
буквальный текст; для однозначных диапазонов `format_data` кодирует `EMPHASIS`
как `bold`, `CODE` как `italic`. Для части с non-BMP, combining или format
символами адаптер заранее выбирает plain fallback, поскольку единицы смещения
для них не подтверждены живой пробой. Лимит 3500 измеряется в UTF-16 единицах
текста. Канальный вывод одинаков для немедленного ответа и `BackgroundReply`.
Видимые правила и реестры ответов находятся в [USER_MESSAGES.md](../USER_MESSAGES.md).

## Каталог команд, меню и выбор действия

`ChatCommand` и публичные `CapabilityDescriptor`/`CapabilityCommand` дают
точные имена, синтаксис и описание команд. `CommandParameter` отмечает
обязательный аргумент; меню включает лишь команду, которую можно выполнить без
неизвестного значения, в том числе команду, запускающую пошаговый ввод.
`/help` собирается заново из допуска профиля, личного выбора, серверного
списка, режима данного чата, проверенного ожидания ввода и снимка подтверждений.
До регистрации справка и главное меню предлагают `/register` и `/link`. При
вводе имени справка объясняет этот шаг, а меню оставляет кнопку отмены.
У зарегистрированного профиля главное меню
состоит из доступных в данном чате входов. `/start` и `/help` доступны вручную.
В активном режиме меню показывает его команды, `/exit` и доступные
одноразовые входы. Контекстные `/cancel` и `/confirm` появляются при действующем
ожидании ввода или полном снимке подтверждений с действиями соответственно.
Неполный снимок подтверждений явно назван неполным; `/confirm` без аргументов
показывает актуальные действия и не выбирает решение.

Активная возможность может реализовать `ContextualCommandQueryPort`, чтобы
отобрать объявленные команды для текущего раздела. Ядро вызывает порт только
при действующем допуске и передаёт профиль, адрес чата и ревизию режима.
Меню и справка используют один и тот же отбор. При ошибке чтения снимка или
пустом наборе остаются общие команды и доступные одноразовые входы.
Возможность без порта показывает команды из статического каталога. Этот каталог
также определяет владельца каждой команды при ручном вводе и нажатии кнопки.
При исполнении обработчик заново проверяет выбранный раздел. Обработка в
активном режиме получает его ревизию через `HandlerContext.mode_revision`.
При входе `mode_revision` равна `None`. Успешный повторный вход создаёт новую
ревизию, поэтому состояние раздела для прежней ревизии больше не применяется.

`CommandMenu` — состояние чата, отдельное от действий конкретного ответа.
Telegram публикует команды для личного чата в меню `/`; VK показывает
постоянную клавиатуру личного диалога. Обновление передаётся через
`CommandMenuUpdate`. Telegram сверяет меню при старте и периодически.
VK прикладывает изменившееся меню к содержательному обычному или фоновому
ответу того же чата, включая уведомление об истечении ожидания. При событии
без сообщения, например смене доступа из привязанного чата, показанное меню
сохраняется. Ядро проверяет актуальное состояние и доступ при каждой команде.
Запись групповой активности сохраняет ранее известный личный адрес.
Непосредственный ответ адресуется исходному чату события.
`ReplyAction` и `ConfirmationAction` могут получить
временные кнопки под ответом; текст ответа сохраняет полную команду для
канала или клиента без кнопок. Кнопки прикрепляются к последней части длинного
ответа. Подпись кнопки не исполняется как команда.

`ResponseActionStore` выдаёт кнопке непрозрачный одноразовый token с TTL
10 минут и ограничением памяти; token привязан к отправителю, исходному чату,
конкретному ответу и снимку профиля, режима, доступа и ожидаемого ввода.
`select_action` заново проверяет контекст и адресное подтверждение, затем
проводит точную команду через обычный вход. Выбор одной кнопки погашает
соседние кнопки того же ответа; после перезапуска или истечения token
недействителен. Текстовая команда остаётся доступна и снова проходит
серверные проверки.

Обработчик активного режима может передать в `IncomingResponse.view`
`ResponseView` с устойчивым ключом представления. `update=False` публикует
сообщение. `update=True` запрашивает замену последней подтверждённой доставки
и требует указать в `unavailable`, как открыть представление заново. Ручная
команда использует последнюю подтверждённую доставку. Выбор кнопки дополнительно
требует совпадения с ID сообщения кнопки. Адаптер передаёт его в
`IncomingEvent.callback_message_id` отдельно от ID самого события нажатия.
Цель привязана к ключу представления, возможности, адресу чата, автору,
профилю и ревизии режима. Она хранится в ограниченном реестре процесса с тем же
сроком, что и кнопки. После смены режима, истечения срока или перезапуска
пользователь открывает представление заново.

Перед сетевой доставкой управляемого ответа адаптер вызывает
`ResponseViewDelivery.start()`. После допуска он сообщает ID сообщения через
`finish()`, а при сбое или отмене передаёт `None`. При обновлении нужно
передать прежний ID после замены текста и клавиатуры. Неудавшееся редактирование
снимает подтверждение цели. Поколение ответа
определяется перед вызовом обработчика. Запоздалый результат не редактирует
позже подтверждённый ответ, а две доставки одного представления не выполняются
параллельно. Кнопки нового поколения действуют после подтверждения, старое
нажатие не очищает свежую клавиатуру. При отсутствии цели или неудачном
обновлении канал доставляет подсказку владельца представления. Сценарий
возможности повторно при этом не выполняется.

Telegram использует `message_id` из ответа Bot API и меняет текст и клавиатуру
одним `editMessageText`. VK публикует управляемый ответ через `messages.send`
с `peer_ids` и сохраняет подтверждённый `conversation_message_id` этого
диалога. Нажатие VK использует тот же тип ID, а `messages.edit` принимает его
как `cmid`. Управляемые сообщения VK сохраняют обычный текст, поскольку
`messages.edit` не принимает `format_data`. Оба адаптера передают пустую
inline-клавиатуру при замене, которая снимает все кнопки. Изменившееся нижнее
меню VK доставляется отдельным сообщением после успешной доставки представления
или вместе с подсказкой при неудавшемся редактировании.

Обновляемое представление должно помещаться в одно сообщение канала.
Многосоставная публикация сохраняет текстовый путь без активации кнопок и цели
для этого ответа. Если полный текст обновления потребовал бы нескольких частей,
адаптер доставляет подсказку из `unavailable`.

## Ожидание следующего значения

`PendingInputStore` хранит в памяти процесса одно ожидание на `ReplyAddress`:
владельца (`core` или ID возможности), тип значения, `request_id`, профиль,
требуемый режим, название значения и исходный срок 10 минут. Следующее
сообщение без команды передаётся только публичному продолжению владельца;
ошибочное значение оставляет тот же срок, принятое атомарно завершает
ожидание до внешнего долгого действия. `/cancel` очищает ожидание без смены
режима. `/help` и `/start`, а также `/status` и `/capabilities` в режиме настроек
сохраняют ожидание. Другая команда прерывает ввод. Истечение срока, смена
профиля, режима или доступа прекращают ожидание. После перезапуска пользователь
повторяет исходную команду. Сценарии ввода описаны в
[реестре ядра](../user-messages/CORE.md), [ИИ](../user-messages/AI.md) и
[Obsidian](../user-messages/OBSIDIAN.md).

## Режим чата и данные

Начальная SQL-схема находится в
`compadre_assistant/core/data/sqlite/migrations/0001_initial_schema.sql`, а
`0002_user_capability_preferences.sql` добавляет личные настройки без изменения
применённой `0001`. Ядро владеет таблицами пользователей, identities,
`active_chat_modes` и `user_capability_preferences`. Ключ режима —
`app_user_id`, `channel`, `chat_id`; значение — nullable `capability_id`,
положительная `revision` и технический `updated_at`. Отсутствие строки означает
ревизию 0. После `/exit` строка остаётся с `capability_id = NULL` и увеличенной
ревизией: поздний результат не может принять очищенный чат за новый.
Личное или серверное отключение возможности сохраняет выбранный режим,
настройки и предметные данные.

Успешный `enter` с результатом `ACTIVE` заменяет режим только текущего чата. Ошибка или
одноразовый вход сохраняет прежний режим. Успешно завершённый `handle` очищает
маршрут; `/exit` очищает только выбор этого чата без удаления предметных данных.
Перед `enter` и `handle` ядро читает ревизию чата. После вызова обработчика
смена режима или завершение применяются только при той же ревизии. Короткая
SQLite write-транзакция сериализует проверку и запись между процессами TG/VK;
внешний обработчик выполняется без этой транзакции. Отключённый вход сохраняет
режим. Если сохранённый режим недоступен, обычное сообщение оставляет его ID
и получает подсказку о `/exit` и доступных входах. У каждого пользователя, канала
и чата свой режим. После перезапуска выбор восстанавливается из SQLite.

## Профиль и включённые возможности

После `/register` ядро запрашивает имя. `UserIdentityService` создаёт профиль
без выбора режима. Telegram и VK используют отдельные внешние identities
одного внутреннего профиля. Создание `app_user` и первой `external_identity`
выполняется одной короткой SQLite-транзакцией. Повторный запрос от той же
identity возвращает существующий
профиль, в том числе после конкурирующей регистрации. `/link <code>` погашает
код и создаёт связь также одной транзакцией: конфликт identity или ошибка
вставки сохраняет код непогашенным.

### Настройки профиля и каналов

Сборка всегда регистрирует `settings`. Любой зарегистрированный профиль может
войти через `/settings`. Возможность исключена из личного переключения.
В этом режиме доступны `/name`, `/status`, `/link_code`, `/link`, `/capabilities`,
`/enable` и `/disable`. Для ещё не привязанной внешней identity `/link` доступна
до регистрации. В штатной сборке операции связи и подтверждение переноса
ограничены личным чатом.

`/link_code` создаёт короткий код. `/link <code>` связывает текущую identity с
профилем, который создал код. Если identity уже принадлежит другому профилю,
перенос требует [адресного подтверждения](#подтверждение-переноса-identity).

После проверки режима и доступа диспетчер передаёт обработчику
`HandlerContext.profile_operation`. `settings/presentation` отвечает за вход
и отображение настроек. Профиль, связи каналов и личный выбор принадлежат ядру.
Работа с профилем не открывает scope Obsidian и доступна при отключённом Obsidian.

### Допуск к возможностям

`ENABLED_CAPABILITIES` задаёт верхнюю серверную границу входов (по умолчанию
`obsidian`, пустая строка отключает все настраиваемые на сервере возможности).
Core разбирает форму списка, а конкретные допустимые сборки проверяет
composition root. Из него же приходят метаданные отключённых входов,
без предметных ID и команд в core.
Для каждого `AppUser` таблица `user_capability_preferences` хранит явные
переопределения по ключу `(app_user_id, capability_id)`. Отсутствие строки у
нового или существующего профиля означает default из descriptor: ИИ и «Семья»
включены, Obsidian выключен, Admin выбран для доверенного профиля. Фактический допуск
требует серверной доступности, личного выбора и доверенного права для
ограниченного входа. Право проверяется по разрешённому внутреннему ID
профиля события с явным автором. Серверное отключение сохраняет личную
настройку. `/enable` меняет личный выбор в пределах серверного и профильного
допуска.

Перед входом по команде, продолжением сохранённого режима и предметным
`/confirm` диспетчер читает личный набор один раз на событие и создаёт его
неизменяемый снимок. `/capabilities` показывает видимые профилю возможности,
личный выбор и серверную доступность.
`/enable <id>` и `/disable <id>` атомарно меняют один известный ID после
успешного commit. Выбор действует для всех Telegram/VK identities одного
`AppUser`. Подтверждённый rebind использует выбор профиля назначения.
Уже допущенная долгая операция может доставить ответ в исходный чат после
`/disable`. Отложенные сценарии с повторным допуском проверяют право перед
доставкой, как при [распознавании фото](AI.md). Следующий вход проверяет
актуальную БД. Ревизия чата защищает `/exit` и выбранный режим от устаревших
результатов и изменений личного выбора.

## Подтверждение переноса identity

Перенос identity хранит собственные адрес, источник/цель, версию и TTL в core.
Решение, погашение link token, перенос identity и удаление пустого предыдущего
профиля атомарны. Устаревший ID не подтверждает новое ожидание. Обычный текст
Obsidian не перехватывается ожиданием identity.

Если удалить исходный профиль нельзя из-за действующей связи с данными,
перенос последнего канала целиком откатывается. Код и подтверждение
сохраняются до истечения срока. Когда у исходного профиля есть другой канал,
перенос не требует удаления профиля.
[Действующее семейное членство](FAMILY.md#членство-и-приглашения) удерживает исходный профиль.

## Миграции и совместимость SQLite

Production уже применил `0001_initial_schema.sql`: `0002` и следующие изменения
схемы выпускают последовательными миграциями, не изменяя применённый файл.
Порядок для отдельной локальной development-БД описан в [RUN.md](../RUN.md#пересоздание-базы-после-изменения-схемы).

При изменении SQLite-репозитория проверьте его операции чтения и записи на
временной БД с актуальными миграциями. Обратную совместимость проверяйте
по поведению репозиториев принятого выпуска на схеме кандидата. Столбец
можно удалить новой миграцией, когда принятый выпуск больше к нему не
обращается, нужные данные сохранены и проверки совместимости проходят.
Если принятый выпуск ещё использует столбец, сначала выпустите версию,
в которой поле и оставшийся переходный код помечены `Deprecated`, а
репозитории используют новый контракт. Условия удаления описаны в
[порядке выпуска](../RELEASES.md#вывести-из-использования-поле-sqlite).

## Сборка и время жизни зависимостей

При старте процесса `compadre_assistant/bootstrap.py` один раз создаёт реестр
обработчиков и descriptors для `ChannelMessageProcessor`. Для каждого события
процессор открывает SQLite-соединение ядра для identity, личного выбора, общих
команд и режима чата. [Obsidian](OBSIDIAN.md#конфигурация-и-время-жизни-зависимостей)
открывает собственный scope для операций своего модуля.

Публичная фабрика диспетчера принимает произвольные реализации общего protocol;
добавление fake-возможности не требует изменений ядра или TG/VK-адаптеров.
`presentation/cli/main.py` проверяет конфигурацию перед запуском адаптеров и
запускает диагностические команды через composition root. `--process-url`
читает общие настройки без токенов каналов и провайдеров.

### Конфигурация включённых модулей

`load_config` в `core/data/config.py` читает `APP_ENV`, путь SQLite, выбранные
каналы, их credentials/proxy, debug-флаг и список ID возможностей.

`ENABLED_CHANNELS` задаёт каналы для scripts и общей диагностики. Флаги
запуска конкретного бота выбирают его канал. Сборка проверяет состав
возможностей и читает конфигурацию каждого подключаемого модуля только при
его включении. Профили описаны в документах [Obsidian](OBSIDIAN.md),
[ИИ](AI.md), [Admin](ADMIN.md) и [«Семья»](FAMILY.md).

Healthcheck проверяет выбранные каналы, локальные настройки провайдеров и
SQLite без вызовов внешних API и без проверки пользовательского vault.
Отсутствующего провайдера он отмечает отдельно от готовности общего входа.
Область диагностики и автономных smoke — в [RUN.md](../RUN.md).

### Обработка событий в Telegram и VK

Docker Compose запускает два независимых worker-контейнера из одного образа:
`tg_assistant` с Telegram polling и `vk_assistant` с VK Long Poll. Каждый контейнер
проверяет в healthcheck только свой канал. Scripts выбирают сервисы по
`ENABLED_CHANNELS` (по умолчанию оба). Оба используют SQLite и ключ GitHub App
из постоянного тома. Хранение и восстановление описаны в [OPERATIONS.md](../OPERATIONS.md).
Каждый адаптер преобразует сообщение платформы в `IncomingEvent`. Для долгой
операции он может отправить
раннюю квитанцию по предикату, полученному при сборке Obsidian. Результат и
фоновое завершение форматируются до нейтрального ответа каналу.

VK Long Poll получает updates и передаёт `message_new` в пул из четырёх
workers. Адаптер хранит отдельную FIFO-очередь для каждого `peer_id`: следующий
update чата начинает выполняться после завершения предыдущего, в том числе
между разными ответами Long Poll. Разные чаты могут выполняться одновременно.
Общая очередь ограничена 128 ожидающими updates; при заполнении поток Long Poll
ждёт освобождения места и не отбрасывает события. Ошибка обработки update
логируется внутри worker и не останавливает остальные сообщения. При выходе из
polling пул перестаёт принимать события и дожидается завершения всех уже
принятых updates до закрытия процессного runtime.
