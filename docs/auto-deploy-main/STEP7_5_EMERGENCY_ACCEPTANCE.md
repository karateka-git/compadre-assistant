## Правило выпуска

Выбранные `release/X.Y` независимы. Взаимные полные URL в описаниях PR
позволяют проследить исправление; состояние PR другой линии не блокирует
слияние, публикацию или развёртывание текущей. Исправление обязательно
должно быть в `main`: через слитый PR либо достижимый существующий commit.
Собственный release PR перед выпуском должен быть слит в выпускаемую ветку.

После слияния main PR доверенный workflow обрабатывает все связанные
открытые release PR. Успешный `hotfix-deps` пропускается; для отсутствующего
в API run/job и выполняющегося `pr-fast`/`hotfix-deps` предусмотрено ожидание
с общим бюджетом 240 секунд и интервалом опроса до 5 секунд. Все готовые
линии обрабатываются до паузы. Текущий failed job перезапускается после
повторной проверки SHA, целевой ветки, описания, состояния PR, main и latest job.
Отказ одной линии не препятствует обработке остальных;
workflow сообщает совокупную ошибку после обработки группы. Merge другой
релизной линии больше не запускает rerun. Auto-merge остаётся собственным
решением для каждого PR и требует всех обязательных checks.

Сохранены проверки репозитория, взаимных URL, main, точного candidate,
истории PR текущей линии, защищённого тега, неизменяемого Release и версии.
Обычная публикация требует полный CI. Аварийная допускает непрошедший CI
с причиной и аудитом; backup, совместимость схемы и безопасный возврат
этим разрешением не отключаются.

Ограничение: после истечения общего бюджета ожидания workflow завершается
ошибкой с номерами незавершённых линий. Когда их актуальный run завершится,
оператор повторяет доверенный workflow либо адресный failed job, сверив
текущий PR и main. Completion-trigger за пределами бюджета отсутствует;
весь workflow также ограничен 10 минутами, включая запросы GitHub API.

## Метод многолинейной GitHub-пробы

Здесь сохранена использованная методика; фактические результаты и cleanup
описаны выше. Повторная проба для закрытия шага 7.5 не требуется.

Для безопасной проверки создаются две временные линии `release/90.6` и
`release/90.7` от одного SHA с допуском полного main-full. Связанный main PR
и оба release PR содержат одинаковое изменение этого документа и взаимные
URL всех участников в `Hotfix-Links`. Публикация Release не требуется.

После первоначального `hotfix-deps FAILURE` обеих линий и успешного main
`pr-fast` только для второй линии запускается новый PR run. Дополнительный
временный unittest этой линии удерживает `pr-fast` на 60 секунд; workflow
остаётся штатным. Main PR сливается, когда новый release run ещё выполняется.
После этого состав группы, тела PR, head и base фиксируются до конца пробы.

Критерий fan-out: доверенный workflow точного main merge запрашивает адресный
rerun `hotfix-deps` обеих линий. Готовая первая линия получает POST до
завершения второй; pending run второй дожидается завершения в общем бюджете
240 секунд и затем получает свой POST. Оба job становятся успешными без
повторного выполнения `pr-fast` и без слияния release PR друг друга.
Таймлайн API и логи сохраняют SHA, run/attempt/job IDs и времена действий.
Если trusted workflow стартовал после завершения второго run, pending race
не считается воспроизведённой. Отсутствующий run и превышение бюджета
проверяются отдельно; этот сценарий сам по себе их не доказывает.

Оба временных release PR после сохранения результатов закрываются без merge;
их ветки и временные heads удаляются. Задержка существует только в тестовой
ветке второй линии и не попадает в main. Рабочие release PR, version tags,
auto-merge и production VPS в этой пробе не меняются.
