# Этап 4, шаг 2: парные PR исправления

Для исправления существующей `release/X.Y` открывают два PR: один в эту
релизную ветку, второй в `main`. В описании **каждого** PR нужна отдельная
строка `Hotfix-Pair: #N` с номером другого PR. PR создают оба до слияния;
после появления второй ссылки редактирование описания запускает `pr-fast`
повторно. Для PR в `release/*` проверка обязательна всегда; для PR в `main`
она включается при наличии `Hotfix-Pair:`. Проверяются взаимность ссылок и
целевые ветки. Это ранняя проверка структуры пары, а не допуск версии.

Рекомендуется перенести один и тот же commit в обе ветки. Когда это
невозможно, в PR описывают адаптацию и различия. Оба PR проходят обычный
`pr-fast` и сливаются отдельными merge commits. Слияние в `release/X.Y`
автоматически вызывает `release-full` для нового tip независимо от того,
успел ли слиться парный PR в `main`. Порог полного CI в `main` остаётся общим.

Перед публикацией версии `scripts/check_hotfix_pairs.py release` проверяет
**все** изменения первой родительской линии релизной ветки после baseline:

1. `baseline` — точный SHA последнего опубликованного выпуска той же `X.Y`,
   либо, до первого выпуска линии, SHA её создания с успешным `main-full`.
   Команда сверяет эти факты с GitHub. Нельзя произвольно выбрать более
   позднюю точку и пропустить прежний PR.
2. Candidate должен быть точным текущим tip `release/X.Y` и `HEAD` чистого
   локального checkout; каждый commit после baseline должен быть merge
   единственного PR в эту релизную ветку. Для него по API проверяются
   взаимные ссылки, слитый парный PR в текущей истории `main` и точные
   merge SHA.
3. Сравниваются точные байты `git diff --binary --full-index` изменений
   первого родителя каждого merge commit. Совпадение SHA-256 подтверждает
   одинаковый Git diff, но не семантическую эквивалентность в разных
   контекстах веток. При разных diff или пустом diff требуется ручное
   подтверждение.
4. Для ручного подтверждения владелец `karateka-git` после обоих merge
   оставляет **комментарий к релизному PR** со строкой:

   ```text
   Hotfix-Adaptation-Approved: #<main-PR> release=<40-символьный-merge-SHA> main=<40-символьный-merge-SHA>
   ```

   До комментария владелец сравнивает адаптации и результаты проверок.
   Команда сверяет автора комментария и оба SHA. Такая запись фиксирует
   человеческое решение; программа не утверждает семантическое равенство.
5. Точный candidate обязан иметь успешный `release-full` со всеми
   обязательными jobs и steps через общий selector. Ошибка Git/API,
   неполный CI, отсутствие связи или ручной записи закрывают допуск.

Пример проверки после получения актуальных refs и опубликованных выпусков:

```powershell
$env:GITHUB_TOKEN = gh auth token
python -m scripts.check_hotfix_pairs release release/1.0 <candidate-SHA> <baseline-SHA>
```

Команда только читает GitHub и локальный Git. Её успешный вывод содержит
каждую пару PR и способ подтверждения. Перед созданием тега на шаге 4.3
проверка пары должна выполняться вместе с остальными условиями публикации;
само наличие успешного `release-full` без парного PR публикацию не разрешает.
Первую фактическую проверку пары на GitHub провести после появления
настоящей поддерживаемой релизной линии. Пока проверены локальные fixtures;
теги, GitHub Releases, production и правила защиты не менялись.
