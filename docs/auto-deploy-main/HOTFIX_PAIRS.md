# Этап 4, шаг 2: связанные PR исправления

Для hotfix явно выбирают затронутые релизные линии. Если исправления ещё нет
в `main`, создают PR в `main` и по одному PR в каждую выбранную `release/X.Y`.
Описание каждого PR содержит отдельный блок `Hotfix-Links:`:

```text
Hotfix-Links:
https://github.com/karateka-git/compadre-assistant/pull/21
https://github.com/karateka-git/compadre-assistant/pull/22
```

В блоке указывают **все остальные** PR группы, без собственной ссылки.
Примерные номера заменяют на реальные URL. Если есть новый main PR, он
перечисляет каждый выбранный release PR, а каждый release PR перечисляет
main PR и остальные выбранные release PR. Одна строка — один полный URL PR
этого репозитория.
Блоки должны быть взаимными, целевые ветки — `main` и различные
`release/X.Y`. Если исправление **уже есть в `main`**, новый PR туда не нужен:
в каждом релизном PR вместо ссылки на main PR указывают полный URL
конкретного коммита, содержащего исправление, отдельным полем:

```text
Hotfix-Main-Commit: https://github.com/karateka-git/compadre-assistant/commit/<SHA>
```

Все выбранные релизные PR по-прежнему ссылаются друг на друга в
`Hotfix-Links:`. Если выбран только один релиз и нового main PR нет, блок
`Hotfix-Links:` не нужен: связь задаёт `Hotfix-Main-Commit:`. Проверка должна
доказать достижимость указанного SHA из текущего `main`. Ссылка на коммит
показывает происхождение фикса, но не доказывает семантическое равенство
перенесённого патча. Никакой алгоритм не
определит намеренно забытую линию: выбор линий делает владелец явно.

## Алгоритм слияния

1. Подготовить изменения и ссылки во всех PR; просмотреть различия патчей.
   Релизные PR открывать обычными, без обязательного draft. Для каждого из
   них заранее включить GitHub auto-merge методом **merge commit**. Включение
   auto-merge означает согласие слить именно этот PR после выполнения всех
   обязательных условий; его можно отключить до слияния.
2. Если есть новый PR в `main`, дождаться `pr-fast` и слить его первым.
   Main PR не ждёт релизные PR. Если фикс уже есть в `main`, начать с проверки
   ссылки на существующий commit.
3. Для release PR требовать два результата: `pr-fast` проверяет код и
   взаимные ссылки, `hotfix-deps` подтверждает, что main PR или указанный
   commit вошёл в `main` и что выбранные более старые релизные PR уже слиты.
   Неисполненная зависимость даёт **failure**, а не skipped/neutral.
4. Слияние предыдущего PR в `main` или более старый релиз запускает отдельный
   доверенный workflow по событию `pull_request_target` `closed` с
   `merged=true`.
   Он находит по ссылкам связанные открытые release PR и через GitHub API
   повторно запускает только их актуальный job `hotfix-deps`. Перед запуском
   сверяет репозиторий, номера PR, целевые ветки и SHA их текущих head.
   Само изменение другого PR не перезапускает проверку зависимости.
5. После успешного `hotfix-deps` GitHub auto-merge сливает готовый release PR,
   когда `pr-fast` тоже успешен и нет конфликтов. Его merge запускает шаг 4
   для следующей выбранной линии. Порядок: от старой линии к новой. Ошибка
   проверки, конфликт или невозможность повторного запуска останавливает
   цепочку; автоматического обхода нет. Если фикс уже был в `main`, а первый
   release PR стал полностью готов до включения auto-merge, человек один раз
   сливает этот PR обычной кнопкой Merge, начиная цепочку следующих линий.
6. После каждого слияния release PR выполняется полный `release-full` для
   нового точного SHA ветки. Публикация тега и GitHub Release требует
   успешного полного CI, а обновление VPS — отдельной команды.

GitHub auto-merge действует отдельно для каждого PR: включение настройки
репозитория не ставит все PR на автоматическое слияние. Workflow повторного
запуска получает право `actions: write`, но исполняет только доверенный код
из защищённой целевой ветки и не загружает и не исполняет код из PR. Необходимо
проверить, что повторный запуск относится к последнему SHA PR; при смене
head обычное событие `synchronize` запускает новые проверки. Для `release/*`
в GitHub ruleset должны быть обязательны **оба** check (`pr-fast` и
`hotfix-deps`), для `main` — `pr-fast`. Успех `hotfix-deps` для старого SHA или
устаревших ссылок не должен разрешать слияние.

После включения auto-merge не менять блок ссылок ни в одном PR группы.
Если связь надо исправить, сначала отключить auto-merge у всех ещё открытых
связанных PR, затем обновить описания, получить свежие результаты проверок
для каждого затронутого PR и только после этого снова включить auto-merge.
Событие `edited` одного PR не обновляет автоматически уже зелёный результат
другого PR; этот случай включить в пробную проверку цепочки.

**Состояние на 18.10.2026:** локально подготовленный вариант проверяет ссылки
только между PR, предполагает draft и не перезапускает job после merge
другого PR. В GitHub auto-merge для репозитория выключен, а ruleset требует
только `pr-fast`. Поэтому описанный выше алгоритм пока не действует; нужны
доработка проверок, workflow повторного запуска, включение auto-merge,
обновление ruleset и пробная цепочка PR до рабочего применения.

Workflow `pull_request` исполняется из PR test merge, поэтому required check
сам по себе не защищает от автора, который меняет workflow. Это предел
модели GitHub checks, а не доказательство защищённого исполнения.

Перед публикацией `scripts/check_hotfix_pairs.py release` независимо читает
живые описания, проверяет все merge commits первой родительской линии после
последнего опубликованного baseline, соответствие PR целевым веткам,
взаимность URL, фактический merge main и старших выбранных release линий,
точный текущий candidate и успешный `release-full`. Для первого выпуска
линии baseline — её точка создания с успешным `main-full`. Ошибка Git/API
закрывает допуск. Бинарное сравнение патчей и owner attestation не являются
условиями новой публикации. Различия реализации описывают в PR и release
notes; ссылки не доказывают семантическое равенство.

```powershell
$env:GITHUB_TOKEN = gh auth token
python -m scripts.check_hotfix_pairs release release/1.0 <candidate-SHA> <baseline-SHA>
```

Проверка только читает GitHub и локальный Git. Успешный Release manifest
должен содержать URL связанных PR и проверенное основание в `main`: merge
SHA нового PR либо SHA существующего коммита. Уже опубликованный `v1.0.3`
остаётся историческим выпуском по прежним правилам.
