# Этап 3, шаг 1: отдельная команда миграций

Реализовано 2026-10-14 в ветке `codex/auto-deploy-production-main`.
Документ временный: действующий контракт перед завершением этапа перенести
в постоянную документацию по матрице `PLAN.md`.

## Контракт CLI

```bash
python -m compadre_assistant --migrate
```

Команда читает только `DATABASE_PATH` из окружения и локального `.env`
по существующему соглашению `python-dotenv`. Уже заданное окружение имеет
приоритет над `.env`. Относительный путь разрешается относительно текущего
рабочего каталога. Отсутствующий каталог и новый SQLite-файл создаются.

Для явного выбора файла, в том числе автономной проверки:

```bash
python -m compadre_assistant --migrate --database-path /tmp/migration-check/app.db
```

`--database-path` имеет приоритет над `DATABASE_PATH` и полностью исключает
чтение `.env`. Опция разрешена только с `--migrate`. Вывод содержит выбранный
абсолютный путь, имена применённых файлов или сообщение об актуальной схеме.

Режим запускается до загрузки общей runtime-конфигурации. `APP_ENV`, токены
Telegram/VK, настройки GitHub App/LLM/embeddings/Ask и список возможностей
не требуются и не проверяются. Polling, Long Poll, сборка возможностей и
внешние API не вызываются. Флаги других режимов и `--channels` одновременно
с `--migrate` отклоняются parser.

| Exit code | Значение |
| --- | --- |
| `0` | Все ожидающие миграции применены либо схема уже актуальна |
| `1` | Ошибка файловой системы, SQLite, обнаружения или применения миграции |
| `2` | DATABASE_PATH отсутствует/пуст либо аргументы CLI несовместимы |

## Применение и сохранение данных

Команда использует тот же `connect_database` и `apply_migrations`, что и
runtime: WAL, foreign keys, busy timeout и отдельная `BEGIN IMMEDIATE`
транзакция для каждого SQL-файла. Запись `schema_migrations` фиксируется
вместе с SQL этого файла. Ошибка откатывает его изменения и запись журнала.
Повторный запуск пропускает уже применённые номера/имена; после захвата
SQLite lock runner повторно проверяет запись для текущего файла.

SQL-файлы должны иметь имена `NNNN_lowercase_name.sql` и последовательные
версии от `0001`. Пустой каталог, пропущенные номера, дубли и неверные имена
отклоняются до создания журнала. Применённые записи должны быть непрерывным
префиксом доступных файлов с совпадающими именами. Неизвестная более новая
схема, удалённый/переименованный файл и пропуск в журнале отклоняются до
применения ожидающего SQL. Автоматического downgrade нет.

Production уже содержит `0001_initial_schema.sql`. Этот файл и структура
`schema_migrations` не менялись; новые production SQL-файлы на этом шаге
не нужны. Последующие изменения оформляются только новыми `0002+` с
сохранением данных. Пустая `0002` не создаётся. Правило development-БД
из `AGENTS.md` не разрешает переписывать production-схему или очищать её.

Runner не хранит checksum SQL в БД. Изменение содержимого применённого файла
под прежним именем не определяется им; неизменность файлов обеспечивает
уже существующая Git/PR-проверка `scripts/check_pr_fast.py`. Полный CI с
синтетической схемой прежнего выпуска относится к шагу 2 и здесь не включён.

Каждый новый SQL-файл должен обходиться без собственного управления
транзакцией: её границы задаёт runner. Не следует добавлять `BEGIN`,
`COMMIT`, `ROLLBACK`, `VACUUM` или действия, требующие выключить foreign keys.
SQLite splitter сохраняет многострочные statements и triggers; для обычных
statements использовать отдельные строки с завершающей точкой с запятой.

Если несколько миграций ожидают применения и поздняя завершается ошибкой,
ранние успешные миграции остаются зафиксированными. Это не атомарный пакет
всего релиза. Повтор команды после устранения причины выполнит оставшиеся
файлы. Автоматический rollback образа/БД этим режимом не выполняется.

Для будущего deploy вызов нужен из выбранного candidate image после
остановки обоих writers и проверенного backup. Сама команда не останавливает
каналы, не создаёт backup и не проверяет совместимость старого кода с новой
схемой. Эти действия принадлежат этапу 5. На этом шаге VPS, production-БД,
Compose и GitHub workflow не менялись; production-команда не запускалась.

## Локальная проверка

Все базы и synthetic SQL-файлы создаются в `TemporaryDirectory`. Данные
production и её секреты не используются.

- `tests/test_cli_migrate.py`: новая БД с минимальным окружением; повтор с
  сохранением строк и журнала; игнорирование ошибочных чужих профилей;
  приоритет явного пути без dotenv; чтение пути через dotenv; отсутствующий
  путь; недоступный/повреждённый файл; ошибка pending SQL с rollback DDL и
  DML; несовместимые флаги; настоящий `python -m` subprocess.
- `tests/test_migration_runner.py`: synthetic переход с неизменённой `0001`
  на `0002/0003`, порядок, данные, журнал и целостность; отказ некорректных
  последовательностей файлов/журнала; сохранение успешной миграции при сбое
  следующей и последующий retry; прежний тест параллельного старта.
