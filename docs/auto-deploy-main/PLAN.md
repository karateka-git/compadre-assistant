# План этапа: автоматическое развёртывание production из `main`

Статус: планирование. Рабочая ветка: `codex/auto-deploy-production-main`
в отдельном worktree этого чата. Общая рабочая папка возвращена на `main`.

Этот каталог хранит рабочие документы только на время этапа. После приёмки
перенести действующие инструкции в постоянные документы проекта, зафиксировать
результат в истории и удалить `docs/auto-deploy-main/` из ветки до её слияния.

## Цель и границы

Коммит, попавший в `main`, автоматически развёртывается на VPS только после
успешных автоматических проверок. Telegram и VK работают на одном проверенном
SHA. Неуспешный выпуск сохраняет или восстанавливает рабочую версию и сообщает
о проблеме. Production-секреты и SQLite остаются на сервере; удаление базы не
является способом обновления схемы.

## Исходное состояние

- Production использует `/opt/obs-chat-bot`, detached HEAD и Compose-сервисы
  `tg_assistant` и `vk_assistant`. Серверный deploy key читает репозиторий.
- В репозитории нет CI workflow и автоматического механизма развёртывания.
- Compose сейчас собирает общий образ `compadre-assistant:dev`. Для надёжного
  возврата нужен образ, однозначно связанный с SHA, и сохранённый предыдущий
  образ.
- Штатный healthcheck проверяет конфигурацию и открывает SQLite, но не применяет
  миграции и не подтверждает доступность Telegram, VK, LLM или GitHub. Открытие
  может создать файл БД и включить WAL. Миграции сейчас применяются при обычном
  старте обоих ботов, до начала polling; отдельной команды миграции нет.
- `docs/OPERATIONS.md` содержит устаревший рецепт обновления прежних сервисов.
  Актуальное состояние и запрет очистки базы описаны в `docs/PRODUCTION.md`.
- Существующий migration runner применяет новые версии SQL по одной транзакции
  на файл. Он сверяет номер и имя миграции, но не checksum. Изменение уже
  применённого `0001_initial_schema.sql` не обновит production-БД.
- Существующие systemd unit, override и скрипт ночного backup находятся только
  на VPS. Прежний rollback bundle уже не содержит копию БД; его исторический
  сценарий возврата нельзя использовать как базу новой автоматики.

## Порядок работы

### 1. Создать правила реализации новых функциональностей

Подготовить отдельный документ с правилами для каждой новой функциональности:
создание ветки от актуального `main` в отдельном worktree, закреплённом за
чатом разработки; временного каталога в `docs` для плана и решений; проверки и
приёмка перед слиянием; перенос действующих инструкций в постоянную
документацию и удаление временного каталога после завершения этапа. Переключать
ветки, править файлы и выполнять коммиты только в worktree этого чата: общая
рабочая папка и другие чаты не должны менять ветку или файлы из-за этой задачи.
Перенос текущей ветки и плана в отдельный worktree уже выполнен; до следующих
изменений проверить, что общая папка чистая и находится на `main`.

Согласовать правила с существующими требованиями `AGENTS.md`, включая проверку
статуса Git и запрет `git push` без явного согласия пользователя. Разграничить
локальную development-БД, которую разрешено пересоздавать, и production-БД,
для которой нужны новые миграции с сохранением данных. Окончательную версию
закрепить в постоянной документации (в первую очередь `AGENTS.md`), чтобы она
сохранилась после удаления каталога этого этапа.

### 2. Зафиксировать контракт CI и выбор выпуска

Добавить workflow на PR и push в `main`. Обязательный gate для SHA должен
включать полный `python -m unittest discover -s tests`, три автономных smoke
(`--sqlite-smoke`, `--pipeline-smoke`, `--analysis-smoke`), сборку Docker image
и проверку миграции как на чистой БД, так и на сохранённой схеме предыдущего
выпуска. CI использует только временные данные и тестовую конфигурацию.
Текущий `scripts/check-all.ps1` не запускает unittest и использует Compose
с локальными `.env` и `data`, поэтому он не является готовым CI gate.

Защитить `main` обязательным CI check, включая прямые изменения и изменения
самого workflow. Задокументировать точное имя обязательного workflow и
условия, при которых его результат считается действительным; пропущенный или
отменённый run не считать успешным.

**Аварийный выпуск через PR.** Предусмотреть явный путь для владельца проекта:
изменения всё равно попадают в `main` через PR, но полный набор CI-проверок
можно пропустить при осознанном решении выпустить конкретный коммит. Ограничить
GitHub bypass режимом «только через PR», без прямого push в `main`. Для выпуска
потребовать отдельное проверяемое разрешение, привязанное к номеру слитого PR,
его итоговому SHA, уполномоченному участнику и причине обхода. Способ выдачи
разрешения через GitHub определить и проверить до включения автоматики;
произвольная метка PR, текст коммита или `[skip ci]` сами по себе разрешением
не являются. Аварийный путь пропускает тестовый CI gate, но сохраняет
серверные проверки SHA, сборки, backup, миграций и работы обоих каналов.

Предпочтительный способ запуска — серверный systemd timer: VPS получает
`refs/heads/main` существующим read-only deploy key и запрашивает результат
обязательного CI run. Selector допускает к deploy только текущий полный SHA
ветки `main`, для которого есть либо успешный run обязательного CI для нужного
репозитория, workflow, события, ветки и `head_sha`, либо проверенное аварийное
разрешение из слитого PR. `queued`, `in_progress`, отсутствующий, ошибочный или
неоднозначный результат без такого разрешения не дают права на выпуск. При
ошибке API selector завершает проверку без выпуска. После выбора закрепить SHA,
путь допуска и ID подтверждающего run/разрешения. Перед переключением повторно
проверить, что SHA всё ещё является tip `main`.
Промежуточные коммиты, вытесненные новым tip до переключения, пропускать.

Проверить с VPS доступность CI API и определить минимальные read-only права,
если необходим token; хранить его только на сервере. Решение не должно
требовать ключа входа на VPS в GitHub. Зафиксировать формат состояния выпуска
вне Git checkout: последний успешный SHA и image ID, кандидат, стадия операции,
CI run ID и отказанный SHA с временем следующей попытки. Запись состояния
выполнять атомарно. Определить отдельные сигналы об успешном выпуске, сбое CI,
сбое deploy и невозможности проверить CI; повторные сообщения об одном SHA
не дублировать. До реализации выбрать адресата и канал уведомления, работающий
также при остановленных ботах, и проверить обработку ошибки доставки.

### 3. Реализовать безопасное развёртывание

Сначала провести read-only инвентаризацию VPS: фактические unit/override,
backup script и timer, права каталогов, checkout, Compose, образы, SQLite,
состояние обоих контейнеров и возможность обращения к CI API. Сверить их с
`docs/PRODUCTION.md`. Затем хранить версионируемые шаблоны deploy-скрипта,
systemd unit/timer и процедуру установки в репозитории. До включения timer
убедиться, что обычный boot и ручной запуск используют тот же pinned release.

**Подготовка кандидата без остановки каналов.** Взять единую блокировку для
автоматического и ручного deploy; проверить чистоту checkout и соответствие
`HEAD` текущему рабочему SHA. Получить одобренный коммит, проверить его полный
SHA и собрать образ из чистого checkout. Присвоить образу тег по SHA и OCI
revision label, сохранить предыдущий image ID и защитить его от удаления.
Тег сам по себе изменяем, поэтому сверять также image ID. Проверить candidate
на временной БД и тестовых настройках. Текущий Dockerfile загружает пакеты из
сети: один source SHA сам по себе не гарантирует одинаковые байты образа;
выпуск фиксирует фактически собранный image ID. Ошибки fetch, сборки и
предварительных проверок не останавливают работающие контейнеры.

**Backup и миграции.** Проверить свободное место и возможность сохранить
отдельный снимок выпуска вне ротации ночных backup. Остановить оба writer и
убедиться, что нет второго polling с теми же credentials. Сделать SQLite
backup через SQLite API и проверить `integrity_check` именно копии; записать
её идентификатор в состояние выпуска. Секреты, PEM и содержимое БД не выводить
в логи и не передавать в CI. Отдельно реализовать управляемую команду миграции
из candidate image: сейчас миграции запускаются при старте ботов, а healthcheck
их не выполняет. Применять только новые неизменяемые файлы `0002+`, затем
проверять `schema_migrations` и целостность рабочей БД. Зафиксировать, что
runner транзакционен на один файл, а сбой между несколькими файлами требует
явного восстановления. Запретить переход, если миграция не совместима с
предыдущим кодом и не подготовлен отдельный ручной план.

**Переключение и проверка.** Настроить Compose так, чтобы оба сервиса запускали
один закреплённый image ID без сборки или pull при `up` и после reboot.
Запустить оба канала, дождаться `healthy`, проверить image ID и revision label,
устойчивость состояния и счётчики рестартов. Проверить безопасные признаки
Telegram polling и VK Long Poll; Compose healthcheck сам по себе внешние каналы
не проверяет. Функциональную проверку реальными сообщениями выполнить по
приёмочному сценарию. Только после проверки обоих каналов и systemd записать
новый `last_good_sha` и успешное уведомление. Ночной backup timer должен
возобновляться после любого исхода deploy.

### 4. Обработать ошибки и возврат

Для каждого отказа записать действие и проверяемое состояние:

| Момент отказа | Действие |
| --- | --- |
| CI неуспешен или результат неизвестен и нет проверенного аварийного разрешения; fetch или сборка не удались | Оставить текущие контейнеры и SHA; сообщить причину без повторных уведомлений об одном результате. |
| Каналы остановлены, но миграция ещё не началась | Вернуть прежний pinned образ и оба канала; проверить их состояние. |
| Миграция началась или частично завершилась | Не восстанавливать снимок БД автоматически. Возвращать старый код только при доказанной совместимости с полученной схемой; иначе остановить выпуск и сообщить, что нужен отдельный план восстановления. |
| Новый образ запустился только в одном канале либо проверка каналов не прошла | Остановить кандидат в обоих каналах и вернуть оба на прежний совместимый выпуск; при неудаче честно зафиксировать degraded state и известить об этом. |
| Процесс deploy прерван или VPS перезагрузился | По сохранённой стадии и фактическим image ID/контейнерам завершить проверку либо безопасный возврат; не объявлять успех без проверки обоих каналов. |

Автоматический выпуск допускает только изменения схемы, после которых прежний
код работоспособен в период возврата. Для несовместимой миграции требуется
отдельный план и ручное решение до её развёртывания. Backup нужен для
аварийного восстановления, но автоматическая замена текущей БД снимком после
возможных пользовательских записей теряет данные; она также не отменяет
коммиты, уже сделанные в GitHub vault.

Проверить повторный запуск после прерывания, конкурентные автоматический и
ручной deploy, пересечение с ночным backup, отказ одного канала и частичное
переключение. Заблокировать частые повторы одного неудачного SHA и описать
безопасный способ повторной попытки. После каждого исхода сверять и сохранять
реальные SHA, image ID, состояние systemd, двух контейнеров и backup timer.

### 5. Проверить и ввести в эксплуатацию

В CI проверить обязательный workflow, защиту `main`, тесты, оба сценария
миграций и сборку образа на временных данных. Отдельно проверить аварийный PR:
слияние только уполномоченным участником, явное разрешение точного SHA,
отклонение чужой метки/текста коммита и отсутствие прямого push. В изолированном
окружении проверить selector и deploy с подменёнными ответами CI и управляемыми
отказами:
ожидание проверки, неверный SHA, отказ API, ошибка сборки, ошибка backup,
ошибка миграции, отказ одного контейнера, перезапуск посреди выпуска и повтор
неудачного SHA. Не использовать production credentials или копию
пользовательской БД в GitHub CI.

Перед первым включением автоматики повторно снять фактическое состояние VPS
и сделать контролируемый выпуск от текущего Assistant SHA. Подтвердить новый
SHA по серверной записи, checkout и обоим контейнерам, проверить Telegram и
VK, сохранность SQLite, systemd restart и ночной backup timer. Зафиксировать,
кто подтверждает функциональную приёмку обоих ботов и какие ответы считаются
достаточным свидетельством. Включать timer только после этой проверки.

Обновить `docs/OPERATIONS.md` до включения timer: убрать устаревший рецепт
`git pull` со старыми именами сервисов, описать обычный и аварийный PR-выпуск,
просмотр состояния, уведомления, паузу автоматики, безопасный ручной повтор и
возврат. Обновить `docs/PRODUCTION.md` датированным результатом первого выпуска
и процедурой
проверки текущей версии; источником истины для изменяющегося SHA служит
серверная запись выпуска и контейнеры, а не вручную обновляемая строка в
документе. Обновить `docs/RUN.md` и `AGENTS.md` для правила новых миграций.
Существующие локальные backup на одном VPS не защищают от потери всей VM;
границу этой гарантии оставить явной в эксплуатационной инструкции.

После пользовательской приёмки записать результат в `docs/HISTORY.md`,
актуализировать пункт бэклога, перенести постоянные правила и эксплуатационные
сведения из рабочего каталога и удалить `docs/auto-deploy-main/` до слияния
ветки. Push и дальнейшие действия с production выполнять по `AGENTS.md` и
`docs/PRODUCTION.md`.

## Критерии готовности

1. Только актуальный SHA `main` с успешным обязательным CI run для того же SHA
   либо с проверенным аварийным разрешением из слитого PR допускается к выпуску.
   Он развёртывается без ручных команд на VPS; неуспешный или неизвестный CI
   без такого разрешения блокирует обновление.
2. Оба канала после выпуска используют один зафиксированный image ID и SHA;
   серверная запись и состояние контейнеров совпадают, включая после reboot.
3. Сбой до переключения сохраняет рабочую версию. Сбой после переключения
   завершает проверенный возврат только при совместимой схеме; иначе система
   фиксирует безопасное состояние и сообщает о необходимости ручного решения.
4. Production SQLite и записи пользователей сохраняются. Новые миграции,
   резервная копия и ограничения возврата проверены; секреты не попадают в Git,
   GitHub workflow, CI-артефакты или логи.
5. Результат обычного или аварийного выпуска и сбоя сообщается один раз с SHA,
   способом допуска и стадией. Автоматику можно остановить по документированной
   процедуре; аварийный обход требует явного разрешения через PR и не отменяет
   серверные проверки и сохранение production-данных.
6. Постоянные правила для новых функциональностей приняты, эксплуатационные
   документы обновлены, а временный каталог этапа удалён до слияния ветки.
