# Шаг 7.2: хранение релизных веток

Проверка выполнена 16 октября 2026 года на синтетических данных. Настоящих
`release/1.0`, опубликованного `v1.0.0` и первого выпуска на VPS пока нет.
Удалённых веток, тегов, Releases, образов и записей VPS этот шаг не менял.

## Правило и процедура

`scripts/release_branch_retention.py` содержит чистую функцию
`plan_retention(snapshot, now=...)`. Она упорядочивает канонические
`release/X.Y` численно, оставляет активную линию VPS и три непосредственно
предшествующие, а также все более новые линии. Дополнительно сохраняет линии,
которые поддерживаются, служат base или локальным head открытого PR, связаны с незавершённым выпуском
или нужны для rollback. Лишь остальные линии становятся **кандидатами**.
Функция ничего не удаляет. `revalidate_candidate` требует перед отдельным
действием второй полный снимок и совпадение всех значимых данных; допускается
только более позднее время чтения VPS. Оба снимка должны оставаться не старше
пяти минут на момент сверки. Если исходный план устарел, нужен новый план.

Серверная версия берётся из `state.json:last_good.version`, а `stage` — из
`state.json:stage`; оператор дополнительно сверяет версию и SHA с фактическим
pin контейнеров и checkout. Снимок должен содержать репозиторий, полный список
веток с SHA, полный список защищённых тегов, **все** открытые PR репозитория
с номером, base и head (репозиторий и точное имя ref для каждого конца), поддерживаемые,
незавершённые и rollback линии, а также серверные версию, `stage`, отсутствие
`deploy-in-progress` и время чтения. Для каждого источника отдельно
подтверждается полнота. Снимок VPS не должен быть старше пяти минут; допустим
только `stage=success`, а активный тег должен присутствовать в списке.
Ошибка API, неполный список, отсутствие тега или ref, плохой SHA, старый снимок,
`rolled_back`/`degraded`/`preparing`/`rollback_started` останавливают план.

Когда реальные линии появятся, оператор в доверенной административной среде:

1. Сначала проверяет production по `docs/PRODUCTION.md` и
   `docs/auto-deploy-main/STAGE5_STEP4.md`: `state.json`, текущую версию и SHA,
   marker, оба контейнера, текущий pin и необходимость rollback. Секреты,
   содержимое `.env` и SQLite не печатает.
2. Полностью читает GitHub branches, protected tags, все открытые PR независимо
   от их base и сведения о незавершённых выпусках. Локальный head защищает
   релизную ветку даже при base `main` или другой линии; одноимённый head
   чужого fork не считается ref проекта. Отдельно устанавливает
   поддерживаемые линии. Если полноту любого источника подтвердить нельзя,
   останавливается.
3. Строит план и сохраняет кандидатов вместе с точными SHA refs в журнале.
   Согласовывает удаление удалённых веток согласно `AGENTS.md`: оно запрещено
   без явного согласия пользователя на `git push` или эквивалентную запись.
4. Непосредственно перед **каждой** отдельной записью вновь читает VPS и все
   источники GitHub, вызывает `revalidate_candidate`, затем ещё раз сверяет
   SHA конкретного ref. При любом изменении плана, ref, PR или серверного
   состояния прекращает действие и получает новое согласование. После записи
   проверяет отсутствие только указанного ref и журналирует его имя и SHA.

GitHub REST deletion ref не предоставляет условие `expected SHA`, поэтому
последний интервал между чтением и удалением не защищён от гонки. Пока не
появится надёжный механизм атомарной записи или отдельная согласованная ручная
процедура с контролем отсутствия параллельных изменений, этот шаг **не даёт
команды execute** и не разрешает фактическое удаление. Токен записи GitHub
на VPS не размещается; удаление относится только к административной среде.
Правило не удаляет теги, образы, Release и серверные записи.

## Результат тестовых данных

Команда:

```powershell
.\.venv\Scripts\python.exe -m unittest tests.test_release_branch_retention -v
```

Результат: 15 тестов, `OK`. Снимок с активной `release/2.0` и шестью прежними
линиями сохраняет `release/2.0`, `release/1.5`, `release/1.4`, `release/1.3`;
`release/1.2`, `release/1.1`, `release/1.0` становятся кандидатами. Отдельные
тесты подтверждают сохранение обеих сторон локального PR, поддержку, pending и
rollback, сохранение более новой линии, отказ на пустых/неполных источниках,
устаревшем VPS, незавершённой стадии, отсутствующем активном ref или теге.
Head PR из fork не защищает одноимённый локальный ref. Изменение PR либо SHA
ref между планом и повторным снимком даёт отказ; повторный снимок VPS должен
быть новее исходного.

Это закрывает **проверку правила на тестовых данных** шага 7.2. Фактический
cleanup после появления достаточного числа реальных линий остаётся будущей
эксплуатационной задачей. Шаг 7.3, первый выпуск и приёмка VPS не начинались.
