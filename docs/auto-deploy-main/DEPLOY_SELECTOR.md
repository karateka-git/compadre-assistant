# Этап 5, шаг 1: выбор точного production-выпуска

`python -m scripts.select_deploy_release vX.Y.Z` читает GitHub API и печатает
один JSON-манифест: репозиторий, версию, ветку, полный SHA, Release ID,
workflow, run ID и attempt. На этом шаге команда не выполняет fetch, сборку,
остановку ботов, backup, миграции или переключение контейнеров. Её результат
предназначен для следующей стадии серверной команды. После fetch и непосредственно
перед остановкой каналов требуется повторить проверку Release и тега, сверить
чистый detached checkout с SHA манифеста и сохранить выбранный candidate.

Аргумент обязателен; автоматического выбора latest нет. Допускается только
канонический `vMAJOR.MINOR.PATCH`. CLI сверяет origin локального checkout и
GitHub API с `karateka-git/compadre-assistant`. Репозиторий публичный:
`GITHUB_TOKEN` необязателен, при наличии используется для чтения API. Ошибка
или лимит API завершает команду с кодом 1 без JSON и без допуска. Токен и
секреты не печатаются.

Обычный выпуск требует опубликованный GitHub Release с точным tag/name,
`draft=false`, `prerelease=false`, полным `target_commitish` и явным
`Тип выпуска: обычный` в единственном служебном блоке. Там же должны быть
точные SHA, `release/X.Y` и ссылка на CI run/attempt этого репозитория.
Publisher создаёт этот блок и запрещает служебные поля в пользовательских
notes. Любой иной или отсутствующий тип, включая будущий аварийный выпуск,
обычный selector отвергает.

Тег должен напрямую указывать на commit SHA; annotated tag не принимается.
Selector проверяет действующий tag ruleset с запретом update/deletion и `immutable=true`
у конкретного Release,
совпадение SHA тега, Release и манифеста, а также достижимость commit из
текущего `release/X.Y`. Ветка может уйти вперёд после публикации: прежний
выпуск остаётся допустимым, если его commit является предком tip. Для
`vX.Y.0` требуется `main-full`, для PATCH — `release-full`, причём именно
закреплённые run ID и текущий attempt должны иметь полный успех всех
обязательных jobs и steps на точном SHA. После проверки selector повторно
читает Release, тег и ветку; изменение снимка закрывает допуск.

Локальные fixture-тесты покрывают обычный выпуск, PATCH, продвижение ветки,
ошибочный репозиторий, версию, tag, SHA, защиту, emergency marker, CI,
недоступность API и изменение Release во время проверки. Реального `v1.0.0`
пока нет; работа команды с опубликованным выпуском и VPS остаётся проверкой
последующих шагов этапа 5.

Поле `immutable` документировано в [GitHub REST Release response](https://docs.github.com/en/rest/releases/releases?apiVersion=latest).
Настройку всего репозитория через `/immutable-releases` по-прежнему проверяет
publisher с правом Administration(read); этот endpoint возвращает 401 без
авторизации. Серверному selector достаточно публичного поля самого выпуска,
поэтому ему не нужен admin token.
Публичный GET tag ruleset скрывает `bypass_actors`; selector принимает
отсутствие этого поля, а publisher с привилегированным доступом требует
явный пустой список до создания выпуска. Точный SHA тега, Release и манифеста
сверяется при выборе и повторно перед остановкой ботов на следующем шаге.
