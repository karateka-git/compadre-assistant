# Временный runbook: `deploy-prod --emergency`

Шаг 6.4 проверен локально 16 октября 2026 года. Этот документ действует до
переноса в постоянные эксплуатационные инструкции на этапе 7. Команда на
production VPS пока не запускалась.

## Перед запуском

Владелец публикует аварийный `vX.Y.Z` через
`scripts.publish_emergency_release`. Требуются опубликованный недрафтовый
immutable GitHub Release, прямой защищённый тег точного SHA и полный журнал
PR. Для PATCH журнал содержит все merge commits первой родительской линии после
предыдущей версии, две взаимно связанные записи на каждое исправление:
`release/X.Y` и `main`. Для новой линии фиксируются явно выбранные PR из
`main`. Обычный `deploy-prod vX.Y.Z` аварийный Release отвергает.

На VPS проверить текущие оба канала, состояние systemd и backup timer,
доступность GitHub API и свободное место. Зафиксировать решение и отдельную
причину установки. Новые миграции требуют предварительного доказательства
совместимости и ручного плана; текущий контроллер без этого останавливается
до критической секции.

```bash
sudo deploy-prod --emergency vX.Y.Z --reason "срочное восстановление"
```

Команда требует `sudo` от серверного владельца `user`, точную каноническую
версию и непустую однострочную причину. Она показывает SHA, фактическое
состояние полного CI, отдельно причину установки и опубликованную причину.
Обе причины записываются раздельно.

## Допуск и переключение

До остановки каналов selector повторно читает Release, тег, ветку, правила
защиты и полный CI. Сверяются SHA тега/Release/манифеста, принадлежность
ветке и факты каждого PR: цель, merge SHA, время, `pr-fast` на момент merge,
rule suite/bypass. Для PATCH дополнительно проверяются взаимные ссылки PR и
полный список merge commits после прошлого выпуска. URL полного CI в Release
должен принадлежать workflow, SHA и ветке до времени публикации. Заявленный успешный
полный CI требует строгого подтверждения конкретной попытки. Состояния
`failure`, `pending`, `not_run`, `unverified` допускаются только аварийным
путём и остаются видимыми в state. Ошибка API или изменение данных между
чтениями закрывает допуск.

После допуска контроллер использует общий lock и state machine: чистый
detached checkout точного тега, закреплённый image ID, synthetic smoke,
проверка схемы, отдельный SQLite backup, отдельный вызов миграций,
переключение Telegram и VK на один образ, health и возврат обоих каналов
при ошибке. Реальные `.env`, PEM и SQLite в GitHub не передаются.

## State, отказ и восстановление

Приватный `/var/lib/compadre-assistant-deploy/state.json` хранит последнюю
попытку: инициатора, причину команды, опубликованную причину, версию, SHA,
Release ID, workflow, состояние и источник CI при установке и при
публикации. При успехе `last_good` содержит тот же `deployment` и путь к
отдельному backup. При неуспехе после остановки каналов контроллер пишет
`rollback_started`, возвращает прежний checkout/image и проверяет оба
канала. Если безопасный возврат невозможен, `degraded` блокирует следующий
выпуск до ручного разбора; автоматического восстановления SQLite из backup
нет. Состояние последней попытки нужно сохранять во внешнем эксплуатационном
журнале перед следующим выпуском.

Отказ до остановки каналов оставляет их работать и записывает
`failed_preflight`. Не повторять команду вслепую: проверить `state.json`,
marker `deploy-in-progress`, оба канала, backup и причину отказа. Для
`degraded` остановиться и составить отдельный план восстановления данных и
сервисов согласно `docs/OPERATIONS.md`.

## Граница достоверности журнала

GitHub `immutable=true` и защищённый тег фиксируют выпуск и SHA, но API не
предоставляет независимого неизменяемого источника для первоначального текста
Release notes. Selector сравнивает текущий структурный манифест с PR, Git и
CI; опубликованную причину он может только прочитать как текущую запись
Release. Исторические `not_run`/`unverified` и текст метода сравнения двух
патчей нельзя независимо восстановить после исчезновения GitHub Actions или
rule suite history. Изменение notes, не противоречащее доступным фактам,
остаётся границей доверия. Сохранить проверенный текст Release и решение
владельца во внешнем журнале сразу после публикации; сверять его перед
production deploy. Успех `pr-fast` после merge не меняет снимок на момент
merge; потеря истории может закрыть повторный допуск.
