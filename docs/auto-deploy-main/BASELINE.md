## GitHub

Репозиторий `karateka-git/compadre-assistant` публичный; `main` на момент
снимка — `73b0a4e58b8b654e0593ba634ca71b94264f2bd1`. В GitHub пока нет
PR, релизных тегов, опубликованных Releases, workflow runs и repository
rulesets. `main` не защищён. Actions разрешены. Разрешены merge commit,
squash и rebase; для подсчёта PR по merge commits это предстоит ограничить.

Текущий `gh`-сеанс пользователя `karateka-git` имеет admin-доступ к
репозиторию. Чтение repository/rulesets, PR, check runs, Actions runs и
Releases через API удалось; пустые списки означают отсутствие объектов, а
не готовность будущей настройки. Ruleset bypass `pull_request` поддерживается
API для branch rulesets, но фактический обход проверить можно только после
создания правила и пробного PR. Никакие настройки GitHub не менялись.

С VPS без GitHub API token получен HTTP 200 на чтение списков PR, check runs,
Actions runs и Releases публичного репозитория. Это подтверждает базовую
доступность API, но не проверяет будущие поля run/jobs и ограничения частоты
анонимных запросов. Read-only deploy key на VPS предназначен для Git fetch,
не для аутентификации GitHub REST API. До шага 5 проверить достаточность
анонимного чтения конкретного опубликованного релиза и run; если его
недостаточно, выбрать минимальные read-only полномочия без GitHub write
token на VPS.

Документация GitHub по режиму обхода `pull_request` для branch rulesets:
<https://docs.github.com/en/rest/repos/rules>.

## Принятые точки отсчёта и границы

1. Порог полного CI — три PR, слитых в `main` через merge commit после
   включения контроллера. При его включении записать точный SHA тогдашнего
   `main` как anchor и начать счёт с нуля. Сегодняшний SHA выше — снимок,
   а не неизменяемая будущая точка: слияния до включения контроллера не
   выдавать за уже посчитанные. `release/*` проверяется после каждого merge
   независимо от этого счётчика.
2. Первый выпуск процесса — `release/1.0` и `v1.0.0` от конкретного успешно
   прошедшего полный CI commit `main`. Историческому production SHA версия
   задним числом не назначается. До первого выпуска сохранить его SHA,
   текущий image ID и рабочую копию БД для процедуры возврата.
3. На шаге 3 добавить отдельный режим CLI `python -m compadre_assistant
   --migrate`: он должен применять только ожидающие неизменяемые миграции к
   настроенному файлу БД и завершаться без запуска каналов и внешних API.
   Deploy вызывает этот режим из candidate image однократно после остановки
   обоих writers и проверенного backup. Конкретная реализация CLI и её
   тесты относятся к шагу 3; до неё миграции на VPS не запускать.
4. Для уже существующей production-схемы новые изменения оформлять файлами
   `0002+`; сохранение данных обязательно. Автоматический возврат старого
   image допустим только при доказанной совместимости новой схемы со старым
   кодом. После записи новых пользовательских данных восстановление старой
   SQLite-копии автоматически недопустимо; оно может потерять данные и не
   отменит внешние GitHub commits. Несовместимая схема или частично
   применённые несколько миграций требуют отдельного плана восстановления.

## Требует проверки в следующих шагах

- Перед включением rulesets проверить пробным PR обязательный `pr-fast`,
  защиту от прямого push и доступность PR-only bypass для владельца; сейчас
  нельзя утверждать, что конкретное правило уже работает.
- До первой миграции сравнить фактическую production-схему с ожидаемой базой
  предыдущего выпуска, затем испытать переход на копии БД. Список таблиц и
  строка `schema_migrations` этого сравнения не заменяют.
- До первого deploy зафиксировать реальные image ID, проверить backup и
  восстановление в изолированной среде, а также выбранный независимый канал
  уведомлений. Эти решения нельзя подтвердить одним read-only снимком.
- Перед использованием GitHub API на VPS проверить работу для непустых
  PR/checks/runs/releases и выбранную модель ограничений доступа.
