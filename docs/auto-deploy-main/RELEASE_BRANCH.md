# Этап 4, шаг 1: новая релизная ветка

Команда `scripts/create_release_branch.py` создаёт локальный ref
`release/X.Y` без переключения текущего worktree. Её явный режим
`--publish-remote` после этого создаёт ref на GitHub через
`POST /git/refs`. Команда принимает полный SHA успешного `main-full`;
имя `main` не используется как источник ref при создании. Запись в GitHub
требует отдельного явного согласия пользователя.

Перед созданием команда проверяет, что `origin` и GitHub API относятся к
`karateka-git/compadre-assistant`, SHA существует локально как commit, имя
ветки свободно локально и на GitHub, а SHA является предком наблюдаемого
текущего `main`. Затем общий selector проверяет настоящий завершённый
`main-full` этого SHA: workflow ID/путь, репозиторий, ветку, run, текущую
попытку и успех всех обязательных jobs и steps. История `main` читается
повторно после выбора run. Любая ошибка Git, API или отсутствие допуска
останавливает команду до записи локального ref. `git update-ref` с ожидаемым
нулевым старым SHA предотвращает повторное создание и локальную гонку.

Пример после появления успешного полного run на `main`:

```powershell
git fetch origin main
$env:GITHUB_TOKEN = gh auth token
python -m scripts.create_release_branch release/1.0 <полный-SHA> --check-only
python -m scripts.create_release_branch release/1.0 <полный-SHA>
# Только после явного согласия на создание удалённой ветки:
python -m scripts.create_release_branch release/1.0 <полный-SHA> --publish-remote
```

Команда выводит проверенные SHA, run ID и номер попытки. `--check-only`
выполняет те же проверки без создания ref. Режим `--publish-remote`
требует, чтобы локальный ref уже указывал на тот же SHA. Непосредственно
перед записью он заново проверяет историю `main`, полный CI и отсутствие
удалённой ветки. Создание через GitHub API атомарно отвергает конфликт
имени при гонке; ответ POST и последующее чтение ref должны подтвердить
точное имя и SHA. Если запрос или read-back не подтвердился, команда
завершается ошибкой; состояние GitHub тогда нужно проверить вручную до
повтора. Обычный `git push` для этой операции не использовать: он может
обновить уже созданную кем-то ветку. Для POST нужен token с правом записи
`contents`. Правило `AGENTS.md` требует явного согласия пользователя перед
любой публикацией.
`release-full` при событии создания ветки ещё раз проверит тот же SHA через
`main-full` и пропустит повтор полного набора. Если `main` продвинулся,
прежний проверенный SHA остаётся допустимым, пока принадлежит его истории.

На момент реализации шага `main-full` ещё не зарегистрирован в default
branch; фактического успешного run `main` для выбора нет. Поэтому настоящая
`release/1.0` не создавалась и POST не выполнялся. Фактическую проверку создания и пропуска
повторного CI выполнить после слияния caller в `main` и успешного полного
run. До того локальные тесты покрывают SHA, идентичность репозитория и
workflow, skipped шаг, чужую историю, сдвиг `main`, занятое имя, ошибку API,
атомарную запись локального ref, конфликт POST и сверку read-back.
