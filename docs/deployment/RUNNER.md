# Опубликовать подписанный PATCH на runner

Оператор берёт `signer_attempt` в форме `run_id:run_attempt` из сводки отдельного запуска подписи после полного CI. При запуске `Production release` из защищённой `main` он указывает выбранные версию, SHA, это значение и обычные поля выпуска. Восстановление также получает исходный `source_attempt` установки. [Выдача и смена ключей](CI_ADMISSION.md)

Защищённое окружение `production-release` поставляет `PATCH_ALLOWED_SIGNERS` (строки OpenSSH), `COMPATIBILITY_POLICY_SHA` и разрешение `PRODUCTION_SIGNED_PATCH=true`. Включать путь после обновления контроллера и проверки его snapshot. При выключенном флаге обычные выпуски работают по прежнему протоколу. Явно переданный подписанный допуск с выключенным флагом завершает команду отказом. При включённом флаге новый PATCH требует допуск. Старый готовый Release устанавливается по прежним правилам. Ручная публикация, первый выпуск линии и аварийный выпуск сохраняют свои точки входа.

## Подтвердить публикацию

Runner читает точную завершённую попытку подписанта, метаданные артефакта этого запуска и ZIP по ID. После сверки digest он локально проверяет подпись, версию, SHA и внешний pin политики. Один GraphQL-запрос с правами выделенного писателя читает `release(tagName:)`, `ref(qualifiedName:)` и `latestRelease`. Так проверяются занятость имени Release и Git ref, черновик с запланированным именем тега (pending tag), статус prerelease и текущий Latest. Черновики должны быть видны учётной записи с правом записи содержимого. Ошибка GraphQL или неполный ответ останавливает публикацию. Для готовой версии runner дополнительно сверяет immutable Release, ссылку и объект тега. [Поля репозитория](https://docs.github.com/en/graphql/reference/repos#repository) · [Поля Release](https://docs.github.com/en/graphql/reference/releases#release) · [Поиск черновика по pending tag в GitHub CLI](https://github.com/cli/cli/blob/trunk/pkg/cmd/release/shared/fetch.go)

Для свободного имени runner создаёт объект тега, его ref и Release. Ответы API должны подтверждать выбранный SHA, аннотацию и реквизиты публикации. Более старая линия сохраняет существующий Latest. При сбое записи разрешено чтение текущего состояния. Готовая совпадающая публикация допускает продолжение. Чужой ref или частичный тег без Release требует сверки. Аннотация версии 2 и поля манифеста совместимы с читателями предыдущих выпусков.

## Передать попытку контроллеру

Команда ограниченного SSH имеет вид `sudo -n /usr/local/sbin/deploy-prod VERSION --patch-attempt ACTION SHA KEY OWNER SNAPSHOT D18 STATUS_ID`. До получения ID runner передаёт `0`. Для `reserve` и `resume` в stdin поступает один JSON-объект с полями:

| Поле | Значение |
| --- | --- |
| `admission` | Исходный канонический подписанный JSON в виде строки |
| `release_id` | Точный числовой ID подтверждённого immutable Release |
| `tag_object_sha` | Полный SHA объекта аннотированного тега |

Лимит stdin составляет 16 КиБ для всего конверта, внутри помещается подписанный JSON до 8 КиБ. Остальные действия получают только аргументы. Контроллер проверяет допустимые размеры и поля до сохранения резервации.

Контроллер независимо читает Release, ref и аннотированный объект. Он сверяет их с переданными полями, проверяет подпись по собственным ключам, pin политики, актуальную базу и активную попытку. Резервация поверх предыдущего штатного v2 сверяет последний Deployment и его действующий статус с локальными SHA, CI, поколением и миграцией. Все три дополнительных запроса входят в расход первой штатной выкладки. Подтверждённое закрытие подписанной попытки сохраняет принятую базу в приватном журнале. На следующем PATCH контроллер сверяет её с фактической приёмкой без чтения истории. Открытая попытка запрещает резервирование другого выпуска.

Ответы на `reserve` и `resume` содержат `attempt`, `deployment_id` и `started`. При `resume` с другим владельцем контроллер подтверждает завершение прежней попытки Actions и записывает владельца под блокировкой. Перед каждым POST Deployment/status runner получает от контроллера однократное разрешение (`create`, `in_progress`, `finish`). Право записи статуса содержит проверенную квитанцию базы либо результата. После POST runner использует проверенные ID из ответа. Он передаёт D18 уже в `in_progress`, а ID статуса — в следующих командах. При утрате ответа или ранее выданном разрешении runner читает результат без повторной записи. Перед `close` он перечитывает текущий статус и сверяет его ID, состояние и описание. Контроллер проверяет локальное владение и результат, фиксирует ID статуса и закрывает журнал до ответа. Установка и очистка сохраняют прежнюю последовательность `install`, `complete`, `finish`, `close`.

### Проверить восстановление на стенде

В проектном venv запустите `python -m unittest tests.test_signed_patch_controller`. Тест вызывает штатные CLI runner и контроллера через парсер SSH. Git, подпись и временная SQLite настоящие. Ответы GitHub, службы, контейнеры и системное переключение берутся из фикстуры. Для истории из 16 Deployment транспорт и отчёты CLI дали следующие результаты.

| Сценарий | Runner, запросов API | VPS, запросов API | Наблюдаемый результат |
| --- | ---: | ---: | --- |
| Прежняя принятая база v2 | 11 | 7 | Первый подписанный PATCH, одна установка и очистка |
| Закрытая подписанная база | 11 | 4 | Одна установка и очистка |
| Потеря ответов создания и двух статусов после записи | 15 | 4 | Три ошибки учтены, один Deployment |
| Обрыв SSH после очистки | 9 | 4 | Сохранена квитанция, попытка открыта |
| Продолжение после завершения исходного запуска | 21 | 5 | Тот же Deployment закрыт без повторной установки и очистки |
| Подтверждённый возврат | 11 | 4 | Записан failure, сохранена прежняя база |

Если создание осталось неподтверждённым и запись по исходному ключу отсутствует, повторная отправка требует отдельной операторской сверки. Для `resume` нужны исходный signer run/attempt и source attempt. Контроллер сверяет сохранённые намерения, текущий статус GitHub и фактический runtime. При надёжной резервации ручная правка статуса в GitHub во время штатного выпуска больше не является командой остановки. [Сверка спорного POST](../OPERATIONS.md#разобрать-неподтверждённый-post)

## Воспроизвести расход runner

В проектном venv выполнить `python -m unittest tests.test_signed_patch_runner`. [Проверка на двух объёмах истории](../../tests/test_signed_patch_runner.py) запускает `release_production.main` из shallow checkout защищённой `main` с другим SHA. Во временном Git и HTTP-стенде сохранены две пары PR, одна миграция и 16 предыдущих Release. После регистрации каждого реального HTTP-запроса независимым транспортом тест сверяет счётчики с отчётом runner. GitHub и SSH заменены локальными ответами.

| Этап штатного runner | REST GET | GraphQL | REST POST | Страницы | Ошибки | GET хранилища |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Получение допуска (попытка, метаданные, ZIP через API) | 3 | 0 | 0 | 1 | 0 | 1 |
| Проверка имени, черновика, ref и Latest | 0 | 1 | 0 | 0 | 0 | 0 |
| Создание аннотированного тега, ref и Release | 0 | 0 | 3 | 0 | 0 | 0 |
| Deployment, два статуса и подтверждение текущего результата | 1 | 0 | 3 | 1 | 0 | 0 |
| **Итого при истории из 16 или 1000 Deployment** | **4** | **1** | **6** | **2** | **0** | **1** |

В каждом прогоне получено **11 запросов runner к GitHub API**, один ZIP после редиректа и семь команд SSH. Две страницы уже учтены в REST GET. Отдельных запросов по PR, ветке или списку Deployment тестовый транспорт не наблюдал. Старый сопоставимый runner выполнял 206 чтений и 6 записей. В этом замере VPS выдаёт квитанции из фикстуры. Сквозной стенд с CLI контроллера и живой выпуск подтвердили 18 обращений суммарно на runner и VPS. [Сквозной результат](DEPLOY_MEASUREMENTS.md#проверить-бюджет-подписанного-patch-на-стенде) · [Замер в production](DEPLOY_MEASUREMENTS.md#проверить-живой-подписанный-patch-v441). Проверку старой трассы с ожидаемым HTTP 404 сохраняет исходная [методика замеров](DEPLOY_MEASUREMENTS.md#воспроизвести-замеры-patch).
