# Релизная линия и версия на VPS

`release/1.0` — поддерживаемая линия разработки. В ней последовательно
появились коммиты, отмеченные тегами `v1.0.1`, `v1.0.2` и `v1.0.3`. Тег
указывает на точный commit конкретного выпуска; имя ветки указывает на
движущуюся линию, которая может содержать и более новые коммиты.

Наглядная схема (буквы и показанное состояние VPS условные):

```text
release/1.0: A (v1.0.1) → B (v1.0.2) → C (v1.0.3)
VPS: пока работает на v1.0.1
```

Команда `sudo deploy-prod v1.0.2` выбирает тег `v1.0.2`, то есть commit B,
и проверяет, что B находится в истории `release/1.0`. Когда head ветки — C,
это доказывает сравнение GitHub; когда head ещё B, достаточно уже проверенного
равенства двух SHA. Фактический `v1.0.3` опубликован 18.10.2026 для commit
`e7b06ddcf397c5e82e3dc92b3c4ab62f0b54178f` после успешного
`release-full` run `39138180586`, attempt 1. Публикация не меняет VPS:
установленную там версию подтверждают отдельно по
[production-контексту](PRODUCTION.md).

Новый тег или GitHub Release сам по себе не обновляет VPS. Например, после
публикации `v1.0.2` сервер может всё ещё работать на `v1.0.1`. Оператор
отдельно запускает `sudo deploy-prod vX.Y.Z` с выбранной опубликованной
версией. Контроллер читает защищённый тег и его SHA, сверяет GitHub Release и
доказывает, что commit принадлежит соответствующей релизной ветке: если SHA
тега совпадает с head ветки, равенство уже подтверждено независимыми GitHub
ref; если ветка ушла вперёд, запрос сравнения GitHub должен подтвердить
достижимость тега из её head. Отдельно проверяется полный CI именно этого
SHA. Затем контроллер получает точный commit в локальный checkout VPS и
проверяет его до переключения обоих каналов на один закреплённый образ.

Текущий порядок ручного запуска, backup и восстановления описан в
[эксплуатационной инструкции](OPERATIONS.md); фактически установленный SHA,
образ и состояние VPS фиксируются в [production-контексте](PRODUCTION.md).

## Исправления в поддерживаемых линиях

Для исправления выбирают затронутые поддерживаемые линии. Если фикса ещё нет
в `main`, открывают PR туда и по одному PR в каждую выбранную `release/X.Y`.
Все PR группы ссылаются друг на друга полными URL в `Hotfix-Links:` своих
описаний. Например, main PR `#21` ссылается на release PR `#22`, а `#22` —
на `#21`. Если выбран также `release/1.1` (`#23`), каждый PR ссылается на
два остальных. Номера условные. Если фикс **уже вошёл в `main`** в составе
другой работы, новый main PR не открывают: в каждом release PR указывают
`Hotfix-Main-Commit:` с URL конкретного коммита в `main`, а выбранные release
PR ссылаются друг на друга. Для одного release PR в этом случае достаточно
`Hotfix-Main-Commit:` без блока `Hotfix-Links:`. Выбор линий делает владелец;
программа не может узнать, какую линию он намеревался включить, но не указал.

Релизные PR открывают обычными, проверяют изменения и заранее включают для
каждого GitHub auto-merge методом merge commit. Это разовое решение слить
данный PR, когда все обязательные условия будут выполнены. Новый main PR
после `pr-fast` сливают первым. В release PR `pr-fast` проверяет код и ссылки,
а обязательный `hotfix-deps` подтверждает фактическое вхождение исправления
в `main` и слияние выбранных более старых релизных PR. После слияния
предыдущего PR отдельный workflow повторно запускает `hotfix-deps` связанных
открытых PR. Как только оба результата успешны, GitHub автоматически
сливает следующий release PR. Цепочка идёт от старой линии к новой; сбой
проверки или конфликт останавливает её. Черновики и отдельное нажатие Merge
для каждого следующего release PR не требуются. Если фикс уже есть в `main`
и первый release PR готов раньше включения auto-merge, человек один раз
сливает его обычным Merge и запускает цепочку остальных линий.
После включения auto-merge связи PR не редактируют. Для исправления ссылок
его сначала отключают у всех ещё открытых PR группы, обновляют описания и
проверки и затем включают снова.

После каждого изменения релизной ветки выполняется полный `release-full`
точного SHA. Перед публикацией версия повторно проходит read-only проверку
актуальных ссылок, коммитов GitHub и полного CI. Release содержит URL
связанных PR и подтверждённый SHA основания в `main`: merge commit main PR
или уже существующий commit. Ссылки помогают проследить изменения, но не
доказывают семантическое равенство разных патчей. Обновление VPS остаётся
отдельной ручной командой.

**Этот порядок ещё не включён:** локальная заготовка рассчитана на draft и
не поддерживает ссылку на существующий commit в `main` и автоматический
перезапуск после merge. В GitHub auto-merge выключен, а ruleset пока требует
только `pr-fast`. До применения порядка нужно завершить реализацию,
настроить GitHub и проверить пробную цепочку. Даже после обновления checks,
запущенные через `pull_request`, не защищают от автора PR, который изменил
сам workflow; публикационный валидатор повторно читает живые данные.
Исторический `v1.0.3` опубликован по прежнему маршруту: новые правила не
меняют его тег, SHA или Release. Детали и текущие ограничения описаны в
[документе этапа](auto-deploy-main/HOTFIX_PAIRS.md).
