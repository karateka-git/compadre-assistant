# Релизная линия и версия на VPS

`release/1.0` — поддерживаемая линия разработки. В ней последовательно
появились коммиты, отмеченные тегами `v1.0.1`, `v1.0.2` и `v1.0.3`. Тег
указывает на точный commit конкретного выпуска; имя ветки указывает на
движущуюся линию, которая может содержать и более новые коммиты.

Наглядная схема (буквы и показанное состояние VPS условные):

```text
release/1.0: A (v1.0.1) → B (v1.0.2) → C (v1.0.3)
VPS: пока работает на v1.0.1
```

Команда `sudo deploy-prod v1.0.2` выбирает тег `v1.0.2`, то есть commit B,
и проверяет, что B находится в истории `release/1.0`. Когда head ветки — C,
это доказывает сравнение GitHub; когда head ещё B, достаточно уже проверенного
равенства двух SHA. Фактический `v1.0.3` опубликован 18.10.2026 для commit
`e7b06ddcf397c5e82e3dc92b3c4ab62f0b54178f` после успешного
`release-full` run `39138180586`, attempt 1. Публикация не меняет VPS:
установленную там версию подтверждают отдельно по
[production-контексту](PRODUCTION.md).

Новый тег или GitHub Release сам по себе не обновляет VPS. Например, после
публикации `v1.0.2` сервер может всё ещё работать на `v1.0.1`. Оператор
отдельно запускает `sudo deploy-prod vX.Y.Z` с выбранной опубликованной
версией. Контроллер читает защищённый тег и его SHA, сверяет GitHub Release и
доказывает, что commit принадлежит соответствующей релизной ветке: если SHA
тега совпадает с head ветки, равенство уже подтверждено независимыми GitHub
ref; если ветка ушла вперёд, запрос сравнения GitHub должен подтвердить
достижимость тега из её head. Отдельно проверяется полный CI именно этого
SHA. Затем контроллер получает точный commit в локальный checkout VPS и
проверяет его до переключения обоих каналов на один закреплённый образ.

Текущий порядок ручного запуска, backup и восстановления описан в
[эксплуатационной инструкции](OPERATIONS.md); фактически установленный SHA,
образ и состояние VPS фиксируются в [production-контексте](PRODUCTION.md).
