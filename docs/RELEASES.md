# Релизы и допуск на production

```text
ветка задачи → PR → pr-fast → main → main-full → release/X.Y
исправление → PR в main и выбранные release/X.Y → release-full
release/X.Y → защищённый тег и GitHub Release vX.Y.Z
           → отдельная команда deploy-prod vX.Y.Z → VPS
```

Слияние PR, создание тега и публикация Release сами по себе не обновляют VPS.
Линия `release/X.Y` движется: в ней могут быть несколько выпущенных коммитов.
Например, `release/1.0: A (v1.0.1) → B (v1.0.2) → C (v1.0.3)`, а на VPS
пока работает `v1.0.1`. Команда `deploy-prod v1.0.2` выбирает B и
проверяет, что он входит в историю `release/1.0`; ему необязательно
быть вершиной. При этом контроллер не устанавливает версию с номером
ниже уже успешно установленной на VPS; возврат старого runtime — отдельная
процедура. Фактическое состояние VPS — в [PRODUCTION.md](PRODUCTION.md).

## PR и проверки CI

Изменения входят в `main` через PR с merge commit. Действующий GitHub ruleset
требует `pr-fast` для `main`, а для `release/*` — `pr-fast` и
`hotfix-deps`; обязательных Approve от людей нет. Текущие правила GitHub
следует сверять перед операцией. Обход владельцем через PR описан ниже.

`pr-fast` запускается при открытии, повторном открытии, новом коммите,
редактировании описания и смене draft/ready у PR в `main` или `release/*`.
Он проверяет синтаксис Python, отслеживаемые файлы и миграции, ссылки
связанных исправлений, фиксированный набор unit-тестов и Compose с
синтетической конфигурацией. Проверяется тестовое слияние PR с базой.
Новый коммит PR вызывает новый прогон; сдвиг `main` без события PR сам
по себе не перезапускает `pr-fast`. GitHub также проверяет mergeability.
Полный набор на каждом PR не запускается.

После push в `main` контроллер `main-full` считает merge PR с последнего
успешного полного прогона. На каждом третьем слиянии запускается
`full-suite`; перед новым релизом его можно запустить вручную для
текущего SHA `main`. После push нового SHA в существующую `release/X.Y`
`release-full` запускает полный набор. Создание линии от уже проверенного
SHA `main` не повторяет его. Успешный controller без `full-suite` **не
является** допуском. Успешный полный результат того же SHA повторно
используется; после неуспешной попытки нужен явный rerun.

`full-suite` проверяет точный checkout, все unittest, три автономных smoke,
свежую и предыдущую SQLite-схему, сборку образа и healthcheck. CI использует
тестовые данные: он не подтверждает реальные ответы ботов, systemd или
production SQLite. Допуск к обычному выпуску сверяет репозиторий, workflow
(`main-full.yml` для новой линии, `release-full.yml` для PATCH), ref,
полный SHA, run/attempt и обязательные jobs/steps. Pending, skipped, failure
и сбой API закрывают допуск. Результат другого SHA, даже более позднего в
той же линии, не заменяет проверку выбранного коммита.

## Релизные линии и версии

Новую `release/X.Y` создают `scripts/create_release_branch.py` из
точного SHA `main` с успешным полным `main-full`. Команда сверяет tip
`main` и отсутствие занятого имени перед записью; сдвиг tip требует
новой проверки. Версии имеют формат `vMAJOR.MINOR.PATCH`: PATCH —
исправление существующей линии, MINOR — новая совместимая линия, MAJOR —
новая линия с несовместимым публичным поведением или данными. Номер
выбирается при подготовке выпуска, не по количеству PR. PATCH внутри
линии последователен, версия не переиспользуется.

`scripts/publish_release.py` принимает `--change initial|major|minor|patch`,
точный SHA tip линии и файл release notes. `--check` проверяет без
записи, `--dry-run` показывает текст, `--publish` после повторной
проверки создаёт прямой защищённый тег и недрафтовый GitHub Release.
Требуются чистый checkout, уникальное имя, защита `v*`, Immutable Releases
и успешный полный CI точного SHA. PATCH дополнительно проверяет все merge
PR с предыдущего выпуска **этой** линии и их подтверждённое основание в
`main`. Тег, SHA в Release и коммит должны совпасть. Между созданием
тега и Release нет транзакции: при частичном сбое имя занято, автоматического
удаления/перемещения тега нет. Команды — в [OPERATIONS.md](OPERATIONS.md).

После выпуска сохраняют активную линию VPS и три предыдущие, а также более
новые, поддерживаемые, связанные с открытыми PR, незавершённым выпуском
или rollback. `scripts/release_branch_retention.py` строит и повторно
проверяет план, но **не удаляет ветки**: GitHub REST delete не принимает
expected SHA, и между чтением и записью остаётся гонка. Удаление требует
отдельной безопасной процедуры и разрешения на запись. Теги, Releases,
образы и серверные записи этим правилом не удаляются.

## Исправления поддерживаемых линий

Владелец выбирает затронутые линии. Если исправления ещё нет в `main`,
создают PR в `main` и по PR в каждую выбранную `release/X.Y`. Все PR
группы содержат взаимные полные URL в `Hotfix-Links:` своих описаний.
Если фикс уже вошёл в `main` в составе другой работы, новый main PR не
открывают: каждый релизный PR содержит `Hotfix-Main-Commit:` с URL
достижимого коммита `main`, а выбранные релизные PR ссылаются друг
на друга. Для единственного релизного PR достаточно URL коммита.
Ссылки дают навигацию, но не доказывают смысловую одинаковость патчей.

Новый main PR сливают после `pr-fast` первым. Для release PR `pr-fast`
проверяет код и ссылки, а `hotfix-deps` — фактическое вхождение
связанного PR или коммита в `main`. После main merge доверенный workflow
повторно запускает актуальный failed `hotfix-deps` всех связанных
открытых release PR, ожидает ещё выполняющиеся checks в ограниченном
окне и перед rerun вновь сверяет PR и job. `pr-fast` это не перезапускает.
При заранее включённом GitHub auto-merge методом merge commit GitHub
сливает release PR после успешных checks и при отсутствии конфликтов;
возможен и ручной merge. После включения auto-merge связи не редактируют:
для исправления сначала отключают его у всех открытых PR группы.
Релизные линии независимы: PR другой линии не блокирует слияние,
публикацию или deploy текущей.

## Аварийный маршрут

Только владелец может явно обойти обязательный `pr-fast` при **слиянии PR**
в защищённую ветку; прямой push и force push это не разрешает. Решение и
причина записываются отдельно. `scripts/publish_emergency_release.py`
с причиной и перечнем PR сохраняет проверку ветки, SHA, merge PR, SemVer,
защищённого тега и Release, но допускает отсутствующий/неуспешный полный CI.
В Release фиксируются состояние `pr-fast` на момент merge, обход ruleset,
состояние полного CI и непроверенные проверки. PATCH сохраняет подтверждение
основания в `main`; другие линии независимы.

Сервер принимает аварийный Release только с `--emergency` и `--reason`.
Он повторно читает GitHub, различает тип Release и сохраняет проверки SHA,
тега, ветки, backup, миграций, здоровья и rollback. Обычная команда
`deploy-prod` аварийный Release отвергает. GitHub API не доказывает
первоначальный текст изменяемых release notes, поэтому перед запуском нужна
внешняя запись утверждённого решения и текста. Реальный аварийный Release
и переключение VPS пока не испытывались; подтверждены изолированные
сценарии. Практический порядок — в [OPERATIONS.md](OPERATIONS.md).
