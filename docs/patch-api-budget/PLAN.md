# План сокращения обращений при выпуске PATCH

План переводит проверку неизменного содержимого кандидата в полный CI, а решение о переключении версии оставляет контроллеру VPS. На каждом этапе сверяемся с [требованиями и правилами подсчёта](REQUIREMENTS.md). Текущие числа относятся к одному штатному PATCH на стенде; числа целевого протокола ниже — смета до реализации.

## Разобрать источники экономии

В действующем пути одни и те же факты заново устанавливают публикатор, установщик и обработчики нескольких SSH-команд. Например, запрос двух последних Deployment выполняется **18 раз**, по 9 на runner и на VPS. Ответы о теге базы и кандидата запрашиваются соответственно 22 и 20 раз. Даже если воображаемый общий кеш вернёт каждый повторный ответ бесплатно, трасса всё ещё содержит 67 разных REST-чтений и 2 разных GraphQL-запроса. С шестью записями это 75 обращений. Для бюджета 20 часть вопросов нужно перестать задавать во время установки.

| --- | --- | --- | --- |
| Deployment и статусы — 93 | Убрать поиск последней установки перед каждой командой SSH и повторный обход D17/D18. Сохранить ID и исходный runtime в журнале при резервировании. | Единственный контроллер под блокировкой сверяет базу допуска с фактической приёмкой, а дальнейшие команды предъявляют ту же попытку. Если сохраняем отмену через GitHub, прочитать статус перед переключением. |
| Ветки, ссылки тегов и объекты Git — 84 | Полный CI подтверждает выбранный SHA в истории линии, предыдущий тег и диапазон исправлений. Убрать повторное чтение файлов по HTTP при подготовке и на VPS. | В допуске закреплены ревизия доверенной политики и ожидаемый результат. Исходная точка принята по [замеру штатного PATCH](../DEPLOY_METRICS.md#воспроизвести-замеры-patch) на `d31a3bc1efeaf754f3108eed851e1143736ba4f1`: 350 запросов при 16 и 1000 Deployment. Runner выполнил 206 чтений и 6 записей, VPS — 138 чтений.

## Этап 1. Перенести проверку кандидата в CI (в работе)

- [x] **Шаг 1 — определить доказательство допуска. Модель: 6 Astra (высокий).** Расширить существующий артефакт совместимости данными из требований. Предпочтительный вариант для оценки — подтверждение доверенным workflow, которое контроллер может проверить локально по закреплённому ключу. До реализации проверить изоляцию от кода кандидата, выпуск и смену ключа, привязку к успешному run/attempt и отказ при повторном предъявлении допуска на другую базу. Если выбран вариант с проверкой происхождения через GitHub, добавить все его запросы к смете. Выбран [формат подписанного допуска с локальным доверенным ключом](CI_ADMISSION.md).

- [ ] **Шаг 2 — сформировать результат один раз. Модель: 6.2 Sol (высокий).** Перенести выбор предыдущего тега, проверку следующего номера PATCH, диапазона по первым родителям и байтов workflow в доверенный полный CI. Передать runner точный ID попытки. Измерить обращения CI до и после. На фикстуре с двумя парами PR проверить точные границы диапазона и отсутствие запросов для повторной проверки связей PR в полном CI и при выкладке. Допуск для другой политики, SHA или неуспешной попытки отклонить.

- [ ] **Шаг 3 — запускать все unit-тесты на PR. Модель: 6.2 Sol (высокий).** Для PR в `main` и `release/*` запускать `unittest discover -s tests` на тестовом слиянии. Проверить запуск набора при обновлении PR и удалить его повторный запуск для кандидата из полного CI. Сохранить тесты принятой версии в проверке обратной совместимости с базой, smoke-проверки и проверку образа. Стоимость изменений показать отдельно для PR и полного CI.

## Этап 2. Упростить публикацию на runner

- [ ] **Шаг 1 — публиковать по закреплённому допуску. Модель: 6.2 Sol (высокий).** В `release_production` и `publish_release` заменить повторную сборку допуска перед каждой записью проверкой сохранённых реквизитов. Подтверждать значения из ответов API. При занятости имени, неоднозначном ответе или готовом Release идти по соответствующему пути сверки. Ручную публикацию, emergency и первый выпуск линии проверить на сохранение их контрактов.

- [ ] **Шаг 2 — проверить смету до интеграции. Модель: 6.2 Astra (средний).** По трассе доказать назначение каждого вызова. Ниже рабочее распределение на один новый PATCH при заранее известном ID полного CI и локально проверяемом допуске.

| Операция | Runner | VPS |
| --- | ---: | ---: |
| Наличие целевого Release | 1 | 0 |
| Попытка CI, метаданные артефакта, запрос API для скачивания | 3 | 0 |
| Создание объекта тега, ссылки и Release | 3 | 0 |
| Независимое чтение Release, ссылки тега и аннотированного объекта | 0 | 3 |
| Проверка активного владельца при резервировании | 0 | 1 |
| Создание Deployment, статусы in_progress и success | 3 | 0 |
| Подтверждение финального текущего статуса | 1 | 0 |
| **Расчёт** | **11** | **4** |

Из 20 остаётся пять вызовов для подтверждений, которые потребуются при проверке протокола, например поиска CI или сопоставления текущего статуса с точным ID. Если реальный транспорт потребует двух запросов для последней строки, оба включить в отчёт. Штатный PATCH не должен скрыто возвращаться к полному обходу при исчерпании бюджета.

Проверить случай, когда CI одобрил A для следующего PATCH, а до публикации ветка продвинулась на B. При свободном имени runner должен поставить тег на A. Если имя уже занято выпуском B, публикация A под этим именем должна остановиться.

## Этап 3. Закрепить установку за контроллером VPS

- [ ] **Шаг 1 — разделить допуск и фактическое состояние. Модель: 6 Astra (высокий).** Передать допуск через ограниченный SSH-вход и проверить его на сервере. Под блокировкой сверить локальный runtime, базу, точный SHA кандидата и владельца. Между командами использовать сохранённую резервацию. Перед переключением проверить владение и состояние на VPS. Сохранить запрет параллельных установок, backup, сверку миграций, health и очистку. Расхождение GitHub и локального журнала при восстановлении требует разбора.

- [ ] **Шаг 2 — проверить обрывы и совместимость. Модель: 6.2 Sol (высокий).** Проверить потерю ответа на создание и оба статуса, перезапуск runner, закрытие исходной попытки и подтверждённый возврат. Не допускать второго Deployment, повторной установки или повторения очистки вслепую. Испытать старый Release без нового допуска и поэтапное обновление CI/контроллера до включения нового пути. Прогоны восстановления и прежнего протокола получают отдельные отчёты.

## Этап 4. Доказать результат на том же PATCH

- [ ] **Шаг 1 — сравнить транспорт до и после. Модель: 6.2 Sol (высокий).** В той же фикстуре запустить реальные точки входа runner и CLI контроллера с разными SHA у runner и кандидата. Сохранить две пары PR, одну миграцию, 16 Release, одинаковый полный CI и принятый v2. Повторить сначала с 16, затем с 1000 Deployment. Добавить проверку `runner_reads + runner_writes + vps_reads + vps_writes <= 20` на каждый успешный прогон, сверить точные объекты, конечную версию и закрытие журнала. Любой 404 и каждая страница уже должны входить в сумму. Сопоставить отчёты с транспортом и отдельно опубликовать стоимость CI, Git/SSH и storage. Инъекция ошибочного SHA, подменённого допуска, смены базы или занятого тега должна блокировать опасную операцию.

- [ ] **Шаг 2 — подтвердить штатный выпуск. Модель: 6.2 Astra (средний).** После успешного стенда в согласованное окно измерить следующий подходящий реальный PATCH с теми же границами учёта. В постоянные документы перенести фактическую трассу и ограничения. Цель принимается по измеренному результату; стенд и production подписать отдельно.

## Этап 5. Автоматически обновлять сводку после выкладки

- [ ] **Шаг 1 — переработать общую таблицу. Модель: 6.2 Sol (высокий).** Поместить сводку в начало [DEPLOY_METRICS.md](../DEPLOY_METRICS.md). На каждую выкладку отвести одну строку с датой UTC, версией со ссылкой на запуск Actions, сценарием, временем установки, техническим простоем ботов, числом обращений к GitHub API и результатом. Сохранить существующие строки, добавить пропущенные выпуски по подтверждённым журналам. Полный SHA доступен в журнале. Сохранить исторические замеры токенов и изменений, методику и стендовые результаты ниже основной таблицы.

- [ ] **Шаг 2 — собирать данные при завершении попытки. Модель: 6.2 Sol (высокий).** Runner формирует запись из реквизитов запуска, отметок времени и уже полученных отчётов без дополнительных запросов к GitHub. Время установки считать от начала установки на VPS до подтверждённого завершения, простой брать из отчёта контроллера. Для обращений к API учитывать весь выпуск с момента запуска, включая публикацию, по [границам замера](REQUIREMENTS.md). Успех фиксировать после подтверждения очистки, текущего статуса `success` и закрытия попытки на VPS. При обрыве до подтверждения указывать «результат не подтверждён». Для отсутствующих или неполных показателей указывать «нет данных», ноль использовать для измеренного нуля.

- [ ] **Шаг 3 — обновлять файл через PR. Модель: 6.2 Sol (высокий).** После попытки отдельный workflow создаёт PR в защищённую `main` или обновляет уже открытый PR сводки. При `resume` того же Deployment обновлять исходную строку, отмечать восстановление, сохранять ссылки на исходный и последующие запуски. Для отказа до создания Deployment идентифицировать попытку по запуску и номеру попытки Actions. При повторной доставке отчёта учитывать каждый исходный отчёт один раз. Расход API на обновление документации показывать отдельно. Проверить штатный выпуск, обрыв, восстановление и повторную обработку, а также два выпуска подряд в одном открытом PR. Повтор после сбоя записи документа должен обновить сводку без перезапуска выкладки.
