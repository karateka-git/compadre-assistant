# Проверить происхождение допуска PATCH

Контракт [PatchAdmission](../../scripts/patch_admission.py) связывает SHA кандидата, релизную линию, следующий номер PATCH, предыдущий тег и SHA его коммита с результатом точной попытки полного CI. SHA предыдущего тега задаёт начало диапазона. Отдельное поле `baseline` задаёт принятую установку, включая версию, SHA, ID Release, Deployment и статуса.

## Выдать допуск

После успешного завершения `release-full.yml` отдельный workflow из защищённой `main` должен подтвердить через GitHub исходные repository, workflow, run ID, attempt, event, SHA и успешные обязательные jobs. Закрытый ключ Ed25519 хранится в выделенном окружении подписи с разрешённой веткой `main`. Окружение доступно только проверенному коду доверенной ветки. Задание с ключом использует отдельную машину GitHub Actions, запускает только закреплённые инструменты и читает Git-объекты кандидата как данные. Тесты, зависимости и скрипты кандидата запускаются в других jobs без доступа к ключу.

Подписант проверяет существующий артефакт `repository-compatibility-<run_id>-<attempt>` с помощью [проверки evidence](../../scripts/predeploy_compatibility.py), включая байты workflow, идентичность попытки, SHA256 ZIP, базу и результаты тестов. Поле `evidence_sha256` закрепляет SHA256 этих байтов ZIP, `schema_fingerprint` содержит проверенный отпечаток новой схемы из отчёта, `migration` — ожидаемое имя последней миграции в точном коммите. Перед выдачей вычисляются предыдущий тег в линии, диапазон по первым родителям и следующий PATCH. Пропущенный или завершившийся ошибкой полный прогон допуска не получает.

В [workflow полного CI](../../.github/workflows/full-suite.yml) отдельный Docker-контейнер выполняет тесты/установку зависимостей без каталога runner, управляющих файлов Actions и Docker socket. В контейнер передаются экспорт проверенной policy, временный bare Git-репозиторий только для чтения и отдельный каталог результатов. После остановки контейнера доверенный код сверяет результаты и отправляет их в хранилище Actions. Платформа подставляет ID и SHA256 именно этой загрузки в имя шага следующего job. Подписант сравнивает эту квитанцию из API jobs с метаданными и полученными байтами ZIP.

Для включения [workflow подписи](../../.github/workflows/patch-admission.yml) требуется согласованное обновление policy и совпадающих workflow полного CI в кандидате. Создайте окружение `patch-admission-signing` с разрешённой веткой `main`, установите в нём `PATCH_ADMISSION_SIGNING_KEY` и затем включите переменную репозитория `PATCH_ADMISSION_ENABLED=true`. После успешной загрузки артефакта оператор берёт из сводки этого запуска точные пары идентификаторов исходного CI и подписанта. Имя артефакта `patch-admission-<signer_run>-<signer_attempt>`, файл внутри — `patch-admission.json`. Чтение результатов по указанным парам исключает поиск попыток по истории.

### Измерить добавленную работу CI

На стенде с 16 Deployment, одной миграцией и двумя парами PR [транспортный тест](../../tests/test_issue_patch_admission.py) считает запросы контроллера полного CI, повторную сверку базы harness и выдачу допуска. Исходный сценарий — push нового SHA в существующую релизную ветку. Для обеих групп совпали инструментальные отчёты и независимый транспортный счётчик.

| Скрипты CI на стенде | REST GET GitHub | GraphQL | Записи GitHub | ZIP из хранилища |
| --- | ---: | ---: | ---: | ---: |
| Прежние контроллер CI и сверка базы harness | 16 | 2 | 0 | 0 |
| Дополнительно изолированный подписант | 42 | 1 | 0 | 1 |
| Всего в измеренных скриптах | 58 | 3 | 0 | 1 |

Строка `patch-admission-http` в журнале подписанта показывает каждую группу чтений, включая страницы и ошибки. Отдельно выполняются Git checkout, загрузка зависимостей и отправка одного нового артефакта с подписью через `upload-artifact`. Сетевые вызовы внутри SDK Actions, внешнее хранилище загрузки, подготовка runner и существующий сбор статистики jobs в эти числа не входят. Это стендовый замер до запуска `Production release`.

## Проверить и сменить ключ

Runner и VPS используют один подписанный JSON и локально установленный доверенный файл OpenSSH `allowed_signers`. В нём оператор закрепляет открытый ключ в строке `compadre-patch-ci ssh-ed25519 <публичный ключ>`. На VPS файл находится вне checkout кандидата и доступен для записи только администратору. Каноническая сериализация и пространство имён `compadre-patch-admission-v1` закрепляют формат подписи. Проверка через `ssh-keygen -Y verify` сверяет подпись, номер и SHA выпуска, попытку CI, ревизию политики и фактическую приёмку базы. Для проверки подписи требуется ноль обращений к GitHub.

Для выпуска ключа оператор создаёт выделенную пару Ed25519 вне checkout, устанавливает публичную часть проверяющим и закрытую часть в окружение подписания. При плановой смене сначала добавляет новый публичный ключ с тем же принципалом, затем меняет ключ подписанта и после завершения открытых попыток удаляет прежнюю строку. При отзыве ключа уже выданный им допуск перестаёт проходить проверку. Возобновление требует отдельной сверки состояния и подтверждения действующим ключом. Для стенда ключи создаются во временном каталоге теста.
