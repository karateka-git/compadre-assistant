# Требования к расходу GitHub API при выпуске PATCH

Цель — опубликовать новый обычный PATCH из защищённой `main`, установить выбранный SHA на VPS и подтвердить результат **не более чем за 20 обращений к GitHub API суммарно**. Это требование к будущей реализации. Порядок изменений описан в [плане](PLAN.md), действующий процесс — в [правилах выпуска](../RELEASES.md).

## Определить границу замера

Начало — запуск `Production release` после успешного полного CI кандидата. Конец — оба канала прошли техническую приёмку, очистка подтверждена, текущий Deployment получил подтверждённый `success`, журнал VPS закрыт. Нужен путь с созданием нового тега и Release при разных SHA у `main` и `release/X.Y`. До запуска на VPS уже принята база v2. На штатном пути нет обрыва, конкурирующего выпуска и ручного вмешательства.

Сложить все обращения runner и VPS к GitHub REST и GraphQL, включая запросы вспомогательных процессов от их имени. Один HTTP-запрос GraphQL считается один раз. Учитывать каждую страницу, запись, HTTP-ошибку, повтор и запрос API перед перенаправлением. Ожидаемый 404 при первой проверке имени тоже расходует бюджет. Исключить двойной учёт отчёта VPS, переданного runner. Любая дополнительная проверка или поиск ID внутри запуска расходует тот же бюджет.

Отдельно показывать обращения предшествующего CI, изменение его расхода относительно исходного CI, загрузки из хранилища после редиректа, Git-транспорт и число SSH-команд. Если подготовка требует получения реквизитов для оператора, указать, кто и когда их получает. В отчёте должны быть видны как стоимость выкладки, так и перенос работы на более раннюю стадию. Действующая методика приведена в [DEPLOY_METRICS.md](../DEPLOY_METRICS.md#воспроизвести-замеры-patch).

## Определить, кому доверяют runner и VPS

- **CI подтверждает содержимое выпуска.** Доверенная политика проверяет точный SHA кандидата, предыдущий тег линии, весь диапазон слияний, пары PR, применимость к принятой базе и ожидаемую схему SQLite. Результат связывает репозиторий, линию, кандидата, предыдущий тег, базу установки, идентификаторы workflow/run/attempt, ревизию политики и миграцию с отпечатком схемы. Базу установки и предыдущий тег линии хранить отдельно: на VPS может быть принята другая линия.
- **Runner публикует согласованный SHA.** Перед созданием тега подтверждает вершину линии, номер версии и допуск CI. После публикации новый коммит в ветке или правка текста PR сами по себе не отменяют допуск уже проверенного SHA. Конфликт имени требует сверки существующего объекта; повторное использование версии для другого SHA запрещено.
- **VPS отвечает за фактическое состояние.** Под `deploy.lock` контроллер сверяет допуск с локальными `last_good`, поколением SQLite и состоянием runtime, закрепляет владельца в долговечном журнале и отказывает при расхождении. Опубликованная более новая версия сама по себе не мешает установке. Уже установленная более новая версия требует отдельного решения об откате.
- **Доказательство CI проверяется независимо.** Переданный runner файл сам по себе не даёт права установки. Контроллер должен уметь подтвердить происхождение, точную попытку и целостность результата по закреплённому источнику доверия. Способ и стоимость проверки выбрать на этапе 2. Кандидат и его тесты не должны иметь возможности выпустить себе доверенное подтверждение.
- **Deployment сохраняет историю.** Остаются одна запись попытки, `in_progress` и итоговый статус. Для предложенного бюджета предполагаются единственный обычный писатель и управление установками через контроллер VPS. При такой модели ручная правка статуса в GitHub больше не служит командой остановки. Если нужна отмена через GitHub, предусмотреть свежую проверку точного статуса непосредственно перед переключением и включить её в 20.
- **Сохраняются восстановление и проверки данных.** Обязательны backup, проверка SQLite и миграций, health Telegram/VK, подтверждение очистки, запрет повторной установки после потери ответа. При неопределённом результате POST использовать журнал, ключ попытки и точные ID. При недоказанном результате остановиться для сверки. Авария и `resume` имеют отдельные замеры.

## Принять результат

На прежней [интеграционной фикстуре](../../tests/test_patch_http_baseline.py) выпустить `v4.2.1` поверх `v4.2.0` с двумя парами PR, 16 предыдущими Release и одной миграцией. Сначала взять историю из 16 Deployment, затем добавить старые записи до 1000, оставив остальные входы прежними. В каждом прогоне требуется успешный полный маршрут, ровно один новый Deployment и **≤20 фактических запросов**. Чтение истории установки не должно расти при добавлении 984 старых записей.

Исходный штатный v2 на обоих объёмах даёт **350 обращений**: 344 чтения и 6 записей. Из них runner выполняет 206 чтений и 6 записей, VPS — 138 чтений. Дополнительно скачивается один ZIP из хранилища. Живой первый переход на v2 у `v4.2.5` дал 501 чтение и 6 записей при сверке прежней истории v1. Для него применяются отдельные условия сравнения. [Замеры и команды](../DEPLOY_METRICS.md)

Хранить воспроизводимую таблицу «до/после» с разбивкой по месту, этапу, REST-чтениям, GraphQL, записям, ошибкам и загрузкам. Суммы должны совпасть с независимым счётчиком транспорта. Установку готового Release, повтор после обрыва, старые форматы допуска и откат проверять отдельно. Превышение 20 в успешном штатном сценарии означает, что цель не достигнута.
