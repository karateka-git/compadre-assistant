# Динамическое подключение возможностей: рабочий план

Этот временный каталог хранит решения и материалы до завершения задачи из
[бэклога](../BACKLOG.md#динамическое-подключение-возможностей-ассистента).
Постоянные правила после приёмки переходят в
[архитектуру](../ARCHITECTURE.md), [запуск](../RUN.md) и
[эксплуатацию](../OPERATIONS.md). Каталог удаляется отдельным завершающим
изменением после проверки полноты переноса.

## Цель и границы

Оператор устанавливает доверенную возможность, включает или отключает её без
перезапуска Telegram и VK. Справка и маршрутизация каждого сообщения видят
одно состояние. Уже начатые операции завершаются с прежними зависимостями;
новые после отключения не допускаются. Сохранённый режим чата и предметные
данные не удаляются.

Установка, включение, отключение и обновление версии — разные операции.
Горячее обновление уже загруженной версии не входит в первый контракт: смену
кода и зависимостей нужно рассматривать отдельно от переключения входа.

## Проверенные ограничения текущего кода

| Узел | Ограничение для задачи |
| --- | --- |
| `compadre_assistant/bootstrap.py` | Импортирует Ask и Obsidian и собирает один процессный реестр при старте. |
| `core/presentation/incoming/registry.py` | Проверяет конфликт входов, но не умеет менять поколение и учитывать запросы. |
| `core/presentation/incoming/dispatcher.py` | Читает реестр несколько раз за сообщение; замена состояния в середине обработки недопустима. |
| `capabilities/obsidian/domain/vaults/github_connection.py` | Device Flow запускает поток без учёта в жизненном цикле runtime. |
| `docker-compose.yml` | Telegram и VK — разные процессы с общей SQLite; локальной замены реестра недостаточно. |
| `core/data/sqlite/migration_runner.py` | Глобальные версии миграций непрерывны от `0001`; файлы модуля нельзя подмешать в этот ряд. |

## Решения для первого этапа

1. Ввести единый контракт сборки и владения ресурсами для встроенных
   возможностей. Подготовка runtime не публикует его вход. Закрытие ждёт
   запросы и фоновые операции, которые пользуются его клиентами.
2. Публиковать неизменяемый снимок реестра с поколением. На начало обработки
   сообщения брать один снимок и lease; справка и маршрутизация используют
   его до ответа. Запрет новых lease предшествует drain. Ошибка подготовки
   оставляет действующий снимок.
3. Хранить желаемое состояние и поколение в общей SQLite. Оба процесса
   подтверждают подготовку и переключение; подтверждение относится к
   конкретному запуску worker. Перед допуском нового сообщения worker
   сверяет общий gate, чтобы запоздавший polling не оставил старый вход.
4. При отключении начатые операции продолжаются. Ожидающие в очереди VK
   сообщения получают состояние на фактическом начале обработки. При долгом
   drain операция остаётся незавершённой и показывает число активных работ.
5. `ENABLED_CAPABILITIES` задаёт начальное состояние только до создания
   каталога; после этого сохранённое состояние переживает рестарт.

## Поставка, доверие и схема

Первый формат внешнего модуля — неизменяемый архив pure-Python кода и ресурсов
с manifest. Manifest до импорта кода объявляет ID, версию, версию API,
совместимость приложения и Python, factory entrypoint, команды, зависимости,
миграции и хеши файлов. Установщик проверяет безопасные пути и размер архива,
полноту хешей, совместимость и одобрение digest оператором, затем кладёт пакет
в каталог с именем по digest. Установка не запускает код и не активирует вход.
`pip install` и build scripts в работающих worker не выполняются. Модуль с
новыми системными или native зависимостями требует обычного выпуска.

Проверенный digest подтверждает конкретный архив, а не безопасность кода.
Загруженный в процесс Python-код имеет доступ к секретам и ресурсам процесса;
для недоверенного кода понадобится отдельная изоляция. Управление пакетами
предоставляется локальному оператору, а не обычным сообщениям Telegram/VK.

`0001_initial_schema.sql` и имена применённых миграций не меняются. Общий
каталог управления добавляется новой последовательной миграцией `0002+`.
Миграции модуля учитываются по отдельному namespace и checksum. Отключение
не удаляет данные и не откатывает схему. Пакет с отсутствующей схемой можно
установить, но его включение получает статус `schema_pending`.

Для production действующий [порядок миграций](../RUN.md#пересоздание-базы-после-изменения-схемы)
требует остановить оба writer и сделать проверенную копию. Путь применения
новой схемы без перезапуска процессов пока **не решён**. До отдельного решения
горячее включение пакета, которому нужна новая схема, запрещено; этот пункт
бэклога нельзя закрыть одним переключением уже установленных возможностей.

## Этапы и проверка

1. Перевести встроенные Ask и Obsidian на управляемый lifecycle, учесть Device
   Flow и фоновые завершения. Проверить, что клиент закрывается после всех
   использующих его операций и ошибки подготовки не публикуют вход.
2. Добавить атомарные снимки и lease. Проверить гонки help/dispatch/disable,
   сохранение режима через revision CAS и отсутствие новых входов после gate.
3. Добавить общий каталог, CLI управления и согласование TG/VK. Проверить два
   процесса, рестарт одного worker, устаревшее подтверждение, ошибки prepare
   и drain, повторное переключение.
4. Реализовать установщик доверенного пакета. Проверить новый fake-пакет в
   обоих каналах без перезапуска и отказ до исполнения недоверенного кода.
5. Реализовать учёт схем модулей, preflight и эксплуатационный порядок.
   Проверить повторное применение, checksum mismatch, частичную ошибку,
   сохранение данных и совместимость возврата версии.
6. Провести приёмку с двумя каналами и длительными операциями, перенести
   постоянные правила в основную документацию и удалить этот каталог
   отдельным завершающим изменением.

Для гонок нужны управляемые `Event`/barrier и независимые соединения или
процессы; задержки по времени не дают надёжной проверки.
