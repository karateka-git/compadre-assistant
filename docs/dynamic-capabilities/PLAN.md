# Личные настройки возможностей: рабочий план

Этот план реализует [включение возможностей пользователем](../BACKLOG.md#включение-возможностей-пользователем): зарегистрированный пользователь выбирает свой набор встроенных возможностей, а Telegram и VK применяют выбор одного AppUser. Практические команды после реализации войдут в [RUN.md](../RUN.md), границы модулей — в [ARCHITECTURE.md](../ARCHITECTURE.md). Ниже описано запланированное поведение, а не уже доступные команды.

Временный каталог сохраняется через все PR и эксплуатационную приёмку. После переноса действующих правил в постоянные документы его удаляют отдельным завершающим изменением, затем закрывают пункт бэклога.

## 1. Зафиксировать границы и начальное состояние

Список возможностей фиксирован кодом приложения: Ask и Obsidian. Composition root явно собирает разрешённые конфигурацией запуска обработчики. Личное включение меняет только доступ пользователя к готовому обработчику, не создаёт и не закрывает runtime. Все пользователи продолжают пользоваться процессными зависимостями; каналы не перезапускаются и не ставятся на паузу.

Доступность определяется пересечением двух условий: возможность собрана и доступна в текущем процессе; пользователь включил её для своего AppUser. Глобальное отключение имеет приоритет. Недоступность внешнего API во время запроса остаётся обычной ошибкой возможности. Настройка личного vault и другие предметные условия проверяются самой возможностью после входа.

По умолчанию личный выбор — Ask включён, Obsidian выключен. Это правило применяется и к новым, и к существующим пользователям, у которых ещё нет явных настроек. После первого выпуска существующий пользователь должен явно включить Obsidian; его прежний режим, vault и статьи сохраняются. Такое изменение доступа следует указать в описании выпуска и подсказке при первом обращении к выключенному режиму.

Личный default Ask не переопределяет серверную конфигурацию. Если Ask глобально выключен, список показывает «выбрана, недоступна на сервере», а фактически доступных возможностей может не быть. Значение `ENABLED_CAPABILITIES` и требования credentials этим изменением не расширяются автоматически. Для приёмки обоих сценариев сервер должен собирать Ask и Obsidian; отдельно проверяется конфигурация только с одной возможностью и без возможностей.

Выбор относится к AppUser, не к identity, каналу или чату. После обычной привязки и подтверждённого переноса identity действуют настройки профиля назначения; настройки разных профилей не объединяются и не копируются. Режим по-прежнему хранится отдельно для каждого чата.

## 2. Реализовать общие команды

Команды обрабатываются ядром после разрешения identity и до предметного маршрута. Они доступны зарегистрированному пользователю даже до заполнения имени и не превращаются в новое имя профиля. Аргументы команд не содержат ID другого пользователя: действие всегда относится к разрешённому AppUser.

| Команда | Результат |
| --- | --- |
| `/capabilities` | Список всех известных встроенных возможностей: ID, описание, личный выбор и доступность на сервере; подсказки включения и отключения. |
| `/enable ask`, `/enable obsidian` | Сохранить личное включение, если обработчик доступен в процессе. Подтвердить, что выбор действует во всех привязанных каналах. Режим чата не менять. |
| `/disable ask`, `/disable obsidian` | Сохранить личное отключение известной возможности, даже если она сейчас глобально недоступна. Сохранить режимы и данные. |

Повторное включение или отключение возвращает «уже включена/отключена» и не меняет смысл состояния. Отключить можно все возможности, включая Ask. В ответе остаются общие команды и предложение `/capabilities`.

ID вводится точно в нижнем регистре. Отсутствующий, неизвестный или лишний аргумент даёт usage и ссылку на `/capabilities`, без записи в БД. `/capabilities` с аргументами также возвращает usage. Включение глобально недоступной возможности возвращает отдельное объяснение и не меняет личный выбор. Незарегистрированному пользователю эти команды предлагают `/register`.

`/help` остаётся доступна без регистрации: показывает общую справку и способ регистрации, без персональных предметных разделов. Для зарегистрированного пользователя справка содержит общие команды и только эффективно включённые возможности. `/start`, `/status`, `/exit` и все подсказки выбора используют тот же персональный набор. `/status` показывает сохранённый режим и отдельно сообщает, если он лично выключен либо недоступен на сервере.

Прямая команда выключенной возможности, обычный текст в её сохранённом режиме и адресный `/confirm` не вызывают её обработчик. При личном отключении ответ предлагает `/enable <id>` и `/capabilities`; при глобальной недоступности сообщает об ограничении сервера. Проверки общих подтверждений `core` сохраняют прежний приоритет. Повторное включение восстанавливает возможность маршрутизации сохранённого режима; `/exit` в любой момент очищает только режим текущего чата.

## 3. Добавить модель и хранение личного выбора

Общая ответственность принадлежит `core`. В `core/domain` добавить модель личной настройки, port repository и use cases чтения списка и изменения выбора. В `core/data/sqlite` добавить DTO, явные mapper-функции и реализацию port. Presentation получает доступность и метаданные из существующего реестра, а не импортирует Ask/Obsidian.

Публичные метаданные возможности дополняются `enabled_by_default: bool`, по умолчанию False. Composition root/описание Ask задаёт True, Obsidian — False. Для глобально отключённого входа доступны те же метаданные без сборки его клиентов. Ядро вычисляет выбор по метаданным, не содержит проверки `id == "ask"`. Новый встроенный ID в будущем по умолчанию выключен; изменение defaults существующих ID требует отдельного решения о переходе.

Новая последовательная core-миграция `0002_user_capability_preferences.sql` добавляет `user_capability_preferences`:

- `app_user_id INTEGER NOT NULL`, внешний ключ на `app_users(id)` с `ON DELETE CASCADE`;
- `capability_id TEXT NOT NULL`;
- `enabled INTEGER NOT NULL CHECK(enabled IN (0, 1))`;
- составной первичный ключ `(app_user_id, capability_id)`.

Если к началу реализации номер 0002 уже занят, использовать следующий свободный номер без изменения применённых файлов. `0001_initial_schema.sql` остаётся неизменным. Схема и профиль пользователя не пересоздаются.

Таблица хранит только явные настройки. Отсутствие строки означает `enabled_by_default` из каталога. Поэтому миграция не требует перечисления возможностей в SQL или backfill; регистрация автоматически получает начальный выбор без отдельной конкурентной инициализации. Явное отключение Ask сохраняется строкой False и переживает рестарт. Неизвестные будущему/старому коду сохранённые ID не удаляются и не дают маршрута.

Изменение выполняется атомарным upsert одной строки. Если нужно определить ответ «уже», чтение старого значения и upsert выполняются в одной короткой транзакции. Не записывать весь набор после чтения: параллельное изменение Ask не должно потерять изменение Obsidian. Ошибка записи возвращает понятный отказ и не выдаёт подтверждение успеха.

Миграция выполняется обычным выпуском по [RUN.md](../RUN.md#пересоздание-базы-после-изменения-схемы) и [OPERATIONS.md](../OPERATIONS.md). Команды пользователя выполняют только DML и не меняют схему. Production-доступ и согласование остаются по [PRODUCTION.md](../PRODUCTION.md). Отдельный механизм схем возможностей не требуется.

## 4. Применить выбор к справке и маршрутизации

Реестр собранных возможностей остаётся неизменным на время процесса. Добавить получение каталога доступных и глобально отключённых descriptors и создание представления реестра для конкретного пользователя. Персональное представление не меняет общий registry и не закрывает обработчики.

Для каждого обычного события dispatcher разрешает AppUser, затем одним запросом читает его настройки и создаёт неизменяемый набор эффективного доступа. Это чтение является точкой допуска события. Все последующие проверки входа, сохранённого режима, `/confirm`, справки и подсказок в этом событии используют один набор. Нельзя повторно читать настройки посередине предметного вызова.

Команды изменения сначала фиксируют запись, затем формируют ответ по свежему состоянию. Следующее событие любого привязанного канала читает SQLite заново: долгоживущий cache настроек и межпроцессные уведомления не нужны. В TG/VK при штатном развёртывании используется одинаковая серверная конфигурация; если она различается, личный выбор всё равно общий, но эффективная доступность ограничивается локально собранными обработчиками.

Предметный scope открывается только после успешного допуска. Отклонённый вход не обращается к article repositories, LLM, GitHub или другим зависимостям возможности. Неполный профиль продолжает обрабатываться текущими правилами регистрации, кроме явно доступных команд управления набором. Привязка identity не меняет источник настроек вручную: каждое новое событие заново разрешает AppUser.

## 5. Определить конкуренцию и начатые операции

Commit команды отключения отделяет новые события от уже допущенных. Если чтение настроек события произошло до commit, событие считается начатым и может завершить вызов после команды отключения. Если чтение произошло после commit, обработчик выключенной возможности не вызывается. Это правило действует также для события, ожидавшего в очереди VK или executor Telegram: приём update транспортом ещё не является допуском.

Два изменения одного ID упорядочиваются SQLite: действует последняя успешно зафиксированная запись. Изменения разных ID сохраняются независимо. Подтверждение команды описывает её собственный результат; последующая параллельная команда может сразу изменить выбор снова. Настройка одного AppUser не меняет настройки другого.

Начатые Ask, статья, sync, подтверждённый write-back и Device Flow завершаются по прежнему контракту, включая фоновый ответ в исходный чат. Фоновый callback не является новым входящим сообщением и не перепроверяет личное включение. После отключения не закрываются общие HTTP/LLM-клиенты и не отменяются потоки, поэтому отдельный lifecycle/drain протокол для этой задачи не нужен.

Поздний результат может сохранить или завершить режим только через существующий revision CAS. Отключение не увеличивает ревизию режима и не заменяет `/exit`. Поэтому уже начатый вход может завершиться сохранением лично отключённого режима; следующий текст получит подсказку включения. Если пользователь выполнил `/exit` или сменил режим, поздний результат не восстанавливает старый выбор.

## 6. Реализовать и проверить по этапам

Этапы выполняются по порядку. Новый и изменяемый публичный Python-код получает русские Google-style docstrings; реализации ports явно наследуются от соответствующих Protocol. Перед каждой отдельной задачей с исходным кодом перечитывается AGENTS.md.

| Этап | Изменения | Условие выхода |
| --- | --- | --- |
| 1. Domain и SQLite | Модель, defaults в descriptor, repository port, use cases, DTO/mappers, миграция и SQLite repository. | На временной БД подтверждены default для новых/существующих пользователей, сохранение явного выбора, idempotence миграции и независимые конкурентные upsert. |
| 2. Персональный доступ | Внедрить repository в сборку processor/dispatcher; единое чтение настроек; каталог и персональное представление registry. | Fake-возможность фильтруется без знания её ID ядром; отключённый вход не открывает предметный scope; defaults глобально отключённых descriptors совпадают с активными. |
| 3. Общие команды и UX | Добавить `/capabilities`, `/enable`, `/disable` в ChatCommand; обновить help/start/status/exit, вход, режим и confirm. | Проверены валидация аргументов, незарегистрированный и неполный профиль, все виды недоступности, повторные команды и состояние без возможностей. |
| 4. Каналы и гонки | Проверить два независимых processor с общей БД, связывание identities, in-flight и background delivery. | Выбор виден TG/VK после commit, другие AppUser изолированы, обе стороны гонки admission/disable воспроизводятся детерминированно, CAS режима не регрессирует. |
| 5. Выпуск и приёмка | Обновить постоянные пользовательские инструкции и архитектуру; провести обязательные проверки по RUN/RELEASES для точного SHA. | Миграция сохраняет данные предыдущей схемы; при живом переключении PID/boot ID каналов не меняются; пользователь подтвердил сценарии обоих каналов. |
| 6. Завершение | Перенести оставшиеся действующие решения, проверить ссылки, отдельно удалить временный каталог и закрыть backlog после эксплуатационной приёмки. | Выполнен завершающий порядок AGENTS.md, включая чистые рабочие копии и завершение worktree. |

### Этап 1 — шаги и отдельные коммиты

1. **1.1. Определить личный выбор в domain.** Добавить default в публичный
   descriptor (Ask включён, Obsidian выключен), domain-модель, repository port
   и сценарии чтения/изменения выбора. Проверить default, явное переопределение,
   неизвестный ID и независимость от конкретных возможностей. Сделать отдельный
   коммит.
2. **1.2. Добавить миграцию.** Создать следующий неизменяемый SQL-файл `0002+`
   с таблицей личных настроек и FK к AppUser. Проверить свежую и ранее
   применённую `0001` БД, повторный запуск и сохранность прежних данных.
   Сделать отдельный коммит.
3. **1.3. Реализовать SQLite-хранилище.** Добавить отдельную DTO, явные mapper
   и repository, атомарную запись по `(app_user_id, capability_id)` и чтение
   личного набора. Проверить независимые изменения разных ID, порядок записей
   одного ID и сохранение после нового соединения. Сделать отдельный коммит.

Этап 1 завершён, когда все три коммита сделаны в worktree задачи, целевые
тесты проходят и `git diff --check` не показывает ошибок. До этапа 2
диспетчер ещё не применяет личный выбор к сообщениям.

### Этап 2 — шаги и отдельные коммиты

1. **2.1. Построить каталог и личное представление.** Реестр отдаёт
   descriptors собранных и глобально отключённых входов; defaults для одного
   ID совпадают в обоих состояниях. Чистая логика строит для AppUser один
   неизменяемый набор «известна / глобально доступна / лично включена» без
   знания ядром имён Ask и Obsidian. Проверить fake-возможность и оба вида
   глобальной доступности. Сделать отдельный коммит.
2. **2.2. Подключить хранилище и применить допуск.** Composition root создаёт
   SQLite repository в scope события и передаёт его dispatcher. После
   разрешения AppUser dispatcher один раз читает личный выбор и использует
   полученное представление для прямого входа, сохранённого режима и
   предметного `/confirm`. После отказа предметный обработчик и его
   зависимости не вызываются; ранее допущенный вызов завершается. Проверить
   маршруты и сохранение revision CAS. Сделать отдельный коммит.
3. **2.3. Согласовать справку и два процесса.** `/help`, `/start`, `/status`,
   `/exit` и подсказки используют тот же личный набор в пределах события;
   общие команды остаются доступны. Два processor с общей временной БД
   видят изменения AppUser после commit без cache; выбор другого AppUser не
   меняется. Проверить границу чтения до/после commit и обновить относящиеся
   к этапу fixtures. Сделать отдельный коммит.

Этап 2 завершён после трёх коммитов и целевых проверок маршрутизации,
справки, композиции и двух процессоров. Пользовательских команд изменения
на этом этапе ещё нет: выбор для проверок задаётся через repository.

### Этап 3 — шаги и отдельные коммиты

1. **3.1. Показать личный каталог.** Добавить общую команду `/capabilities`
   и ответ со всеми известными ID, описаниями, личным выбором и серверной
   доступностью. Без регистрации предложить `/register`; зарегистрированному
   пользователю с незаполненным именем показать каталог без записи имени.
   Отклонить лишние аргументы. Проверить обычный, пустой и частично доступный
   каталог. Сделать отдельный коммит.
2. **3.2. Включать доступную возможность.** Добавить `/enable <id>` с точной
   проверкой аргумента и ID, проверкой серверной доступности и атомарным
   сохранением выбора только текущего AppUser. Повтор возвращает «уже
   включена», ошибка записи не подтверждает успех. Проверить оба канала и
   сохранение выбранного режима. Сделать отдельный коммит.
3. **3.3. Отключать и завершить UX.** Добавить `/disable <id>` для любого
   известного ID, даже временно глобально недоступного. Повтор идемпотентен;
   можно отключить все возможности. Сохранить данные, режим и фоновые ответы,
   согласовать сообщения `/help`, `/start`, `/status`, `/exit` и отказ
   предметного входа с работающими командами управления. Проверить неполный
   профиль, неизвестный ID, лишние аргументы и полный набор тестов. Сделать
   отдельный коммит.

Этап 3 завершён после трёх коммитов: пользователь может самостоятельно
увидеть, включить и отключить доступные возможности через оба канала.

Новые проверки добавить по месту: repository/use cases личных настроек, `test_migration_runner.py`, `test_incoming_boundary.py`, `test_incoming_commands.py`, `test_chat_modes.py`, `test_capability_composition.py`, `test_ask_channels.py` и тесты адаптеров. Прежние тесты, которым нужен активный Obsidian, явно включают его в fixture; не сохранять старый доступ обходным контрактом ради тестов.

Обязательные проверочные сценарии:

1. Новый и существующий AppUser без строки настроек: Ask выбран, Obsidian выключен; ранее сохранённые статьи и режим доступны после явного включения.
2. Явное отключение Ask сохраняется после нового соединения и рестарта processor; повторный `/register` не сбрасывает выбор.
3. Личное включение глобально отключённой возможности отвергается; глобальная недоступность не удаляет существующий личный выбор.
4. Один AppUser в Telegram и VK видит общий выбор, второй AppUser не меняется. Подтверждённый rebind использует настройки профиля назначения.
5. `/help`, `/start`, `/status`, `/exit`, прямая команда, обычный текст и предметный `/confirm` согласованы с выбранным набором; core confirm сохраняет прежнюю семантику.
6. При выключенном Obsidian ни обычный текст, ни его команда, ни confirm не вызывают предметный handler; после enable сохранённый режим работает снова.
7. Долгий Ask и Device Flow заканчиваются и отвечают в исходный чат после disable; runtime остаётся пригоден для другого пользователя.
8. Управляемые Event/barrier доказывают порядок «допуск до commit — завершение разрешено» и «допуск после commit — отказ». Проверки используют независимые соединения, а межканальная проверка — независимые процессы с общей временной БД.
9. Параллельные изменения разных ID не теряются; одинакового ID имеют итог последнего commit. Ошибка SQLite не превращается в успешное подтверждение.
10. Поздний вход не отменяет `/exit` и новый режим; отключение само по себе не стирает режим или предметные данные.

Тесты используют fake внешние API и временные БД. Полный список команд проверки определяется [RUN.md](../RUN.md#проверка-изменения-кода), допуск релиза — [RELEASES.md](../RELEASES.md); планирование само по себе не подтверждает прохождение проверок.

## 7. Приёмка и постоянная документация

Для живой приёмки два связанных канала одного профиля и второй отдельный профиль работают на одной версии приложения с Ask и Obsidian. Первый профиль включает Obsidian в Telegram и видит его в VK, выбирает режим, отключает его через VK и получает подсказку вместо обработки следующего текста в Telegram. Второй профиль сохраняет свой набор. Повторное включение возвращает доступ к сохранённому режиму и данным. Длинный запрос, начатый до disable, присылает итог. Переключение не меняет PID/boot ID каналов.

В [ARCHITECTURE.md](../ARCHITECTURE.md) описать пересечение глобального и личного доступа, единый AppUser и точку допуска. В [RUN.md](../RUN.md) добавить команды, default, поведение существующих пользователей и различие отключения от `/exit`. В [SETUP.md](../SETUP.md) объяснить верхнюю границу серверной конфигурации и Ask при глобальной недоступности. В [OPERATIONS.md](../OPERATIONS.md) отразить новую core-миграцию и сохранение данных. В [CODE_MAP.md](../CODE_MAP.md) добавить точки входа личных настроек и тесты после их создания. Отдельное изменение правил выпуска, AGENTS.md и исторического снимка VPS для этой функции не требуется.

Пункт [BACKLOG.md](../BACKLOG.md#включение-возможностей-пользователем) остаётся открытым до приёмки и удаления временного каталога. Здесь фиксировать результаты этапов, проверенный SHA и оставшиеся конкретные дефекты; не считать написанный план реализованной функциональностью.
