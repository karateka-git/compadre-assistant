# Динамическое подключение возможностей: рабочий план

План ведёт задачу из [бэклога](../BACKLOG.md#динамическое-подключение-возможностей-ассистента)
до приёмки. Временный каталог остаётся через все PR и эксплуатационную
проверку. Действующие правила переходят в постоянную документацию; каталог
удаляется отдельным завершающим изменением перед закрытием бэклога.

## Результат и граница первой версии

Оператор устанавливает проверенный пакет новой возможности, включает и
отключает установленную возможность во время работы Telegram и VK. Справка и
маршрутизация каждого сообщения используют одно поколение реестра. Начатые
операции завершаются со своими зависимостями; новые вызовы отключённого входа
не принимаются. Режимы чатов и предметные данные сохраняются.

**Текущее решение о схеме:** включение и отключение не выполняют миграций и не
ставят оба канала на паузу. Новые таблицы применяются обычным выпуском с
остановкой writers и проверенной копией по [действующему порядку](../OPERATIONS.md#подготовка-и-запуск-версии).
После выпуска возможность включается без нового перезапуска. Пользователь
допускает позднейшее уточнение этого решения. Пока оно не изменено, нельзя
вводить миграции общей БД во время работы каналов. Перед этапом 6 решение
нужно повторно сверить, если потребуется горячая установка пакета с новой
схемой.

Первая версия поддерживает новый ID, включение, отключение и повторное
включение той же версии. Горячая замена кода уже установленного ID, удаление
пакета и удаление его данных в контракт не входят. Смена версии идёт через
обычный выпуск.

### Приёмочный сценарий

1. В двух работающих процессах включить и отключить Ask и Obsidian без смены
   PID/boot ID. Проверить `/help`, команды входа, сохранённый режим и данные.
2. Установить новый проверенный тестовый пакет без миграций. Без перезапуска
   включить его в Telegram и VK, вызвать, отключить и включить снова.
3. Проверить пакет с новой таблицей: до выпуска включение даёт
   `schema_pending`; обычный выпуск применяет его SQL; после выпуска вход
   включается без ещё одного перезапуска. Данные остаются после отключения.
4. Отключить возможность во время долгого Ask и Device Flow. Начатые действия
   дают итог, новые не попадают в обработчик, клиенты закрываются после
   фонового завершения.

## Зафиксированные технические решения

### Поставка и доверие

- Пакет — неизменяемый ZIP `name-version.cap.zip` с UTF-8
  `capability.json`, pure-Python кодом, ресурсами и, если нужны, SQL-файлами.
  Manifest v1 содержит ID, SemVer, версию публичного API, диапазоны версий
  приложения и Python, factory entrypoint, descriptor и справку, требования
  к уже установленным dependencies, список файлов и миграций с SHA-256.
  SHA-256 самого архива хранится в каталоге и allowlist вне архива, чтобы
  manifest не ссылался на собственный digest.
- ID имеет форму `[a-z][a-z0-9_]{0,63}`. Команды проверяются существующим
  реестром на формат и конфликты, в том числе с отключёнными пакетами.
  API major должен совпадать; требуемый minor не выше поддерживаемого.
  Совместимость проверяют установщик и оба worker до загрузки фабрики.
- Установщик отвергает абсолютные и выходящие из каталога пути, дубли,
  symlink, `.pth`, native extensions, build hooks и превышение лимитов.
  Python-пакет обязан занимать уникальный top-level namespace `cap_<id>`;
  перекрытие stdlib, `compadre_assistant` и host dependencies отвергается до
  импорта, чтобы `sys.modules` не вернул код другого пакета.
  Проверенные файлы атомарно попадают в
  `data/capability-packages/<sha256>/`; workers читают этот каталог без права
  записи. Compose монтирует каталог в оба worker отдельным read-only mount;
  локальный installer получает отдельный writable доступ. `pip install` в
  работающих контейнерах не выполняется. Новые
  системные или native зависимости требуют выпуска.
- Импорт разрешён только для digest, явно одобренного оператором в
  защищённом host allowlist после проверки происхождения артефакта и CI
  точного commit SHA. Один хеш не доказывает доверие. Пакет исполняется с
  правами процесса, sandbox не обещается; установка через Telegram/VK
  недоступна. Встроенные Ask/Obsidian остаются явно зарегистрированными
  composition root; произвольного поиска plugins нет.

### Runtime, snapshots и запросы

- Фабрика API v1 выполняет `prepare(services, settings)` и возвращает runtime
  с `handler`, `stop_accepting()`, `drain()` и идемпотентным `close()`.
  Подготовка проверяет настройки и создаёт зависимости, но не публикует вход
  и не запускает периодические работы. Автономные периодические jobs вне
  запроса не поддерживаются в API v1; фоновые jobs принадлежат принятому
  запросу и наследуют его lease.
- Реестр каждого поколения неизменяем. В начале сообщения processor
  атомарно проверяет committed generation и допуск, берёт snapshot и создаёт
  request lease в короткой SQLite-транзакции. Обработчик и внешний I/O идут
  после commit. `/help` и маршрутизация используют один snapshot.
  Устаревший worker сначала синхронизируется либо сообщает о временной
  недоступности, но не обслуживает запрос старым реестром.
- Фоновая работа получает дочерний lease до освобождения родительского.
  Device Flow держит его до completion callback, включая новое соединение.
  Потоки учитываются и дожидаются при `drain`; HTTP/LLM-клиенты закрываются
  после последнего lease. Таймаут оставляет операцию `draining`, без
  принудительного закрытия и повтора внешнего действия.
- Запрос считается начатым после создания lease, а не после получения update
  транспортом. Очередь VK и executor Telegram используют состояние на
  фактическом начале обработки. Revision CAS режима сохраняется.

### Координация Telegram и VK

- Новая core-миграция `0002+` создаёт каталог пакетов, desired state,
  committed generation, операции, worker boot ID/ACK и leases. В
  `core/domain` лежат правила и ports, в `core/data` — отдельные DTO,
  mappers и SQLite adapters. Core не импортирует возможности.
- Административная операция одна за раз, с operation ID, idempotency key и
  expected revision. Оба worker подтверждают `prepare` до публикации
  поколения. Если один не готов, подготовленные runtimes закрываются,
  действующее поколение остаётся. Команда успешна после ACK обоих.
- Disable транзакционно публикует поколение без входа и запрещает новые
  leases этой возможности. Descriptor остаётся в каталоге для понятного
  ответа на отключённую команду. После drain оба worker закрывают runtime и
  подтверждают завершение. Повторный enable во время drain возвращает
  конфликт с ID операции.
- На старте worker сверяет каталог до приёма сообщений.
  `ENABLED_CAPABILITIES` задаёт seed только при первом создании каталога;
  затем приоритет у persisted state. ACK относится к boot ID. Недоступный
  worker оставляет операцию `pending` или `failed`, а не успешной.
  Lease не исчезает только по TTL. Каждый channel slot держит эксклюзивный
  lifetime file lock на общем томе. Новый worker захватывает тот же lock до
  очистки leases прежнего boot ID; если lock ещё занят или проверка
  недостоверна, stale leases остаются и операция не завершается. PID и
  heartbeat timeout сами по себе не служат доказательством смерти.
- Один межпроцессный administration file lock разделяют mutation каталога,
  deploy и recovery. Его захватывают **до** начала SQLite-транзакции и
  отпускают после durable результата. Если процесс умер, durable незавершённая
  операция блокирует следующую mutation до recovery. Проверки «выпуск сейчас
  не идёт» без этого lock недостаточно.

Состояния записи пакета: `schema_pending` (требуемая схема ещё не выпущена),
`installed_disabled`, `enabled`, `draining` и `degraded`.
`install` не выполняет код и приводит в одно из первых двух состояний.
`enable` допустим только из `installed_disabled` и после подготовки обоих
workers; `disable` публикует новое поколение и переводит в `draining`, затем
после освобождения leases — в `installed_disabled`. `re-enable` во время
`draining` отвергается. Отдельная запись операции различает `pending`,
`completed`, `rejected`, `failed` и `degraded` с сохранённым operation ID.
`degraded` блокирует новые mutations до ручной диагностики. Состояния и
committed generation читаются из SQLite после каждого рестарта.

### Данные, миграции и возврат

- `0001_initial_schema.sql` и имена применённых файлов не меняются. Core
  control schema получает `0002+`. Все последующие SQL-файлы, включая SQL
  возможностей, получают **следующий общий номер** `0003+`, `0004+` и далее,
  чтобы выполнять правило `AGENTS.md` о последовательной production-схеме.
  Файл остаётся в каталоге модуля-владельца, а release manifest задаёт общий
  порядок, точные имена и SHA-256. Runner записывает их в существующий
  `schema_migrations`; манифест предыдущих выпусков должен оставаться
  доступным для проверки уже применённых записей.
- Новые объекты модуля называются `cap_<id>_*`. Runner проверяет SQL через
  SQLite authorizer: запрещены изменения core/чужих объектов, `ATTACH`,
  `DETACH`, опасные PRAGMA и управление транзакцией из файла. Для первой
  версии нет triggers/views и межмодульных foreign keys. Проверка имени
  файла или regex по SQL не заменяет проверку фактически выполняемых
  операций.
- При выпуске deploy controller останавливает оба writer, делает и проверяет
  backup, затем применяет core и закреплённые в release manifest миграции
  модулей. SQL одного выпуска применяется атомарным batch. Если пакет с новой
  схемой установлен до выпуска, он остаётся `schema_pending`; включение
  доступно только после выпуска, который закрепил точный digest пакета и его
  SQL. Release image содержит копию точного архива и все исторические SQL,
  поэтому схема проверяема даже при удалённом внешнем staging. Контроллер
  синхронизирует архив с общим каталогом до запуска новых workers. Disable
  не делает down migration и не удаляет данные.
- При смене версии пакета обычный release manifest закрепляет новый digest и
  желаемое состояние. После остановки writers контроллер проверяет и при
  необходимости применяет схему, обновляет каталог и только затем запускает
  workers с новым кодом. Старый digest допустим для rollback только если
  прежний код совместим со всей уже применённой схемой.
- Release controller и recovery сверяют core schema, общий список миграций, digest
  пакетов и совместимость API. Неизвестная схема или несовпадающий checksum
  блокируют запуск старого кода. Backup автоматически не восстанавливается.
  Прямой доступ модуля к таблицам core и других модулей запрещён.

## Этапы реализации

Каждый этап проверяется до начала зависящего от него. По мере выполнения
записывать решение, точный SHA проверки и обнаруженные ограничения здесь.

| Этап | Работа | Условие завершения |
| --- | --- | --- |
| 1. Контракт | Утвердить manifest v1, lifecycle API, состояния операций, доверие и migration/release manifest, описанные выше. | Контракты версионированы и закреплены в рабочих материалах; нет ветвей поведения «решить при реализации». |
| 2. Durable storage | Добавить core `0002+`, DTO/mappers, поколения, worker boot ID, операции и leases. | Миграция применяется к свежей и прежней тестовой БД; хранилище выдерживает повтор и конкурентную запись. |
| 3. Lifecycle | Перевести Ask/Obsidian на фабрики; учесть Device Flow, callback и закрытие клиентов. | Ошибка `prepare` освобождает ресурсы; `drain` ждёт запросы и фон; клиент жив до callback. |
| 4. Snapshot и admission | Добавить неизменяемые поколения и request/child leases в processor/dispatcher. | Управляемые гонки help/route/disable проходят; CAS режима сохраняется. |
| 5. Общее управление | Реализовать state machine, межпроцессный lock, ACK/recovery и CLI `list/status/enable/disable`. | Два независимых процесса видят одно поколение; restart, stale ACK, prepare failure и drain проверены. |
| 6. Установка | Реализовать inspect, allowlist, проверку ZIP/manifest, immutable storage и factory loader; добавить CLI `install`. | Недоверенный пакет не исполняется; новый пакет без миграций доступен в обоих каналах без restart. |
| 7. Схема пакетов | Добавить package preflight, `schema_pending`, общий migration manifest и применение SQL через deploy controller. | На временной БД проверены новый/повторный выпуск, ошибка batch, checksum mismatch, сохранение данных и несовместимый rollback. |
| 8. Приёмка | Проверить оба канала, длинный Ask, Device Flow, disable/re-enable и пакет с миграцией после выпуска. | Есть локальные проверки, CI точного SHA и отдельная живая проверка TG/VK; при переключении PID не меняются. |
| 9. Завершение | Перенести правила в постоянные docs, обновить CODE_MAP и BACKLOG; удалить этот каталог отдельным изменением после эксплуатации. | Ссылки проверены, каталог удалён, backlog закрыт, рабочие копии чистые. |

Гонки проверять управляемыми `Event`/barrier и независимыми процессами и
SQLite-соединениями, а не случайными задержками. Сквозной тест использует
fake API и временную БД, а не production.

## Управление, ошибки и документация

Планируемый локальный интерфейс:
`python -m compadre_assistant capabilities list|status|inspect|install|enable|disable|recover`.
Это описание будущего CLI, а не готовые команды. Вывод различает
`completed`, `pending`, `draining`, `rejected`, `failed` и `degraded` без
секретов. Production wrapper проверяет allowlist, происхождение артефакта и
отсутствие одновременного deploy/recovery. Bot user не управляет каталогом.

Ошибка до публикации поколения закрывает подготовленный runtime, сохраняя
действующий. После публикации enable поколение **не откатывается
автоматически**: операция остаётся `pending`, новый worker готовит runtime
этого поколения и подтверждает его. Если подготовка невосстановимо ошибается,
оператор запускает отдельный disable с новым поколением. После публикации
disable операция ждёт leases; crash восстанавливается по durable operation и
boot ID. Recovery не повторяет внешние side effects и не удаляет данные.
Если worker недоступен, результат остаётся незавершённым. Неизвестная схема
означает `degraded` до ручной диагностики.

При реализации изменить [ARCHITECTURE.md](../ARCHITECTURE.md) (authority,
factory, snapshots/leases), [RUN.md](../RUN.md) (CLI и seed env),
[OPERATIONS.md](../OPERATIONS.md) (trust, выпуск и recovery),
[RELEASES.md](../RELEASES.md) (публикация пакета и manifest),
[PRODUCTION.md](../PRODUCTION.md) (проверка состояния каталога перед
операцией) и [CODE_MAP.md](../CODE_MAP.md) (новые точки входа и тесты).
Исторический снимок VPS не переписывать. Правила `AGENTS.md` о `0002+`,
явной регистрации и сохранении production данных сохраняются.
