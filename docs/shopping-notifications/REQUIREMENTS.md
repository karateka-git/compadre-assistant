# Уведомления о семейных покупках

Когда один участник добавляет продукты, остальные узнают об этом до похода в магазин. Каждый получает короткую сводку в личном чате и может открыть актуальный список. Этот документ описывает согласованное поведение для разработки. [План по этапам](PLAN.md) · [Действующий сценарий покупок](../architecture/FAMILY.md)

## Собрать добавления для получателя

1. Успешное добавление одной или нескольких строк запускает сбор сводки для остальных участников той же семьи. Автору его собственные позиции в сводку не попадают, в том числе во втором связанном мессенджере.
2. Отправка назначается через две минуты после последнего подходящего добавления, но не позже десяти минут с первого добавления в этой подборке. После отправки следующее добавление открывает новую подборку. Покупка, удаление и очистка купленного сами по себе рассылку не запускают.
3. Перед отправкой бот проверяет действующее членство и доступ получателя к «Семье». В сводку входят только позиции подборки, которые всё ещё нужно купить. Если их не осталось, сообщение не отправляется. Перезапуск между добавлением и отправкой сохраняет ожидающую подборку и её срок.

Например, добавления в 18:00 и 18:01 дают одну сводку в 18:03. Если продукты добавляют каждую минуту с 18:00 по 18:09, срок наступает в 18:10.

## Прочитать сводку и открыть покупки

Сводка показывает, кто пополнил список, и названия товаров в порядке добавления. До пяти позиций включительно видны все. Для более длинной подборки бот показывает общее число, первые пять позиций и остаток в формате «и ещё N». Подсчёт ведётся по позициям, включая одинаковые названия. Например, если из двадцати позиций одну уже купили, в сводке останется девятнадцать, из которых четырнадцать скрыты.

Сообщение приходит и вне режима «Семья». Получение сохраняет активный режим чата. Нажатие «Открыть покупки» служит явным входом и показывает текущий полный список с обычной разбивкой на страницы. При нажатии бот заново проверяет доступ к семье, для которой отправлена сводка.

## Выбрать мессенджер

У профиля одно значение — мессенджер для уведомлений. Регистрация записывает в него текущий мессенджер. Привязка второго и просмотр покупок из другого канала сохраняют это значение. При отправке бот читает текущее значение и отправляет одну сводку в один личный чат получателя.

В «Настройки» → «Мессенджеры», рядом с привязкой, виден текущий канал. При двух связанных каналах пользователь может выбрать другой. Выбор заменяет значение того же поля и действует в том числе на ожидающие сводки. При отвязке выбранного канала значением становится оставшийся связанный мессенджер.

## Уточнить при проектировании

Для существующих профилей требуется заполнить то же поле. При регистрации ядро создаёт профиль и первую привязку одной транзакцией. Привязка по коду добавляет новую строку. При переносе аккаунта между профилями строка привязки сохраняет свой ID и дату создания. Если исходный профиль удалён после переноса последней привязки, внешний ключ удаляет и запись подтверждения переноса. Полную историю присоединения каналов по оставшимся данным восстановить нельзя. [Операции с привязками](../../compadre_assistant/core/data/sqlite/user_identity_repository.py) · [Связи таблиц](../../compadre_assistant/core/data/sqlite/migrations/0001_initial_schema.sql)

Например, человек зарегистрировал VK в январе, Telegram в феврале и в марте перенёс VK к профилю Telegram. У этого профиля самый старый ID привязки относится к VK, хотя зарегистрирован он в Telegram.

Если доступна одна привязка Telegram или VK, миграция может выбрать её однозначно. При двух привязках можно выбрать самую раннюю действующую строку по дате создания и ID. Другой вариант — сначала искать совпадение дат создания профиля и привязки, затем применить тот же порядок. Даже совпадение дат с точностью до секунды не доказывает первоначальную регистрацию. Правило для старых профилей согласуется с пользователем до реализации заполнения. Новые профили сразу сохраняют фактический канал регистрации.

Для проверки миграции подготовить временную БД со старой схемой. Включить профиль без поддерживаемой привязки, профили с одной и двумя привязками, одинаковое время создания и перенос более старой привязки к более новому профилю. После обновления проверить сохранность профилей и принадлежность выбранного канала. Для профиля без поддерживаемой привязки проверить отсутствие адреса доставки.

Если подборку пополнили несколько человек, сводка должна учитывать собственные добавления отдельно для каждого получателя. Точную формулировку с несколькими авторами и поведение при неопределённом результате отправки через API зафиксировать в плане соответствующего этапа.
