# Метрики выкладки

Здесь описано, как сравнивать время выкладки, расход HTTP и токены Codex.
Локальная фикстура помогает повторить замер PATCH. По журналам Actions
и отчёту VPS можно снять показатели реальной выкладки.

[Локальные замеры PATCH](#воспроизвести-замеры-patch) ·
[Первый выпуск с Deployment v2](#измерить-первый-production-выпуск-с-deployment-v2)

## Что сравниваем

| Показатель | Как считать |
| --- | --- |
| Длительность штатной выкладки | От начала установки опубликованного Release до подтверждения текущего `success`. При Deployment v2 runner также подтверждает закрытие попытки контроллером. При отсутствии отметки начала установки у runner используйте начало из отчёта контроллера и явно укажите эти границы. |
| Токены Codex | Токены, относящиеся к выкладке в тех же границах. Сохраняем источник и фактический охват замера. Если расход нельзя достоверно отделить от остальной работы в чате, указываем `unknown`. |

В общий интервал входят очистка прежней SQLite, техническая приёмка, ожидания,
повторы и восстановление в рамках той же выкладки. При отказе и повторе
через `resume` отсчитываем время от первой попытки установки до подтверждения
того же Deployment. Для незавершённой выкладки фиксируем время до остановки
работ и её результат. Разработку, CI, публикацию Release и подготовку
отчёта учитываем отдельно.

Сохраняйте время запуска workflow по `run_started_at` и `updated_at`
завершённой попытки. Для job `release` берите её `started_at` и
`completed_at`, а для `Run production release` — отметки этого шага.
Интервал запуска охватывает весь workflow. Job включает подготовку runner
и завершающие шаги. Шаг выпуска включает публикацию, если Release ещё нет,
резервацию, установку и закрытие. Длительность работы контроллера и простой
снимайте из его отчёта отдельно.

Если нужна живая проверка Telegram и VK, отметьте её время отдельно.
Сравнивайте историческую длительность до живого ответа только с замерами,
которые заканчиваются тем же событием. Выкладки с восстановлением
помечаем отдельно, чтобы сравнивать однотипные сценарии.

## Как снять замер

1. Перед установкой запишите время UTC, версию и полный SHA опубликованного
   Release. В журнале v1 отметкой начала служило сообщение «Установка
   Release на VPS». В v2 берите отметку начала `install`, а если журнал её
   не содержит, используйте начало из отчёта контроллера. Если Codex
   участвует в выкладке, отметьте первый
   относящийся к ней ход в чате.
2. Для каждой попытки сопоставьте приватный отчёт `metrics-*.json` с
   выкладкой по версии, SHA и времени запуска. Если отказ произошёл до
   определения SHA, сопоставьте по версии и времени. Отметьте ожидания,
   повторы и восстановление внутри того же замера. Если для восстановления
   нет отдельного отчёта, запишите его начало, конец и результат в UTC.
3. Запишите время подтверждения Deployment в UTC. В v2 возьмите время
   вывода итога `state=success` и `cleanup=completed` после закрытия
   попытки в контроллере. Если работы прерваны,
   запишите время остановки и результат. Разность с отметкой начала даёт
   время всей выкладки. Для каждой попытки `deploy-prod` отдельно укажите
   `wall_seconds` и `downtime_seconds`. При `downtime_open=true` простой
   продолжался на момент последней записи отчёта.

Для разбора разницы сначала сопоставьте допуск, backup и миграции, запуск
ботов, финализацию, очистку и приёмку. Учитывайте ожидания, повторы,
восстановление и запросы к GitHub. Время всей выкладки считайте по её
началу и концу, поскольку этапы в журналах могут пересекаться.
Токены по отдельным этапам показывайте, если источник позволяет их
достоверно разделить.

## Какие этапы видны в отчёте

`deploy-prod` записывает начало и конец установки, технический простой и
длительность достигнутых этапов. Техническую приёмку после установки
считайте по отдельным отметкам. Ниже приведены метки для SQLite v2.
[Сборщик метрик](../scripts/deploy_metrics.py)

| Метки отчёта | Что измеряют |
| --- | --- |
| `build` | Сборка образа кандидата. |
| `predeploy.evidence` | Ранняя проверка доказательства допуска. |
| `predeploy.evidence_recheck` | Повтор после миграции предварительной копии на маршруте с артефактом. |
| `v2.admission_recheck` | Сверка перед остановкой ботов. Для policy v2 включает подтверждение актуальной базы по Deployments. |
| `predeploy.copy` | Подготовка предварительной копии, её миграция и проверка. |
| `deploy.stop_both` | Остановка двух каналов. |
| `v2.final_copy` | Окончательный backup, миграция и проверка копии после остановки ботов. Это один общий замер. |
| `v2.start_channels`, `deploy.verify_both_1` | Проверка сохранённого допуска к запуску и запуск контейнеров, затем первая техническая проверка каналов. |
| `v2.finalize` | Финализация, включая возврат основного unit, итоговую проверку и восстановление таймера. |

Переходы SQLite v2 также печатаются как события. Если журнал сохранил
их время, по нему можно оценить промежутки между этапами, например время
между готовностью копии и выбором новой БД.
[Переключение SQLite](../scripts/deploy_database_switch.py)

## Как снять расход HTTP выпуска

В журнале `Production release` найдите строки `deploy-http-metrics` за
нужную попытку. Runner выводит один отчёт `release` или `resume`, а также
отдельный отчёт `vps` для каждой завершившейся SSH-команды установки,
приёмки, очистки или владения попыткой Deployment v2. Повторные вызовы
приёмки дают отдельные строки. Контроллер
пишет отчёт в stderr, поэтому stdout приёмки и очистки по-прежнему содержит
одну машинную запись. Runner сохраняет агрегат и при ненулевом коде SSH,
если отчёт дошёл до него. При обрыве связи до получения отчёта или старом
snapshot без метрик помечайте результат VPS как `unknown`. Пустой список
`http` в полученном отчёте означает, что команда не сделала HTTP-запросов.

Для сравнения суммируйте `attempts`, `pages`, `errors` и `elapsed_ns` по
`location`, `phase`, `target` и `method`. `attempts` считает каждую попытку
отправки HTTP, `pages` — обращения с явным номером страницы. В `errors`
входят ответы 4xx и 5xx, сетевые ошибки и сбои чтения тела, включая ожидаемый
404 при поиске ещё не опубликованного Release. `elapsed_ns` суммирует время
соединения, получения заголовков и чтения ответа. Считайте
`target=github_graphql_query` и `method=POST` как чтение GitHub через GraphQL.
`target=github_api` обозначает REST, где POST относится к записи.
Запрос к хранилищу ZIP после редиректа имеет отдельный
`target=artifact_storage`. Отчёт не включает
Git-транспорт, сборку или управляющие SSH-вызовы. URL, параметры, токены и
тела HTTP в этих строках не сохраняются.

## Воспроизвести замеры PATCH

Фикстура выпускает `v4.2.1` поверх `v4.2.0` с двумя парами слитых PR,
16 предыдущими Release и одной миграцией. История из 1000 Deployment
добавляет старые попытки с подтверждённым возвратом. Прогон с первой записью
v2 использует 16 старых Deployment v1. Фикстура запускает штатные runner,
публикатор, проверку CI и CLI контроллера, сравнивает отчёты с независимым
счётчиком запросов и использует локальные ответы GitHub и SSH. Время
прогона зависит от машины, Git и имитации внешних операций. Для сравнения
с реальным VPS используйте число запросов и отдельно учитывайте загрузку
ZIP. [Фикстура](../tests/test_patch_http_baseline.py)

1. Откройте отдельный Git checkout точного коммита из таблицы с доступом
   к историческим объектам политики. Вариант из ZIP-архива без Git-истории
   не подходит. Используйте Python проектного `.venv`.

   | Состояние кода | SHA | Аргументы модуля |
   | --- | --- | --- |
   | Исходная публикация v1 | `8c1c10509f58beb6383aaf9420fc9a1d96d765e7` | Без аргументов |
   | Публикация v1 после исправления PATCH | `7aa7c7e872e67e22d0d321e760f23830ea9e3592` | Без аргументов |
   | Исходный полный путь v2 | `7100a43d49696cadb7ffd521225b8ddc0e77195c` | `--v2` |
   | v2 после сокращения повторных чтений | `f9f93fee26d39e4a8832299b1d3cf1eba2e599ff` | `--v2` |
   | v2 с пакетным чтением истории v1 | `d31a3bc1efeaf754f3108eed851e1143736ba4f1` | `--v2` |

2. Из корня выбранного checkout запустите модуль с нужным вариантом
   аргументов. В PowerShell задайте полный путь к интерпретатору. Последняя
   команда запускает проверки сценариев вместо печати отчёта.

   ```powershell
   $projectPython = '<полный-путь-к-python.exe-проектного-.venv>'
   & $projectPython -m tests.test_patch_http_baseline
   & $projectPython -m tests.test_patch_http_baseline --v2
   & $projectPython -m unittest tests.test_patch_http_baseline
   ```

3. Сопоставьте одинаковые сценарии по `summary`. Раздел `scenarios` хранит
   агрегаты по этапам и отдельным SSH-вызовам. Колонки «База» ниже
   включают GET и GraphQL из фазы `deployment_base`. Она покрывает выбор
   и прямое подтверждение базы, включая Release, тег и миграцию. База
   входит в число чтений GitHub. Чтения новой попытки, полномочий
   владельца и загрузку ZIP учитывайте отдельно.
   [Правила чтения отчёта](#как-снять-расход-http-выпуска)

### Сравнить первую публикацию

Наблюдения 19.11.2026, Windows и Python 3.12.10. Исходному публикатору
v1 предоставили чистый checkout точного кандидата. После исправления
PATCH runner работал из shallow checkout `main` с другим SHA и без
объекта коммита кандидата. Все ревизии проверяли две пары PR и сохраняли
контроль точного CI.

| Маршрут | История | Runner REST GET + GraphQL | VPS REST GET + GraphQL | Всего чтений | База runner + VPS | REST POST | ZIP GET |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| v1 исходный | 16 v1 | 282 + 0 | 57 + 0 | 339 | 60 + 40 | 5 | 2 |
| v1 после исправления PATCH | 16 v1 | 265 + 0 | 57 + 0 | 322 | 60 + 40 | 5 | 2 |
| v2 до сокращения повторов | 16 или 1000, принятая база v2 | 277 + 16 | 210 + 31 | 534 | 70 + 133 | 6 | 2 |
| v2 после сокращения повторов | 16 или 1000, принятая база v2 | 192 + 14 | 121 + 17 | 344 | 43 + 58 | 6 | 1 |
| Первый v2 до сокращения повторов | 16 v1 | 332 + 80 | 279 + 67 | 758 | 192 + 232 | 6 | 2 |
| Первый v2 после сокращения повторов | 16 v1 | 259 + 78 | 206 + 55 | 598 | 175 + 175 | 6 | 1 |
| Первый v2 с пакетным чтением v1 | 16 v1 | 255 + 18 | 204 + 25 | 502 | 111 + 143 | 6 | 1 |

Исправление PATCH сократило расход runner на 17 GET. При 16 и 1000
Deployment оба штатных прогона v2 после оптимизации дали 344 чтения,
из них 101 для выбора и подтверждения базы. Полный маршрут v2 на той же
фикстуре с 16 записями включает проверки резервации, владельца и двух
статусов, поэтому после оптимизации остаётся на 22 чтения больше v1 с
исправленным PATCH. Первый запуск v2 сверяет старый и новый выбор по всей
прежней истории v1. Пакетные GraphQL-запросы и
переиспользование уже подтверждённого текущего статуса снизили эту выкладку
до 502 чтений. При запуске на GitHub число запросов меняется вместе с
входными данными, нумерацией страниц и результатами проверок.

В v2 runner переиспользует неизменяемые Git-объекты и Contents по полному
SHA в пределах одной команды. Для CI сверяет прежний ID и digest архивного
артефакта, поэтому повторно загружать тот же ZIP не требуется. Release,
ref ветки и статусы перечитываются на границах операций. Перед
переключением контроллер повторно проверяет текущий Deployment и его
ссылку на базу. После каждого POST runner перечитывает результат.

## Как посчитать токены Codex

1. Откройте локальные JSONL-журналы Codex Desktop в каталоге
   `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-*.jsonl` (по умолчанию
   `~/.codex`). Для архивированных чатов проверьте `archived_sessions`
   там же. Определите по `session_meta.payload.id` чат выкладки и отметьте
   её первый и последний ходы. Сопоставляйте `task_started` с
   `task_complete` или `turn_aborted` по `turn_id`. Событие счётчика
   относится к открытому на тот момент ходу в этом журнале. Подготовку
   отчёта начинайте в отдельных ходах за границами замера.
2. Для каждого относящегося к выкладке хода возьмите разность накопленных
   значений до и после хода. Это поле
   `payload.info.total_token_usage.total_tokens` в событии `event_msg`
   с `payload.type=token_count`. Для первого хода можно взять ноль за
   начало только при полной истории новой сессии. Повторы одного
   накопленного значения учитываются один раз. Входные токены уже
   включают кэшированные, выходные — токены рассуждения.
3. Сложите разности по ходам основного чата и дочерних сессий. Связывайте
   дочерние журналы через `parent_thread_id` и `root_turn_id` и сверяйте
   набор с вызванными субагентами. Для одного `session_meta.payload.id`
   сверяйте продолжения журнала и исключайте дубли. После возобновления
   чата проверяйте непрерывность счётчика перед подсчётом.

Завершённый ход без события со счётчиком оставляет его расход
неподтверждённым. Если границы выкладки, завершение хода или охват дочерних
сессий нельзя подтвердить, счётчик отсутствует или сбросился, полный итог
записываем как `unknown`.
Счётчик показывает наблюдаемый расход Desktop. Для сводки достаточно
агрегированных чисел и отметки об охвате. Содержимое журналов остаётся
локально.
