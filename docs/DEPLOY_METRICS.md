# Метрики выкладки

Для каждого выпуска сравниваем время выкладки и расход токенов Codex.
Разбивка по этапам помогает объяснить изменения. Порядок запуска и
действия при отказе описаны в [инструкции выпуска](OPERATIONS.md#выпустить-обычную-версию-из-github-actions).

## Что сравниваем

| Показатель | Как считать |
| --- | --- |
| Длительность штатной выкладки | От начала установки опубликованного Release до подтверждения текущего `success` в GitHub Deployments. Для одной попытки в Actions границы видны в журнале `production-release` по сообщениям «Установка Release на VPS» и «Deployment … (success)». |
| Токены Codex | Токены, относящиеся к выкладке в тех же границах. Сохраняем источник и фактический охват замера. Если расход нельзя достоверно отделить от остальной работы в чате, указываем `unknown`. |

В общий интервал входят очистка прежней SQLite, техническая приёмка, ожидания,
повторы и восстановление в рамках той же выкладки. При отказе и повторе
через `resume` отсчитываем время от первой попытки установки до подтверждения
того же Deployment. Для незавершённой выкладки фиксируем время до остановки
работ и её результат. Разработку, CI, публикацию Release и подготовку
отчёта учитываем отдельно.

Если нужна живая проверка Telegram и VK, отметьте её время отдельно.
Сравнивайте историческую длительность до живого ответа только с замерами,
которые заканчиваются тем же событием. Выкладки с восстановлением
помечаем отдельно, чтобы сравнивать однотипные сценарии.

## Как снять замер

1. Перед установкой запишите время UTC, версию и полный SHA опубликованного
   Release. Для штатного запуска возьмите время из сообщения «Установка
   Release на VPS». Если Codex участвует в выкладке, отметьте первый
   относящийся к ней ход в чате.
2. Для каждой попытки сопоставьте приватный отчёт `metrics-*.json` с
   выкладкой по версии, SHA и времени запуска. Если отказ произошёл до
   определения SHA, сопоставьте по версии и времени. Отметьте ожидания,
   повторы и восстановление внутри того же замера. Если для восстановления
   нет отдельного отчёта, запишите его начало, конец и результат в UTC.
3. Запишите время подтверждения Deployment в UTC. Если работы прерваны,
   запишите время остановки и результат. Разность с отметкой начала даёт
   время всей выкладки. Для каждой попытки `deploy-prod` отдельно укажите
   `wall_seconds` и `downtime_seconds`. При `downtime_open=true` простой
   продолжался на момент последней записи отчёта.

Для разбора разницы сначала сопоставьте допуск, backup и миграции, запуск
ботов, финализацию, очистку и приёмку. Учитывайте ожидания, повторы,
восстановление и запросы к GitHub. Время всей выкладки считайте по её
началу и концу, поскольку этапы в журналах могут пересекаться.
Токены по отдельным этапам показывайте, если источник позволяет их
достоверно разделить.

## Какие этапы видны в отчёте

`deploy-prod` записывает начало и конец установки, технический простой и
длительность достигнутых этапов. Техническую приёмку после установки
считайте по отдельным отметкам. Ниже приведены метки для SQLite v2.
[Сборщик метрик](../scripts/deploy_metrics.py)

| Метки отчёта | Что измеряют |
| --- | --- |
| `build` | Сборка образа кандидата. |
| `predeploy.evidence` | Ранняя проверка доказательства допуска. |
| `predeploy.evidence_recheck` | Повтор после миграции предварительной копии на маршруте с артефактом. |
| `v2.admission_recheck` | Сверка перед остановкой ботов. Для policy v2 включает подтверждение актуальной базы по Deployments. |
| `predeploy.copy` | Подготовка предварительной копии, её миграция и проверка. |
| `deploy.stop_both` | Остановка двух каналов. |
| `v2.final_copy` | Окончательный backup, миграция и проверка копии после остановки ботов. Это один общий замер. |
| `v2.start_channels`, `deploy.verify_both_1` | Проверка сохранённого допуска к запуску и запуск контейнеров, затем первая техническая проверка каналов. |
| `v2.finalize` | Финализация, включая возврат основного unit, итоговую проверку и восстановление таймера. |

Переходы SQLite v2 также печатаются как события. Если журнал сохранил
их время, по нему можно оценить промежутки между этапами, например время
между готовностью копии и выбором новой БД.
[Переключение SQLite](../scripts/deploy_database_switch.py)
· [Приёмка выпуска](OPERATIONS.md#подготовка-и-запуск-версии)

## Как посчитать токены Codex

1. Откройте локальные JSONL-журналы Codex Desktop в каталоге
   `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-*.jsonl` (по умолчанию
   `~/.codex`). Для архивированных чатов проверьте `archived_sessions`
   там же. Определите по `session_meta.payload.id` чат выкладки и отметьте
   её первый и последний ходы. Сопоставляйте `task_started` с
   `task_complete` или `turn_aborted` по `turn_id`. Событие счётчика
   относится к открытому на тот момент ходу в этом журнале. Подготовку
   отчёта начинайте в отдельных ходах за границами замера.
2. Для каждого относящегося к выкладке хода возьмите разность накопленных
   значений до и после хода. Это поле
   `payload.info.total_token_usage.total_tokens` в событии `event_msg`
   с `payload.type=token_count`. Для первого хода можно взять ноль за
   начало только при полной истории новой сессии. Повторы одного
   накопленного значения учитываются один раз. Входные токены уже
   включают кэшированные, выходные — токены рассуждения.
3. Сложите разности по ходам основного чата и дочерних сессий. Связывайте
   дочерние журналы через `parent_thread_id` и `root_turn_id` и сверяйте
   набор с вызванными субагентами. Для одного `session_meta.payload.id`
   сверяйте продолжения журнала и исключайте дубли. После возобновления
   чата проверяйте непрерывность счётчика перед подсчётом.

Завершённый ход без события со счётчиком оставляет его расход
неподтверждённым. Если границы выкладки, завершение хода или охват дочерних
сессий нельзя подтвердить, счётчик отсутствует или сбросился, полный итог
записываем как `unknown`.
Счётчик показывает наблюдаемый расход Desktop. Для сводки достаточно
агрегированных чисел и отметки об охвате. Содержимое журналов остаётся
локально.
