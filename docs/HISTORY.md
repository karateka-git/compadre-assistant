## Исходное направление проекта

Предпочтительное направление:

- Основной сервис: Python.
- Каналы: Telegram и VK через общий incoming flow.
- Запуск: Docker Compose с самого начала.
- Хранилище: файл SQLite в постоянной папке `data/`.
- LLM: OpenAI-совместимое API через переменные окружения.
- Извлечение текста статей: Python `trafilatura`.
- RAG: Python-интерфейсы для chunking, embeddings и поиска; GitHub
  остаётся source of truth для vault, SQLite — для локального индекса и
  application workflow.

### Масштабировать загрузку GitHub snapshot — завершено

Реализовано:

- GitHub HTTP adapter использует общий thread-safe connection pool вместо
  отдельного HTTPS-соединения для каждого запроса;
- read timeout увеличен до 30 секунд, временные GET-ошибки повторяются до трёх
  раз, а `Retry-After` GitHub имеет приоритет над локальным exponential backoff;
- первая синхронизация и обновление с 50 или более изменёнными Markdown/rules
  файлами скачивают один ZIP snapshot конкретного commit SHA;
- recursive tree остаётся источником полного manifest и blob SHA, поэтому после
  массовой загрузки сохраняется точная инкрементальная проверка;
- обновление менее 50 файлов загружает только изменённые blobs;
- ZIP читается в памяти без распаковки на диск; извлекаются только нужные
  Markdown и instruction-файлы;
- archive, суммарный извлечённый текст и отдельные Markdown/config/rules файлы
  имеют явные лимиты размера;
- если tree не содержит надёжных размеров, vault превышает безопасный порог
  archive или ZIP всего repository оказывается слишком велик из-за файлов вне
  вложенного vault, синхронизация использует точечную blob-загрузку;
- логи фиксируют выбранный режим `archive`/`blobs`, число файлов и длительность,
  но не содержимое файлов или installation token;
- тесты покрывают массовый ZIP snapshot, точечную инкрементальную загрузку,
  сетевые повторы и `Retry-After`.

## RAG indexing и поиск похожих заметок

Цель: находить связанные со статьёй Obsidian-заметки с помощью гибридного
полнотекстового и смыслового поиска, показывать пользователю конкретное
предложение и после явного подтверждения применять его прямым commit в vault.

Статус этапа: **завершён; 10.1–10.23 выполнены**. Основной article/review
workflow и checkpoint-сохранение embedding batches реализованы. Эксперимент
с FAISS или отдельной vector database остаётся в бэклоге.

Обязательный preflight перед формированием `add` или `update`: загрузить весь
упорядоченный набор instruction-файлов из 9.11, определить целевой раздел и
прочитать соседние заметки. Без полного набора правил предложение не создаётся.

Согласованный контракт chunking, границы независимой библиотеки, передача ID,
policy и правила переиндексации зафиксированы в
[`docs/DOCUMENT_CHUNKER.md`](DOCUMENT_CHUNKER.md). Этот документ является
обязательной частью плана Этапа 10.

Реализовано:

7. **10.7 — завершено.** Добавлен hybrid retrieval по текущему поколению vault:
   - lexical ветвь использует существующий FTS5/BM25 и `lexical_text` Этапа
     10.6, semantic ветвь отдельно вызывает `embed_query()` для
     `semantic_text`;
   - vector search до платного запроса проверяет chunk marker, embedding marker,
     обе модели, dimension, полный набор `chunk_id` и `content_hash`;
   - cosine similarity вычисляется линейным scan float32 vectors из SQLite и
     нормализуется в диапазон 0..1 только как диагностический branch score;
   - каждая ветвь отдаёт до 20 кандидатов, после чего ранги объединяются через
     Reciprocal Rank Fusion с `k=60`; несопоставимые BM25 и cosine scores между
     собой не складываются;
   - chunk, найденный обеими ветвями, получает вклад от обоих ranks; итог по
     умолчанию ограничен 10 лучшими chunks;
   - typed result хранит RRF score, branch ranks и исходные branch scores и
     готов для будущего recommendation prompt;
   - scope каждой ветви повторно проверяется до fusion, поэтому malformed
     adapter не может смешать пользователей или vault;
   - пустой vault не вызывает embedding provider, а semantic failures переданы
     retrieval coordinator для явной fallback-политики 10.8.

      `max_retries`, HTTP status, provider request ID при наличии, итоговый
      status, error/cause type и fallback reason;
    - оставить встроенные retries OpenAI SDK (`max_retries=2`, то есть не более
      трёх HTTP-попыток): логировать общую latency и окончательный результат, не
      обещая недоступные adapter'у число, длительность и причину каждой внутренней
      попытки;
    - успешный SDK-запрос логировать на `INFO`, окончательный сбой — на `ERROR`
      с доступной вложенной причиной, semantic fallback — на `WARNING`, но без

    - считать стоимость только при наличии provider usage и настроенного тарифа;
      хранить `estimated_cost`, валюту и `tariff_version`, а кабинет Timeweb

    - тариф задавать конфигурацией, не зашивать цену провайдера в код; отсутствие
      тарифа не блокирует embeddings и оставляет `estimated_cost` пустым;
    - добавить итоговые counters операции, чтобы массовая индексация показывала
      общее число batches, texts, tokens, ошибок, latency и оценочную
      стоимость, а query можно было связать с fallback в review-flow;
    - выводить события в тот же console stream, который Docker уже собирает для
      остальных модулей; одинаковые поля позволяют фильтровать и агрегировать
      их по пользователю, vault, article, модели, статусу и периоду без
      синхронных telemetry-записей в рабочую SQLite;
    - application-слой передаёт adapter'у только технический контекст логирования
      операции; usage, billing и logging поля не добавляются в domain-модели
      `EmbeddingVector`;
    - покрыть success, final timeout/HTTP error после SDK retries, malformed
      response, отсутствующий `usage`, batching и безопасное отсутствие текстов
      и ключей в логах.

14. **10.14 — завершено.** Для `add` и `update` выпускается repository-scoped

15. **10.15 — завершено.** После успешного commit локальный Markdown, metadata,

    - отдельный `content_deleted_at` не добавлять;
    - намеренную очистку определять по `ArticleStatus.REVIEWED`;
    - время завершения review брать из записи применённого предложения.
16. **10.16 — завершено.** При ошибке commit сохраняются `cleaned_text` и статус

17. **10.17 — завершено.** Подтверждённый `skip` завершает review и очищает

18. **10.18 — завершено.** Повторная ссылка на `reviewed`-статью возвращает

    нового proposal. История результата сохраняется при замене активного vault.
19. **10.19 — завершено.** Явный `/reanalyze <ID статьи>` повторно загружает

    уничтожает сохранённый результат.
20. **10.20 — завершено.** Write-back статьи связан с немедленной
    инкрементальной индексацией без повторного чтения GitHub:
    - успешный commit по-прежнему атомарно сохраняет Markdown, metadata и source
      SHA, после чего освобождает общий write/sync lease;
    - сразу после commit общий `VaultSyncManager` внутри шестичасового freshness
      window обновляет локальные индексы из SQLite и не выполняет GitHub-запрос;
    - per-note state хранит `source_blob_sha` и `index_signature`, поэтому
      отсутствие global marker больше не означает полное удаление chunks;
    - только заметки с новым blob SHA или несовместимой parser/policy signature
      повторно проходят chunker; `replace_for_note` сохраняет `chunk_id` для
      прежних `chunk_key` и удаляет только исчезнувшие chunks;
    - chunk global marker публикуется лишь когда per-note states покрывают все
      заметки vault текущей signature; он отвечает за готовность полного FTS
      поколения, но не определяет список работ;
    - embedding index использует сохранённые `chunk_id`, model и `content_hash`,
      отправляет provider только новые и изменённые chunks и публикует свой
      global marker только после полного совместимого покрытия;
    - ошибка embeddings не отменяет уже успешный GitHub commit и `reviewed`:
      пользователь получает отдельное предупреждение, chunk marker остаётся
      актуальным для FTS fallback, embedding marker отсутствует, а следующий
      ручной `/github_sync`, post-commit update или плановая проверка после
      freshness-window повторяет только недостающие vectors;
    - полная логическая переиндексация всех заметок нужна при смене parser или
      chunking policy, но стабильные keys/IDs и совместимые vectors не удаляются
      без необходимости;
    - development-схема дополнена per-note states в изменяемой миграции `0001`;
      рабочая development-БД должна быть пересоздана согласно принятой политике.

    Причина: прежний write-back удалял только global markers. Следующий sync не
    мог отличить одну изменённую заметку от смены всей chunking policy, удалял и
    заново создавал все chunks, а каскадно — все embeddings. Добавление одной
    статьи поэтому могло повторно отправить provider весь vault и снова списать
    стоимость. Per-note source state разделяет два вопроса: hashes указывают,
    **что обновлять**, а global markers подтверждают, **готово ли всё поколение**.
21. **10.21 — завершено.** Публикация GitHub source/FTS отделена от optional
    semantic enrichment:
    - после успешной записи Markdown, instruction-файлов и всех dirty chunks
      HEAD commit SHA, vault tree SHA, ETag и время source sync сохраняются до
      внешнего embedding-запроса;
    - `EmbeddingProviderError` больше не отменяет готовый source snapshot и не
      выдаёт его за неуспешную GitHub-синхронизацию;
    - chunk global marker остаётся опубликованным, embedding marker —
      отсутствующим, поэтому hybrid retrieval безопасно использует FTS fallback;
    - первая, ручная, автоматическая и post-commit синхронизации возвращают
      структурированный `embedding_update_failed`, а пользовательский ответ
      отдельно сообщает: Markdown/FTS готовы, semantic index временно нет;
    - article preflight внутри шестичасового freshness-window не повторяет
      сбойную индексацию всего vault: он сразу использует готовый FTS fallback;
      явный повтор остаётся у `/github_sync`, post-commit update и следующей
      плановой GitHub-проверки;
    - локальные `ValueError`, повреждение SQLite и неожиданные runtime invariants
      по-прежнему не маскируются как недоступность provider.

    Причина: embeddings являются платной производной проекцией и не входят в
    GitHub source of truth. Прежний порядок фиксировал source SHA только после
    semantic API, поэтому один malformed batch оставлял 173 корректно
    загруженные заметки без snapshot SHA и блокировал весь review workflow.
22. **10.22 — завершено.** До загрузки страницы и LLM-анализа добавлен readiness
    gate безопасного локального fallback:
    - при ошибке автоматической GitHub/SQLite-синхронизации продолжать article
      pipeline разрешено только если сохранены HEAD commit SHA и tree SHA и
      опубликован chunk global marker текущей parser/policy signature;
    - то же правило применяется, если lease занят синхронизацией из другого
      связанного канала;
    - при отсутствии пригодного snapshot обработка URL останавливается до
      article fetch/extraction/LLM, возвращая понятную sync-ошибку без лишних
      токенов;
    - при готовых source/FTS и неготовых embeddings pipeline продолжается через
      FTS fallback с отдельным semantic-предупреждением;
    - readiness берётся из общего `VaultStatus`, одинакового для Telegram и VK,
      поэтому канал не влияет на решение.

    Причина: прежний fallback проверял лишь наличие локальных заметок и ловил
    слишком широкий набор ошибок. При первой незавершённой синхронизации он
    запускал платный LLM-анализ, а только затем review обнаруживал отсутствующие
    HEAD/tree SHA. Gate переносит известную блокирующую проверку перед любыми
    платными стадиями.
23. **10.23 — завершено.** Реализованы checkpoint-сохранение embedding-пакетов
    и безопасная диагностика некорректных ответов provider:
    - после успешного ответа на каждый batch сразу сохраняются полученные vectors
      в SQLite, не ожидая завершения всей операции по vault;
    - при сбое последующего batch сохраняются предыдущие успешные результаты;
      global embedding marker не публикуется до полного покрытия;
    - при следующем `/github_sync` или плановом retry provider получает только
      chunks без совместимого embedding, не оплачивая повторно готовые batches;
    - логи содержат номер и размер проблемного batch, ожидаемое и фактическое число
      vectors, наличие обязательных полей, типы значений, HTTP status и provider
      request ID;
    - в логи не записываются полный provider response, исходные тексты chunks,
      API key или другие чувствительные и потенциально объёмные данные;
    - malformed `200 OK` отличается от transport/HTTP errors; исходная вложенная
      причина сохраняется в цепочке исключений, её тип — в структурированных логах;
    - application-indexer получает ленивые пакеты через `iter_document_batches`;
      следующий HTTP-запрос выполняется после сохранения предыдущего checkpoint;
    - `save_batch` и `complete_generation` разделены; source hashes, полное
      покрытие и lease проверяются под коротким SQLite write lock;
    - смена размерности атомарно удаляет несовместимые vectors при первом новом
      checkpoint; новые успешно оплаченные пакеты сохраняются для retry;
    - потеря или истечение lease останавливает дальнейшие запросы и записи;
      локальные SQLite/runtime errors не маскируются как provider fallback;
    - схема БД не менялась. Проверки используют временные тестовые БД и HTTP mock
      настоящего SDK без внешней сети и платных обращений.

    Причина: при эксперименте с 623 chunks первые девять batches завершились
    успешно, а некорректный ответ последнего batch отменил публикацию всей
    операции. Полученные vectors не были сохранены, поэтому следующий запуск
    повторно отправил весь vault. Одна такая полная попытка оценивалась примерно
    в 7,20 ₽ по настроенному тарифу.

Критерии готовности:

- По сохранённой статье приложение находит заметки по словам и по смыслу.
- Одинаковые document, parser и policy дают одинаковые chunks; библиотека не
  получает проектные ID, а adapter корректно связывает результат с пользователем,
  vault и заметкой.
- Изменение chunking policy или версии parser полностью перестраивает индекс
  vault; обычная синхронизация обрабатывает только изменённые chunks.
- Результаты FTS5 и embeddings объединяются в одну выдачу.
- При недоступности embeddings остаётся рабочий FTS5 fallback.
- Предложение `add`, `update` или `skip` сохраняется, показывается пользователю и
  не применяется без явного `да`.
- Подтверждённые `add` и `update` создают прямой commit в default branch vault.
- Конфликт SHA не перезаписывает изменения, сделанные после подготовки
  предложения.
- Успешное применение атомарно переводит статью в `reviewed` и удаляет полный
  `cleaned_text`; ошибка commit сохраняет данные для повтора.
- Повторная ссылка использует сохранённый результат и не скачивает статью
  заново.
- После подтверждённого `add`/`update` индексы обновляются сразу; обычная статья
  не пересоздаёт chunks и embeddings остальных заметок vault.
- Сбой optional embeddings не отменяет готовые source/FTS, а отсутствие
  пригодного source/FTS snapshot останавливает статью до платного LLM-вызова.
- Успешные embedding batches переживают сбой последующего
  batch; повтор не отправляет provider уже сохранённые совместимые vectors.
- GitHub остаётся source of truth для vault, SQLite — локальной копией и source
  of truth для article/review workflow.
- FAISS не требуется для корректной работы.

## Выполненные отдельные задачи

Новые выполненные задачи добавляются в конец этого списка в порядке

### Показывать готовность semantic index в ответах чата

`/github_sync` и `/github_status` явно сообщают состояние embeddings, чтобы
частично построенный индекс не выглядел ни полностью готовым, ни полностью
неудавшимся.

- Для готового индекса показывается количество сохранённых embeddings и chunks,
  например `623 из 623`.
- Для частичного индекса показываются сохранённое и общее количество, число
  оставшихся chunks и сообщение о временном FTS fallback.
- Если embeddings не настроены, это сообщается отдельно от ошибки обновления.
- После повторной синхронизации показывается, сколько embeddings добавлено и
  сколько переиспользовано из уже сохранённых.

Обобщённая формулировка «embeddings обновить не удалось» заменена сообщением
с точным покрытием, когда оно известно.

### Устойчивость VK и Telegram к сетевым сбоям

VK Long Poll повторяет временные ошибки при первоначальном получении server,
ожидании событий и обновлении server. Число повторов не ограничено, задержка
растёт экспоненциально с jitter и ограничена 30 секундами; после успешного
запроса backoff начинается заново. В журнале есть этап, номер попытки, задержка,
тип и безопасные признаки вложенной сетевой причины без token и Long Poll key.
Постоянные ошибки VK не повторяются внутри adapter.

Telegram использует встроенный retry aiogram во время получения updates.
Временные ошибки при запуске или выходе из polling повторяются с задержкой до
30 секунд; неверный токен и конфликт параллельного polling завершают adapter.
Оба Compose-сервиса имеют `restart: unless-stopped` как дополнительную защиту.
На VPS systemd override запускает после reboot оба канала: Telegram теперь
обращается к Bot API через отдельный WireGuard-туннель и SOCKS5.

Проверены unit-тесты временных и постоянных ошибок, восстановления и штатной
остановки; полный набор тестов прошёл локально. Новый код развёрнут на VPS:
VK Long Poll стартовал, контейнер healthy, restart policy применена. Новый
пользовательский обмен сообщениями после обновления ещё не проверялся.
Telegram `getMe`, polling и восстановление обоих контейнеров после перезапуска
systemd-сервиса проверены 2026-09-29; пользователь подтвердил ответ на
`/status`.

### Доступ Telegram Bot API с российских VPS

Статус: выполнено 2026-09-29.

На VPS H3llo прямое исходящее HTTPS-соединение к `api.telegram.org:443`
не устанавливается: DNS работает, но TCP/HTTPS-запрос завершается таймаутом.
Это ограничение доступа к Telegram со стороны Роскомнадзора, а не ошибка
long polling или конфигурации бота. VK adapter продолжает работать напрямую.

Реализовано 2026-09-29: отдельный туннель WireGuard H3LLO–Timeweb и SOCKS5
на адресе туннеля. Код Telegram adapter принимает необязательный
`TELEGRAM_PROXY_URL`. С VPS успешен Telegram `getMe`, `tg_catcher` вошёл в
polling и восстановился вместе с VK после перезапуска systemd-сервиса.
Пользователь получил ответ на `/status`; обработка update видна в журнале VPS.

Критерии готовности:

- Telegram long polling и отправка ответов работают с VPS при недоступном
  прямом соединении к `api.telegram.org`;
- VK и остальные исходящие интеграции не перенаправляются через Telegram-прокси;
- секреты прокси не попадают в репозиторий и логи.
