# Шаг 6.2. Подготовить окончательный снимок и новое поколение SQLite

Код от 03.11.2026 реализует подготовительную часть
[протокола переключения](STAGE6_DB_SWITCH.md). Интерфейс для шага 6.3
находится в [deploy_final_snapshot.py](../../scripts/deploy_final_snapshot.py).
Для действующего `deploy-prod` применяется [эксплуатационная инструкция](../OPERATIONS.md).

## Подготовить два файла

1. Под deploy lock сверить selector, его исходное поколение и результаты
   predeploy. Установить marker, запретить рестарт контейнеров, остановить оба
   канала и завершить ночной backup. `Host.require_snapshot_quiescence`
   проверяет marker, оба контейнера и их restart policy, основной unit,
   backup timer и service. Контроллер также обязан исключить сторонние writers,
   включая CLI и процессы вне этих двух контейнеров.
2. Вызвать `prepare` с новым UUID поколения. SQLite backup API читает
   согласованное состояние исходного поколения, включая committed WAL. Снимок
   проходит проверку integrity, точного старого журнала и foreign keys.
   Контроллер получает путь `final-<generation-id>.db` и SHA-256 только после
   синхронизации файла и каталога. Снимок имеет права 0400 на Linux.
3. Сохранить `snapshot_verified` через callback до вызова мигратора. Передать
   `Host.migrate_copy` неизменяемый candidate image ID, приватный staging-каталог
   и basename `app-<generation-id>.db`. Docker получает только этот каталог,
   без production env и сети. Копия переносит WAL в основной файл и закрывает
   соединение перед публикацией. Проверяются точный новый журнал, integrity,
   foreign keys, CI fingerprint и равенство мультимножеств общих полей каждой
   исходной таблицы. Изменение существующего значения даёт отказ, включая
   backfill при наличии строк, которые он меняет.
4. Ещё раз подтвердить остановку writers и backup. Опубликовать проверенный
   `app-<generation-id>.db` в существующем `data` с синхронизацией файла и
   каталогов. На Linux новое имя создаётся атомарным `link`, затем staging-имя
   удаляется. Коллизия имени даёт отказ; после прерывания между операциями файл
   с двумя ссылками закрыт для выбора. После успеха вызывающий может записать
   `candidate_copy_verified` и переходить к шагу 6.3.

Исходная БД открывается SQLite в режиме чтения. Helper оставляет selector
вызывающему контроллеру. При штатном отказе staging-каталоги убираются, а уже
сохранённый снимок остаётся доступен. Если синхронизация после публикации
имени отказала, проверенный файл может остаться в `data` без допуска к выбору.
При прерывании процесса возможны остатки staging; правила их разбора входят
в последующие шаги.

## Подключить к контроллеру в 6.3

Штатный deploy пока использует прежнюю последовательность. В 6.3 передать
fingerprint от проверенного `Host.predeploy`, вызвать helper вместо прежней
миграции рабочей БД и включить модуль в controller snapshot. До смены selector
отказ подготовки должен провести прежний runtime через проверяемый возврат
обоих каналов и timer на прежней БД. После успешной подготовки контроллер
должен сохранить идентичности файлов и обе durable-стадии до переключения.
Для проверки прерывания применить [протокол 6.1](STAGE6_DB_SWITCH.md#выбрать-recovery-после-прерывания).

## Воспроизвести локальную проверку

Из корня worktree, при отсутствии его `.venv`, использовать окружение
основной рабочей папки.

```powershell
$env:PYTHONUTF8='1'
& 'C:/Users/compadre/Documents/obsChatBot/.venv/Scripts/python.exe' -m unittest tests.test_deploy_final_snapshot tests.test_predeploy_compatibility tests.test_deploy_prod tests.test_migration_runner tests.test_runtime_schema
```

Тесты создают временную SQLite с SQL миграциями 0001–0002 и строкой в WAL.
Проверка команды Docker подменяет Docker транспорт, но запускает настоящий
локальный `python -m compadre_assistant --migrate --database-path ...` с
миграциями 0001–0004. Проверяются неизменность исходного main/WAL и selector,
сохранение снимка, очистка staging, коллизия, отказ синхронизации, повторная
проверка writers, а также отказы integrity, foreign keys, fingerprint,
журнала, сохранности данных, записи состояния и мигратора.
Групповой прогон завершился: 69 тестов, 1 пропуск. Добавленная следом
отдельная проверка коллизии между проверкой имени и публикацией прошла.
Локальный Docker daemon недоступен. Linux bind mount, systemd, отключение
питания и production recovery остаются за пределами этой проверки.
