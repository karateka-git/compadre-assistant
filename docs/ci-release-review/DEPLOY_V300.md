Указанные в плане «около 3:35» не воспроизведены как длительность серверной
команды. Разница с 215 s составляет 25.394727 s; относить её к SSH, ожиданию
агента или preflight без исходных клиентских timestamps нельзя. Более широкое
клиентское окно, build целиком, обе проверки и простой остаются `unknown`.

По коду порядок такой: build → synthetic smoke/preflight → остановка обоих
writers → backup и validation → migration → validation схемы → pin → запуск
каналов → первый `verify_both` → restart policy `unless-stopped`, снятие marker,
`activate_unit` → второй `verify_both` → timer restore → success. Два вызова в
успешном пути не доказывают, что оба выполнялись в этой неуспешной установке.

## Объяснить ложный unhealthy

В [Compose v3.0.0](https://github.com/karateka-git/compadre-assistant/blob/523ce4c595e7fe87771a10752944358a19c3bed8/docker-compose.yml)
у обоих каналов были `interval: 30s`, `timeout: 5s`, `retries: 3`,
`start_period: 5s`. Probe запускает отдельный процесс
`python -m compadre_assistant --healthcheck --channels <канал>`.

`run_healthcheck` пишет `Health check passed` после проверки конфигурации,
доступности каталога и SQLite, затем возвращает 0. Сообщение доказывает
успех этих проверок внутри процесса; Docker оценивает итог выполнения всего
probe, включая запуск Python, imports и завершение. Если его временной бюджет
исчерпан, строка успеха сама по себе не гарантирует успешный exit, принятый
Docker. Поэтому такой лог совместим с timeout и последующим `unhealthy`.
Точную гонку между печатью строки, завершением процесса и timeout в этом
инциденте без старой Health.Log доказать нельзя.

S6 сообщает о холодном Telegram healthcheck с exit code 0 за **7.407 s** при
recovery на v3.0.1: это на 2.407 s больше старого бюджета. Измерение поддерживает
диагноз недостаточного лимита, но не является замером probe v3.0.0 и не даёт
его timestamp. В v3.0.1 лимит обоих каналов изменён с 5 s на 30 s; остальные
указанные параметры Compose сохранены. Успешный healthcheck не проверяет
реальные ответы Telegram/VK и не заменяет polling-проверки контроллера.

`verify_both` проверяет image ID, running/healthy, ноль рестартов, OCI revision,
сигналы polling обоих каналов и отсутствие traceback/conflict в доступных
логах. Условия должны удерживаться не менее 10 s; опрос идёт через 3 s,
бюджет вызова — 120 s. Поэтому 120 s нельзя автоматически подставлять как
точную длительность и тем более складывать два бюджета в фактический deploy.

## Объяснить degraded и границы восстановления

S3 хранит `migration_attempted=true` и разные manifest до/после. В `_recover`
это запрещает автоматический запуск старого кода: схема уже могла измениться,
даже если новая миграция не завершилась. Ошибка `Новая миграция могла изменить
схему` описывает отказ безопасного возврата, а не первоначальную причину
провала проверки здоровья. Исходная ошибка перезаписана стадией recovery.

По S6 выполнено ручное восстановление вперёд на v3.0.1
(`4d58c9c09259f8f9b1578a467b20c5e6055a6bc2`); оба backup сохранены,
на 30.10.2026 04:33:27 UTC каналы healthy и схема `0001–0004`. Это отдельная
recovery-процедура, не успешное окончание обычного deploy v3.0.0.

Поиск journal по `deploy-prod stage=`, `Health check passed`, `health_status`
и `degraded` не дал отдельных стадий в проверенном историческом окне.
S1/S2 сохранились, поэтому отсутствие стадий не равнозначно отсутствию событий.
Старые tg/vk assistant-контейнеры уже заменены контейнерами, созданными
30.10.2026 04:32:20 UTC; их текущий health не восстанавливает старые probes.
Для заполнения пробелов нужен сохранённый stdout исходного deploy или
историческая выборка Docker Health.Log; новые проверки production не заменят
эти исторические данные.
