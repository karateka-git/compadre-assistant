## Разделить этапы deploy и пробелы

По [хронологии](DEPLOY_V300.md#прочитать-хронологию) candidate image создан в 17:21:45.859412195, остановка unit началась в 17:22:03.768862 и закончилась в 17:22:14.892817 (**11.123955 с**), backup-файл появился в 17:22:15.248236698, `degraded` сохранён в 17:24:35.342235. Создание image не отмечает конец `docker build`; разность birth/mtime backup-файла **0.020000210 с** не измеряет backup с проверками. Длительности build, backup, миграций `0003`/`0004`, простоя приложения и каждого `verify_both` — **unknown**. В успешном пути код предусматривает два `verify_both` с бюджетом по 120 с; факт выполнения второго в неудачном deploy не подтверждён. Эти бюджеты нельзя складывать как фактическое время.

В Compose `v3.0.0` Docker healthcheck имел timeout 5 с. Строка `Health check passed` подтверждает пройденные внутренние проверки, но не итог probe, если процесс не уложился в Docker timeout. Историческая Health.Log старых контейнеров недоступна, поэтому точный probe, его время и гонка завершения остаются **unknown**. Измеренные при recovery `v3.0.1` **7.407 с** холодного Telegram healthcheck поддерживают объяснение слишком короткого лимита, но не являются замером `v3.0.0`. `degraded` после начатой миграции означает отказ от автоматического возврата на прежний образ при неопределённой схеме; сообщение recovery не устанавливает исходную причину отказа. Ручное восстановление вперёд на `v3.0.1` — отдельное событие, не успешное окончание установки `v3.0.0`.

Для всего исторического пути остаются **unknown**: число и длительность manual actions, retries запросов GitHub API агента, число и длительность agent waits, Codex tokens конкретного desktop-чата. GitHub timestamps не являются журналом этих действий; [AGENT_BASELINE.md](AGENT_BASELINE.md#оценить-исторические-метрики-агента) объясняет доступные источники и их границы. Так же `unknown` клиентский wall-clock от начала работы над PR до конца deploy.

## Заполнить запись следующего сопоставимого выпуска

Следующий выпуск следует занести **после его фактического завершения** отдельной строкой или таблицей под этим заголовком, не смешивая его SHA и события с прогонами 30.10. Порядок записи:

1. Зафиксировать PR, head SHA, merge SHA, timestamps открытия/слияния и ссылку на PR; отдельно сохранить SHA тестового merge, если источник его действительно даёт.
2. Для `pr-fast`, полного `main-full` либо необходимого `release-full` записать workflow, run/attempt, точный SHA, `run_started_at`, `updated_at`, conclusion, status `full-suite`, ссылки на run/jobs; рассчитать run, job и step durations по их собственным границам. Пропущенную `full-suite` явно отметить.
3. Зафиксировать tag SHA, `published_at` и ссылку на Release. Отдельно рассчитать интервалы PR → полный CI → Release; не выдавать интервалы событий за время ручной работы.
4. По безопасно сохранённому отчёту deploy записать SHA Release и controller snapshot, серверные start/end, build, остановку обоих каналов, backup, migrations, каждый фактически достигнутый `verify_both`, простой, результат и источник каждой метки. Клиентское окно записать отдельно, только если есть его timestamps. При недоступной стадии указать `unknown`, а не подставлять таймаут или время соседних событий.
5. По привязанному к этому выпуску журналу действий отдельно посчитать manual actions, API retries и agent waits; записать Codex tokens только при проверенном счётчике того же desktop-чата. Для отсутствующего источника оставить `unknown`.
6. Сопоставить одинаковые типы прогонов и deploy со строками выше, проверить арифметику, точный SHA и ссылки. После этого оценить критерий этапа 1 по [плану](PLAN.md#1-снять-базовые-замеры-и-разобрать-текущий-выпуск).
