# Шаг 6.1: выбрать SQLite после прерывания

Решение от 03.11.2026 задаёт протокол для последующих шагов
[этапа 6](PLAN.md#6-мигрировать-копию-и-изменить-возврат). Локальный
[воспроизводимый стенд](sqlite_switch_experiment.py) подтвердил выбор файлов
при аварии процесса. **Production controller ещё не реализует этот протокол**;
действующие команды и recovery остаются в [OPERATIONS.md](../OPERATIONS.md).
Это решение шага 6.1, а не допуск установки snapshot или выпуска.

## Выбрать механизм

Оставить существующий bind mount `./data:/app/data` и каталог `data` на месте.
Каждая новая рабочая SQLite получает уникальное непереиспользуемое имя
`app-<generation-id>.db`. Её WAL/SHM имеют тот же префикс:
`app-<generation-id>.db-wal`, `app-<generation-id>.db-shm`.
Атомарно заменяется только внешний root-owned `active-db.json`, содержащий
ID перехода, ID поколения и его относительное имя. Сам файл БД, его WAL/SHM
и каталог `data` при переключении не переименовываются и не перезаписываются.
В примерах стенда ID фиксирован; production обязан выделять новый уникальный
ID на каждую попытку, включая повтор того же Release.

Начальная SQLite `data/app.db` принимается как первое поколение **на месте**,
с её существующими WAL/SHM. Это исключает аварийное окно преобразования
существующего каталога в symlink или переноса тройки файлов. Снимок делается
SQLite backup API после остановки writers; новый рабочий файл создаётся из
снимка под новым именем. Остальные файлы `data` и его inode сохраняются.
После успешного перехода следующие поколения используют тот же принцип.

| Вариант | Решение и причина |
| --- | --- |
| Заменить только `app.db` через rename | Отклонён: имя старого WAL остаётся рядом с новой БД. |
| Переименовать БД, WAL и SHM по очереди | Отклонён: три операции не образуют атомарного перехода. |
| Заменить symlink `data` или `app.db` | Отклонён: нужны отдельный переход существующего каталога и доказательство разрешения путей/уже открытых mount и соединений. |
| Уникальные имена, внешний selector, явный `DATABASE_PATH` | Выбран: содержимое каждой тройки остаётся на своём пути; разрыв между selector и конфигурацией обрабатывается под marker до запуска. |

Основания: SQLite описывает WAL как часть состояния БД и предупреждает
против отделения журнала от своего файла и переименования используемой БД
([WAL](https://www.sqlite.org/wal.html),
[причины повреждения](https://www.sqlite.org/howtocorrupt.html)).
Здесь изоляцию обеспечивает уникальность имён, а не предположение, что SQLite
обязательно распознает любой чужой WAL. Контроллер никогда не удаляет
sidecars для «очистки» и не открывает существующую БД с режимом, создающим
пустую SQLite при отсутствии файла.

## Сохранить durable-состояние

Один внешний deploy lock сериализует всю операцию и recovery. Marker,
остановленный backup timer/service, запрет Docker restart и подтверждённая
остановка обоих polling-процессов предшествуют снимку и переключению.
Нужна проверка также других writers/CLI; отсутствие только двух известных
контейнеров не разрешает стороннюю запись. Все участники используют один
канонический путь, без symlink/hardlink-алиасов и сетевого filesystem.

`state.json` новой версии должен хранить как минимум:

- `protocol_version`, уникальный `transition_id`, `controller_sha`, stage;
- `old` и `new`: generation ID, канонический host-путь, container-путь,
  device/inode при регистрации, ожидаемый manifest миграций и fingerprint
  проверенной схемы. Inode — дополнительная проверка подмены, не идентичность
  поколения вместо уникального имени;
- окончательный immutable snapshot: путь, digest, результат integrity/FK,
  manifest/проверки данных; snapshot никогда не является runtime-файлом;
- точные previous/candidate SHA, image ID, pin/tag, доказательство допуска
  точной пары этапа 5; SHA controller отдельно от обоих SHA приложения;
- `switch_intent` с from/to; подтверждённый выбранный generation ID;
- `admission_may_have_started` — монотонный boolean и привязка к transition,
  новому поколению и допущенному runtime; состояние timer и текущий recovery.

Имена полей выше — контракт реализации, стенд использует сокращённую модель.
Отсутствующая/неверная версия или граница не равна `false`. Старое состояние
допускается только через явный переход legacy-протокола в 6.5 при доказанном
стабильном runtime. Незавершённый старый deploy не превращается в новый
протокол автоматически. Поля допуска сохраняются и при `rollback_started`,
`rolled_back`, `success`, ошибках записи state и повторе команды.

Каждая durable-публикация: записать новый файл в том же каталоге, flush,
`fsync(file)`, `os.replace`, `fsync(parent directory)`, проверить результат.
Каталоги и новые файлы поколения/snapshot также требуют синхронизации
до публикации ссылок на них. WAL новой БД либо сохраняется и синхронизируется
как часть её состояния, либо выполняются проверенный checkpoint и закрытие
всех соединений; нельзя синхронизировать только main DB при незаписанном WAL.
Ошибка любого sync запрещает продвижение и запуск. На целевом локальном
Linux filesystem и storage должны быть проверены atomic rename и fsync;
Windows process-crash опыт не доказывает сохранность при power loss.

## Выполнить переход по шагам

| Durable stage | Предусловие и следующий шаг |
| --- | --- |
| `prepared` | Runtime/pin/допуск проверены. При первом включении register legacy `app.db`, затем durable selector old; прерывание регистрации оставляет файлы на месте и запуск закрытым до сверки. |
| `writers_stopped` | Marker и запрет автозапуска сохранены; оба канала и прочие writers остановлены; timer/service завершены. |
| `snapshot_verified` | Окончательный backup API снимок синхронизирован и проверен, его digest записан. Old остаётся выбранной. |
| `candidate_copy_verified` | Отдельная копия мигрирована настоящим candidate CLI; journal, integrity/FK, fingerprint и данные проверены. Мигратор завершён; частичный кандидат не выбирается. |
| `switch_intent` | Durable state уже описывает оба поколения и намерение old → new, граница false. |
| `database_selected` | Атомарно опубликовать selector new и синхронизировать каталог; **это точка выбора новой БД**. Затем записать подтверждение в state; при crash между ними selector показывает фактический выбор. |
| `runtime_prepared` | Сформировать runtime.env и Compose для выбранного пути/образа; проверить оба сервиса. Создать контейнеры без start, проверить mount, env, image ID и отсутствие иных polling. |
| `admission_recorded` | Надёжно сохранить границу true **до команды start первого polling**, перечитать и сверить selector new. Теперь даже отказ до первого start сохраняет new. |
| `candidate_started` / `success` | Запустить только проверенные созданные контейнеры; проверить оба канала. Завершить штатные проверки, restart/systemd/timer и state, сохраняя generation и границу. |

При аварии до `fsync(parent)` наблюдаемый после reboot selector может быть
old или new; обе альтернативы обрабатываются таблицей ниже. Если файл
недоступен/испорчен, угадывать нельзя. Если публикация admission не вернула
успех, polling не запускается; recovery принимает уже сохранившееся true
консервативно. После успешного durable true ложное false при reboot означает
нарушенный storage-контракт, а не допустимую ветку протокола.

## Выбрать recovery после прерывания

Под тем же lock сначала закрыть возможный автозапуск и остановить оба writer.
Прочитать state и selector, проверить transition, имена, существование,
идентичность файлов и отсутствие алиасов. Selector определяет **выбранную**
БД; Docker inspect определяет БД, с которой был настроен каждый контейнер.
Это разные факты: selector сам по себе не меняет уже работающий процесс.
Несогласованный runtime не разрешает считать новую БД нетронутой.

| Наблюдение | Решение |
| --- | --- |
| Граница false, selector old, runtime не мог начать приём кандидатом | Вернуть прежний runtime на old. Кандидат/snapshot сохраняются для разбора. |
| Граница false, selector new, есть switch intent, запуск исключён | Durable recovery intent new → old; атомарно вернуть selector old, согласовать конфигурацию; запустить прежний runtime только после проверки old. |
| Граница true, selector new | Сохранить new со всеми записями; прежний runtime разрешён только по точному допуску repository-кода, fingerprint и локальному pin. Не применять down-миграции и не восстанавливать snapshot поверх new. |
| Граница true, selector old; чужой transition; пропавшая выбранная БД; повреждённые state/selector; false при обнаруженном старте кандидата | `degraded`: marker остаётся, writers остановлены, автоматический выбор/запуск запрещён. Сохранить данные для отдельного recovery. |

Recovery intent отдельно описывает from/to, поэтому crash до/после обратной
публикации old повторяется идемпотентно. Граница не сбрасывается при recovery.
Новый deploy может начать новую запись перехода только после завершения
предыдущего; его old — последнее выбранное рабочее поколение, а не всегда
`app.db`. При true recovery не ищет «более целую» old как автоматическую замену
new. Если недоступны обе копии, действует тот же закрытый отказ.

## Связать выбор с Docker, systemd и backup

Внешний проверенный Compose override задаёт обоим сервисам
`environment.DATABASE_PATH: ${ASSISTANT_DATABASE_PATH:?required}`.
Контроллер выводит `ASSISTANT_DATABASE_PATH=/app/data/<selected-name>`
из selector в root-owned runtime.env вместе с image pin. Значение
`environment` имеет приоритет над legacy `.env`/`env_file`
([Docker precedence](https://docs.docker.com/compose/how-tos/environment-variables/envvars-precedence/)).
Нельзя рассчитывать, что простое добавление переменной в runtime.env само
передаст её внутрь контейнера. Нет selector/переменной — отказ без default.

Runtime.env — производная конфигурация, не второй источник выбора. Crash
между selector и runtime.env исправляется под marker по durable state;
`runtime_tag()` сейчас принимает ровно две строки и требует изменения в 6.3.
До start требуется настоящий `compose config` плюс inspect **созданных, ещё
не запущенных** контейнеров: оба DATABASE_PATH, единственный bind `data`,
его канонический source, image ID и restart policy. Нужны force-recreate,
затем start конкретных проверенных контейнеров; прежний `up -d` запускает
слишком рано для этой проверки. Это требование будущей реализации, не правка 6.1.

Исходный bind mount остаётся тем же каталогом, поэтому путь внутри контейнера
меняется только именем файла. Отсутствуют переадресация symlink, замена
mount source и тройка неатомарных rename. `AppConfig.data_dir` остаётся `/app/data`.
Healthcheck, CLI migrate, systemd restart и backup должны читать то же выбранное
поколение. Жёсткие `data/app.db` в controller/predeploy/backup нужно устранить
при интеграции; legacy shell backup не должен молча копировать старую БД.
До этого timer не возобновлять. Старый runtime отдельно проверяется на startup
с admission новой схемы; зелёные repository tests этого не доказывают.

Цена решения: несколько полных SQLite-файлов и snapshot занимают диск;
нужны расчёт места с WAL и явный retention после приёмки, а не удаление при
ошибке. Доступ приложения к прежним файлам в общем bind сохраняется: протокол
защищает от штатных ошибок переключения, не от вредоносного приложения или
внешней подмены. Старые поколения и snapshot автоматически не удаляются.
