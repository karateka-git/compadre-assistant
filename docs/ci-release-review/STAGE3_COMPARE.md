## Сверить cache и artifact по логам

В [логе холодного job](https://github.com/karateka-git/compadre-assistant/actions/runs/41316919979/job/124878809759) `Setup Python` сообщил `pip cache is not found`; `Post Setup Python` сохранил кэш с ключом `setup-python-Linux-x64-24.04-Ubuntu-python-3.12.15-pip-223243bcb47f4b0e0a2821f344c3b7a021eb24d4f8b0abed09e261f6a321f971`. В [логе rerun](https://github.com/karateka-git/compadre-assistant/actions/runs/41316919979/job/124879040261) записаны `Cache hit for` **этого же ключа**, восстановление около 40 MB и `Cache hit occurred on the primary key ... not saving cache`. Это точное попадание, не partial restore. Строки `Using cached` для wheel и metadata показывают использование pip cache, но `Installing collected packages` и `Successfully installed` подтверждают повторную установку.

У `ci-metrics` во всех четырёх попытках пропущен сбор и загружен `ci-metrics-unavailable.json` с причиной `collector_missing_in_base`. Логи upload показывают artifact `ci-metrics-41315349925-1`, `ci-metrics-41315519360-1`, `ci-metrics-41316919979-1` и `ci-metrics-41316919979-2`. При повторной проверке списка artifacts GitHub API показывает по одному для каждого run: оба baseline artifacts и только `ci-metrics-41316919979-2` у нового run (ID `13087697007`, 697 байт, не expired). Лог первой attempt подтверждает её успешный upload, но её artifact сейчас отсутствует в списке run; не следует считать его доступным. `ci-metrics=success` здесь означает явный unavailable-result, а не полноценный сбор показателей.

## Оценить эффект и передать шагу 3.4

`Install runtime dependencies` после правки занял **10 с и при miss, и при точном hit** против 9 и 8 с baseline. Измеренного выигрыша установки нет. `Setup Python` вместе с `Post Setup Python` заняли 5 с при miss и 3 с при hit против 0 с по секундным полям baseline; сохранение холодного кэша добавило работу. Проверочный job занял 29 с при miss и 21 с при hit против 16–18 с baseline. Полный run занял 40 и 34 с против 28–29 с. Следовательно, по этим четырём наблюдениям улучшение wall-clock **не подтверждено**.

Тёплая attempt быстрее холодной на 8 с по job и на 6 с по run, но это не равно эффекту cache: `pip install` одинаков по секундам, Compose различается на 5 с, а runner, scheduling и сеть могут колебаться. Baseline имеет другие head/merge SHA; новые попытки имеют один SHA, но разные attempt и разные времена выполнения. Сравнивать attempt 2 с исходным `created_at` run либо включать в полный run полноценный collector другого base было бы ошибкой. Здесь структура `ci-metrics` осталась unavailable, поэтому полный run приведён как осторожное сравнение, не как причинный замер cache. Четырёх runs недостаточно для устойчивой оценки распределения времени.

**Рекомендация для 3.4:** откатить `cache: pip` и `cache-dependency-path` в `pr-fast`, если нет нового воспроизводимого замера с выигрышем общего времени. Текущая правка сохраняет успешность проверок, но добавляет setup/post работу без измеренного сокращения install или job. Перед решением о безопасности 3.4 отдельно сверить неизменность полного допуска точного SHA, полного набора и отказа при ошибке API; эти четыре `pr-fast` runs не проверяют `main-full` или `release-full`.

Время ручных действий, число API retries, ожидание агента и Codex tokens для этих runs — **unknown**: GitHub timestamps и job logs их не измеряют. Эти значения не включены в wall-clock CI.
