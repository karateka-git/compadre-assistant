## Выбрать одно узкое место

**Наблюдение:** в двух сопоставимых runs #59 `Install runtime dependencies` занимает 9 и 8 с, то есть примерно половину проверочного job (16 и 18 с), больше каждого отдельного шага unit или Compose. В [логе второго job](https://github.com/karateka-git/compadre-assistant/actions/runs/41315519360/job/124874606907) видны `Downloading` для metadata и wheels, затем `Installing collected packages` и успешное окончание. [Текущий workflow](../../.github/workflows/pr-fast.yml) выполняет `pip install -r requirements.txt` на каждом PR run; у `actions/setup-python` не задан `cache`. Это подтверждает повторную установку в отдельных runs, но не разделяет её 8–9 с точно на сеть, разрешение зависимостей и запись файлов.

**Правка-кандидат для шага 3.2:** только в `pr-fast` job добавить к существующему `actions/setup-python` настройку `cache: pip` с зависимостью от `requirements.txt`; сохранить команду установки полного `requirements.txt` и все проверки. Это минимальная попытка сократить повторную загрузку пакетов. Кэш не устраняет разрешение зависимостей и установку, его восстановление тоже занимает время. Выигрыш, величина выигрыша и даже знак изменения полного wall-clock пока **unknown**. Первый run с новым ключом кэша считать холодным, следующий с тем же ключом — тёплым; не выдавать разницу разных SHA и загрузки runner за чистый эффект кэша.

## Сравнить после правки

1. До изменения сохранить приведённые `41315349925/1` и `41315519360/1` как baseline `pr-fast` с `ci-metrics=unavailable`. После шага 3.2 получить завершённые `pr-fast` для PR #59 либо другого PR в `main` с тем же составом проверочных jobs и результатом, записать head SHA, run/attempt, `run_started_at`, `updated_at`, job и step timestamps, состояние cache hit/miss из лога setup-python. Rerun считать отдельной attempt, не смешивать с первоначальным `created_at`.
2. Сравнивать отдельно `Install runtime dependencies`, `pr-fast` job и полный run. Если новый base SHA уже содержит collector, `ci-metrics` станет полноценным и полный run перестанет быть структурно сопоставим с указанными runs #59; тогда найти baseline с таким же отчётным job либо ограничить вывод временем проверочного job/step. Отмечать колебания runner и сети, не приписывать всю разницу кэшу.
3. Проверить, что setup/restore кэша и `pip install` завершились успешно, `Fixed unit subset` и Compose остались успешными, а `ci-metrics` сохранил явный результат. Если step ускорился, но job/run нет, записать отсутствие выигрыша по wall-clock. Если ускорения нет или кэш ухудшает время, не расширять оптимизацию без нового замера.

## Границы и риски

Статический просмотр [workflow](../../.github/workflows/pr-fast.yml), [collector](../../scripts/ci_metrics.py), [контроллера](../../scripts/full_ci_controller.py), [допуска](../../scripts/full_ci_admission.py) и [выбора deploy](../../scripts/select_deploy_release.py) показывает отдельные API чтения истории runs/jobs для измерения и проверки допуска. В collector текущая attempt читается через endpoint attempt, история — отдельно; чтения прошлых jobs зависят от поиска сопоставимого run. Это не доказательство лишнего повторного запроса. Число HTTP retries, время API, опросы и чтение логов агентом в историческом PR → Release → deploy, ручные действия и Codex tokens конкретного чата — **unknown** согласно [AGENT_BASELINE.md](AGENT_BASELINE.md#оценить-исторические-метрики-агента). Периоды между GitHub событиями не являются временем ожидания агента. Для этой категории нет подтверждённого узкого места, поэтому API-код и polling в шаге 3.2 не менять.

Кэш не должен менять `checkout` тестового merge, содержимое `requirements.txt` или результат `pip install`. При ошибке восстановления кэша требуется проверить поведение шага и итог job, а не считать сохранённые пакеты доказательством прохождения тестов. Полный `main-full`/`release-full` для **точного SHA выпуска**, полный `full-suite` и отказ допуска при ошибке GitHub API остаются условиями [RELEASES.md](../RELEASES.md#2-получить-полный-ci-для-точного-коммита); `pr-fast` и его возможное ускорение их не заменяют. Не изменять fail-closed проверку API ради времени без отдельного измерения и проверки инвариантов.
