# Проверить ограниченный запуск на новой схеме: шаг 4.2

Этот документ фиксирует реализацию потребления допуска будущей схемы от
02.11.2026. Он позволяет проверить базовый runtime локально; production-выдача
допуска и автоматический возврат ещё не реализованы. Границы решения заданы
[аудитом 4.1](STAGE4_AUDIT.md), порядок выпуска остаётся в
[RELEASES.md](../RELEASES.md), recovery — в [OPERATIONS.md](../OPERATIONS.md#отказ-выпуска-и-возврат).

## Выбрать режим запуска

[Runtime schema](../../compadre_assistant/core/data/sqlite/runtime_schema.py)
содержит отдельный потребитель контракта. Без двух переменных запуска
`COMPADRE_SCHEMA_ADMISSION` и `COMPADRE_SCHEMA_LAUNCH_CONTEXT` обычный startup
использует прежний строгий `apply_migrations`. Неизвестная версия отвергается.
Если задана хотя бы одна переменная, обе должны указывать на корректные JSON
файлы. Неполный контекст или ошибка проверки закрывает запуск без fallback.

Обычный CLI, `--telegram-bot`, `--vk-bot` и отдельный `run_process_url_command`
используют этот выбор до предметной обработки. `--migrate` всегда вызывает
строгий мигратор, даже если переменные присутствуют. Автономные smoke остаются
строгими; healthcheck не является доказательством совместимости startup.

В режиме допуска runtime не применяет даже известные pending-миграции.
Его полный локальный набор файлов должен совпадать с базовым журналом;
целевой журнал обязан строго продолжать этот набор. Успех возвращает пустой
список применённых миграций. Новой production SQL-миграции в шаге 4.2 нет.

## Сверить поля и доверенную границу

Оба JSON — объекты с точным набором полей; лишние, пропущенные и повторяющиеся
ключи отвергаются. Общие обязательные поля допуска и launch context:

| Поле | Смысл и формат |
| --- | --- |
| `base_sha`, `base_image_id` | Точная прежняя версия: 40 lowercase hex и `sha256:` плюс 64 lowercase hex. |
| `candidate_sha`, `candidate_image_id` | Точная версия, создающая целевую схему, в тех же форматах. |
| `controller_sha` | 40 lowercase hex SHA отдельно установленного controller snapshot. |
| `verification_id` | 64 lowercase hex идентификатор доказательства проверки пары; будущий harness определяет и проверяет происхождение этого evidence. |

Допуск дополнительно содержит:

| Поле | Проверка |
| --- | --- |
| `format_version` | Целое число `1`; boolean не принимается. |
| `base_journal` | Полный упорядоченный массив `[version, name]` базового образа от 1 без пропусков. |
| `target_journal` | Точный более длинный журнал; базовый журнал является полным префиксом. |
| `base_sql_sha256` | Digest имён, версий и SHA-256 точных байтов локальных SQL-файлов. |
| `schema_sha256` | Digest точной структуры целевой SQLite. |

`validate_release_pair` — чистый validator, доступный будущему контроллеру.
Он не выдаёт разрешение. `verification_id` синтаксически проверяется и
сопоставляется с независимым launch context; одно его наличие не доказывает
успех тестов. Настоящее происхождение evidence должен проверить контроллер
перед созданием файлов.

**JSON и env не аутентифицируют работающий образ.** Выбран доверенный launch
context вместо встроенного SHA: контроллер независимо проверяет Docker image
ID и OCI revision, запускает именно этот ID, проверяет свой отдельный snapshot
и доставляет оба файла вне изменяемой БД только read-only. Runtime проверяет
согласованность предоставленных идентичностей. Возможность подменить оба файла
означает нарушение доверенной границы контроллера, которое этот модуль не
устраняет. Ни переменная SHA, ни сравнение двух самостоятельно написанных JSON
не являются доказательством подлинности. Действующий deploy эти файлы не создаёт
и не монтирует; примеров ручной выдачи production-допуска здесь намеренно нет.

## Проверить журнал и физическую структуру

После проверки формата и локальных файлов validator требует соединение вне
пользовательской транзакции и начинает `BEGIN IMMEDIATE`. Это не DDL и не запись
журнала: блокировка запрещает конкурентный DDL и изменение истории до окончания
проверки журнала и fingerprint. В завершение выполняется rollback пустой
транзакции при успехе и отказе. Отсутствующий журнал не создаётся.

`schema_fingerprint` сериализует все строки `sqlite_schema`, отсортированные по
`type, name, tbl_name`, с полями `type, name, tbl_name, sql`. Внутренние индексы,
`sqlite_sequence`, FTS shadow tables и таблицы статистики включены. `rootpage`,
содержимое таблиц и время применения миграций не включены. SQL хранится дословно;
семантически эквивалентный другой DDL не получает прежний допуск. Создание
таблицы статистики тоже изменяет digest и требует новой аттестации.

Канонизация обоих digest: `json.dumps(..., ensure_ascii=True,
separators=(",", ":"))`, UTF-8, SHA-256. Для SQL digest исходный массив имеет
элементы `[version, name, sha256(file_bytes)]` по версии. Общие функции
канонизации должен использовать и выдающий допуск код.

Обычные изменения пользовательских строк не меняют fingerprint. Это не
проверка совместимости данных: её обеспечивают сценарии следующего этапа.
После возврата validator блокировка отпущена; запрет внешнего изменения схемы
во время runtime обеспечивается жизненным циклом контроллера, а не вечным
SQLite lock. Подключение по-прежнему включает WAL, поэтому обещание отсутствия
любых дисковых записей не даётся. Проверяется отсутствие DDL, исполнения
неизвестного SQL и изменения журнала самим режимом допуска.

## Повторить локальную проверку

[Тесты контракта](../../tests/test_runtime_schema.py) создают отдельную временную
БД с синтетической `0005_future.sql`. Они проверяют точную пару, каждый SHA/image,
неверный digest, имя/пропуск/префикс журнала, испорченный JSON, лишние/пропущенные
поля, DDL с тем же журналом, локально изменённый SQL, пустую БД, повторный и
параллельный startup, блокировку concurrent DDL, отсутствие DDL/записей при отказе
и сохранность данных. CLI-проверки охватывают оба канала до polling,
process-url и строгий `--migrate` при наличии допуска.

Запускать проектным venv согласно AGENTS.md; для прямого перечисления модулей
тестов добавить корень проекта и `tests` в `PYTHONPATH` (вспомогательные тестовые
импорты используют этот каталог). Проверяемые модули: `test_runtime_schema`,
`test_migration_runner`, `test_cli_migrate`, `test_cli_process_url`,
`test_deploy_prod`. Точные результаты прогона приведены в отчёте шага 4.4;
локальный результат не заменяет полный CI опубликованного SHA.

## Завершить оставшиеся гарантии

Этап 5 обязан запустить точный предыдущий образ на изолированной мигрированной
копии, проверить startup и двусторонние сценарии чтения/записи, определить
проверяемое evidence и лишь затем разрешить контроллеру выдачу допуска.
Пробный контекст harness не должен доставляться в production.

Этап 6 обязан сверить окончательную схему после остановки, выбрать активную БД,
доставить защищённые read-only файлы обоим каналам, сохранить их при recreation
и reboot, реализовать границу приёма и безопасное восстановление. Отдельный
controller snapshot на VPS не обновляется правкой исходников.

`deploy_prod._recover` не изменён: после попытки новой миграции сохраняется
`degraded`, включая сбой без новой строки журнала. Шаг 4.2 не разрешает возврат
на новую production-БД. Выпуск и установка базового образа — отдельный шаг 4.5;
совместимость с будущим релизом будет доказана только для конкретной пары.
