# Подготовить базовую версию для будущего возврата: аудит 4.1

Запись от 02.11.2026 определяет контракт и проверки для шагов 4.2–4.4
[плана](PLAN.md#4-подготовить-версию-пригодную-для-будущего-возврата).
Это проект решения по исходникам, а не подтверждение установленного runtime.
Действующий выпуск описан в [RELEASES.md](../RELEASES.md), установка отдельного
контроллера — в [OPERATIONS.md](../OPERATIONS.md#обновить-отдельно-установленный-controller-snapshot).
VPS, публикация и Git-запись в этом аудите не выполнялись; тесты не запускались.

## Зафиксировать текущие ограничения

1. [Мигратор](../../compadre_assistant/core/data/sqlite/migration_runner.py)
   сверяет последовательный журнал `(version, name)` с файлами образа.
   `_validate_applied_migrations` отвергает любой неизвестный хвост до нового
   SQL. `_ensure_migrations_table` вызывается раньше валидации и уже делает
   DDL/commit: для режима совместимого запуска этот порядок надо разделить.
   Проверка имён не доказывает неизменность физической схемы или SQL-файлов.
2. [CLI](../../compadre_assistant/presentation/cli/main.py) вызывает
   `initialize_database` при обычном запуске и для обоих отдельных каналов;
   `--migrate` использует ту же функцию. `run_process_url_command` отдельно
   вызывает `apply_migrations`. Разрешение должно действовать согласованно
   во всех runtime-входах, но не превращать `--migrate` в пропуск неизвестной
   миграции. Healthcheck без startup не доказывает совместимость.
3. [Контроллер](../../scripts/deploy_prod.py) в `_prepare_candidate` сверяет
   префикс имён, образ и SHA, но не запускает старый образ на новой схеме.
   `Host.migrate` меняет рабочую БД после остановки. `_recover` намеренно
   оставляет `degraded` после попытки новой миграции, даже если новая строка
   журнала ещё не появилась. Ослаблять это правило на этапе 4 нельзя.
4. [Проверка full migrations](../../scripts/check_full_migrations.py)
   проверяет свежую БД, upgrade, неизменность прежнего SQL, сохранность строки
   и синтетическую pending-миграцию. [Probe прежнего кода](../../scripts/probe_previous_code.py)
   импортирует только прежний user repository в текущем Python: нет обычного
   startup, прежнего контейнера и сценариев остальных модулей.
   [Full suite](../../.github/workflows/full-suite.yml) запускает этот probe;
   зелёный результат сейчас не является разрешением будущего rollback.
5. [Сборка образа](../../scripts/deploy_prepare.py) присваивает OCI revision
   и проверяет Docker image ID. [Dockerfile](../../Dockerfile) не встраивает
   SHA в доступный приложению файл. Внутри контейнера OCI label автоматически
   не доступен: нельзя считать переданную переменную SHA доказательством
   подлинности образа. Сверка image ID/revision принадлежит контроллеру.

## Ввести ограниченный контракт запуска

Выбрать два явных режима. Обычный режим сохраняет нынешнее применение только
известных миграций и строгий отказ на неизвестный хвост. Режим совместимого
runtime допускает исключительно полностью проверенную более новую схему и
вообще не применяет миграции, не создаёт журнал и не исправляет историю.
Успех этого режима возвращает пустой список применённых миграций. Его наличие
в базовом образе само по себе не разрешает ни одной будущей схемы.

Разрешение хранится вне изменяемой БД в отдельном файле доверенного
контроллера, монтируется в runtime только для чтения. Это не универсальный
флаг `allow_unknown`, не номер максимальной версии и не таблица, которую
новый бот может сам заполнить. Контракт версии 1 должен фиксировать:

| Поле | Проверка |
| --- | --- |
| Версия формата | Неизвестный формат, пропущенные обязательные поля и неверные типы закрывают запуск. |
| Прежний полный SHA и точный image ID | Контроллер сверяет с реально установленным образом и запускает только этот ID; runtime сверяет свою доступную идентичность с разрешением. |
| Candidate SHA/image ID, SHA controller snapshot | Источник схемы и выдающий допуск код фиксируются отдельно от прежнего runtime. |
| Базовый журнал и целевой журнал | Полные упорядоченные пары version/name; локальная история образа должна быть точным полным префиксом, а БД — точно целевым журналом. |
| Digest целевой схемы | Стабильная канонизация записей `sqlite_schema` по type/name/tbl_name/sql, без rootpage и данных, с явно определённым составом внутренних объектов; одинаковая реализация у выдающего и проверяющего. |
| Идентификатор успешной проверки | Связывает допуск с проверкой конкретной пары образов/схемы; один только `passed: true` из произвольного файла не является доказательством. |

Для runtime SHA предпочтителен неизменяемый файл идентичности, записанный
при Docker build; контроллер независимо проверяет OCI revision/image ID.
Если реализация шага 4.2 использует доверенный launch context вместо встроенного
SHA, это надо явно документировать: runtime не аутентифицирует собственный
образ, доверенная граница проходит по контроллеру и read-only mount. Нельзя
заявлять, что сравнение двух переменных окружения решает эту задачу.

Digest схемы не заменяет сценарии чтения/записи и проверку данных. Он лишь
не позволяет перенести допуск на другую структуру с теми же именами миграций.
Не хешировать всю БД: пользовательские записи и WAL меняются штатно.
Базовые файлы SQL также сверяются с исходной историей; неизменяемость всех
выпущенных миграций сохраняется. На этапе 4 новые production-миграции не нужны.

При совместимом запуске сначала прочитать и проверить контракт, журнал и
структуру БД; удержать согласованный SQLite transaction/lock до окончания
проверки, исключив изменение схемы между проверками. Затем разрешить обычную
работу repositories. Отказ не должен изменять схему или журнал. Не обещать
полного отсутствия любой дисковой записи: обычное подключение включает WAL.
Незнакомые SQL-файлы не загружаются извне и никогда не исполняются старым кодом.
`--migrate` остаётся строгим даже при наличии runtime-разрешения.

## Разделить выдачу допуска и его потребление

В 4.2 можно реализовать формат, строгую валидацию и потребление разрешения,
а также чистую проверку контроллером точной пары без включения нового recovery.
Для unit/integration fixtures разрешение создаётся тестом на временной БД.
Действующий `deploy-prod` не должен выдавать production-разрешение из
результата нынешнего `check_full_migrations.py`: необходимых доказательств нет.

На этапе 5 проверяющий harness запускает базовый образ на отдельной
мигрированной копии без сети, credentials и реального polling. Ему нужен
изолированный пробный контекст, иначе возникает цикл «startup требует допуск,
а допуск требует startup». Такой контекст ограничен тестовой копией и не
монтируется в рабочий runtime. Только успешные сценарии дают контроллеру
право сформировать окончательное разрешение. Проверяются и записи нового
кода, и их безопасное чтение прежним, и записи прежнего с последующим чтением
новым. Для неизменной схемы новые значения данных тоже требуют этих проверок.

Перед остановкой проверяется фактически установленный SHA/image ID, а не
просто предыдущий тег. После остановки в этапе 6 сверяются окончательная
мигрированная копия, её журнал, fingerprint и сохранность данных. Повторная
полная проверка совместимости здесь не нужна, но несовпадение схемы закрывает
переключение. Разрешение относится к этой паре, а не ко всем будущим схемам.

Доставка read-only mount обоим ботам, его сохранение при systemd recreation,
повторном запуске и reboot, выбор активной БД, граница приёма и восстановление
относятся к этапу 6. До этого изменение `_recover` запрещено смыслом плана:
возврат на новую БД без этих гарантий не реализован. Обновление исходников
контроллера не обновляет его отдельный snapshot на VPS.

в enum нет. Свободные `channel`, capability ID и MIME/type строки требуют
своих реестров/правил, а не общего enum fallback. При обнаружении дополнительной
реальной границы чтения в 4.3 расширить список и указать её consumer.

### Сохранить инварианты domain-моделей

[ObsidianReviewPlan и ObsidianProposal](../../compadre_assistant/capabilities/obsidian/domain/reviews/entities.py)
сейчас трактуют не-SKIP как известное изменение, а не-ADD как UPDATE.
Простое добавление UNKNOWN всё ещё приводит к ValueError при отсутствии
path/markdown/blob; неизвестный статус с commit SHA тоже отвергается.
Нужна явная ветвь для неисполняемого неизвестного состояния, которая сохраняет
общие инварианты ID/origin/version и не навязывает семантику ADD/UPDATE/APPLIED.
Для известных значений все прежние инварианты остаются. Mapper не должен
затирать path/commit/markdown ради прохождения конструктора. Все операции
записи такой модели должны быть закрыты до побочных эффектов; sentinel UNKNOWN
не записывается поверх исходного нового значения в БД.

Аналогично, UNKNOWN действия vault не должен терять сохранённый replacement
или приводить к его применению. Изменение строковых lifecycle-статусов на enum
затрагивает публичные domain-модели: сделать переход явно, обновить callers и
тесты, не оставлять wrapper для старого API. DTO остаются моделями хранения
со строковыми полями. Общий mapper может жить в своём модуле; ядро не импортирует
Obsidian. Нужные пользовательские ответы сверить с [правилами сообщений](../USER_MESSAGES.md).

Текущий SQL содержит CHECK для proposal action/status и обоих confirmation
status. Для неизвестных значений сначала тестировать DTO/API напрямую;
интеграционный тест использует отдельную синтетическую будущую схему/копию.
Не редактировать `0001_initial_schema.sql` и не ослаблять production CHECK ради
тестов. Проверить, что `UNKNOWN` не становится допустимой командой записи.

## Проверить реализацию и определить предел результата

В 4.4 необходимы следующие проверки, а не только чтение нового кода:

- Расширить [test_migration_runner](../../tests/test_migration_runner.py):
  строгий отказ без разрешения; точная допустимая схема; другой SHA, история,
  пропуск, имя и fingerprint; повреждённый/неполный контракт; повторный и
  параллельный startup; неизменность SQL/journal и данных; `--migrate` не
  использует разрешение. Проверять DDL с тем же журналом, а не только новую
  строку версии. CLI обоих каналов должен завершаться до polling при отказе.

  `test_candidate_failure_after_new_migration_stays_degraded`,
  `test_new_migration_failure_without_history_row_stays_degraded` и
  `test_interrupted_new_migration_stays_degraded_without_history_row`.
  Тесты чистого validator пары не выдавать за готовый production recovery.
- Для неизвестных значений покрыть mapper и реальный consumer: [article](../../tests/test_process_article_url.py),
  [review](../../tests/test_prepare_obsidian_review.py), [proposal repository](../../tests/test_obsidian_proposal_repository.py),
  [confirmation](../../tests/test_obsidian_proposal_confirmation.py), [vault](../../tests/test_vault_repositories.py),
  [vault domain](../../tests/test_vault_domain.py), [GitHub API](../../tests/test_github_app_client.py),
  [GitHub flow](../../tests/test_github_connection.py), [LLM](../../tests/test_openai_obsidian_proposal_generator.py).
  Для identity найти текущие сценарии rebind в `tests/` и проверить отсутствие
  изменения связей, token и status. Обязательны spies на внешние вызовы и
  сравнение сохранённых строк, а не только проверка `enum is UNKNOWN`.
- Локальный полный unittest и автономные smoke выполнять проектным venv по
  AGENTS.md; полный CI подтверждать для точного опубликованного SHA отдельно.
  Нынешние fresh/upgrade/synthetic migration checks сохраняются.

Шаги 4.2–4.4 дают проверяемый базовый кандидат и контракт потребления допуска.
Они не доказывают совместимость с ещё не существующим релизом. Шаг 4.5 отдельно
публикует и устанавливает базовую версию действующим порядком и фиксирует её
реальный SHA/image ID/схему; до него этап 4 не завершён. Этап 5 выдаёт доказательство
конкретной пары, этап 6 доставляет разрешение и реализует безопасный возврат.

## Устранить неоднозначности перед реализацией

В плане нет противоречия с подготовкой базового образа, если «контроллер
допускает только пару» означает подготовку закрытого контракта в 4.2, а
production-выдачу после проверок этапов 5/6. Если понимать эту фразу как уже
работающий автоматический rollback на новую БД в этапе 4, это противоречит
порядку этапов: нынешние миграции рабочей БД и recovery такой гарантии не дают.

Базовый выпуск не обязан включать новую SQL-миграцию. Старый уже опубликованный
строгий образ остаётся строгим; его нельзя «исправить» новым env-флагом.
Точный предыдущий image не заменяется сборкой прежнего SHA. Даже завершение
4.5 делает версию лишь установленной потенциальной целью: подтверждённая
пара с будущей схемой появится позднее. Эти ограничения нужно сохранить
в отчёте 4.4 и не закрывать весь этап по одному зелёному PR.
