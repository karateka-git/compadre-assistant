# План клиентской пробы VK для шага 3.4

Документ задаёт безопасный порядок проверки `messages.send` в личном диалоге
VK. Он дополняет [контрактную сверку](STAGE3_CHANNEL_CONTRACTS.md),
[инвентаризацию адаптера](STAGE3_CHANNEL_INVENTORY.md) и
[порядок передачи polling](STAGE3_HANDOFF.md). Владелец уже разрешил безопасные
синтетические пробы существующих ботов. Этот документ не разрешает управление
клиентом, изменение локального контейнера или работу с VPS.

## Текущее ограничение

На момент проб production polling остановлен; локальные `stage3-probe-vk` и
`stage3-probe-tg` принимают сообщения. Telegram был кратко остановлен во время
исправления локального токена и затем запущен с правильным ботом. Возврат на
VPS владелец отложил до отдельного указания. Не запускать второй обработчик
VK Long Poll параллельно с контейнером; отдельный наблюдатель события только
читал поток и не подтверждал его.

Адаптер `compadre_assistant/presentation/vk/bot.py` вызывает
`messages.send` только с `peer_id`, `message` и `random_id`; параметр `keyboard`
не передаётся. Обработчик принимает только `message_new`; `message_event`
игнорируется, а ответное событие не подтверждается через API. Поэтому
проверенная VK-клавиатура не является поддерживаемым интерфейсом приложения.
Получение события отдельным наблюдателем не доказывает его обработку штатным
адаптером.

## Условия допуска

Использовать только личный диалог владельца с ботом и только синтетические
сообщения из probe. Не использовать рабочие данные, другие диалоги, ссылки,
команды приложения или тексты, способные вызвать Ask, запись в vault, БД,
публикацию, синхронизацию либо внешний запрос. Разрешение на синтетические
пробы и включение настройки VK-возможностей сообщества было дано владельцем.
Настройки не изменять сверх явно согласованного действия.

Текстовую пробу выполнил временный скрипт `data/stage3_vk_messages_probe.py`,
который игнорируется Git и не входит в исходники проекта. Без флага он работает
только как dry-run и выводит число
сообщений и длину каждой части. Отправка требует явного `--send`; peer берётся
только из `VK_PROBE_PEER_ID`, а токен — из `VK_BOT_TOKEN`. Скрипт проверяет,
что peer относится к личному диалогу, и вызывает только `messages.send`.
Код не импортирует application use cases, не передаёт тексты текущему
обработчику и не выполняет команды бота. Он не печатает окружение, URL запроса,
заголовки, traceback с параметрами, token, `peer_id` или сырой ответ VK.
Клавиатуры в этот текстовый probe не входят. Отдельная клиентская проба
клавиатуры описана в фактических результатах ниже. Текущий скрипт проверяет
только сообщения с обычным текстом.

## Последовательность проб

1. **Записать безопасный контекст.** Зафиксировать дату/время, тип клиента и
   его версию, ОС и метку «личный диалог владельца». Не записывать имя, URL
   профиля, peer/user/group ID, токены или переписку. Зафиксировать версию VK
   API (`5.199`) и отдельно отметить любые изменения capability, явно
   согласованные владельцем. Сам probe не должен менять настройки сообщества.
2. **Проверить обычный текст и оформление.** Запустить dry-run во временном
   контейнере с тем же образом, сверить число частей и длины, затем выполнить
   разрешённый `--send` с локальной конфигурацией и адресом личного диалога
   только в памяти процесса. Скрипт отправляет по одному сообщению с
   синтетическими строками: `*жирный*`, `**жирный**`, `_курсив_`, `` `моно` ``,
   `<b>тег</b> & < > " ' \\` и Unicode/emoji. Ссылку пока не отправлять:
   без проверенного способа отключить превью VK может обратиться к внешнему
   адресу. Зафиксировать, что именно показывает клиент: буквальные маркеры,
   стили и переносы. Не трактовать наличие HTML-подобного текста как разметку
   VK; проверку ссылок вынести в отдельную безопасную пробу.
3. **Проверить переносы и списки.** Отправить строки с LF, пустой строкой,
   маркированными символами (`•`, `-`, `1.`) и отступом. Сверить видимые
   границы абзацев, порядок и сохранение символов. Не применять форматирование
   для имитации неподтверждённых списков.
4. **Проверить длину и разбиение.** Отдельный probe должен передать длинный
   синтетический текст через `messages.send` с безопасным пределом 3500,
   сначала один фрагмент ниже порога, затем несколько фрагментов выше порога.
   Добавить emoji и кириллицу рядом с границей, проверить отсутствие потерь,
   дублей и перестановки. Границу VK API не угадывать и не отправлять запросы
   размером в предполагаемый максимум без отдельного согласования. Записать
   число вызовов/фрагментов и результат клиента, но не сохранять текст или ID.
5. **Проверить клавиатуру и событие.** Первый запрос был отклонён при выключенной
   настройке. После её включения по явной просьбе владельца `messages.send`
   успешно создал inline-кнопку, клиент её показал. Read-only наблюдатель
   получил `message_event`; он не обрабатывал и не подтверждал событие, поэтому
   клиент оставался в ожидании. Подробности результата приведены ниже.
6. **Проверить очистку клавиатуры.** Замена на другую клавиатуру отдельно не
   проверялась. Удаление тестовой inline-клавиатуры проверено вызовом
   `messages.edit` с пустой inline-клавиатурой; клиент подтвердил, что кнопка
   исчезла.
7. **Завершить и зафиксировать статус.** Удалить временные файлы probe и
   очищенные диагностические материалы, если они созданы в ignored `data/`.
   Не удалять каталог базы. Передать владельцу короткий результат по каждому
   пункту: подтверждено, не подтверждено или остановлено; отдельно указать
   клиент и ограничения. Статус production/VK контейнера проверяет владелец по
   отдельному порядку передачи polling; этот план не содержит команд запуска
   или остановки.

## Фактические результаты шага 3.4 (25.10.2026)

| Замена клавиатуры | Не проверено | — | Не выполнялась | Тестировалось удаление, а не замена на другую клавиатуру |
| Удаление клавиатуры | Проверено | VK API `v=5.199`, VK клиент | `messages.edit` с пустой inline-клавиатурой успешен; пользователь подтвердил, что кнопка исчезла | Проверен только этот способ очистки |

Все фактические наблюдения выше относятся к 25.10.2026. VK API-проба
отправила пять обычных сообщений; дополнительно отправлены две части отдельной
нумерованной проверки и одно сообщение с кнопкой после включения capability.
Read-only observer не отправлял ack. Личные идентификаторы, токены и тексты
переписки в протокол не включены.

Результаты подтверждают обычную текстовую доставку, отображение inline-кнопки,
получение `message_event` и удаление клавиатуры в проверенном клиенте после
включения capability по явной просьбе владельца. Маркеры жирного, курсива,
моноширинного и HTML-подобные теги в проверенных сообщениях VK остались
буквальными. Штатный адаптер не передаёт `keyboard`, не обрабатывает
`message_event` и не отправляет ack; поэтому кнопки пока нельзя использовать
как интерфейс приложения. Для будущих команд и подтверждений обязателен
текстовый fallback. Отдельно не проверена замена одной клавиатуры другой.
