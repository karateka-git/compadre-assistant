# Протокол проверки Telegram для шага 3.3

Документ задаёт воспроизводимую проверку меню команд, inline-кнопок и вида
сообщений Telegram в личном диалоге с отдельным тестовым ботом. Он дополняет
[план этапа 3](PLAN.md#проверить-каналы-и-согласовать-модель-сообщения),
[инвентаризацию каналов](STAGE3_CHANNEL_INVENTORY.md) и
[сверку контрактов](STAGE3_CHANNEL_CONTRACTS.md). Пока тестовый бот и личный
диалог не подготовлены, сетевые вызовы и клиентские пробы не выполнять.

## Текущее состояние

Протокол составлен 25.10.2026 по материалам текущей задачи. Пользователь
сообщил, что тестовый Telegram-бот и личный диалог с ним пока не подготовлены.
Production-бот не используется. Поэтому ниже описан протокол, а не результат
клиентского теста.

В `requirements.txt` закреплён `aiogram==3.29.1`. Проверка локальной Python
3.12 командой `python -c "import importlib.metadata; print(importlib.metadata.version('aiogram'))"`
завершилась `PackageNotFoundError`: пакет в этой среде не установлен. Подписи
aiogram локально не проверены; установленный runtime проекта также не
инспектировался. Это не тест Telegram API и не клиентская проверка.

## Подготовить изолированную среду

Начинать только после выделения отдельного тестового бота, права менять его
команды, личного чата с ним и проверяемого клиента Telegram. Убедиться, что
токен относится к тестовому боту, а идентификатор чата — к личному диалогу с
ним. Не читать конфигурацию production и не копировать её секреты.

Для проверки SDK можно создать отдельное окружение вне репозитория и поставить
только зафиксированную версию:

```powershell
$probeVenv = Join-Path $env:TEMP 'obs-chatbot-telegram-probe-venv'
py -3.12 -m venv $probeVenv
& "$probeVenv\Scripts\python.exe" -m pip install 'aiogram==3.29.1'
```

После установки проверить версию и доступные сигнатуры без создания `Bot` и
без сетевого вызова:

```powershell
@'
import inspect
from importlib.metadata import version
from aiogram import Bot
from aiogram.methods import SetMyCommands
from aiogram.types import BotCommand, BotCommandScopeChat, InlineKeyboardButton

print("aiogram", version("aiogram"))
for item in (Bot.set_my_commands, Bot.delete_my_commands, Bot.send_message,
             SetMyCommands, BotCommand, BotCommandScopeChat,
             InlineKeyboardButton):
    print(item.__qualname__, inspect.signature(item))
'@ | & "$probeVenv\Scripts\python.exe" -
```

Сохранить вывод версии и сигнатур как локальную проверку SDK. Это подтверждает
только установленный Python API aiogram 3.29.1; наличие метода/поля не
подтверждает принятие запроса сервером и ничего не говорит о виде в клиенте.
Если установка недоступна, оставить проверку SDK неподтверждённой и сверять
вызовы только с документацией версии 3.29.1.

Перед сетевыми пробами получить секрет тестового токена из принятого хранилища
секретов в переменную окружения процесса, а `TELEGRAM_PROBE_CHAT_ID` — из
диалога тестового бота. Не вставлять значение токена в команду, файл,
скриншот, трассировку, документ или Git. Не печатать объект `Bot`, заголовки
HTTP, полный URL запроса или окружение процесса: там может быть токен.

## Выполнить пробы в личном диалоге

Зафиксировать до начала дату и UTC-время, ОС/платформу, имя и версию клиента,
что открыт именно личный диалог с тестовым ботом, а также нейтральную метку
тестового бота и чата. Не записывать токен. Проводить пробы последовательно;
после каждого изменения проверять интерфейс клиента заново, при необходимости
закрывая и открывая меню команд.

Минимальный API-набор для проверки меню и сообщения на aiogram 3.29.1:

```python
import os

from aiogram import Bot
from aiogram.types import (
    BotCommand,
    BotCommandScopeChat,
    InlineKeyboardButton,
    InlineKeyboardMarkup,
)

token = os.environ["TELEGRAM_PROBE_BOT_TOKEN"]
chat_id = int(os.environ["TELEGRAM_PROBE_CHAT_ID"])
scope = BotCommandScopeChat(chat_id=chat_id)
bot = Bot(token=token)

# Для теста команды должны быть безопасными и не запускать операции проекта.
commands = [
    BotCommand(command="probe_one", description="Проба: первый пункт"),
    BotCommand(command="probe_two", description="Проба: второй пункт"),
]
await bot.set_my_commands(commands, scope=scope)

# Удаление только этого chat scope возвращает видимость более общего scope.
await bot.delete_my_commands(scope=scope)

keyboard = InlineKeyboardMarkup(inline_keyboard=[
    [InlineKeyboardButton(text="Тестовая кнопка", callback_data="probe:v1")],
])
await bot.send_message(
    chat_id=chat_id,
    text="Проба кнопки. Текстовый путь: /probe_one",
    reply_markup=keyboard,
)
```

Фрагмент предполагает запуск внутри `async`-функции и намеренно не содержит
секретов или команды запуска. Выполнять его разрешено только с тестовыми
переменными окружения и тестовым `chat_id`. Для проверки нажатия приложение
должно принять `CallbackQuery` и вызвать `await callback.answer()`; записать
тип события и только несекретную пробную нагрузку `probe:v1`. Не логировать
объект запроса целиком. После нажатия отдельно проверить текстовую команду
`/probe_one`, чтобы кнопка не была единственным путём.

### Матрица проб и ожидаемых наблюдений

| Проба | Действие | Что наблюдать и сохранить |
| --- | --- | --- |
| Исходный список | Вызвать `set_my_commands` с двумя пробными командами в `BotCommandScopeChat(chat_id=...)`. Открыть меню бота и поле ввода, набрать `/`. | Успешный ответ API и scope; видны ли оба пункта в меню и подсказках ввода. Снять экран клиента с видимым контекстом тестового диалога и без приватных данных. |
| Замена списка | Заменить команды, например оставить `probe_two` и добавить `probe_three`; снова открыть меню и набрать `/`. | Ответ API; появились ли новые и исчезли ли старые пункты, сразу или после повторного открытия. Записать задержку и действия обновления клиента. |
| Очистка chat scope | Вызвать `delete_my_commands(scope=BotCommandScopeChat(chat_id=...))`; проверить меню и ввод `/`. | Успешный ответ API и какой более общий список стал виден (либо что меню пусто). Не считать удаление эквивалентом отключения всех команд: применяется общий scope по правилам Bot API. |
| Inline callback | Отправить сообщение с одной кнопкой `callback_data="probe:v1"`; нажать её. | Внешний вид и расположение кнопки; получил ли изолированный обработчик `CallbackQuery`; прекратился ли индикатор ожидания после `answer()`. Проверить, что обычную команду из текста можно отправить вручную. |
| Устаревшая кнопка | После первого сообщения удалить/изменить его клавиатуру через `edit_message_reply_markup`, затем повторить нажатие, если клиент позволяет. Отдельно нажать старую кнопку до удаления, если сообщение ещё доступно. | Видна ли старая кнопка, какое событие пришло, можно ли обнаружить устаревшее действие. Не выполнять реальное действие: тестовый обработчик только фиксирует callback и отвечает на него. |
| Обычный текст и спецсимволы | Отправить отдельно plain text и HTML-вариант с жирным/моноширинным фрагментом, URL, переносами, списком и образцами `& < >`, кавычек, обратного слеша, emoji. Динамические образцы должны быть искусственными. | Для каждого сообщения записать режим/параметры отправки и вид текста в клиенте: переносы, стили, ссылка, буквальное/ошибочное отображение спецсимволов. При HTML сравнить экранированные значения с буквальным текстом без разметки. |
| Команда подтверждения | Отправить безопасный искусственный текст с точной многоаргументной командой, например `/confirm demo operation 17 2 yes`, и короткой кнопкой. | Сверить посимвольно показанную команду и скопированный/введённый текст. Не связывать пробу с реальным ожиданием или операцией. Проверить, что текстовый путь самодостаточен. |
| Длинный ответ | Отправить обычный текст и выбранный форматированный текст в нескольких сообщениях чуть ниже и выше внутреннего порога 3900 символов; отдельно проверить разрыв около переноса строки и длинную строку без пробелов. | Сохранить число, порядок и длину частей; сравнить восстановленный текст с исходным и отметить пропуски/дубли, сломанные теги/entities и вид в клиенте. Это тест наблюдаемого поведения, не доказательство серверного лимита. |

Если `set_my_commands`, `delete_my_commands`, `send_message` или редактирование
клавиатуры возвращают ошибку, сохранить код и безопасное описание ошибки,
scope и время. Не повторять неизвестный запрос с другим ботом или production
для «сравнения». Сетевой повтор допустим лишь для той же тестовой конфигурации
после выяснения причины; пробная команда не должна запускать бизнес-операцию.

## Зафиксировать доказательства безопасно

Для каждого результата отметить одно из состояний: **подтверждено в API**,
**наблюдалось в клиенте**, **не наблюдалось** или **не проверено**. API-ответ
свидетельствует о принятии запроса, но не о том, что клиент обновил интерфейс.

Сохранять в материалах задачи:

- дату и время, версию aiogram при локальной проверке, имя/версию/платформу
  Telegram-клиента и метки тестового бота/личного чата;
- точные несекретные поля вызова (`scope`, список пробных команд, `chat_id`
  можно заменить стабильной меткой), статус/ограниченно очищенный ответ API;
- снимки меню, подсказок, сообщения и кнопки до/после изменения; перед
  сохранением убрать имена, аватары, ID, уведомления и любой секрет;
- для кнопки — тип события, время и только искусственное значение payload;
- длину и хеш исходного образца, длины/порядок частей и наблюдаемое
  отображение; исходный приватный текст не прикладывать.

Токен, заголовки авторизации, полный URL Bot API, необработанные HTTP-тела,
полные объекты update/callback и дамп окружения не сохранять. Для безопасного
повторения достаточно названий проб, искусственных текстов и команды
воспроизведения с переменными окружения. Если артефакт случайно содержит
секрет, удалить его из доступных материалов и заменить очищенной копией;
не включать исходный файл в коммит.

## Критерии завершения и открытые пункты

Шаг 3.3 можно считать подтверждённым для конкретной платформы/версии клиента,
когда получены раздельные API- и клиентские свидетельства для списка команд,
замены и очистки scope; зафиксированы появление списка в меню и при `/`;
нажатие inline-кнопки породило ожидаемый callback, обработчик ответил на него,
а устаревшее действие наблюдаемо; обычный текстовый путь, точная команда,
спецсимволы, переносы и выбранное форматирование проверены; несколько частей
дошли в нужном порядке и сверены с исходным искусственным текстом. В выводе
назвать платформу и версию клиента: результат нельзя автоматически переносить
на другие клиенты.

Пока не подготовлены тестовый бот, право изменения его меню, личный диалог и
клиент для наблюдений, остаются заблокированы доступом:

- вызовы Bot API и подтверждение успешной/ошибочной публикации меню;
- наблюдение меню, автоподсказок, обновления и fallback-scope в клиенте;
- фактический вид inline-кнопки, доставка `CallbackQuery`, поведение после
  удаления/изменения клавиатуры;
- вид обычного/форматированного текста, спецсимволов, точной команды,
  переносов и нескольких длинных частей.

Установка aiogram в отдельное окружение может подтвердить только локальные
сигнатуры Python API и не снимает ни один из этих блокеров. По состоянию на
25.10.2026 клиентские результаты для шага 3.3 отсутствуют; этот протокол сам
по себе не завершает шаг 3.3 или этап 3.
