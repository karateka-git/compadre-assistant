# Протокол проверки Telegram для шага 3.3

Документ задаёт безопасные пробы Telegram в личном диалоге с существующим
ботом во время временной передачи polling локальной сборке. Отдельный тестовый
бот не создаётся. Последовательность переключения и возврата приведена в
[runbook шага 3.3](STAGE3_HANDOFF.md); статический снимок реализации — в
[инвентаризации каналов](STAGE3_CHANNEL_INVENTORY.md), общие решения — в
[плане этапа 3](PLAN.md#проверить-каналы-и-согласовать-модель-сообщения).

## Текущее состояние и историческая запись

Протокол впервые составлен 25.10.2026. На эту дату пользователь сообщал, что
отдельный Telegram test bot и личный диалог не подготовлены; production-бот
тогда не использовался. Это исторический факт, а не текущее требование.
Позднее принято решение проверять существующих Telegram/VK-ботов, временно
переключая polling на локальную сборку. Пробы ещё не выполнены, и этот документ
не свидетельствует о клиентском поведении.

В `requirements.txt` закреплён `aiogram==3.29.1`. Локальная проверка Python
3.12 завершилась `PackageNotFoundError`; SDK-сигнатуры не подтверждены в этой
среде. Это не тест Bot API и не клиентская проверка.

## Подготовка

1. Прочитать [runbook](STAGE3_HANDOFF.md) целиком и выполнить его read-only
   preflight. Не начинать сетевые пробы, если состояние production, локальный
   образ, отдельная development-БД или локальная конфигурация не подтверждены.
2. Использовать только credentials, уже находящиеся на этой машине. Не читать,
   копировать, передавать или показывать секреты с VPS. Не выводить `.env`,
   токен, полный URL Bot API, заголовки, HTTP-тела или дамп окружения.
3. Работать только в личном диалоге с существующим ботом. Зафиксировать
   нейтральную метку диалога, дату/UTC-время, платформу и версию клиента;
   личные ID и содержимое диалога не включать в материалы.
4. Перед каждым сообщением подтвердить по коду, что команда или искусственный
   текст не меняет настройки, профиль, vault, базу, публикации и иные данные,
   не инициирует синхронизацию и не вызывает внешние интеграции. Если
   безвредность нельзя подтвердить — пробу не отправлять.

## Пробы обычного поведения приложения

Текущий Telegram-адаптер отправляет обычный текст, использует внутренний порог
3900 символов и не задаёт `parse_mode` или клавиатуру. Статический просмотр не
обнаружил `set_my_commands`, inline-кнопок или callback handlers. Поэтому
проверка существующего меню и наблюдение за ответами приложения не означают,
что приложение управляет меню или поддерживает кнопки.

В личном диалоге можно проверить только команды, для которых отдельно
подтверждена read-only семантика в текущем коде (например, справочная команда,
если её обработчик не запускает запись или внешние операции). Для проверки
доставки/переносов допустим короткий искусственный обычный текст только если
путь его обработки не вызывает Ask/LLM, ссылочный pipeline или иной внешний
вызов. Не использовать URL, реальные команды записи/синхронизации, имена,
содержимое заметок, приватные данные или пользовательские тексты.

Наблюдать текущее меню, подсказки ввода `/` и ответы на разрешённые безопасные
сообщения; записать, что именно было видно. Если проверяется изменение списка,
сохранить исходный набор chat scope, временно применить искусственный набор и
обязательно восстановить исходный набор с проверкой до завершения окна. Не
нажимать существующие кнопки, если они могут запускать действие.

## Отдельные синтетические пробы для неподдерживаемых элементов

Текущий адаптер не публикует меню команд, не отправляет inline-кнопки и не
обрабатывает callback. UI/API-проверка таких элементов, если она понадобится,
является отдельным экспериментом, а не клиентской проверкой возможностей
приложения. Для неё нужен временный изолированный probe, который:

- принимает callback только в личном диалоге и лишь записывает тип события и
  искусственный payload, например `probe:v1`, после чего отвечает на callback;
- не вызывает use case приложения, не меняет command scope и не выполняет
  запись, запросы к интеграциям или бизнес-операции;
- запускается и удаляется отдельно от локальной сборки и не попадает в
  production или постоянный код без отдельного изменения плана.

Для проверки отображения `setMyCommands` использовать только chat scope
личного диалога. До изменения сохранить ответ API для этого scope и список,
видимый в клиенте. Задать искусственные команды, проверить меню и подсказки,
затем восстановить исходное состояние: вернуть сохранённый список либо удалить
временный chat override, если scoped список отсутствовал. Если исходный вид
меню был пустым, а удаление override показывает унаследованные команды,
восстановить пустой список в chat scope. Проверить API и клиентом, что прежний
вид вернулся; если это не подтверждено, остановить пробы и продолжать
восстановление. Изменение
global/default scope запрещено. Пробы кнопки, обновления клавиатуры и
устаревшего callback выполнять отдельным временным probe-кодом; они не
подтверждают поддержку со стороны адаптера.

## Фиксация наблюдений

Для каждой пробы записать одно состояние: **подтверждено в API**,
**наблюдалось в клиенте**, **не наблюдалось** или **не проверено**. API-ответ
не доказывает, что клиент обновил интерфейс. Сохранять только дату/время,
платформу и версию клиента, нейтральную метку личного диалога, тип пробы,
искусственный payload и очищенный статус/результат. Скриншоты перед
сохранением очистить от имён, ID, аватаров, уведомлений и приватного текста.

Не сохранять токен, заголовки авторизации, полный Bot API URL, необработанные
HTTP-тела, полный update/callback, вывод `.env` или реальные тексты. Для
проверки длинных ответов использовать искусственный текст; записывать длины и
порядок частей и сверять восстановленное содержимое локально, не прикладывая
исходник к рабочим материалам.

## Критерии и ограничения результата

Для текущей реализации можно подтвердить только наблюдаемые клиентские ответы
и вид обычного текста на конкретной платформе/версии клиента. Публикация меню,
замена/очистка scope, inline-кнопки, callback, редактирование клавиатуры и
оформление через `parse_mode` остаются **не проверены** до появления
реализации либо отдельного изолированного probe. Синтетический API/UI probe не
подтверждает, что приложение поддерживает соответствующий сценарий.

Шаг 3.3 и этап 3 остаются открытыми до выполнения проб и подтверждения возврата
polling production-бота. По состоянию на создание этой редакции результат
клиентского теста отсутствует.
