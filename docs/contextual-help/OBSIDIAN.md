# Obsidian: сценарии и тексты

Каждая схема сопровождается текущими текстами ответов и целевой редакцией. Метки на схеме совпадают с ID в таблице ниже. Общий путь сообщения показан в [маршруте](RESPONSE_MAP.md); новые целевые сценарии выделены отдельно.

## Вход в Obsidian и сообщение внутри режима

```mermaid
flowchart TD
    A[Пользователь: obsidian] --> B[О1: инструкция режима]
    B --> C{Vault выбран?}
    C -->|нет| D[О2: подключи vault]
    C -->|да| E[О3: текущий vault]
    B --> F{Есть ожидающие действия?}
    F -->|предложение| G[О4: ожидание и команды решения]
    F -->|замена или отключение| H[О5: ожидание конфигурации]
    F -->|GitHub-авторизация| I[О6: повтор инструкции или другой канал]
    B --> J{Провайдеры настроены?}
    J -->|GitHub или LLM нет| K[О7: функция временно недоступна]
    L[Текст или команда в режиме] --> M{Распознано?}
    M -->|неизвестная команда| N[О8: неизвестная команда]
    M -->|нет ожидающего подтверждения| O[О9: нет действия]
    M -->|несколько ожиданий| P[О10: нужна адресная команда]
    M -->|предметное действие| Q[GitHub, vault, статьи и предложения]
```

О1–О7 собираются в один ответ; это не семь отдельных сообщений.

Текущий `/help` добавляет следующие предметные строки даже вне режима:
«`/vault_status` — показать состояние локальной копии vault»,
«`/vault_sync` — проверить GitHub и синхронизировать vault»,
«`/vault_disconnect` — отключить vault после подтверждения»,
«`/reanalyze <article_id>` — выполнить анализ статьи повторно».
Заголовки: «Obsidian vault» и «Статьи». Затем следуют инструкции:
«Войди через `/obsidian [текст или URL]`. Подключение vault выполняется внутри
этого режима», «После настройки пришли HTTP/HTTPS-ссылку — сохранить и
проанализировать статью» и «Ответы `да` и `нет` выбирают единственное ожидание
этого чата; при нескольких используй адресную команду `/confirm`.»

В обработчике также принимаются `yes`, `no`, `y` и `n` без учёта регистра;
они выбирают единственное ожидающее действие исходного чата.

## GitHub-авторизация

```mermaid
flowchart TD
    A[Ссылка на GitHub repository] --> B{Нужна авторизация?}
    B -->|нет| C[Выбор vault]
    B -->|да| D{Авторизация уже идёт?}
    D -->|запускается| E[Г1: подождать]
    D -->|код уже выдан здесь| F[Г2: повтор инструкции и код]
    D -->|идёт в другом канале| G[Г3: завершить там]
    D -->|новая| H[Г4: страница и одноразовый код]
    H --> I{Решение GitHub}
    I -->|отказ| J[Г5: авторизация отклонена]
    I -->|истёк код| K[Г6: запросить новый]
    I -->|сбой| L[Г7: авторизация не удалась]
    I -->|успех| M[Г8: проверка repository и первая синхронизация]
    M --> N{GitHub App имеет права?}
    N -->|нет| O[Г9: дать права App и повторить ссылку]
    N -->|да| C
```

## Подключение и замена vault

```mermaid
flowchart TD
    A[Ссылка на GitHub repository и путь] --> B{URL и путь допустимы?}
    B -->|неверная форма| C[Х1: пример команды]
    B -->|путь не найден| D[Х2: проверить путь]
    B -->|репозиторий недоступен| E[Х3: проверить права GitHub App]
    B -->|другая ошибка| F[Х4: повторить проверку позже]
    B -->|да| G{Уже выбран vault?}
    G -->|нет| H[Х5: vault подключён и начата синхронизация]
    G -->|тот же| I[Х6: уже подключён]
    G -->|другой| J[Х7: последствия замены и запрос решения]
    J --> K{Ответ в исходном чате}
    K -->|нет| L[Х8: замена отменена]
    K -->|да| M[Х9: новый vault выбран и синхронизируется]
    K -->|нет ожидания или устарело| N[Х10: повторить запрос]
```

После Х5 и Х9 может добавляться успех или ошибка первой синхронизации;
подключение при этом остаётся сохранённым, если форматтер прямо сообщает это.

## Статус, синхронизация и отключение vault

```mermaid
flowchart TD
    A[Пользователь: github_status] --> B{Vault подключён?}

    G -->|нет| H[Н4: отменено без записи]
    G -->|да для skip| I[Н5: завершено без записи]
    G -->|да для add или update| J{Можно записать?}
    J -->|vault изменился| K[Н6: конфликт, новое предложение]
    J -->|vault занят| L[Н7: повторить решение позже]
    J -->|ошибка GitHub| M[Н8: предложение сохранено, повторить позже]
    J -->|успех| N[Н9: путь и commit]
    N -->|index не обновился| O[Н10: синхронизировать индекс позже]
    P[Повторная ссылка на рассмотренную статью] --> Q[Н11: сохранённый результат]
    R[Адресная команда неверна или устарела] --> S[Н12: причина и актуальная команда]
```

Адресные команды показывают ID и версию ожидания. Простые `да`, `нет`, `yes`,
`no`, `y` и `n` принимаются только при одном ожидании исходного чата.

Для простых решений Obsidian принимаются `да`, `нет`, `yes`, `no`, `y` и `n`
без учёта регистра только при единственном ожидающем действии Obsidian в том
же исходном чате.
Любое адресное решение сверяется с исходными каналом и чатом, статусом, ID и
версией. Предложения статьи не имеют срока ожидания подтверждения; пять минут
в коде относятся к lease выполнения записи. Замена и отключение vault имеют
срок ожидания по умолчанию 10 минут. Если ожидание истекло, получить новое
через исходное действие. Фоновая обработка статьи и GitHub возвращает итог в
тот же сохранённый адрес.
