# Проверить текстовый путь этапа 6

Запись фиксирует автоматическую проверку шага 6.9 на 27 октября 2026 года.
Требования взяты из [таблицы текстового пути](COMMAND_HINTS.md#сквозная-проверка-текстового-пути-решения-для-этапов-34)
и новых веток [ядра](CORE.md), [Ask](ASK.md), [Obsidian](OBSIDIAN.md).
Следующий шаг разработки — меню и кнопки этапа 7; фактический вид сообщений
и действий в клиентах проверяется отдельно на этапе 8 [плана](PLAN.md).

## Воспроизвести проверку

Запускать из корня worktree через Python проектного `.venv`. В этой проверке
использован `C:/Users/compadre/Documents/obsChatBot/.venv/Scripts/python.exe`:

```powershell
& C:/Users/compadre/Documents/obsChatBot/.venv/Scripts/python.exe -m unittest discover -s tests -p test_text_command_sequences.py -v
& C:/Users/compadre/Documents/obsChatBot/.venv/Scripts/python.exe -m unittest discover -s tests
```

Результат: все 7 новых последовательностей прошли; полный прогон — 869 тестов,
`OK (skipped=2)`, 63,707 секунды. `git diff --check` не выявил ошибок пробелов.
Первый полный прогон выявил одно старое текстовое ожидание К10б в
`test_operation_scopes.py`; после обновления на целевую формулировку полный
прогон повторён успешно.

Новый [набор последовательностей](../../tests/test_text_command_sequences.py)
передаёт каждое сообщение штатному `ChannelMessageProcessor`. Каждый вызов
открывает отдельный core scope; профиль, identity, выбор возможностей, режим,
статья и анализ хранятся в настоящей временной SQLite. Ask и article pipeline
используют подменные сетевые сервисы; manager хранилища заметок — тестовый.
Кнопки, callbacks и реальные Telegram/VK в этом наборе не используются.

## Сопоставить сценарии с доказательствами

| Путь | Проверенный результат |
| --- | --- |
| `/register` → неверное имя → `/help` → `/cancel`; повтор и перезапуск | До принятия имени профиль не создан. Повторная регистрация готового профиля не создаёт дубль; обычный текст без ожидания не меняет имя. |
| `/link_code` → `/link` → неверный и правильный код; прямой `/link <код>` | Реальная identity связывает каналы; оба пути выполняются через процессор. |
| `/name`, `/enable`, `/disable` с аргументом и следующим сообщением | Изменение сохраняется и видно из связанного канала. Информационные команды сохраняют ввод; неизвестная slash-команда прекращает его. |
| URL → повтор URL → `/ask` → вопрос → `/reanalyze` → ID; прямые Ask/reanalyze | Повтор URL использует сохранённый анализ. Ask не меняет режим. Повторный анализ обновляет статью и анализ; неверный или недоступный ID можно исправить. Вне Obsidian ID не запускает анализ. |
| TTL, `/cancel`, перезапуск, соседний канал и отключение | Позднее значение не выполняется; ответ даёт команду для нового ввода. Перезапуск теряет временный ввод и сохраняет режим. Отмена изолирована, отключение в связанном канале запрещает ожидаемое действие. |
| Код другого профиля → конфликт → `/confirm` → адресный выбор | Полный и частичный снимки не выполняют перенос; известные команды сохраняются при неполноте. Короткое «да» не подтверждает identity. Чужой чат и повтор уже выполненной команды не переносят профиль. |
| `/github_disconnect` → `/confirm` → `нет`; повтор → адресная команда | Просмотр и `/cancel` не решают предметное ожидание. Короткий отказ сохраняет хранилище; адресное решение вне режима не исполняется. |

Дополнительные границы проверены существующими наборами, включёнными в полный
прогон: `test_pending_input.py`, `test_core_pending_input.py`,
`test_capability_pending_input.py`, `test_confirmation_snapshot.py`,
`test_contextual_help.py`. Они проверяют исходный TTL после неверного значения,
смену профиля/режима/серверной доступности между запросом и ответом, изоляцию
чатов одного канала, конкуренцию, полный пустой и недоступный снимки,
неоднозначный короткий ответ, срок/версию/состояние реальных SQLite-подтверждений.
В частности, предметный proposal без TTL не получает десятиминутный срок ввода.

## Учесть исправления и ограничения

При сверке исправлены тексты ЦО1/ЦО2 (`/cancel`), ЦВ2 (истечение с точной
командой повтора), В2 (пошаговый выбор из `/capabilities`) и К10б (устаревший
перенос identity). Команду повтора задаёт владелец через нейтральный контракт
ожидания; ядро не разбирает виды ввода возможностей.

Проверка маршрута не выявила старого пути регистрации без имени, неявного
переименования обычным текстом или обхода активного режима адресной командой
Obsidian. Существующие предметные тесты остаются частью полного прогона.

Автоматические проверки не доказывают оформление в клиентах Telegram/VK,
работу реальной сети, публикацию меню или доставку событий кнопок. Меню и
кнопки остаются этапом 7; клиентская проверка текста, длинных ответов,
экранирования и устаревших действий — этапом 8. Production не затрагивался.
