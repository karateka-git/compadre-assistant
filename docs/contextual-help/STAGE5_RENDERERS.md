# Проверить чистые renderer — шаг 5.2

На 25.10.2026 реализован независимый от отправки шаг 5.2 из [плана](PLAN.md).
Этот отчёт фиксирует проверяемые гарантии сериализации и ограничения перед
подключением к API на шаге 5.4. Исходный контракт описан в
[проекте представления](FORMATTING_DESIGN.md), результаты API-проб — в
[отчёте этапа 3](STAGE3_FORMAT_MENU_FOLLOWUP.md).

## Использовать готовые части

`render_telegram_content(content, actions, limit=3900)` возвращает tuple
`TelegramChunk(text, parse_mode="HTML")`. Все значения экранируются через
HTML escaping, EMPHASIS получает `b`, CODE — `code`. Каждая часть закрывает
свои теги. Лимит учитывает сериализованные entities и теги в UTF-16 units,
то есть выбран консервативно относительно видимого текста.

`render_vk_content(content, actions, limit=3500)` возвращает tuple
`VkChunk(text, format_data)`. `format_data` — готовая JSON-строка либо `None`;
version равна строке `"1"`, EMPHASIS задаёт диапазоны `bold`, CODE выводится
обычным текстом. Диапазоны вычисляются заново для каждой части. Текстовый
лимит также считается в UTF-16 units, а разрез не разрывает Python code point.

Общий splitter находится внутри `presentation`, не зависит от SDK и
предметных правил. Он сохраняет целый блок, затем целый span, когда они
вмещаются в часть. Слишком длинный span делится сначала по пробельным
границам, затем длинный токен — по безопасным границам составных символов.
Все исходные пробелы и LF
сохраняются. Команда в отдельном CODE-span, URL и путь остаются целиком,
если вмещаются в лимит; слишком длинное значение разделяется без изменения
символов. Внутри длинного токена сохраняются combining marks, variation
selectors, emoji modifiers, ZWJ-последовательности, пары regional indicators
и CRLF. Если такой составной символ вместе с оформлением не вмещается в
лимит, renderer вызывает `ValueError`, не возвращая повреждённые части.
Это ограниченный алгоритм безопасных границ, не полная реализация UAX #29.
Если cluster пересекает разные spans и попадает на границу частей,
renderer перепаковывает ответ по атомарным clusters с сохранением стилей.
В этом редком случае приоритет целостности символов выше сохранения целого
span или команды в одной части.

Пустые структурные блоки пропускаются; полностью пустой ответ возвращает
пустой tuple. Неположительный лимит или невозможность вместить один символ
с его оформлением вызывает `ValueError`.

## Учитывать ограничение VK до живой проверки

Проба этапа 3 подтвердила bold для API 5.199, но не единицы offsets после
emoji. Поэтому для части с non-BMP символами, combining marks или Unicode
format-символами renderer заранее возвращает `format_data=None`. Остальные
части того же ответа сохраняют bold. Это выбор перед отправкой, а не
повторная отправка после ошибки API.

Для обычной кириллицы позиции code points и UTF-16 совпадают. Тесты проверяют
точное попадание каждого диапазона в выделенный текст и сброс offsets между
частями. Для emoji тестируется сохранение данных и безопасный plain fallback;
это не доказательство корректности предполагаемых API offsets. Перед снятием
ограничения нужна отдельная живая проба смешанного текста: emoji до и внутри
выделения, combining/ZWJ, повторное выделение после границы части. Зафиксировать
версию API, наблюдённый клиент и единицы offsets, затем изменить renderer и тесты.

## Проверить локальные гарантии

Профильный прогон: `python -m unittest tests.test_message_rendering
tests.test_message_content tests.test_telegram_bot tests.test_vk_bot` — 42 теста,
успешно. Использован существующий `.venv` основной рабочей папки; системный
Python не содержит aiogram и не подходит для Telegram-тестов.

Проверены порядок блоков и действий, полные команды и URL, буквальные
HTML/Markdown/diff, Unicode и emoji, экранирование всех стилей и подписи
действия, закрытые теги, длина частей, отсутствие потери/дублирования символов,
диапазоны VK и локальный fallback. Отправка, IncomingResponse, callers,
production и версия API не менялись. Фактическая доставка и вид в клиентах
остаются проверками шагов 5.4 и 8.
