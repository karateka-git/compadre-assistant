# Контракты Telegram и VK для этапа 3.2

Этот документ фиксирует сверку официальных контрактов отправки сообщений,
оформления, команд, кнопок и лимитов для [этапа 3](PLAN.md#проверить-каналы-и-согласовать-модель-сообщения).
Он дополняет [исходную инвентаризацию каналов](STAGE3_CHANNEL_INVENTORY.md)
и [проект оформления](FORMATTING_DESIGN.md). Сверка выполнена 25.10.2026;
ссылки ниже ведут на первичные спецификации Telegram, документацию aiogram
3.29.1 и официальный репозиторий схем VKCOM.

Здесь разделены **факт спецификации**, **вывод из спецификации** и **не
проверено**. Наличие поля в API не подтверждает его вывод в конкретной версии
клиента. Клиентские диалоги, API-вызовы, боты и события в этом шаге не
проверялись.

## Telegram Bot API и aiogram 3.29.1

| Тема | Подтверждено официальным контрактом | Вывод для проекта | Не проверено в клиенте |
| --- | --- | --- | --- |
| Отправка и размер | `sendMessage` принимает `text`, `parse_mode`, `entities` и `reply_markup`. Текст ограничен 1–4096 символами **после разбора entities**. Метод возвращает отправленный `Message` при обычном Bot API запросе. | Текущий порог адаптера 3900 символов оставляет запас относительно контракта, но это внутреннее решение; его корректность при разбиении HTML или entities ещё нужно подтвердить. Деление должно учитывать длину именно после разбора форматирования. | Фактическая доставка нескольких частей, клиентский показ переносов и применение лимита разными клиентами.
| Оформление | Обычный `sendMessage` поддерживает `parse_mode` или `entities`. Для HTML разрешены перечисленные спецификацией теги; символы `<`, `>` и `&`, не являющиеся тегами/сущностями, должны быть заменены на `&lt;`, `&gt;`, `&amp;`. Внутри текстовых значений нельзя вкладывать произвольный HTML. | Эскиз с HTML в [проекте оформления](FORMATTING_DESIGN.md) опирается на доступный механизм. Каждый внешний или динамический span следует экранировать отдельно до оборачивания поддерживаемыми тегами. Дословный Markdown/diff/вывод LLM — данные, а не разметка. | Как выбранное форматирование выглядит в целевых клиентах; цель шага 3.3/3.4.
| Команды | `setMyCommands` задаёт список команд для scope и, опционально, языка; максимум 100 команд. Доступны scopes, включая `BotCommandScopeChat`. Для личного диалога Bot API выбирает первый заданный список в порядке: чат + язык, чат, все private chats + язык, все private chats, default + язык, default. `deleteMyCommands` удаляет набор данного scope/языка, после чего пользователю показывается команда из более общего scope. `BotCommand.command` имеет 1–32 символа из `a-z`, `0-9`, `_`; `description` — 1–256 символов. | В меню конкретного диалога можно задавать scope чата; при обновлении/очистке нужно учитывать наследование от более общего scope. Вызов `bot.set_my_commands(...)` и типы scope доступны в aiogram 3.29.1. | Реакция Telegram-клиентов на смену scope/набора, актуальность подсказок после ввода `/`, локализация и задержка обновления интерфейса.
| Inline-кнопки | `InlineKeyboardMarkup` содержит массив строк кнопок и крепится к сообщению. Для `InlineKeyboardButton` требуется ровно один тип действия; `callback_data` имеет размер 1–64 **байта**. Нажатие создаёт `CallbackQuery`; бот должен вызвать `answerCallbackQuery`, даже без текста, иначе клиент продолжает показывать индикатор ожидания. Клавиатуру можно изменить/убрать методами редактирования сообщения и `reply_markup`. | Кнопка может передавать непрозрачный короткий идентификатор действия, а не полную длинную команду. | Команды в сообщении | Текст команды в сообщении не равен объекту меню: сам `setMyCommands` лишь публикует список, а обычная обработка сообщения остаётся обязанностью приложения. | Список команд и обработчик должны согласованно поддерживать текстовый способ выполнения; меню не является контролем доступа. | Как клиенты показывают «Меню» и автоподсказку при вводе `/` после обновления.

## VK API `messages.send`, версия 5.199

Страница официальной документации метода: [`messages.send` в VK API](https://dev.vk.com/method/messages.send).

Адаптер проекта передаёт `peer_id`, `message`, `random_id` и добавляет
`v=5.199`; схема запроса установлена по
[инвентаризации реализации](STAGE3_CHANNEL_INVENTORY.md). Для сверки формы
метода использован официальный репозиторий [VKCOM/vk-api-schema: методы
сообщений](https://github.com/VKCOM/vk-api-schema/blob/master/messages/methods.json),
а формы объектов сообщений и Callback API —
[объекты сообщений](https://github.com/VKCOM/vk-api-schema/blob/master/messages/objects.json)
и [объекты Callback API](https://github.com/VKCOM/vk-api-schema/blob/master/callback/objects.json).
Просмотренная схема VKCOM указывает версию API `5.199`. Ссылки ведут на
изменяемую ветку `master`, а не на неизменный снимок схемы; поэтому сама ссылка
не доказывает, что содержимое совпадает с конкретной ревизией сервера или
клиента.

| Тема | Подтверждено схемой/контрактом VK | Вывод для проекта | Не проверено / ограничение доказательства |
| --- | --- | --- | --- |
| Отправка | Схема метода содержит строковые параметры `message` и `keyboard`; `keyboard` передаётся JSON-строкой. Для `messages.send` также описаны peer/user/chat адресация, `random_id` и параметр версии API. Объект сообщения может содержать `keyboard`. | Клавиатуру технически можно присоединить к сообщению тем же методом, что и текст, если поле поддерживается используемой версией метода и корректно сериализовано. | URL ветки `master` не фиксирует снимок конкретной ревизии схемы; фактический доступный тип токена и права конкретного сообщества.
| Форматирование | В контракте `messages.send` текст передаётся как `message`; просмотренная схема не задаёт параметр `parse_mode`, HTML или Markdown entities для текста сообщения. | Нельзя проектировать Telegram-подобный `parse_mode` для VK на основании этой схемы. Обычный текст является доказуемым совместимым вариантом. Отсутствие параметра в схеме — основание не обещать форматирование, но не универсальное доказательство невозможности иных/клиентских механизмов. | Жирный и моноширинный текст, ссылки, автопревью, обработка HTML-подобных символов и правила экранирования в личном диалоге выбранного клиента.
| Кнопки и callback | Схема сообщений описывает поле клавиатуры у сообщения; схема Callback API содержит `message_event` с `user_id`, `peer_id`, `event_id` и `payload` (и необязательный `conversation_message_id`). Это структурно отличается от обычного `message_new`. | Чтобы callback-кнопки работали, адаптеру нужен приём соответствующего события и разбор payload; текущий инвентаризованный адаптер этого не реализует. Для простого текстового сценария нужна команда/значение, которое можно напечатать вручную. | Полная действующая грамматика кнопок (типы, цвета, флаги, лимиты клавиатуры), настройки подписки на `message_event`, подтверждение события и реальные поля именно для Long Poll, который использует проект.
| Поведение клавиатуры | В схеме `messages.send` есть поле `keyboard`, тип — сериализуемая строка; это позволяет передать описание клавиатуры. | Нельзя выводить расположение, постоянность, одноразовость или скрытие клавиатуры только из наличия параметра. | Где именно клавиатура видна в клиенте, меняет ли она поле ввода, что делают «пустая» клавиатура/сброс, сохранение или удаление предыдущего варианта, влияние `one_time` и `inline`.
| Длина и лимиты | Просмотренная схема `messages.send` не устанавливает числовое ограничение длины `message` и размеров/числа кнопок клавиатуры. В схеме есть другие ограничения на сообщения в иных методах, но переносить их на `messages.send` нельзя. | Значение 3500 символов в адаптере — консервативный внутренний порог, но соответствие лимиту VK не доказано этой сверкой. Деление на части сохраняет порядок только на уровне последовательных API-вызовов; целостность отображения надо проверить. | Точный серверный предел текста/клавиатуры на `v=5.199`, единица подсчёта (символы, байты или иное), поведение на границе и порядок доставки частей в клиенте.
| Экранирование | В схеме нет заявленного языка разметки `message` и специальных правил экранирования для строкового текста. JSON-сериализация клавиатуры — отдельная задача кодирования структуры, не форматирование текста сообщения. | Не вставлять HTML-теги/маркеры Markdown как стили VK. Не вводить собственное «экранирование VK» без доказанного контракта; тестировать `& < >`, кавычки, обратные слеши, emoji и переносы обычным текстом. | Отображение/автоматическая обработка символов и URL в приложениях VK; точные правила сериализации и валидации button payload для конкретной версии API.

### Что требуется закрыть для VK

В просмотренной схеме официального репозитория указана версия API `5.199`, но
ветка `master` изменяема и её URL не является неизменным снимком конкретной
ревизии сервера. Клиентские результаты записаны отдельно в
[плане VK-пробы](STAGE3_VK_PROBE_PLAN.md) и
[отчёте Telegram-пробы](STAGE3_TELEGRAM_PROBE_REVIEW.md): версии клиентов не
зафиксированы, а Telegram callback event и его payload не подтверждены. VK
inline-кнопка и получение `message_event` отдельным observer-ом проверены, но
штатный адаптер всё ещё не отправляет keyboard, не обрабатывает это событие и
не отправляет ack. Поэтому VK-кнопка и Telegram callback не являются
поддержанным путём выполнения команды или подтверждения; точный текстовый
fallback обязателен. Не выводить из наблюдений свойства других клиентов или
серверных ревизий.

## Граница результата шага 3.2

Это контрактная проверка первичных официальных материалов, не клиентский тест.
Для Telegram доказаны поля, лимит текста, форматирование HTML/entities,
scope команд, ограничения callback-data и обязанность отвечать на callback.
Для VK доказаны форма отправки со строковым полем клавиатуры и структура
`message_event` на уровне просмотренной официальной схемы, в которой указана
версия API `5.199`; URL ветки `master` не фиксирует конкретную ревизию схемы.
Клиентские наблюдения 3.3–3.4 записаны отдельно и не доказывают поведение
непроверенных версий; callback Telegram, меню команд и часть лимитов остаются
неподтверждёнными.
