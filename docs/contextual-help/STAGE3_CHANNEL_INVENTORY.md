# Исходное состояние каналов для этапа 3

Этот рабочий документ фиксирует снимок реализации Telegram/VK и подготовку
проверок из этапа 3.1 плана. Он помогает перейти от текущей отправки к
контрактной и клиентской проверке; см. [план](PLAN.md), [проект представления](FORMATTING_DESIGN.md),
[runbook передачи polling локальной сборке](STAGE3_HANDOFF.md) и
[вопросы по каналам](COMMAND_HINTS.md#вопросы-для-проверки-каналов-на-этапе-3).

## Снимок реализации на 25.10.2026

Проверены `compadre_assistant/presentation/telegram/bot.py`,
`compadre_assistant/presentation/vk/bot.py` и `requirements.txt`. В репозитории
найден только `requirements.txt` с закреплёнными зависимостями; lock-файлы и
`pyproject.toml` не найдены.

| Область | Текущее состояние по исходному коду |
| --- | --- |
| Telegram: немедленный ответ | `IncomingResponse.render_text()` передаётся в `safe_send_telegram_reply`; части отправляются последовательно через `message.answer(chunk)`. Вызов передаёт только текст, параметры `parse_mode` и клавиатуры не задаются. См. [адаптер Telegram](../../compadre_assistant/presentation/telegram/bot.py#L268). |
| Telegram: фоновый ответ | `BackgroundReply.response.render_text()` отправляется через тот же безопасный путь разбиения; `_TelegramReplyTarget.answer()` вызывает `bot.send_message(chat_id=..., text=...)`. Callback планирует доставку в event loop. |
| Telegram: разбиение и повторы | Лимит адаптера — 3900 символов на часть. Разрез выбирается по абзацу, строке, пробелу, иначе по лимиту; края обрезаются через `rstrip`/`lstrip`. Части идут по порядку. В `safe_send_telegram_reply` временные ошибки повторяются через общий `safe_send_async`; это исходное поведение, а не доказательство фактического лимита клиента. |
| Telegram: SDK и API | В `requirements.txt` закреплён `aiogram==3.29.1`. Прямой вызов Bot API и версия Bot API в проекте не заданы отдельно. В исходнике не обнаружены `set_my_commands`, `BotCommandScopeChat`, `parse_mode`, `reply_markup`, inline-кнопки или их обработчики; это статический поиск по адаптеру, не проверка конфигурации запущенного бота. |
| VK: немедленный ответ | После обработки обновления `IncomingResponse.render_text()` передаётся в `_safe_send_vk_message`; каждый фрагмент вызывает `VkApiClient.send_message` и метод `messages.send`. Тело запроса формируется из `peer_id`, `message`, `random_id`; API-версия добавляется общим `_api_call` как `v=5.199`. |
| VK: фоновый ответ | `BackgroundReply.response.render_text()` передаётся в тот же `_safe_send_vk_message` по сохранённому `peer_id`, с теми же разбиением и отправкой через `messages.send`. |
| VK: разбиение и повторы | Лимит адаптера — 3500 символов; границы разреза и обрезка аналогичны Telegram. Части отправляются последовательно. Для каждой части создаётся `random_id`; временные ошибки VK повторяются общим `safe_send`. В клиентском API код не передаёт параметр клавиатуры. |
| VK: SDK и API | VK SDK в `requirements.txt` не закреплён и адаптер использует стандартные `urllib`/JSON. Вызовы идут на `https://api.vk.com/method`, параметр версии по умолчанию `5.199`; Long Poll ожидает 25 секунд, сетевой timeout для запроса — 30 секунд. Клавиатура, разметка и события выбора в коде адаптера не реализованы. |
| Настройки содержания | Оба адаптера сериализуют ответ в обычную строку через `render_text()`. В самом вызове отправки не задаются форматирование, меню, кнопки или иные действия сообщения. Значение лимита — внутренний безопасный порог реализации; соответствие лимиту API и поведение клиента проверяются на следующих подпунктах этапа 3. |

Ссылки на основные точки кода: [Telegram: немедленная отправка и обработчик](../../compadre_assistant/presentation/telegram/bot.py#L268), [Telegram: фоновая отправка](../../compadre_assistant/presentation/telegram/bot.py#L280), [Telegram: лимит и разбиение](../../compadre_assistant/presentation/telegram/bot.py#L18); [VK: версия и лимиты](../../compadre_assistant/presentation/vk/bot.py#L24), [VK: отправка API](../../compadre_assistant/presentation/vk/bot.py#L274), [VK: обработка и разбиение](../../compadre_assistant/presentation/vk/bot.py#L372), [зависимости](../../requirements.txt).

## Матрица подготовки проверок

План 3.1 выполнен статически: для каждого вопроса записаны нужные контракты,
пробные вызовы, личный диалог и ожидаемое доказательство. Ни один клиентский
вопрос не считается подтверждённым на этом шаге. Пробные вызовы не выполнялись,
боты не запускались, сообщения в каналы не отправлялись.

| Канал и вопрос | Что сверить по контракту | Какой пробный вызов нужен | Личный диалог | Ожидаемое доказательство и текущий статус |
| --- | --- | --- | --- | --- |

Не менять global/default scope. | Личный диалог пользователя с существующим Telegram-ботом во время контролируемой передачи polling локальной сборке. | Исходный и восстановленный список в chat scope, API-статус, снимки меню/подсказок, клиент, версия и время. **Статус:** не проверено; адаптер сам команды не публикует, синтетическая API-проба выполняется отдельно. |

Параметра клавиатуры и обработчика выбора нет; отдельный искусственный UI/API probe — отдельный эксперимент и не поведение приложения. | Личный диалог пользователя с существующим VK-ботом сообщества при локальном polling. | Клавиатура и обработка выбора текущим адаптером не реализованы; их вид и доставка события **не проверены**. |

## Доступ и границы клиентских проб

Для шага 3.3 отдельные тестовые боты не создаются. В согласованное окно
polling существующих Telegram- и VK-ботов кратковременно передаётся локальной
сборке; подробный порядок и возврат приведены в
[runbook передачи polling](STAGE3_HANDOFF.md). Локальный запуск использует
только учётные данные, уже находящиеся на этой машине. Получать, копировать
или показывать секреты с VPS запрещено.

Исторически на 25.10.2026 пользователь сообщил, что отдельный Telegram
test bot и личный диалог не подготовлены; это объясняет прежний план блокировки.
Теперь это не требование. Это решение не означает, что пробы уже выполнены или
клиентское поведение подтверждено.

Использовать только личные диалоги и безопасные синтетические сообщения. До
отправки убедиться, что текст/команда не запускает запись в vault/БД,
публикацию, синхронизацию, внешний запрос или иную операцию с побочным
эффектом. Текущее статическое обследование не нашло в адаптерах меню команд,
кнопок, callback-обработчиков или клавиатуры VK. Поэтому различать
(1) наблюдение уже существующих меню и обычных ответов приложения и
(2) отдельные искусственные API/UI-пробы интерфейсных элементов временным
probe-кодом, который принимает только тестовый payload и не вызывает
бизнес-сценарии. Второй вид пробы не доказывает поддержку этих элементов
приложением.

Для результатов назвать платформу и версию клиента, отметить статус каждого
наблюдения и убрать личные идентификаторы. Шаг 3.1 остаётся статическим и сам
по себе не доказывает внешнее поведение; шаги 3.3–3.4 остаются открытыми до
проведения согласованных проб. Целевые тексты этапа 4 нужно сверить с
ограничениями, не выдавая неподтверждённое оформление за факт.

## Граница результата

Это инвентаризация кода и план доказательств для шага 3.1, а не завершение
проверки этапа 3. Контрактные утверждения и вид в клиенте остаются открытыми
до проверки по актуальным официальным источникам и в личных диалогах с
существующими ботами. Передача polling локальной сборке сама по себе этот
статус не меняет.
