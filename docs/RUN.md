# Запуск и проверка проекта

Для первого запуска сначала выполните [SETUP.md](SETUP.md): получите код,
создайте и заполните `.env`. Здесь описан запуск уже подготовленного проекта.

## Быстрый запуск через скрипты

Скрипты `open-*.cmd` открывают отдельное окно PowerShell, выполняют нужные команды и оставляют окно открытым после завершения. Скрипты проверок и запуска команд внутри контейнера сначала пересобирают образ `obs-chat-bot:dev`, чтобы Docker использовал свежий код проекта.

Запустить сборку и старт каналов из `ENABLED_CHANNELS` (по умолчанию Telegram и VK):

```powershell
.\scripts\open-dev-start.cmd
```

Для одного канала задайте в `.env` `ENABLED_CHANNELS=telegram` или
`ENABLED_CHANNELS=vk`. Scripts читают итоговую конфигурацию Compose, запускают
выбранные сервисы и останавливают ранее запущенный невыбранный сервис.
`check-health` и `check-all` проверяют все выбранные каналы. Проверки прерываются
при первом ненулевом коде команды Docker. Имена `open-*.cmd` и debug-режим сохранены.

Запустить проект с debug-логами только для текущего окна:

```powershell
.\scripts\open-dev-start.cmd debug
```

Проверить все текущие smoke-сценарии:

```powershell
.\scripts\open-check-all.cmd
```

Минимальный operational checklist для ежедневного запуска описан в
`docs/OPERATIONS.md`.

Проверить реальную ссылку:

```powershell
.\scripts\open-process-url.cmd "https://habr.com/ru/articles/198682/"
```

Обработка обычной статьи в Telegram после регистрации, сохранения имени и
подключения vault (при отсутствии ожидающего подтверждения):

- сообщение без ссылки получает просьбу прислать ссылку и не сохраняется в `incoming_messages`;
- сообщение с HTTP/HTTPS-ссылкой сохраняется в `incoming_messages`;
- после успешной обработки URL сохранённое сообщение связывается со статьёй через `incoming_messages.article_id`;
- после извлечения текста статья анализируется через OpenAI-compatible LLM, результат сохраняется в `analysis_results` и возвращается пользователю Markdown-сводкой;
- повторная ссылка переиспользует сохранённую статью и последний сохранённый анализ;
- если обработка ссылки завершилась ошибкой, диагностическая запись связывается с сообщением через `processing_errors.incoming_message_id`;
- если анализ завершился ошибкой, диагностическая запись также связывается с сообщением через `processing_errors.incoming_message_id`;
- повтор того же Telegram message id не создаёт дубль сообщения.
- ошибки загрузки, извлечения и анализа получают разные пользовательские ответы;
- диагностические ошибки можно смотреть в `processing_errors`.

Если отдельное окно не нужно, можно запускать `.ps1`-версии в текущей консоли:

```powershell
.\scripts\check-all.ps1
```

## Debug-логи

Если нужно видеть больше деталей в консоли сервера, включить в `.env`:

```dotenv
APP_DEBUG=true
```

После перезапуска проекта в логах появятся безопасные debug-события incoming-flow:
регистрация/привязка пользователя, сохранение входящего сообщения, ID статьи,
ID анализа и итоговый тип результата. Секреты и длинные тексты не выводятся.

## Настройки document chunker

Подэтап 10.1 добавляет независимый Markdown/Obsidian chunker. Его технические
размеры задаются необязательными переменными `.env`:

```dotenv
CHUNK_MINIMUM_SIZE_CHARS=300
CHUNK_TARGET_SIZE_CHARS=3000
CHUNK_MAXIMUM_SIZE_CHARS=6000
```

Если переменные отсутствуют, используются эти же значения по умолчанию.
`minimum` и `target` являются мягкими ориентирами, а `maximum` — жёстким лимитом
для обычного делимого текста. Эти параметры не относятся к содержательным
правилам `.knowledge-catcher.yml`.

Подэтап 10.2 сохраняет chunks в SQLite. Изменение параметров меняет index
signature и при следующей ручной или автоматической синхронизации запускает
полный локальный rebuild индекса vault. Если последняя GitHub-проверка ещё
свежая, rebuild выполняется из сохранённого Markdown без лишнего GitHub-запроса.

Подэтап 10.3 добавляет внутренний SQLite FTS5-индекс по title, path, tags,
headings и тексту chunks. Отдельной пользовательской команды поиска пока нет:
FTS используется как источник candidates общего RAG-flow и как fallback
при недоступном semantic index.
Проекция поддерживается автоматически вместе с chunk index и используется
только при совпадении текущей index signature.

## Настройки embeddings

LLM Obsidian и embeddings настраиваются независимыми группами. Например, для LLM:

```dotenv
OPENAI_BASE_URL=https://api.timeweb.ai/v1
OPENAI_API_KEY=replace-me
OPENAI_MODEL=dashscope/qwen3.5-flash
```

Для embeddings:

```dotenv
EMBEDDING_BASE_URL=https://api.timeweb.ai/v1
EMBEDDING_API_KEY=replace-me
EMBEDDING_DOCUMENT_MODEL=openai/text-embedding-3-large
EMBEDDING_QUERY_MODEL=openai/text-embedding-3-large
```

Compose и Python берут каждый ключ из одноимённой переменной. Одинаковые
значения можно задать явно в обеих переменных; автоматической подстановки нет.
Полностью пустая LLM-группа разрешает общие команды, а Obsidian сообщает,
что анализ/review недоступны. Частичная группа останавливает запуск и называет
отсутствующее поле. Если Obsidian отключён, все его группы игнорируются,
включая некорректные настройки, и клиенты провайдеров не создаются.

На уровне приложения embedding-группа опциональна, но при заполнении хотя бы
одного параметра должны быть заданы все четыре. Для FTS fallback оставьте
все семь `EMBEDDING_*` пустыми, как в новом шаблоне. Documents и query должны обрабатываться
совместимой парой моделей:
adapter дополнительно проверяет совпадение dimension их ответов. Healthcheck
проверяет форму конфигурации без сетевого и платного embedding-запроса.
Vectors сохраняются в SQLite после каждого успешного batch. Сбой следующего
пакета не удаляет предыдущие checkpoints, в том числе после перезапуска процесса.
Повторная синхронизация отправляет только chunks без совместимого vector.
Global embedding marker публикуется после проверки полного покрытия; до этого
готовые source/FTS используются через FTS fallback. Повтор остаётся у ручного
`/github_sync`, post-commit обновления и проверки после шестичасового окна.
Если lease истёк или перешёл другому процессу, текущая операция останавливается;
уже сохранённые checkpoints доступны следующему запуску.

Для оценочной стоимости в логах можно дополнительно задать весь тарифный блок:

```dotenv
EMBEDDING_PRICE_PER_MILLION_TOKENS=45
EMBEDDING_PRICE_CURRENCY=RUB
EMBEDDING_TARIFF_VERSION=2026-08-04
```

Цена — стоимость миллиона входных токенов в выбранной валюте, а версия — дата
или внутреннее имя тарифа, по которому потом можно проверить расчёт. Все три
поля опциональны, но задаются только вместе. Без них embeddings работают как
обычно, `usage` продолжает логироваться, а `estimated_cost` имеет значение
`none`. Значение нужно сверять с текущим кабинетом провайдера: именно кабинет,
а не локальная оценка, остаётся источником истины фактического списания.

## Пересоздание базы после изменения схемы

Пока проект находится в активной разработке, актуальная схема целиком хранится в
`obs_chat_bot/core/data/sqlite/migrations/0001_initial_schema.sql`. Новые миграции
`0002`, `0003` и далее не создаются.

Перед новым запуском после изменения схемы остановить контейнеры и другие
процессы, использующие БД. Удалить `data/app.db` и оставшиеся файлы
`data/app.db-wal` / `data/app.db-shm`, затем запустить приложение снова.
При старте оно создаст новую базу и применит актуальную начальную схему.
Каталог `data/` целиком не удалять: в нём хранится также PEM GitHub App.

Этот порядок относится только к локальной development-БД. Production SQLite
нельзя удалять по этому разрешению; см. [PRODUCTION.md](PRODUCTION.md).
После завершения этапа разработки
пересоздание с потерей данных больше не допускается на основании текущего
разрешения: изменения схемы выполняются миграциями с сохранением данных,
а удаление БД требует отдельного явного разрешения пользователя.

Это согласованный порядок разработки: сохранение промежуточных данных,
перенос и резервная копия перед таким пересозданием не требуются, отдельное
подтверждение не нужно. Изменение обычных записей или кода без изменения схемы
не требует очистки. Скрипты запуска автоматически схему не сравнивают и БД
не удаляют; пересоздание выполняется перед запуском.

Новая база не содержит технических пользователей. Первый успешный `/register`
создаёт `app_user_id=1`.

Удаление `data/app.db` полностью удаляет локальные данные разработки, включая
пользователей, привязки Telegram/VK, статьи, анализы и данные Obsidian vault.

После шага 2.1 начальная схема дополнена `active_chat_modes`. Ранее созданная
БД не обновляется повторным применением `0001`: перед запуском пересоздайте
development-БД по правилам выше. Автономные проверки работают с временными БД и не требуют очистки рабочей базы.
В шаге 2.2 схема не менялась. `/obsidian` выбирает режим конкретного чата,
`/exit` очищает только его маршрут. После выхода обычный текст и URL предлагают
вход, не запуская обработку статьи. Сохранение имени завершает регистрацию
профиля; GitHub/vault подключается отдельно внутри Obsidian. В шаге 2.5 схема
не менялась, пересоздание БД из-за одной конфигурации не требуется.

## 4. Собрать и запустить проект

```powershell
docker compose up --build
```

Команда собирает или обновляет образ, создаёт контейнер и запускает Telegram-бота и VK-бота в polling-режиме. Окно нужно оставить открытым, пока бот должен принимать сообщения.

Если настроен только один канал, укажите сервис: `docker compose up --build
tg_catcher` или `docker compose up --build vk_catcher`. Отсутствие токена не
отключает второй сервис автоматически. Используйте scripts с `ENABLED_CHANNELS`
для выбора сервисов. `--telegram-bot` проверяет только Telegram, `--vk-bot` —
только VK; токен другого канала не требуется.

В выводе команды сначала показывается сборка образа:

- строки с `#1`, `#2` и другими номерами шагов выполняет Docker;
- `[internal]` означает внутренние действия сборщика;
- установка пакетов через `pip` относится к зависимостям из `requirements.txt`;
- `CACHED` означает, что готовый слой взят из кэша и не выполнялся заново.

Затем Docker Compose подготавливает и запускает контейнер:

```text
Image obs-chat-bot:dev Built
Network ... Created
Container ... Created
Attaching to tg_catcher-1, vk_catcher-1
```

Строки с префиксом `tg_catcher-1 |` / `vk_catcher-1 |` и именем `obs_chat_bot` выводит уже наше Python-приложение:

```text
tg_catcher-1 | ... INFO obs_chat_bot: Starting obsChatBot 0.1.0
tg_catcher-1 | ... INFO obs_chat_bot: Telegram bot polling started
```

Остановить бота можно через `Ctrl+C` в окне, где запущен `docker compose up`.

Для повторного запуска уже собранного образа без проверки пересборки используется:

```powershell
docker compose up
```

Эта команда запускает существующий образ. После изменения `Dockerfile`, `requirements.txt` или кода проекта нужно снова использовать `docker compose up --build`, чтобы изменения попали в образ.

## 5. Проверить результат запуска

```powershell
docker compose ps -a
```

Команда показывает контейнер проекта. Статус `Exited (0)` означает, что приложение завершилось без ошибки.
Для запущенного бота ожидается статус `Up`.

## 6. Выполнить healthcheck

```powershell
docker compose run --rm tg_catcher python -m obs_chat_bot --healthcheck --channels telegram
docker compose run --rm vk_catcher python -m obs_chat_bot --healthcheck --channels vk
```

Команда проверяет выбранный канал, включённые возможности, доступность папки
`data/` для записи и подключение SQLite. Без `--channels` выбирается список
`ENABLED_CHANNELS` (по умолчанию `telegram,vk`). После проверки временный контейнер удаляется.

Healthcheck не вызывает API Telegram, VK, GitHub или LLM: он проверяет формат
Telegram token или наличие VK token/положительного group ID, настройки включённых
LLM/embeddings и возможность подписать JWT локальным PEM. URL проверяется
локально. Все независимые результаты выводятся отдельно; пользовательский vault
не проверяется. Пустые GitHub/LLM-группы отмечаются как недоступные функции,
пустые embeddings — как FTS fallback; общие команды остаются готовы и результат
может быть успешным. Частичная/невалидная группа включённой возможности даёт
ненулевой код, даже если обычные команды профиля могли бы работать.
Живой polling, права GitHub и доступность моделей этой командой не проверяются.
Она открывает рабочую БД (может создать пустой файл), но не применяет миграции
и не проверяет актуальность схемы. Статус `healthy` не подтверждает полный
пользовательский сценарий.

```powershell
docker compose run --rm tg_catcher python -m obs_chat_bot --sqlite-smoke
```

Команда создаёт временную базу, применяет миграции, повторно проверяет их идемпотентность, записывает тестовую статью через `ArticleRepository` и читает её обратно. Рабочая база `data/app.db` не изменяется.

## 8. Проверить обработку URL

```powershell
docker compose run --rm tg_catcher python -m obs_chat_bot --process-url "https://example.com/article"
```

Команда запускает текущий article pipeline: нормализует URL, создаёт или переиспользует статью в SQLite, загружает HTML, извлекает чистый текст и сохраняет результат в `data/app.db`.

Это только загрузка и извлечение текста, без LLM, поиска и GitHub write-back.
Команда требует только `APP_ENV` и `DATABASE_PATH`; не читает настройки каналов
или провайдеров возможностей. Smoke-команды вообще не загружают `.env`.
Текущий CLI использует `app_user_id=1` и не создаёт пользователя: в выбранной
БД он уже должен существовать (первый `/register` в новой базе создаёт ID 1).
На пустой БД запись статьи завершится ошибкой внешнего ключа. Команда работает
с данными этого пользователя; для проверки без рабочей БД используйте
`--pipeline-smoke`.

## 12. Зарегистрироваться и подключить Obsidian vault

Регистрация App, минимальные write permissions, Device Flow и PEM описаны в
`docs/GITHUB_APP.md`. После заполнения GitHub-группы настроек в `.env` и
перезапуска ботов новый пользователь отправляет в Telegram или VK:

```text
/register
```

После создания пользователя бот просит имя или название общего профиля. Оно
принадлежит внутреннему пользователю и одинаково отображается в связанных
Telegram и VK. Изменить имя позднее можно командой:

```text
/name Влад
```

Сохранение имени завершает регистрацию и не выбирает режим. Подключите vault
отдельно: войдите через `/obsidian` и пришлите ссылку на repository с
необязательным каталогом, либо передайте её аргументом входа:

```text
/obsidian https://github.com/owner/repository
/obsidian https://github.com/owner/repository path/to/vault
```

Если GitHub ещё не авторизован, бот возвращает Device Flow URL и одноразовый код.
Polling выполняется в background thread и не хранит временные tokens в SQLite.
Challenge и продолжение принадлежат исходному чату; другой чат получает только
объяснение занятости общего Device Flow claim, без кода авторизации.
После авторизации бот автоматически продолжает проверку исходного repository.
Если GitHub App не установлено или repository не выбран, бот даёт ссылку
установки/настройки; после изменения настройки ссылку repository нужно прислать
повторно.

Бот запрашивает для конкретного repository краткоживущий token с
`Contents: write`. Если GitHub не подтверждает право записи, в том числе для
публичного repository с доступом только на чтение, vault не подключается.
Архивные и отключённые repositories также отклоняются. После проверки бот читает
default branch и проверяет каталог через GitHub Contents API. Корень repository
используется, если второй аргумент отсутствует. Первый vault сохраняется сразу;
замена существующего требует решения в исходном чате и режиме Obsidian.
Команды подтверждения несут ID и версию операции. При единственном ожидании
этого чата допустимы `да`/`нет`; чужие ожидания при выборе не учитываются.
Replace/disconnect единственного vault взаимно исключаются и не заменяют
уже ожидающее действие. Другой связанный чат продолжает независимые article flows.

До подключения пользователь вручную создаёт в корне выбранного vault обязательный
`.knowledge-catcher.yml`. Готовый пример находится в
[`obs_chat_bot/resources/.knowledge-catcher.yml`](../obs_chat_bot/resources/.knowledge-catcher.yml):

```yaml
version: 1

instructions:
  - memory-bank/AGENTS.md.txt
  - memory-bank/docs/agent-preflight.md.txt
  - memory-bank/docs/content-conventions.md.txt
  - memory-bank/docs/note-types.md.txt
  - memory-bank/docs/project-structure.md.txt
  - memory-bank/docs/workflows.md.txt
```

Все пути задаются относительно корня vault. Если конфигурации нет, YAML
некорректен или хотя бы один обязательный файл отсутствует, синхронизация
завершается ошибкой и показывает этот пример. Ссылки на статьи также не
обрабатываются до исправления обязательной конфигурации. Бот не создаёт её сам.

После выбора или замены автоматически выполняется первая синхронизация Markdown
и обязательных instruction-файлов. Результат содержит число заметок, правил и
количество скачанных, добавленных, обновлённых и удалённых Markdown-файлов.
Первая или массовая загрузка 50+ изменённых файлов использует один ZIP snapshot
commit; небольшие изменения скачиваются точечно по blob SHA. Архив читается
только в памяти с защитными лимитами. В debug-логе выбранный путь виден как
`mode=archive` или `mode=blobs`.
Позднее синхронизацию можно запустить вручную:

```text
/github_sync
```

Состояние локальной копии и количество файлов правил показывает:

```text
/github_status
```

Отключение выполняется только после подтверждения:

```text
/github_disconnect
```

Бот показывает выбранный repository и команды решения
`/confirm obsidian disconnect <id> <версия> yes` и аналогичную команду с `no`.
При единственном локальном ожидании допустимы `да`/`нет`. Подтверждение
удаляет подключение и локальные Markdown/metadata, но не изменяет GitHub
repository и не удаляет профиль, привязанные Telegram/VK-каналы, статьи или
анализы. GitHub-авторизация сохраняется для последующего подключения vault.

Неизменившийся HEAD завершается через ETag без чтения дерева. Если commit
изменился вне папки vault, совпадение tree SHA исключает загрузку blobs.

Перед обработкой ссылки на статью бот смотрит `last_checked_at` активного vault.
Если с последней успешной проверки прошло меньше шести часов, GitHub не
вызывается. На границе шести часов первая следующая статья запускает ту же
инкрементальную проверку, что и `/github_sync`; постоянного таймера нет.

Если автоматическая проверка завершилась ошибкой, обработка статьи продолжается
с последней пригодной локальной копией vault. Если такой копии ещё нет,
обработка блокируется до успешной синхронизации. Ошибка обязательной
конфигурации правил также блокирует обработку. Fallback действует, если vault уже
синхронизируется из другого связанного канала. Ответ о статье содержит отдельное
предупреждение, число локальных заметок и, если оно известно, время последней
успешной проверки GitHub. Сбой проверки GitHub не помечает статью ошибочной.

После анализа бот выполняет hybrid-поиск по локальному vault, читает обязательные
правила и соседние заметки и показывает одно из предложений: создать `.md`,
обновить существующий `.md` или не менять vault. На этом шаге GitHub ещё не
изменён. Предложение сохраняется для общего пользователя Telegram/VK и ждёт:

```text
да
нет
```

`да` применяет именно показанное предложение. Для `add`/`update` бот повторно
проверяет HEAD/tree/blob и делает прямой commit в default branch; для `skip`
GitHub не вызывается. `нет` отменяет proposal без изменения vault. Любой другой
текст напоминает о pending-решении и не запускает новую статью; диагностические
`/status`, `/github_status` и `/help` остаются доступны.

Если vault изменился после подготовки, бот не перезаписывает заметку и просит
повторно прислать ссылку для нового расчёта. Временная ошибка commit сохраняет
proposal и полный текст статьи: позже можно безопасно повторить `да`. Повторная
ссылка на уже завершённую статью возвращает сохранённый анализ и результат без
скачивания страницы и LLM. Новый цикл запускается только явно:

```text
/reanalyze <ID статьи>
```

Неудачная повторная загрузка сохраняет прежний reviewed-результат.

До сохранения имени ссылки на статьи не обрабатываются. Затем обработка статьи
требует режима Obsidian и подключённого vault. Повторный `/register` не создаёт
нового пользователя: для профиля без имени бот запрашивает имя, для готового
профиля показывает имя и доступные входы без проверки vault.
Внутренний `app_user_id` пользователю не показывается.

## 13. Посмотреть доступные команды

Общий список реализованных команд доступен в Telegram и VK до и после
регистрации:

```text
/help
```

Список не показывает команды будущих подэтапов, пока они фактически не
реализованы. Текст строится автоматически из единого реестра команд, который
также используется общим Telegram/VK parser.

Общие команды находятся в [commands.py](../obs_chat_bot/core/presentation/incoming/commands.py),
точки входа регистрирует [registry.py](../obs_chat_bot/core/presentation/incoming/registry.py).
Основные команды: `/start`, `/help`, `/register`, `/name <имя>`, `/status`, `/exit`.
`/status` показывает профиль и выбранный режим текущего чата.
`/obsidian [текст или URL]` включает работу с vault и обрабатывает аргумент.
Без аргумента вход объясняет действия и при необходимости предлагает подключить
vault; после входа доступны внутренние команды. Голая ссылка вне режима
предлагает `/obsidian` и не запускает обработку статьи или подключение GitHub.
Управление vault: `/github_status`, `/github_sync`, `/github_disconnect`;
повторная обработка: `/reanalyze <ID статьи>`.

`ENABLED_CAPABILITIES=obsidian` включает этот вход; пустое значение отключает все
возможности после перезапуска. Общая справка показывает только включённые входы,
их команды и `/exit` для длительных режимов. Сохранённый ID отключённой возможности остаётся в SQLite;
бот предлагает выход или другой доступный вход. Предметные данные не удаляются.
Общие команды профиля работают при отключённом Obsidian. Вход различает
отключённую возможность, ненастроенный GitHub/LLM-провайдер и неподключённый
vault пользователя. Конфигурация и healthcheck разделены в шаге 2.5:
отключённые группы не проверяются; отсутствующий провайдер и неподключённый
vault диагностируются отдельно. Невалидные включённые группы блокируют startup.

Для одного профиля в Telegram и VK отправьте `/link_code` в уже подключённом
канале, затем `/link <код>` во втором. Если второй канал уже принадлежит другому
профилю, бот запросит подтверждение переноса связи. Это перенос канала к
выбранному профилю, а не объединение двух наборов статей и vault.

### Ожидающие действия и исходный чат

Разные статьи одного профиля из Telegram/VK имеют отдельные proposals.
Повтор нормализованного URL использует ту же статью и её активное предложение,
не создавая конкурирующий review. Повтор этой статьи из другого чата получает
указание завершить действие в исходном чате без preview чужого предложения.
Обычные новые ссылки и команды профиля чужим ожиданием не блокируются.

При нескольких локальных ожиданиях выбирайте команду из нужного ответа:

```text
/confirm obsidian proposal <id> <версия> yes
/confirm obsidian proposal <id> <версия> no
```

После `/exit` сначала войдите через `/obsidian` в том же исходном чате.
Старая команда с уже завершённым ID или изменившейся версией не применяет новое
предложение. Sync/write-back одного vault идут под общим SQLite lease; занятость
сохраняет ожидание, а расхождение SHA требует пересчёта с новым подтверждением.
`/reanalyze <article_id>` также требует завершить активное действие этой статьи.

Если `/link` предлагает перенос уже привязанной identity, используйте возвращённые
команды `/confirm core identity <id> <версия> yes|no`. Они доступны независимо
от режима. Обычные `да`/`нет` в Obsidian не подтверждают перенос профиля.

Шаг 2.4 изменяет `0001_initial_schema.sql`. Перед отдельным development-запуском
старую БД необходимо пересоздать по правилам `AGENTS.md`. Автономные проверки
используют временные БД; рабочая БД в этой реализации не открывалась.

## Один вопрос модели: Ask

После `/register` и `/name Имя` отправьте в Telegram или VK `/ask <вопрос>`.
Приём допустимого вопроса сразу подтверждается сообщением «Вопрос принят.
Готовлю ответ…». Результат приходит целиком или несколькими сообщениями через
обычное разбиение длинных ответов канала. Streaming не используется.

Каждый вызов содержит только текущий вопрос и постоянную инструкцию. Истории,
памяти и чтения URL/vault нет. `/ask` с URL рассматривает ссылку как текст.
GitHub и vault не требуются. Команда не меняет текущий режим и не подтверждает
ожидающие изменения Obsidian. Для Ask выход через `/exit` не нужен; обычный
текст и неизвестные команды не отправляются модели.

Пустой или слишком длинный вопрос получает подсказку без вызова API. При timeout,
ошибке провайдера, пустом/некорректном или превышающем лимит ответе бот предлагает
повторить вопрос позже. Автоматические повторы API отключены. Ключи, тело ответа
провайдера и детали исключений пользователю не показываются.

Профиль и четыре сочетания возможностей описаны в [SETUP](SETUP.md#настройка-ask).
Для проверки конфигурации используйте обычный healthcheck. Реальный запрос
проверяйте отдельно командой `/ask Ответь одним словом: готово` в выбранном канале.
Автономные тесты и smoke не выполняют такую внешнюю проверку.
