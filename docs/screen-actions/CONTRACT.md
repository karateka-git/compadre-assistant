# Описать действия экрана и раздела

Этот документ фиксирует контракт, который ядро и адаптеры подключают на этапе 2 [плана](PLAN.md). После подключения владельцы экранов используют его для переноса [сценариев](INVENTORY.md). Наличие типов само по себе ещё не означает работу новых проекций в каналах.

## Вернуть доступные действия

Владелец экрана продолжает возвращать `IncomingResponse.suggested_actions` из `ReplyAction`. В одном месте он выбирает доступные действия и задаёт подпись, точную команду или HTTP(S)-ссылку, область и назначение. `SECTION` описывает действия раздела, `SCREEN` — действия показанного сообщения. `SELECTION` всегда принадлежит сообщению. `NAVIGATION` указывает `ScreenDestination` с именем экрана и необязательной страницей; исполняется всё равно исходная команда, адаптер не синтезирует её по назначению.

Адресные подтверждения остаются в `IncomingResponse.actions` из `ConfirmationAction`. Их публичный снимок, код подтверждения и владелец команды продолжают проверяться штатным путём. `ReplyAction` не заменяет адресный контракт подтверждений. Показ кнопки не заменяет проверку допуска, членства и актуальности выбора при исполнении.

`ResponseView` и подтверждение доставки сохраняют роль границы поколений адресного выбора. Адаптер не снимает предыдущие кнопки до подтверждения замены. URL открывает внешнюю страницу и не поступает в обработчик команд.

## Запросить меню отдельно от ответа

`SectionActionsQueryPort.section_actions` читает текущие действия раздела для проверенных профиля, чата, ревизии режима и ожидания ввода. Владелец использует общий построитель для этого запроса и экрана, без второго каталога подписей и целей. Запрос ничего не исполняет и не отправляет сообщение. Каталог `CapabilityHelp` сохраняет назначение справки и командного меню Telegram.

Пустой проверенный кортеж означает отсутствие доступных действий раздела. `SectionMenuDelivery.RECONCILE` сверяет этот набор с доставленным меню: отсутствие действий снимает прежнее меню, совпадение сохраняет его. `PRESERVE` оставляет меню без запроса нового набора. Ответ без действий сам по себе не добавляет кнопки. Ошибка чтения набора не равна пустому снимку.

Пока реальные экраны переносятся по этапам, прежние вызовы `ContextualCommandMenuPort` и значение `prefer` нужны действующим callers. Они удаляются после перевода этих callers; новый код использует описание действий и `RECONCILE`/`PRESERVE`. Значение `None` у старого ответа продолжает обозначать обычную сверку меню.

## Сформировать страницу до доставки

Адаптер предоставляет нейтральные `ActionLayoutLimits` через `HandlerContext.action_layout`. Владелец вызывает `selection_capacity`, резервирует ряды и кнопки переходов, ограничивает результат своим размером страницы и лишь затем формирует текст, номера и точные цели. Адаптер не обрезает готовую страницу и не перенумеровывает выбор. При нулевой вместимости владелец сохраняет текстовую страницу и ручной путь; ограничения кнопок не запрещают текстовый выбор.

Например, шесть рядов и два служебных ряда оставляют четыре позиции, по одной на ряд. Видимые номера второй страницы остаются связанными с теми же предметными ID. Текстовые команды и предметная сверка доставленного снимка принадлежат владельцу сценария.

## Проверить подключение

Первый шаг этапа проверяет типы и ограничения в [тестах контракта](../../tests/test_screen_action_contracts.py). Следующие шаги проводят главное меню, адресный выбор и обычный текст через реальные привязку и доставку обоих каналов. До них тесты типов не служат доказательством доставки, снятия меню или защиты от устаревшего нажатия.
