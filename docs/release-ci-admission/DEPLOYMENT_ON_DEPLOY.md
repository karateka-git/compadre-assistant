# Публикация Deployment при выкладке

Этот контракт [этапа 10](PLAN.md) задаёт, когда команда оператора должна
записывать технически принятый выпуск в GitHub Deployments и как продолжить
запись после сбоя. Действующие до перехода команды описаны в
[OPERATIONS.md](../OPERATIONS.md). Первая запись для `v3.3.0` уже получила
`success` по порядку этапа 8. Новый маршрут принимаем на будущем выпуске.

## Установить выпуск и записать результат

1. Оператор указывает версию и полный SHA опубликованного immutable Release.
   Команда сверяет их с GitHub и подключается по SSH с проверенным ключом
   хоста. Токен доверенного автора с `Deployments: write` используется на
   машине оператора. VPS использует действующие права чтения GitHub.
2. Команда запускает штатный контроллер VPS. После завершённой установки
   она заново читает техническую приёмку точной версии и SHA. Приёмка
   подтверждает `last_good`, рабочие каналы, выбранную SQLite и её схему.
   Для публикации достаточно этой приёмки и доверенной успешной попытки CI.
3. Команда сверяет Release, CI и техническую приёмку, затем создаёт или
   находит одну запись по [формату этапа 8](DEPLOYMENT_RECORD.md#формат-записи-версии-1),
   публикует `success` и проверяет его повторным чтением. Ротация базы CI
   опирается на подтверждённый текущий `success`. `runtime_id` связывает
   сверки одной установки внутри команды и остаётся у оператора.

Для одного выпуска оператор использует один сеанс записи. При повторе он
начинает со сверки текущего состояния GitHub, включая случай потери ответа
после записи.

## Продолжить после сбоя

| Ситуация | Действие |
| --- | --- |
| Установка прервалась, откатилась или техническая приёмка отказала | Путь записи останавливается. Оператор проверяет фактическое состояние VPS и действует по [порядку восстановления](../OPERATIONS.md#отказ-выпуска-и-возврат). |
| Установка успешна, GitHub недоступен или ответ на запись потерян | Установленный выпуск продолжает работать. Оператор повторяет путь записи без повторной установки. Команда заново читает VPS и GitHub, находит существующий Deployment того же SHA и завершает его, если статус отсутствует. Проверенный `success` завершает повтор без записи. |
| Runtime сменился между сверками, найдены дубликаты или конфликтующий статус | Команда останавливается для разбора. После смены runtime нужна свежая техническая приёмка точного текущего выпуска. |
| Аварийная установка завершилась без успешной точной попытки полного CI | Технический результат установки сохраняется. Публикация `success` и ротация закрыты. Отказную попытку из приёмки разбирают отдельно. |
| Отдельно выполненный forward recovery подтвердил `success` | Оператор продолжает путь записи без новой установки. Команда заново читает техническую приёмку восстановленного выпуска. |

После допуска writers в новую SQLite прежнее поколение может не содержать
новые записи. Возврат к нему закрыт. При сбое после этой границы оператор
действует по условиям восстановления, а при отказе записи в GitHub повторяет
публикацию. Для [очистки прежней SQLite](SQLITE_CLEANUP.md) по-прежнему нужны
живая проверка обоих каналов и отдельное согласие владельца на удаление.
