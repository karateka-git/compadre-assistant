# Публикация Deployment при выкладке

Этот контракт [этапа 10](PLAN.md) задаёт, когда команда оператора должна
записывать технически принятый выпуск в GitHub Deployments и как продолжить
запись после сбоя. [Команды оператора](../OPERATIONS.md#установить-выпуск-и-записать-deployment).
Первая запись для `v3.3.0` получила `success` по порядку этапа 8.
Эксплуатационная приёмка общей команды запланирована на будущий выпуск.

## Установить выпуск и записать результат

1. Оператор указывает версию и полный SHA опубликованного immutable Release.
   Команда сверяет их с GitHub и подключается по SSH с проверенным ключом
   хоста. Токен доверенного автора с `Deployments: write` используется на
   машине оператора. VPS использует действующие права чтения GitHub.
2. Команда запускает штатный контроллер VPS. После завершённой установки
   она заново читает техническую приёмку точной версии и SHA. Приёмка
   подтверждает `last_good`, рабочие каналы, выбранную SQLite и её схему.
   Для публикации достаточно этой приёмки и доверенной успешной попытки CI.
3. Команда сверяет Release, CI и техническую приёмку, затем создаёт или
   находит одну запись по [формату этапа 8](DEPLOYMENT_RECORD.md#формат-записи-версии-1),
   публикует `success` и проверяет его повторным чтением. Ротация базы CI
   опирается на подтверждённый текущий `success`. `runtime_id` связывает
   сверки одной установки внутри команды и остаётся у оператора.

Для одного выпуска оператор использует один сеанс записи. При повторе он
начинает со сверки текущего состояния GitHub, включая случай потери ответа
после записи.

## Продолжить после сбоя

| Ситуация | Действие |
| --- | --- |
| Установка прервалась или откатилась | Путь записи останавливается. Оператор проверяет фактическое состояние VPS и действует по [порядку восстановления](../OPERATIONS.md#отказ-выпуска-и-возврат). |
| Установка успешна, но техническая приёмка отказала, GitHub недоступен или ответ на запись потерян | Оператор устраняет причину и повторяет запись через `--publish`. Команда заново читает VPS и GitHub, находит существующий Deployment того же SHA и завершает его, если статус отсутствует. Проверенный `success` завершает повтор без записи. |
| Runtime сменился между сверками, найдены дубликаты или конфликтующий статус | Команда останавливается для разбора. После смены runtime нужна свежая техническая приёмка точного текущего выпуска. |
| Аварийная установка завершилась без успешной точной попытки полного CI | Технический результат установки сохраняется. Публикация `success` и ротация закрыты. Отказную попытку из приёмки разбирают отдельно. |
| Отдельно выполненный forward recovery подтвердил `success` | Оператор запускает `--publish`. Команда заново читает техническую приёмку восстановленного выпуска. |

После допуска writers в новую SQLite прежнее поколение может не содержать
новые записи. Возврат к нему закрыт. При сбое после этой границы оператор
действует по условиям восстановления, а при отказе записи в GitHub повторяет
публикацию. В этапе 10 очистка сохраняла ручной допуск этапа 9. В этапе 11
она следует за подтверждённым Deployment по техническим условиям.
[Контракт выпуска из GitHub Actions](ACTIONS_RELEASE.md)

## Проверить маршруты локально

- [Операторская команда](../../tests/test_deploy_and_publish.py) проходит
  обычную и аварийную выкладку через локальные модели SSH и GitHub. Тесты
  проверяют точный Release и автора до запуска SSH, передачу причины одним
  аргументом и отсутствие токенов в команде и окружении SSH. При отказе
  выкладки, недоступности SSH, смене runtime или отсутствии точного
  успешного CI тесты проверяют, на какой записи останавливается команда и
  получает ли выпуск допуск к ротации. После отказа чтения GitHub при
  успешной установке `--publish` записывает приёмку без новой выкладки.
- [Повтор и отказы GitHub](../../tests/test_deployment_transition.py) и
  [проверки публикации](../../tests/test_publish_deployment_acceptance.py)
  воспроизводят потерю ответа на каждом POST, повтор без дублей,
  недоступность API и конфликт записей.
- [Сценарий с временной SQLite](../../tests/test_cleanup_full_route.py)
  подтверждает, что `--publish` после forward recovery публикует `success`
  по свежей приёмке, а повтор возвращает ту же запись. Оба вызова обходятся
  без новой установки.
