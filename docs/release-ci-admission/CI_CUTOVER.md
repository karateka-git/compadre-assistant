# Переключение имён проверок CI

Порядок для шага 7.2 [плана](PLAN.md). Используйте [карту имён](CI_CHECK_NAMES.md),
чтобы подготовить PR, проверить обязательные статусы и открыть допуск к
следующему выпуску после смены доверенного CI. Старые прогоны остаются в
истории GitHub.

## Подтвердить готовность

1. Согласовать с владельцем окно перехода и список поддерживаемых релизных
   линий. Приостановить обычные слияния и выкладки, отключить auto-merge у
   открытых связанных PR на время перехода. Проверить свежие вершины веток,
   открытые PR и merge после последнего опубликованного тега каждой линии.
   Завершить до перехода выпуски и hotfix, для которых ещё нужна сверка
   прежней проверки PR на момент merge. Остальные открытые PR должны
   получить новые статусы на актуальных head и base после обновления веток.
2. Сохранить прежние значения обязательных статусов, области rulesets и
   остальные параметры, SHA переходных PR, GitHub и VPS pin, SHA и digest
   установленного controller snapshot. Повторно подтвердить актуальный
   `last_good`, завершённую установку, отсутствие `deploy-in-progress` и
   незавершённого recovery, оба канала и состояние backup timer. При
   незавершённом переходе SQLite сначала закрыть recovery по действующему
   [порядку возврата](../OPERATIONS.md#отказ-выпуска-и-возврат).
3. Подтвердить свежую техническую приёмку и `production/vX.Y.Z` текущей
   установки. Если действующий snapshot ещё не умеет выдавать приёмку,
   сначала провести отдельный PR с кодом приёмки, сохранив три полных
   workflow побайтно из действующего reviewed pin и прежние имена проверок.
   После успешного полного CI точного merge SHA согласовать установку этого
   [снимка контроллера](../OPERATIONS.md#обновить-отдельно-установленный-controller-snapshot).
   Получить свежую приёмку и согласовать создание
   [тега установки](../OPERATIONS.md#зафиксировать-приёмку-тегом-установки).
   Это подготавливает исходную базу до переименования. Новый набор имён
   вступает в действие на следующих шагах.

## Переключить PR и полный CI

1. Открыть переходный PR в `main`. В его `pull_request` прогоне проверить
   `pr-check` на актуальном test merge. После зелёного статуса заменить
   `pr-fast` на `pr-check` в ruleset `25067104` одним сохранением правила.
   Сверить источник и точный SHA проверки в PR. Слить переходный PR с
   действующим обязательным статусом. Обычные слияния пока на паузе.
   Сводку `ci-metrics` подтвердить отдельно на PR с обновлённым base SHA,
   поскольку workflow PR запускает collector из базовой ветки.
2. Для каждой поддерживаемой существующей линии подготовить PR переноса
   перехода с `Hotfix-Main-Commit:` на достижимый merge commit из `main`.
   При нескольких линиях добавить взаимные `Hotfix-Links:`. Проверить
   `pr-check` и `pr-merge-main-check` на test merge каждого PR. Ссылка на
   уже слитый `main` даёт зависимости пройти до смены ruleset и слияния
   релизного PR. На замороженных линиях прежние workflow могут блокировать
   обычные слияния. Перед возобновлением работы в такой линии провести
   проверенный PR переноса.
3. Подготовить reviewed pin с новыми байтами всех трёх полных workflow и
   принятой базой SQLite. Штатная ротация требует отдельный PR, меняющий
   только поля базы в policy. Если база уже совпадает с принятой установкой,
   согласовать отдельный reviewed pin для новых байтов workflow по
   [порядку ротации](../OPERATIONS.md#закрепить-базу-полного-ci-после-установки).
   Сменить pin в GitHub и подтвердить полный CI точного `main` под ним.
   По этому прогону подготовить и проверить новый controller snapshot,
   установить его и активировать тот же pin на VPS. Перед выпуском
   подтвердить оба pin и допуск точного SHA. При частичной ротации
   оставить выкладки на паузе.
4. До слияния PR переноса на действующей линии дождаться нового GitHub pin.
   Релизный полный workflow запускается по `push` в ветку и сверяет байты
   с этим pin. После зелёных новых статусов заменить `hotfix-deps` на
   `pr-merge-main-check` в ruleset `25404080` одним сохранением правила.
   Слить PR переноса с обеими обязательными проверками и подтвердить
   `release-check-full` для полученного SHA. Новую релизную линию создавать
   от SHA с подтверждённым `pre-release-check-full` с новыми именами.
   Если линия без опубликованного Release была создана от SHA со старыми
   проверками, оставить её на паузе до отдельного решения по её базе.
5. На связанной паре PR подтвердить `pr-merge-main-rerun` после обновления
   `main` и целевой релизной ветки. До слияния main PR релизная проверка
   зависимости должна завершиться отказом. Сверить, что после merge
   доверенный `pull_request_target` из `main` повторяет именно эту задачу
   актуального release PR. Перед живой проверкой сверить разрешение события
   в Actions. После подтверждения возобновить обычные слияния. Для первого
   выпуска проверить полный CI его точного SHA.
   [События PR](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows) ·
   [Условия обязательных проверок](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)

Изменения rulesets, GitHub pin и VPS требуют согласования владельца.
Для `git push` требуется отдельное явное согласие по [AGENTS.md](../../AGENTS.md).

## Вернуть прежний порядок при отказе

До merge переходного PR вернуть сохранённые обязательные статусы. После
merge подготовить PR возврата с прежними workflow и скриптами. Сначала
получить на них зелёные прежние статусы, затем восстановить соответствующие
правила и провести merge. Сохранять обязательные статусы активными в обоих
направлениях. Состояние snapshot и обоих pin сверить отдельно. При
расхождении продолжать паузу выкладок до подтверждённой ротации либо
согласованного восстановления, сохраняя работающую установку.

область поддерживаемых линий и новые статусы на реальных PR требуют
подтверждения в согласованное окно.
