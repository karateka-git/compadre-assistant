# Проверить переход на запись приёмки в Deployments

Этот протокол фиксирует локальную проверку шага 8.5 и порядок будущего перехода
от тега установки к [записи Deployments](DEPLOYMENT_RECORD.md). Команды
оператора до переноса правил остаются в [OPERATIONS.md](../OPERATIONS.md),
схема допуска — в [CI_AND_DEPLOY.md](CI_AND_DEPLOY.md). На 11.11.2026
проверена **только локальная модель API**; запись в GitHub и состояние VPS
этими испытаниями не подтверждались.

## Проверить сбой и безопасный повтор

В тестах `test_deployment_transition.py` запись и чтение разделены: fake API
сначала сохраняет объект, затем может потерять ответ или отказать при
последующем чтении. Операторский сценарий не повторяет POST до нового чтения.

| Сценарий модели | Проверенный результат |
| --- | --- |
| Ответ на создание Deployment потерян после записи | Чтение находит единственный объект; статус создаётся для его ID, второй Deployment не создаётся. |
| Чтение после создания Deployment прервано | Сеанс останавливается; следующий сеанс находит тот же объект и создаёт только статус. |
| Ответ на создание статуса потерян после записи | Чтение подтверждает текущий `success`; второй статус не создаётся. |
| Чтение после создания статуса прервано | Сеанс останавливается; следующий сеанс подтверждает существующий `success` без POST. |
| `403` при создании Deployment или статуса | Запись не считается принятой, ротация не получает `success`; причину прав разбирает оператор с владельцем. |
| `403` при чтении Deployments | Публикация и ротация останавливаются; недоступная запись не приравнивается к отсутствующей. |
| Конфликт payload, чужой автор, отказный статус или две записи одного SHA | Проверка закрывает допуск, запись не переписывается; решение передаётся владельцу. |

Последний сценарий покрыт также тестами `test_deployment_acceptance.py` и
`test_publish_deployment_acceptance.py`. Локальная модель не воспроизводит
реальные права токенов, webhook-потребителей и сетевые гонки GitHub.

## Перейти после следующего выпуска

1. До завершения этапа 9 и приёмки следующего выпуска оставить
   `production/v3.2.0` в истории. Ротация базы CI для этого `last_good`
   продолжает читать его тег и immutable Release. Новую запись для
   `v3.2.0` задним числом не создавать.
2. После установки следующего выпуска получить свежую техническую приёмку
   точного SHA. Владелец подтверждает живые ответы Telegram и VK для её
   `runtime_id`. Перед записью заново проверить Release, CI, выбранную SQLite,
   действующие workflow и webhook-потребителей; согласовать один сеанс
   публикации и необходимые права. Практический вызов приведён в
   [порядке публикации](DEPLOYMENT_RECORD.md#подготовить-и-повторить-публикацию).
3. Создать один Deployment и текущий `success`, перечитать GitHub и сверить
   автора, payload, статус и точный SHA с новой технической приёмкой. При
   потере ответа начать повтор с чтения; при конфликте остановиться и
   передать разбор владельцу.
4. Только после подтверждённого `success` нового `last_good` готовить PR
   новой базы CI и продолжать ротацию. Проверка Deployments уже обязательна
   для любого выпуска, кроме `v3.2.0`, при подготовке, перед обновлением pin,
   перед запуском CI и при активации на VPS. Тег новой версии не служит
   запасным путём. Сводка SQLite без `success` оставляет данные принятой БД
   пустыми.

Локальный переход проверен двумя моделями одного репозитория: исторический
тег допускает `v3.2.0` и остаётся неизменным; новый `last_good` до записи
Deployments не допускает ротацию, после записи текущего `success` допускает.
Это подтверждает ветвление кода, но не завершает эксплуатационную приёмку
следующего выпуска. Её проводят после этапа 9.
