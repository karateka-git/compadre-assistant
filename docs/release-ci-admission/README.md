# Сопровождение выпуска и допуск CI

Этот временный каталог хранит план, решения и результаты работы над пунктом
[«Автоматизировать сопровождение выпуска и проверить допуск CI»](../BACKLOG.md#автоматизировать-сопровождение-выпуска-и-проверить-допуск-ci).
Действующие правила допуска находятся в [RELEASES.md](../RELEASES.md), порядок
работы оператора — в [OPERATIONS.md](../OPERATIONS.md). Каталог сохраняется до
завершения всей функциональности и её эксплуатационной приёмки.

## Проверить исходное состояние

Перед проектированием изменения сверить текущие GitHub policy pin, результаты
полного CI точного SHA и подтверждённый `last_good` на VPS. Зафиксированное в
[итоге v3.2.0](../RELEASE_REVIEW.md#сохранить-границы-следующего-выпуска)
расхождение является историческим снимком, а не доказательством текущего
состояния. Перед любым действием на VPS прочитать [PRODUCTION.md](../PRODUCTION.md)
и повторно проверить факты на сервере.

## Выполнить работу по этапам

1. Разобрать `verifier` на точном выпуске: источники previous/candidate SHA,
   run/attempt, policy, workflow, Release, artifact и schema fingerprint.
   Сохранить воспроизводимый протокол успешных и отказных проверок, включая
   недоступный GitHub и лимит 403. Измерить число запросов и устранить лишние
   повторы без ослабления допуска.
2. Спроектировать и проверить обновление базы полного CI от подтверждённого
   `last_good` после независимой приёмки рабочей БД и обоих каналов. Сохранить
   reviewed policy, внешний pin точного SHA, immutable Release/tag и полный CI.
   Проверить идемпотентность и отказ при частичной ротации.
3. На закрытом стенде испытать штатный operator recovery и допустимые
   автоматические действия forward recovery/rollback. Для каждого сценария
   зафиксировать условия входа и остановки, целевой SHA, backup, простой,
   возможную потерю записей и результат повтора.
4. Определить срок хранения прежних поколений SQLite и связанных файлов.
   Проверить безопасную очистку на закрытых копиях с учётом selector, durable
   state, активной БД, backup и незавершённого recovery.
5. Собрать достоверные замеры следующего выпуска: wall-clock, ручные действия,
   ожидания, повторы GitHub API и доступный счёт Codex tokens. Отдельно
   измерить build, backup, migrations, `verify_both` и recovery. Неизвестные
   исторические значения оставить `unknown`; сравнить до и после без
   ослабления exact-SHA допуска и защиты данных.

Внешние уведомления и автоматический запуск нового релиза на VPS остаются
отдельными пунктами бэклога.

## Завершить функциональность

После слияния всех изменений и эксплуатационной приёмки перенести действующие
правила, сценарии и ограничения в постоянную документацию. Проверить ссылки,
удалить этот временный каталог отдельным завершающим изменением и только затем
закрыть пункт бэклога.
