# Выпустить версию из GitHub Actions и очистить прежнюю SQLite

Контракт этапа 11 описывает ручной запуск выпуска в GitHub Actions.
После успешной технической приёмки VPS и записи Deployment этот запуск
очищает прежнюю SQLite. Действующие до ввода этапа правила приведены в
[инструкции оператора](../OPERATIONS.md) и [плане](PLAN.md).
Первый Deployment `v3.3.0` и очистку прежней SQLite на этом выпуске
выполнили по порядку этапов 8–9.

## Запустить выпуск

1. Оператор вручную запускает `workflow_dispatch` для обычного выпуска.
   Он указывает версию, полный SHA, тип изменения и release notes.
   Релизная ветка `release/X.Y` уже существует и соответствует версии.
   Автоматический запуск после трёх слияний остаётся правилом полного CI.
2. Runner берёт код оркестрации из защищённой `main`. Для новой публикации
   штатные проверки подтверждают выбранный SHA как вершину релизной ветки
   и успешный полный CI этого SHA. Команда создаёт защищённый тег и immutable
   Release и подтверждает их повторным чтением. Для уже опубликованного
   точного Release проверяет совпадение выпуска и допуска.
3. Runner по SSH передаёт установку штатному контроллеру VPS. После его
   успешного завершения команда повторно читает техническую приёмку и
   записывает или подтверждает единственный Deployment с текущим доверенным
   `success` для того же SHA по [контракту этапа 10](DEPLOYMENT_ON_DEPLOY.md).
4. После подтверждения Deployment runner вызывает серверную команду очистки
   для тех же версии, SHA и runtime. Контроллер выполняет очистку под
   блокировкой выпуска, сохраняет её результат и подтверждает техническую
   приёмку выбранной новой БД. Для очистки достаточно технических проверок.
   Отдельный вызов владельца и ответы `/help` исключаются из этого маршрута.

## Настроить полномочия

Workflow допускает один активный сеанс выпуска для production. На runner
используется отдельный токен с правами публикации Release и Deployment и
необходимыми правами чтения. Минимальный вариант совместим с текущей
проверкой автора — выделенный fine-grained PAT той же доверенной учётной
записи в защищённом GitHub Environment. Права токена на публикацию и
доступность сведений о правилах тегов проверяются при вводе в эксплуатацию.
Проверки точного автора записи и статуса в ротации базы CI сохраняются.
[Контракт формата и автора](DEPLOYMENT_RECORD.md)

Runner подключается по выделенному SSH-ключу и заранее проверенному
`known_hosts`. Серверный вход разрешает нужные операции установленного
контроллера. Для очистки используется штатный root-вход
`/usr/local/sbin/deploy-prod VERSION --cleanup-old SHA RUNTIME_ID`.
Команда сверяет тот же runtime и продолжает durable intent под deploy lock.
Токен GitHub с правом записи используется на runner.

Команда оркестрации принимает явные реквизиты выпуска и SSH независимо
от события GitHub. Будущий автоматический триггер сможет передать те же
параметры. Порядок выбора будущих автоматических версии и SHA в этот этап
не входит.

## Запустить workflow из GitHub Actions

В настройках репозитория создайте GitHub Environment `production-release`.
Для **Deployment branches and tags** выберите **Selected branches and tags**
и добавьте единственное правило типа **Branch** с именем `main`.
Храните полномочия в этом окружении. Workflow исполняется на точном SHA
защищённой `main`. `deployment: false` оставляет запись о приёмке за
оркестратором, который публикует её после сверки VPS.
[Настройка окружения GitHub](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments),
[окружение без автоматической записи Deployment](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments#using-environments-without-deployments).

| Тип | Имя | Значение |
| --- | --- | --- |
| Secret | `PRODUCTION_RELEASE_TOKEN` | Выделенный fine-grained PAT доверенного автора `karateka-git` для этого репозитория. Подтвердите запись Contents и Deployments, чтение Actions, Variables, Pull requests и необходимых настроек immutable Release и защиты тега. |
| Secret | `PRODUCTION_VPS_SSH_PRIVATE_KEY` | Закрытый выделенный ключ доступа runner к штатному контроллеру VPS. |
| Variable | `PRODUCTION_VPS_HOST` | Адрес VPS в формате `user@host`. |
| Variable | `PRODUCTION_VPS_KNOWN_HOSTS` | Строка `known_hosts` с предварительно проверенным ключом хоста VPS. |

В **Actions → Production release → Run workflow** выберите ветку `main`.
Для `release` укажите `version`, полный `sha`, `change` и `notes`.
Для `resume` достаточно той же версии и SHA уже установленного выпуска.
Оба режима используют одну группу concurrency `production-release`.
Новый запуск не отменяет активный сеанс. Не запускайте параллельно выпуск
с рабочей станции, где это ограничение GitHub не действует.
[Файл workflow](../../.github/workflows/production-release.yml).

## Вызвать команду с runner

Передайте токен через `GITHUB_TOKEN`, а ключ и проверенный `known_hosts`
через временные файлы runner. Код workflow вызывает команду из checkout
репозитория с точными реквизитами выбранного выпуска.

```bash
python3 -m scripts.release_production "$VERSION" "$SHA" \
  --ssh-host "$VPS_HOST" --known-hosts "$KNOWN_HOSTS" --identity "$SSH_KEY" \
  --release --change "$CHANGE" --notes-file "$NOTES_FILE"
```

Для `--release` обязательны тип изменения и release notes в UTF-8. Если
точный immutable Release уже есть, команда проверяет его допуск и сохраняет
опубликованное описание. Только подтверждённый ответ GitHub `404` открывает
путь новой публикации через штатную проверку версии, тега и CI.
Для продолжения уже установленного выпуска передайте те же версию, SHA и
SSH-параметры с `--resume`, без `--change` и `--notes-file`.

Runner использует `sudo -n /usr/local/sbin/deploy-prod` для установки,
технической приёмки и очистки. В журнал выводятся этапы, SHA и идентификаторы
Release, попытки CI и Deployment. После подтверждения очистки и повторной
сверки VPS итоговая строка содержит JSON с `deployment_id`, `status_id`,
`state: success` и `cleanup: completed`.

## Возобновить после отказа

| Наблюдение | Следующее действие |
| --- | --- |
| Допуск, версия, SHA, ветка или Release расходятся | Остановить выпуск до SSH и разобрать расхождение. |
| После сбоя публикации точный immutable Release уже есть | Перечитать его и подтвердить тег и допуск. Продолжить с подтверждённого результата. |
| GitHub сохранил тег, а точный immutable Release подтвердить не удалось | Остановиться для разбора публикации. Автоматическое удаление или перезапись тега запрещены. |
| Установка не подтверждена | Проверить фактическое состояние VPS. При незавершённом переходе действовать по [порядку восстановления](../OPERATIONS.md#отказ-выпуска-и-возврат). |
| Установка подтверждена, а Deployment отсутствует или ответ на запись потерян | В режиме `--resume` возобновить публикацию для уже установленной версии. После подтверждения `success` продолжить к очистке. |
| Deployment подтверждён, очистка прервалась после записи intent | Продолжить ту же операцию очистки через сверку сохранённого intent. После первого unlink обычная приёмка может временно отказать, поэтому серверная команда сверяет runtime и оставшиеся файлы под той же блокировкой. |
| Runtime сменился, backup повреждён, есть новый sidecar или открытый FD | Остановить очистку. Не менять selector и не удалять файлы вручную. |

Очистка сохраняет активную SQLite, резервные копии и данные восстановления.
Под блокировкой контроллер сверяет `last_good`, selector, runtime, целостность
backup, зарегистрированные inode прежней БД и sidecars, открытые FD и состояние
перехода. Intent сохраняет цель и runtime до первого удаления, повтор
продолжает только этот intent. После допуска writers возврат к прежнему
поколению закрыт. [Технические условия очистки](SQLITE_CLEANUP.md)

Для ручного разбора частичного удаления оператор с root-доступом читает
только `old_generation_cleanup_intent.runtime_id` из
`/var/lib/compadre-assistant-deploy/state.json` и использует его с теми же
версией и SHA в `--cleanup-old`. Само состояние и runtime не выводят в
журнал GitHub Actions.

## Подтвердить готовность

Локальные испытания проходят на изолированных моделях GitHub и SSH и
временной SQLite с проверкой сохранности данных и backup. На будущем
согласованном выпуске сверить SHA в полном CI, Release, технической
приёмке VPS и текущем Deployment `success`. Проверить, что очистка
завершилась для прежнего поколения того же перехода, а техническая
приёмка и backup читают выбранную новую БД. Текущие настройки GitHub и
VPS проверяются перед вводом маршрута в эксплуатацию.
