# Определить допуск к очистке прежнего поколения SQLite

Этот рабочий разбор этапа 9 фиксирует, когда прежнее поколение перестаёт быть
целью возврата и какие факты нужно доказать перед его удалением. Действующий
порядок переключения описан в [схеме SQLite](CI_AND_DEPLOY.md#переключить-поколение-sqlite),
результаты испытаний возврата — в [RECOVERY_TRIALS.md](RECOVERY_TRIALS.md#решение-по-восстановлению),
а команды эксплуатации — в [OPERATIONS.md](../OPERATIONS.md#отказ-выпуска-и-возврат).
**Очистка пока не реализована**; ниже перечислены требования к её будущему
допуску, а не доказательство состояния VPS.

## Подтвердить завершённый переход

Разрешать очистку только после успешной обычной или аварийной установки либо
успешного forward recovery **того же выпуска**, полной технической приёмки и
отдельного подтверждения владельцем живых ответов Telegram и VK для её
`runtime_id`. `stage=success` завершает технический переход, но сам по себе
не доказывает живые ответы и не разрешает удаление.

| Факт перед удалением | Источник и требуемое совпадение |
| --- | --- |
| Переход завершён | Приватный `state.json`: протокол SQLite v2, `stage=success`, `boot.outcome=success`, `admission_may_have_started=true`, точные `transition_id` и `generation_id` в `admission`, `boot` и `state.new`. Стадии `rolled_back`, `failed_preflight`, `degraded` и любая промежуточная стадия не подходят. |
| Выбрана новая БД | `active-db.json` указывает на `state.new` этого перехода. Новая БД существует, имеет канонический путь и прежнюю зарегистрированную идентичность, проходит журнал миграций, integrity и foreign keys. `state.old` и `state.new` не совпадают. |
| Работает принятый выпуск | `last_good` соответствует `candidate`, `boot` и точному SHA установленного Release. Два работающих канала используют образ и путь `state.new`; нет дублирующего polling или чужого writable mount. Техническая приёмка подтверждает unit и восстановленный backup timer. |
| Нет незавершённого recovery | Отсутствуют `deploy-in-progress` и `recovery-blocked.json`; сохранённый `state` не содержит незавершённой финализации, возврата или forward recovery. Проверка выполняется под общим deploy lock и повторяется непосредственно перед удалением. |
| Сохранён нужный backup | `state.snapshot.path` совпадает с `last_good.backup_id`. Приватный окончательный snapshot существует вне каталога поколений, его SHA-256 совпадает с сохранённым `state.snapshot.sha256`, а SQLite проходит проверку схемы, integrity и foreign keys. Snapshot и другие backup не входят в набор удаляемых файлов. |
| Владелец подтвердил живые ответы | Оператор связывает явное решение владельца с `runtime_id` свежей технической приёмки и непосредственно перед очисткой подтверждает ту же установку. Решение не выводится из `state=success` или будущего статуса GitHub. |

Граница `admission_may_have_started=true` означает, что новые writers уже могли
записать данные в `state.new`. По [действующему правилу возврата](../OPERATIONS.md#отказ-выпуска-и-возврат)
прежнее поколение после этой границы не выбирают для автоматического возврата.
До завершённого `success` оно всё ещё может быть нужно для разбора или
восстановления. Даже после `success` удаление требует всех перечисленных
доказательств и отдельного согласия на действие на production VPS.
Проверка чужих Docker mounts не исключает host CLI и процессы вне Docker;
перед реальной очисткой оператор должен отдельно исключить их доступ к
прежнему файлу в согласованном окне работ.

## Остановиться при отказе доказательства

Не удалять файл при любом расхождении SHA, версии, поколения, selector,
`last_good`, boot, работающих контейнеров или `runtime_id`; при отсутствии
живого подтверждения, неуспехе проверки backup, занятом lock, marker,
незавершённом recovery, `rolled_back` либо неизвестной стадии. Не трактовать
отсутствующий старый файл как уже завершённую очистку без отдельной
подтверждённой записи её результата. Сохранить активную БД, snapshot,
backup, selector, `state` и recovery-файлы для разбора владельцем.

Действующий [`read_selected`](../../scripts/deploy_database_switch.py)
проверяет идентичность **обоих** поколений даже при selector на `new`.
Его вызывают техническая приёмка, штатный boot, ночной backup и подготовка
следующего выпуска. Поэтому перед реализацией удаления нужен явный контракт
завершённой очистки: после неё проверять выбранную новую БД без требования
существования `old`, сохраняя строгую проверку обоих файлов до очистки и во
всех незавершённых состояниях. Это предмет шага 9.2.

## Сохранить порядок первой записи Deployments

Первая запись GitHub Deployments должна появиться **после завершения этапа 9**,
поэтому требовать её `success` до очистки нельзя: это создало бы замкнутую
зависимость. Для первого выпуска порядок такой: техническая приёмка, живое
подтверждение владельца для `runtime_id`, согласованная очистка, повторная
техническая сверка той же установки и затем отдельное разрешение владельца
на публикацию записи Deployments по [этапу 8](DEPLOYMENT_TRANSITION.md#перейти-после-следующего-выпуска).
Если после очистки `runtime_id` изменился, владелец заново проверяет живые
ответы до публикации. До проверенного `success` новой записи базу CI не
ротируют. Отсутствие записи Deployments пока не подменяется новым тегом
установки.

Этот порядок требует, чтобы повторная техническая приёмка и ночной backup
работали после доказанной очистки `old`. Сейчас они не работают без старого
файла; шаг 9.2 должен закрыть этот разрыв до реализации удаления.
