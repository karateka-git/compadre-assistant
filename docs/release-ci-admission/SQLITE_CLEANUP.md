# Определить допуск к очистке прежнего поколения SQLite

Этот рабочий разбор фиксирует, когда прежнее поколение перестаёт быть
целью возврата и какие факты этапов 9 и 11 нужны перед его удалением. Действующий
порядок переключения описан в [схеме SQLite](CI_AND_DEPLOY.md#переключить-поколение-sqlite),
результаты испытаний возврата — в [RECOVERY_TRIALS.md](RECOVERY_TRIALS.md#решение-по-восстановлению),
а команды эксплуатации — в [OPERATIONS.md](../OPERATIONS.md#отказ-выпуска-и-возврат).
На `v3.3.0` прошла приёмка очистки по этапу 9. Эксплуатационная приёмка
workflow этапа 11 ожидает согласованного выпуска.
Практический порядок запуска, проверки результата и повтора находится в
[OPERATIONS.md](../OPERATIONS.md#удалить-прежнее-поколение-sqlite-после-приёмки).

## Подтвердить завершённый переход

Разрешать очистку только после успешной обычной или аварийной установки либо
успешного forward recovery **того же выпуска** и свежей технической приёмки
для точной версии, SHA и `runtime_id`. Согласованный ручной запуск workflow
покрывает техническую очистку. После её завершения runner повторно сверяет
приёмку и записывает Deployment.

| Факт перед удалением | Источник и требуемое совпадение |
| --- | --- |
| Переход завершён | Приватный `state.json`: протокол SQLite v2, `stage=success`, `boot.outcome=success`, `admission_may_have_started=true`, точные `transition_id` и `generation_id` в `admission`, `boot` и `state.new`. Стадии `rolled_back`, `failed_preflight`, `degraded` и любая промежуточная стадия не подходят. |
| Выбрана новая БД | `active-db.json` указывает на `state.new` этого перехода. Новая БД существует, имеет канонический путь и прежнюю зарегистрированную идентичность, проходит журнал миграций, integrity и foreign keys. `state.old` и `state.new` не совпадают. |
| Работает принятый выпуск | `last_good` соответствует `candidate`, `boot` и точному SHA установленного Release. Два работающих канала используют образ и путь `state.new`; нет дублирующего polling или чужого writable mount. Техническая приёмка подтверждает unit и восстановленный backup timer. |
| Нет незавершённого recovery | Отсутствуют `deploy-in-progress` и `recovery-blocked.json`; сохранённый `state` не содержит незавершённой финализации, возврата или forward recovery. Проверка выполняется под общим deploy lock и повторяется непосредственно перед удалением. |
| Сохранён нужный backup | `state.snapshot.path` совпадает с `last_good.backup_id`. Приватный окончательный snapshot существует вне каталога поколений, его SHA-256 совпадает с сохранённым `state.snapshot.sha256`, а SQLite проходит проверку схемы, integrity и foreign keys. Snapshot и другие backup не входят в набор удаляемых файлов. |
| Подтверждён тот же runtime | Контроллер под блокировкой сверяет ожидаемый `runtime_id` со свежей технической приёмкой. В режиме продолжения он повторно проверяет runtime, связанный с сохранённым intent. |

Граница `admission_may_have_started=true` означает, что новые writers уже могли
записать данные в `state.new`. По [действующему правилу возврата](../OPERATIONS.md#отказ-выпуска-и-возврат)
прежнее поколение после этой границы не выбирают для автоматического возврата.
До завершённого `success` оно всё ещё может быть нужно для разбора или
восстановления. Даже после `success` удаление требует всех перечисленных
технических доказательств.
Команда также отказывает, если обнаружит открытый дескриптор old или sidecar
через Linux `/proc`. Проверки Docker mounts и дескрипторов не исключают новое
открытие файла сразу после осмотра; перед реальной очисткой оператор должен
отдельно исключить доступ host CLI и внешних процессов в согласованном окне
работ. Linux-проверка `/proc` испытана в изолированном контейнере с временной
SQLite: открытый old FD дал отказ до записи intent, после закрытия повтор
завершился.

## Остановиться при отказе доказательства

Не удалять файл при любом расхождении SHA, версии, поколения, selector,
`last_good`, boot, работающих контейнеров или `runtime_id`, а также при
неуспехе проверки backup, занятом lock, marker,
незавершённом recovery, `rolled_back` либо неизвестной стадии. Не трактовать
отсутствующий старый файл как уже завершённую очистку без отдельной
подтверждённой записи её результата. Сохранить активную БД, snapshot,
backup, selector, `state` и recovery-файлы для разбора владельцем.

Реализован read-only контракт шага 9.2 в
[`read_selected`](../../scripts/deploy_database_switch.py). Пока в durable
`state` нет `old_generation_cleanup`, проверка требует идентичность **обоих**
поколений. После удаления отдельная процедура должна записать версионированную
привязку к `transition_id`, прежним path/device/inode и новому поколению.
Только при точной записи, `stage=success`, `boot.outcome=success`, selector на
`new`, совпадении `last_good` с candidate/boot и отсутствии прежнего файла и
его sidecars проверка разрешает отсутствие `old`. Новая БД всё равно проходит
полную проверку идентичности и схемы. Частичная запись, старый selector,
незавершённый переход и пропавший `new` дают отказ. Создание записи и
удаление файла реализованы на шаге 9.3 и проверены на отдельных временных БД
с актуальными миграциями. Одновременное наличие
`old_generation_cleanup` и `old_generation_cleanup_intent` считается
противоречивым состоянием и закрывает чтение выбранной БД.

## Выполнить ограниченную очистку

Runner читает свежую техническую приёмку из установленного controller
snapshot и передаёт точный runtime в root-wrapper:

```sh
sudo -n /usr/local/sbin/deploy-prod vX.Y.Z --cleanup-old PASTE_FULL_SHA "$RUNTIME_ID"
```

При разборе частичного удаления root-оператор берёт идентификатор только из
сохранённого `old_generation_cleanup_intent.runtime_id` в приватном
`state.json`. Полный state и runtime остаются вне журнала GitHub Actions.
[Рабочая инструкция](../OPERATIONS.md#удалить-прежнее-поколение-sqlite-после-приёмки)

Команда удерживает общий deploy lock и заново сверяет `success`, boot,
`last_good`, выбранную новую SQLite, два работающих канала и окончательный
snapshot. Она сверяет SHA-256, схему, integrity и foreign keys snapshot, а
также путь, device и inode старой БД и отсутствие открытых дескрипторов old.
Перед удалением сохраняется durable
`old_generation_cleanup_intent`, включая inode присутствующих SQLite sidecars.
После каждого удаления каталог синхронизируется. Команда удаляет только
зарегистрированные `old` и его sidecars, затем записывает
`old_generation_cleanup`. Активная БД, snapshot, другие backup, selector,
state и recovery-файлы остаются на месте.

Если процесс прервался после удаления, повтор сверяет intent и все ещё
существующие inode. При частичном удалении он отдельно сверяет selector, новую
SQLite, boot, работающие каналы, mount, image, unit, timer и тот же
`runtime_id`: обычная приёмка до completion намеренно требует старую БД.
Новый sidecar или замена файла закрывают повтор. Когда все зарегистрированные
файлы отсутствуют, команда фиксирует завершение и повторяет полную
техническую приёмку для того же `runtime_id`. До завершения другие читатели
намеренно не принимают отсутствие `old`; оператор должен разобрать
прерванный сеанс и безопасно повторить очистку.

Контракт читают техническая приёмка, штатный boot, ночной backup и подготовка
следующего выпуска. Локальный тест подтвердил ту же техническую приёмку и
`runtime_id` после очистки, backup с записью из новой БД и чтение выбранного
поколения перед следующим выпуском.

## Проверить отказные границы на временных БД

На 12 ноября 2026 года локальные поведенческие испытания в проектном venv на
Windows используют отдельную временную SQLite для каждого случая и применяют
все текущие миграции. Проверены успешное удаление и повтор, отказ до durable
intent, прерывание после удаления sidecar, после удаления `old` до завершения
и после `unlink` до синхронизации каталога. Повтор опирается на точный intent;
активная БД и окончательный snapshot сохраняются. Смоделированные подмены
selector, inode старого файла и sidecar, новый sidecar, отсутствие или порча
snapshot, промежуточная и неизвестная стадия, незавершённый recovery и
deploy marker закрывают удаление. Проверены также противоречивые записи
intent и completion. Отказы до первого `unlink` сохраняют старое поколение.
После `unlink` старый файл может уже отсутствовать: durable intent остаётся,
активная БД и snapshot не меняются, а завершение требует безопасного повтора.
В сценариях с намеренной подменой или удалением проверяемого файла его
сохранность не утверждается.

Linux-проверка проведена в локальном `python:3.12-slim` без сети, с временной
SQLite и текущими миграциями. Реальная ветвь `/proc` увидела открытый FD
старого файла и отказала без durable intent и удаления; после закрытия FD
повтор удалил только old, сохранив active DB и snapshot побайтово. До правки
этот же прогон выявил, что intent записывался до отказа; проверка FD теперь
предшествует первой записи intent и повторяется перед каждым `unlink`.
Сценарии `tests.test_deploy_cleanup_old` и `tests.test_cleanup_full_route`
прошли в контейнере под root (14 тестов), а также под `nobody` при root PID 1
(14 тестов, один real-FD тест пропущен из-за прав). Непривилегированный
процесс не может просмотреть `/proc/1/fd`; production helper сохраняет отказ
при такой невозможности, а остальные fixture тесты изолируют только `/proc`
gate. Работа реальных контейнеров, systemd и VPS этим прогоном не проверена.

## Проверить полный локальный маршрут

На 12 ноября 2026 года `tests.test_cleanup_full_route` прошёл в проектном venv
на Windows. Для каждого из трёх путей создана отдельная временная SQLite с
полным текущим набором миграций `0001`–`0004` и контрольной записью. Обычный и
аварийный пути проходят регистрацию и переключение поколений SQLite v2; в
аварийном пути вид выпуска задан до переключения. Третий путь начинает с
`degraded` после отказа финализации и выполняет `forward.recover` до
`success` с прежними ID двух контейнеров. Docker, systemd, Git и GitHub в этом
испытании представлены локальным транспортом, без сетевых и VPS-записей.

На каждом пути свежая техническая приёмка даёт `runtime_id`.
Неверный `runtime_id` закрывает очистку до intent и удаления. С верным ID
очистка удалила ровно **два файла**: старую `app.db` и заранее созданный
закрытый `-shm` этой же БД. Повтор очистки ничего больше не удалил. Побайтово
сохранены новая активная БД, окончательный snapshot и selector; запись из
новой БД читается после очистки. Повторная техническая приёмка дала ровно тот
же `runtime_id`. Завершённый `state` читается перед следующим выпуском:
источником для его `old` и `selector_rebind` становится прежний `new`.
Подмена selector на удалённое поколение даёт отказ чтения, поэтому оно не
выбирается целью возврата. Модель публикации для того же принятого SHA создала
один Deployment и один статус `success` в памяти fake GitHub; повтор не
отправил дополнительных POST.

В сценарии этапа 11 `release_production --resume` через модель SSH получил
свежую приёмку, очистил реальную временную SQLite, перечитал ту же приёмку
и подтвердил Deployment в локальной модели GitHub. Повтор не отправил
новых POST и обошёлся без новой установки. Реальные каналы и GitHub API
в тестах представлены моделями. Подготовка следующего
перехода проверена до построения `selector_rebind`, но новый выпуск целиком не
устанавливался. Linux-проверка `/proc` и fsync каталога выполнена на временной
SQLite в контейнере; работа systemd и первый реальный запуск на VPS требуют
отдельной эксплуатационной приёмки.

## Сверить приёмку после очистки

Условия очистки задают техническая приёмка и проверка backup. На `v3.3.0`
первую запись опубликовали после согласованной очистки. В этапе 11 runner
вызывает очистку после технической приёмки и затем записывает Deployment.
Ротация базы CI идёт отдельным маршрутом.
[Первая запись](DEPLOYMENT_TRANSITION.md#первая-запись-для-v330),
[контракт выпуска из GitHub Actions](ACTIONS_RELEASE.md)

Повторная техническая приёмка и ночной backup читают новую SQLite после
завершённой записи `old_generation_cleanup`. До durable завершения обычные
читатели по-прежнему отказывают при отсутствии прежнего файла.

## Проверить результат на production

Локальные шаги 9.1–9.5 включали Linux-испытание `/proc` на изолированной
копии. Эксплуатационная приёмка шага 9.6 прошла на `v3.3.0`: владелец
подтвердил ответы `/help` в Telegram и VK и отдельно разрешил удаление
прежнего поколения. После очистки техническую приёмку повторили перед
[первой записью Deployments](DEPLOYMENT_TRANSITION.md#первая-запись-для-v330).

Перед запуском workflow оператор сверяет проверенный Linux gate с
версией установленного helper и заново читает фактические
`state`, selector, marker, контейнеры,
unit, timer и backup по
[правилам VPS](../PRODUCTION.md#ограничения-для-работы-с-vps). Установленный
controller snapshot должен содержать проверенную версию helper; сам факт
наличия кода в рабочем worktree этого не доказывает.

После технической приёмки workflow вызывает очистку для точного
`runtime_id` по
[рабочей инструкции](../OPERATIONS.md#удалить-прежнее-поколение-sqlite-после-приёмки).
Критерий завершения — durable completion, отсутствие только старой БД и её
зарегистрированных sidecars, сохранность активной БД и snapshot, успешная
повторная техническая приёмка с тем же `runtime_id`, рабочие каналы и backup
timer. Причины отказа и факт повтора записывают без содержимого SQLite и
секретов. При смене runtime или конфликте состояния и файлов удаление
останавливают для ручного разбора.
