# Запись о приёмке в GitHub Deployments

Этот документ фиксирует контракт этапа 8 для записи о выпуске, который
установлен на VPS и прошёл техническую и живую приёмку. Порядок выпуска и
команды оператора пока остаются в [RELEASES.md](../RELEASES.md) и
[OPERATIONS.md](../OPERATIONS.md); действующая запись через тег установки
описана в [схеме выпуска](CI_AND_DEPLOY.md#кто-выполняет-каждый-шаг-выпуска).
Порядок подтверждения владельцем, публикации и ротации показан в
[схеме независимой приёмки](CI_AND_DEPLOY.md#подтвердить-приёмку-и-безопасно-повторить-запись).
Проверка записи реализована как read-only функция
`scripts.deployment_acceptance.require_accepted_deployment`. Операторская
команда публикации реализована, но до завершения этапа 9 её не запускают
на GitHub. Ротация, активация pin и сводка SQLite уже читают новую запись
для выпусков после исторического `v3.2.0`.

## Формат записи версии 1

Одна принятая установка имеет один Deployment репозитория
`karateka-git/compadre-assistant` с `environment=production`,
`task=compadre:acceptance` и `ref` равным **полному SHA коммита** выпуска.
Это отдельная задача учёта приёмки: событие `deployment` с таким `task` не
запускает установку, миграцию или другой обработчик выкладки. Обработчики
событий проверяются до первой публикации записи.

При создании явно задаются `auto_merge=false`, `required_contexts=[]`,
`transient_environment=false` и `production_environment=true`. Пустой
`required_contexts` отключает дополнительную проверку произвольных commit
statuses самим endpoint: доверенный полный CI, опубликованный immutable
Release и фактическое состояние VPS проверяются до записи своими
сценариями. `auto_merge=false` исключает создание нового коммита вместо
записи для уже установленного SHA. Ответ `201` ещё не означает приёмку.

`payload` — JSON-объект со строго определёнными полями:

| Поле | Значение |
| --- | --- |
| `schema_version` | Целое число `1`; неизвестная версия отклоняется. |
| `version` | Канонический тег опубликованного выпуска `vMAJOR.MINOR.PATCH`. |
| `sha` | Полный SHA установленного коммита; совпадает с `ref` и ответным `sha` Deployment. |
| `kind` | `ordinary` или `emergency` из технической приёмки. |
| `release_id` | Положительный ID проверенного immutable GitHub Release. |
| `run_id` | Положительный ID точного полного прогона CI этого выпуска. |
| `run_attempt` | Положительный номер принятой попытки этого прогона. |
| `generation_id` | Идентификатор выбранного поколения SQLite: 32 строчные шестнадцатеричные цифры. |
| `migration` | Последняя применённая миграция SQLite вида `NNNN_name.sql`, включая `0001_initial_schema.sql`. |

Эти поля соответствуют действующей технической приёмке и аннотации тега
установки. Читатель сверяет их с Release, CI, ожидаемой миграцией коммита и
свежим `last_good` на VPS; неизвестные или дополнительные поля, неверные
типы и несовпадение значений закрывают допуск. `runtime_id` остаётся у
оператора: владелец подтверждает для него живые ответы Telegram и VK, а
оператор перед публикацией заново получает техническую приёмку того же
runtime. В GitHub `runtime_id` не служит доказательством и не записывается.

`description` Deployment содержит `Приёмка vX.Y.Z на VPS`. После записи
текущий статус должен быть `success` с `environment=production`,
`auto_inactive=false`, `description` вида
`Принято vX.Y.Z; CI run 123 attempt 1` и `log_url`,
указывающим на проверенный `html_url` полного прогона Actions. Номер
попытки остаётся в payload и описании: ссылка на run сама по себе его не
удостоверяет. Версия видна в обоих описаниях, установленный коммит — в
истории Deployments, CI открывается по ссылке статуса. Эти подписи и URL
помогают человеку, но допуск опирается на проверенные поля и текущий
статус, а не на текст или ссылку. Историю прежних статусов не используют
как долговременное доказательство: GitHub сохраняет их 90 дней, сохраняя
текущий статус Deployment.

`auto_inactive=false` явно исключает изменение статусов прежних Deployments
при публикации приёмки. По документации GitHub автоматическая деактивация
при `success` и так относится к прежним непроизводственным окружениям;
отдельная задача учёта не должна зависеть от этого значения по умолчанию.

## Автор и права

Доверенный автор Deployment **и** статуса `success` — существующая учётная
запись владельца `karateka-git` (`creator.id=42288695`,
`creator.login=karateka-git`). Публикующий сценарий проверяет свой токен
через `/user` перед записью; читающий сценарий проверяет оба поля `creator`
в ответах GitHub. Токен другого пользователя или GitHub App не подтверждает
приёмку даже при праве записи. Владелец отдельно разрешает создание записи
после живой приёмки; наличие токена не заменяет это решение.

| Сторона | Права в репозитории |
| --- | --- |
| Машина оператора | `Deployments: write` для создания Deployment и статуса, `Contents: read` для тега и манифеста Release; действующие права чтения Release и CI сохраняются. |
| VPS | `Deployments: read` для Deployment и текущего статуса вместе с действующими `Actions: read`, `Contents: read` и `Variables: read` для проверки CI, Release и pin. Токен VPS не получает право записи. |

Ошибки доступа закрывают допуск. При переходе на другой тип доверенной
учётной записи или изменении её ID контракт и проверка автора должны
изменяться отдельным reviewed изменением.

## Переход от тега установки

Тег `production/v3.2.0` остаётся исторической записью и источником допуска
для текущей ротации базы CI. Запись Deployments для него задним числом не
создаётся. Первую запись создают после установки и приёмки **следующего**
выпуска по завершении этапа 9. `v3.2.0` — единственное исключение: для него
ротация и активация по-прежнему сверяют тег установки. Для любого другого
выпуска они уже требуют единственный проверенный текущий `success`; отсутствие
записи останавливает переход, а тег произвольной новой версии не служит
fallback. После первой записи нового `last_good` отдельное переключение
проверки не нужно.
[Локальный протокол перехода и отказов](DEPLOYMENT_TRANSITION.md)

Сводка SQLite для `v3.2.0` сохраняет поля исторического тега. Для следующей
версии она читает Deployments через общую проверку: при `success` показывает
`generation_id`, `applied_migration`, `deployment_id` и `deployment_status_id`.
Это реквизиты проверенной записи GitHub, а не независимое доказательство
текущего состояния VPS. При отсутствии записи или неуспешном статусе сведения
о принятой SQLite остаются пустыми, а `installation_status=pending` и
`deployment_state` показывают причину. Конфликт, дубликат или ошибка API
останавливают сводку.
Сводка не читает VPS: перед ротацией и активацией эти данные повторно
сравниваются со свежим `last_good` и технической приёмкой.

Локальные сценарии подтверждают одинаковый допуск для обычной и аварийной
установки. После `forward recovery` оператор получает новую техническую
приёмку; изменившийся `runtime_id` не меняет payload записи, если точный SHA,
Release, CI и поколение SQLite остались теми же. Если статус стал отказным,
ротация и активация прекращаются до записи pin. Перед обновлением GitHub pin
и запуском полного CI ротация заново читает текущий статус Deployment.

## Проверить запись без изменения GitHub

Читатель сначала сверяет свежую техническую приёмку с immutable Release,
точной попыткой CI в манифесте обычного выпуска и миграцией точного SHA.
Затем он запрашивает все страницы Deployments с фильтрами `sha`, `task` и
`environment`. Отсутствие записи означает отсутствие приёмки. Два и более
результата означают конфликт даже при совпадающих payload. Для единственного
результата проверяются полный `ref` и `sha`, окружение, задача, payload версии 1,
признаки production/non-transient и автор. Читатель получает все страницы
статусов и выбирает самый новый по `created_at`: порядок элементов API не
служит доказательством. Два статуса с одинаковым максимальным временем
делают результат неоднозначным и закрывают допуск. Автор и окружение
выбранного статуса должны совпасть.
Только текущий доверенный `success` даёт допуск. Неизвестный статус остаётся
`UNKNOWN` и допуска не даёт. Ошибка API не превращается в отсутствие записи.

На локальной модели GitHub API с аннотированным релизным тегом проверка
одной записи потребовала **6 GET**: Release, ref, объект тега, каталог
миграций, страницу Deployments и текущий статус. Отсутствующая запись —
**5 GET**, поскольку статус читать не у чего. Если первая страница содержит
100 записей, читатель запрашивает вторую страницу и затем отказывает из-за
дубликатов: **6 GET** до отказа. Число запросов зависит от формы релизного
тега и количества страниц; 101 статус потребовал **7 GET** и нашёл отказ
на второй странице. Это замер локальной модели, не сетевой замер GitHub.

## Подготовить и повторить публикацию

После новой установки оператор читает техническую приёмку командой
`python -m scripts.publish_deployment_acceptance vX.Y.Z <полный-SHA>
--ssh-host <user@host> --known-hosts <путь>` с проверенным SSH-ключом хоста.
Она выводит `runtime_id` и состояние существующего Deployment без записи.
Владелец проверяет живые ответы Telegram и VK именно для этого runtime.
**Первую реальную публикацию выполняют лишь после приёмки следующего выпуска
по завершении этапа 9**; `production/v3.2.0` задним числом не переносится.

Для записи владелец даёт явное решение и предоставляет оператору токен с
`Deployments: write`. Оператор согласует один сеанс записи и запускает ту же
команду с `--publish --confirm-live <runtime_id>`. Скрипт заново читает VPS,
проверяет совпадение runtime, автора токена, immutable Release, точную
успешную попытку CI и ожидаемую миграцию. Затем он читает существующую запись.
Если подтверждён `success`, повтор завершается без POST. Если Deployment
существует без статуса, создаётся только `success`. Другой текущий статус,
дубликат или расхождение данных требует разбора владельцем.

Для отсутствующей записи скрипт создаёт Deployment с `auto_merge=false` и
полным SHA, перечитывает GitHub, создаёт `success` и вновь перечитывает
результат. `runtime_id` не отправляется в GitHub. При потере ответа любого
POST сначала выполняется чтение. Если запись после него не подтверждена,
скрипт останавливается; следующий запуск снова начинает с чтения и не
создаёт второй Deployment при уже существующем. API не даёт атомарного
ограничения уникальности пары SHA/task/environment, поэтому одновременные
сеансы записи запрещены процессом, а обнаруженный дубликат закрывает допуск.

В текущих `.github/workflows/` нет обработчиков событий `deployment` и
`deployment_status`: публикация с `task=compadre:acceptance` не запускает
установку. Перед первым реальным созданием оператор повторно проверяет
действующие workflow и другие webhook-потребители этого репозитория.

## Основание формата

GitHub REST API поддерживает фильтрацию Deployments по `sha`, `task` и
`environment`, JSON `payload`, явный `auto_merge` и `required_contexts`.
Статус содержит собственного автора, `description` и `log_url`; текущий
статус является состоянием Deployment. См. [Create/List Deployment](https://docs.github.com/en/rest/deployments/deployments)
и [Create/List Deployment status и срок хранения](https://docs.github.com/en/rest/deployments/statuses).
