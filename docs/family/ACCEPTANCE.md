Здесь зафиксированы результаты проверки «Семьи» для целевой версии
`v4.2.0`. [Требования](REQUIREMENTS.md), [план](PLAN.md) и
[инструкция для пользователя](../RUN.md#вести-семейный-список-покупок).

## Локальный прогон 16.11.2026

Проверена чистая рабочая копия `codex/family` на коммите
`c515bd352bc6c4a733f12a2b706a54edf98a3c54`. Тесты выполнены на Windows
через Python 3.12.10 из проектной `.venv` основной рабочей папки.
Семейные сценарии использовали отдельные временные SQLite-БД и подмены
API Telegram и VK.

На Windows пропущены три проверки развёртывания. Первая требует Linux
`/proc` с доступом к файловым дескрипторам других процессов, вторая
использует Linux `flock`, третья требует Linux с `systemd-analyze` и Docker CLI.

- На временной БД с миграциями `0001`–`0006` применена только `0007_family.sql`.
  Профиль, связь канала, активный режим и личный выбор сохранились.
  Повторное применение пропустило уже установленную миграцию. На свежей БД
  проверены ограничения владельца, недопустимость второго членства и
  удаление связанных данных закрытой семьи. Обе проверки БД включали
  `integrity_check` и `foreign_key_check`.
  [Сценарии миграции](../../tests/test_family_migration.py).
- Сборка с включённым `family` допускает зарегистрированный профиль
  в личном чате. При отключении меню скрывает команду, а диспетчер отклоняет
  вход. При повторном включении членство сохраняется. Проверены
  создание, одноразовые приглашения, связанный профиль в двух каналах,
  подтверждение действий в исходном чате, потеря доступа, передача роли и
  закрытие семьи. [Сценарии профиля и членства](../../tests/test_family_channels.py).
- Адаптеры обоих каналов получили новые кнопки при последовательном
  обновлении сообщения. Проверены навигация, устаревшие кнопки, отказ
  редактирования и ручные команды. [Сценарии Telegram и VK](../../tests/test_family_shopping_channels.py).

## Совместимость с установленной версией

Дополнительный локальный прогон проверял точную пару `v4.1.0`
(`18e8dd0cec81857f1c80b8a8d8fba34c1a057afd`) и кандидата
(`cd7211dfd0246433bd9a190bbf9e483d6873fb76`). Подготовка тестовых данных,
миграция и проверки целостности прошли. Все 26 отдельных сценариев
совместимости прошли. [Сценарий проверки](../../scripts/check_repository_compatibility.py).

В полном наборе `v4.1.0` из 1401 теста прошли 1397, три пропущены, один
завершился ошибкой утверждения. `test_migration_renames_only_the_ai_ids`
на наложенных миграциях ожидал список только из `0006_ai_capability_id.sql`
и получил также `0007_family.sql`. Из-за этого скрипт не запустил финальную
проверку кандидатом изменений, внесённых предыдущей версией. Допуск
`v4.2.0` ещё не получен. Кандидат в ходе проверки не публиковался.

### Подготовить переход через патч линии 4.1

В локальных ветках `codex/ai-0006-fixture-main` (`0f9db57`) и
`codex/ai-0006-fixture-release-4.1` (`689dc6c`) тесты перехода с `0005`
используют отдельный каталог с миграциями по `0006` включительно. В
кандидате `v4.2.0` (`45f00d1`) удалён `test_migration_renames_only_the_ai_ids`
по согласованию с владельцем. Проверка отката при конфликте осталась.
SQL-файлы и код приложения в этих правках сохранены.

Локально 16.11.2026 полный набор кандидата `45f00d1` запустили на Windows
через проектную `.venv`. Прошли 1479 тестов, три штатно пропущены.
Обе проверки совместимости прошли полностью: `18e8dd0` → `689dc6c`
и `689dc6c` → `45f00d1`. Вторая проверка запустила тесты патча `4.1`
со схемой кандидата, включая изолированную проверку `0006`. Кандидат
прочитал изменения, которые прежняя версия записала в обновлённую БД.

Для допуска сначала нужно провести исправление через `main` и
`release/4.1`, выпустить и принять патч линии `4.1`. Затем нужно запустить
полный CI `v4.2.0` с новой принятой базой. [Порядок выпуска](../RELEASES.md#исправления-поддерживаемых-линий).

## Проверка на VPS 16.11.2026

С 12:12:55 до 12:13:33 UTC проверили кандидат `v4.2.0` из
`cd7211dfd0246433bd9a190bbf9e483d6873fb76`. Образ Docker —
`sha256:3260026d659f661a013b5e4c090c3a2a7b973e7eb00138e565b1a03540765a5f`.
Разница между этой ревизией и коммитом локального прогона состоит из правок
Markdown. Healthcheck в Linux-контейнере подтвердил конфигурацию обоих
каналов и доступность SQLite без сетевых запросов.

Перед проверкой остановили сервис ботов и таймер резервного копирования.
Одноразовый контейнер создал отдельную временную SQLite с актуальными
миграциями. Production SQLite читалась вне теста только для сверки адресов
связанных чатов. Схема и данные production не изменились.

| Действие | Результат |
| --- | --- |
| Создание семьи и приглашение | Создана семья, выдан одноразовый код, по нему вступил отдельный синтетический профиль. |
| Список в двух каналах | Для связанного профиля владельца оба канала вернули один список. Покупка обработана через Telegram, удаление через VK. Контрольное чтение подтвердило общее состояние списка. |
| Отправка и обновление | API Telegram и VK успешно отправили сообщение со списком и дважды отредактировали тот же ID сообщения в каждом из двух согласованных личных чатов владельца. |

Входящие события и нажатия подавались программно без polling. Проверка
охватила исходящую отправку и редактирование через действующие API.
Доставка входящих событий от клиентов, внешний вид меню и кнопок
в приложениях Telegram и VK остаются непроверенными. Устаревшие кнопки,
отказ после исключения, передача роли и закрытие семьи проверены локальными
тестами на временных БД.

В 12:13:33 UTC проверочный контейнер был удалён. Рабочая копия production
оставалась чистой на `v4.1.0`, коммит
`18e8dd0cec81857f1c80b8a8d8fba34c1a057afd`. Сервис ботов и таймер имели статус
`inactive`, systemd показал `Result=success` у сервиса. У обоих контейнеров
политика перезапуска `no` и статус `Exited`. Telegram завершился с кодом 0.
Docker отправил VK `SIGTERM`, через 10 секунд по тайм-ауту — `SIGKILL`.
VK завершился с кодом 137, `OOMKilled=false`. По просьбе владельца сервис
и таймер оставили выключенными.
