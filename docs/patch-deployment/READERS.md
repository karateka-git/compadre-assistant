# Прочитать приёмку Deployment v2

Читатель выбирает установленную базу CI, подтверждает ссылку из старого отчёта и показывает результат для точного Release. Подготовленный код по умолчанию читает v2. Точные условия перехода действующих runner, CI и VPS описаны в [порядке включения](ROLLOUT.md).

## Выбрать текущую базу

1. Отсутствующая переменная `COMPADRE_DEPLOYMENT_READER` выбирает `_DEFAULT_READER=v2` из закреплённого кода. Для сравнения до первой записи v2 явно задать `COMPADRE_DEPLOYMENT_READER=v1` в доверенном диагностическом процессе. Неизвестное значение закрывает допуск. При v1 GitHub GraphQL не требуется.
2. Запросить `repository.deployments(first:2, environments:["production"], orderBy:{field:CREATED_AT,direction:DESC})` с `totalCount` и полями `id`, `createdAt`, `latestStatus { id }`. Для сводки конкретного SHA применить тот же запрос к `repository.object(oid:$sha) ... on Commit`. При равном времени двух Deployments остановиться. Для статусов одной секунды GitHub прямо указывает текущий глобальный ID.
3. Сопоставить глобальный ID с `node_id` в `GET /repos/{owner}/{repo}/deployments?environment=production&per_page=10&page=1`, для сводки добавить `sha`. Затем сопоставить `latestStatus.id` в `GET /repos/{owner}/{repo}/deployments/{id}/statuses?per_page=10&page=1`. Порядок REST произволен. При отсутствии совпадения, неполном GraphQL-ответе, расхождении времени, автора, окружения или назначения остановиться. Только проверенный REST-объект даёт числовой ID, в том числе больше 2147483647.
4. Если свежая попытка v1, выбрать текущий success с максимальным временем по всей прежней истории v1. В режиме v2 переиспользуется уже проверенный статус свежей записи. Остальные точные глобальные ID передаются в `nodes(ids:)` пакетами до 50, затем для каждого Deployment проверяется одна страница REST с его точным `latestStatus.id`. Расхождение API или недостающий элемент пакета закрывают допуск. Новый v1 поверх ранее записанного v2 блокирует такой обход. При первом переходе сверить результат со старым правилом и фактической установкой.
5. При v2 и success проверить формат результата, Release, точный тег, CI и миграцию коммита. Для failure требуется квитанция возврата от доверенного автора статуса. Напрямую прочитать сохранённый `GET /deployments/{id}`, его `node(id:)` и страницу статусов. Целевая запись должна быть создана раньше, сохранять тот же текущий success и совпадать по всем реквизитам принятой базы. Вложенные возвраты закрывают допуск. Любой другой статус блокирует выбор базы. Прямая проверка старого тега или отчёта читает указанный Deployment и требует прежний текущий status ID.

## Сформировать реквизиты попытки

Payload v2 содержит ровно поля `schema_version=2`, `attempt_key`, `version`, `sha`, `kind`, `release_id`, `run_id`, `run_attempt`, `baseline`. Ключ записывается как `<run_id установки>:<run_attempt установки>`; оба числа положительные, без начальных нулей. Поля CI в payload относятся к доказательству совместимости выпуска. Объект `baseline` повторяет реквизиты принятой базы из допуска — `sha`, `version`, `release_id`, `deployment_id`, `status_id`. У обычного выпуска они должны совпасть с аннотацией тега. Для аварийного выпуска сохраняются проверки его манифеста.

В success записать `v1 gen=<32 строчных hex> migration=<имя миграции>`. Допустимое имя — четыре цифры, подчёркивание, строчные латинские буквы, цифры или подчёркивания и суффикс `.sql`. До установки проверить, что всё описание помещается в 140 символов; после установки сверить фактическое поколение и миграцию. В failure после подтверждённого возврата записать `v1 restored=<deployment_id>/<status_id>` с точными числами из baseline. Доступ к записи таких статусов имеет только доверенный автор.

## Включить перед первой записью v2

Оба caller полного CI запускают контроллер из отдельно полученного checkout внешнего `COMPATIBILITY_POLICY_SHA`. Они проверяют фактический HEAD политики и ожидаемый pin ручного запуска, затем запускают Python с `-I -B`. Текущий каталог Git остаётся checkout кандидата. Независимый harness читает базу из того же pin повторно. На VPS версия чтения берётся из проверенных байтов snapshot, поэтому работает после `env -i` в `deploy-prod`. Перед первым D18 выполнить [порядок включения](ROLLOUT.md). Откат писателя сохраняет читателей v2.

## Сверить стартовую базу при переключении

1. В согласованное окно закрыть новые ручные запуски, дождаться завершения уже запущенных release/resume и исключить отдельные публикации от имени владельца. Работать в общей секции `production-release` с `cancel-in-progress: false`. Перед первым v2 должны действовать правила единственного писателя из этапа 4. Одна проверка списка runs оставляет гонку с новым запуском.
2. Занять существующий `deploy.lock` VPS. Проверить завершённый stage, отсутствие marker и блокировок recovery, фактические checkout/образ, штатную приёмку обоих каналов и неизменность `last_good`, SQLite generation и миграции. Учитывать, что повторная команда, самостоятельно берущая тот же lock, не сможет его занять. Использовать проверку внутри уже удерживаемой блокировки.
3. В той же секции выполнить старый выбор v1 по текущим success во всей истории, новый выбор v2 и прямую сверку точных ID. Сравнить SHA, версию, Release ID, Deployment ID, status ID с полученной приёмкой и базой аннотации первого кандидата. При любом разногласии остановить переход до выяснения причины.
4. Сохранять исключение других писателей до подтверждённого создания и перечитывания первой попытки v2 со ссылкой на эту базу. До переключения на VPS повторить сверку неизменных и изменяемых условий из этапа 4. Потерявший блокировку процесс начинает проверку заново. Датированное наблюдение из разработки не переносится в допуск первого выпуска.
