# Исходный расход HTTP при PATCH

Замер от 19.11.2026 фиксирует расход до исправления PATCH и перехода на
Deployment v2. Он воспроизводится локально для PATCH `v4.2.0` → `v4.2.1`
с двумя парами слитых PR, 16 исходными Deployment со статусом `success`,
16 предыдущими версиями и одной миграцией. GitHub API отвечает локальной
фикстурой. Метрики считаются в [штатных HTTP-клиентах](../DEPLOY_METRICS.md#как-снять-расход-http-выпуска).

## Воспроизвести замер

Исторический замер воспроизводится из корня checkout коммита `8c1c105`
через Python проектного `.venv`.

```text
python -m tests.test_patch_http_baseline
```

В выходном JSON `summary` содержит суммы, а `scenarios` сохраняет
агрегаты по этапам и отчёты отдельных SSH-вызовов. Фикстура независимо
сверяет суммы HTTP-попыток с полученными запросами. Для автоматической
проверки исходных маршрутов откройте тот же checkout и запустите
`python -m unittest tests.test_patch_http_baseline`. Команда на рабочей
ветке измеряет текущую реализацию. [Код фикстуры](../../tests/test_patch_http_baseline.py)

| Сценарий | Место | GET API | POST API | GET базы¹ | Страницы | Ошибки | GET хранилища ZIP | HTTP, мс² |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Публикация и установка (`publish`) | runner | 282 | 5 | 60 | 105 | 1 | 2 | 93,59 |
| Публикация и установка (`publish`) | VPS | 57 | 0 | 40 | 37 | 0 | 0 | 3,77 |
| Установка готового Release (`install_ready`) | runner | 38 | 2 | 0 | 8 | 0 | 0 | 2,60 |
| Установка готового Release (`install_ready`) | VPS | 57 | 0 | 40 | 37 | 0 | 0 | 3,88 |
| Продолжение после установки (`resume`) | runner | 32 | 1 | 0 | 7 | 0 | 0 | 3,15 |
| Продолжение после установки (`resume`) | VPS | 0 | 0 | 0 | 0 | 0 | 0 | 0 |
| Checkout на другом SHA (`wrong_checkout`) | runner | 2 | 0 | 0 | 0 | 1 | 0 | 0,11 |
| Checkout на другом SHA (`wrong_checkout`) | VPS | — | — | — | — | — | — | — |

¹ Колонка `GET базы` входит в `GET API`. Runner при первой публикации
трижды читает список Deployments и 16 списков статусов, затем при каждой
сверке делает ещё три чтения Release, тега и миграций принятой базы.
Контроллер выполняет два таких обхода, по одному при подготовке и перед
переключением. Ошибка в первой и последней строке runner — ожидаемый 404
для отсутствующего Release.

² Время HTTP — наблюдение одного прогона на Windows и Python 3.12.10.
Оно включает работу локальных обработчиков ответов, в том числе создание
тега в Git во время эмуляции POST. Полное время сценариев по порядку
составило 6,69 с, 1,82 с, 0,59 с и 0,16 с. В повторном замере сравнивайте
число запросов, время зависит от машины и нагрузки.

## Условия и охват

- В первом сценарии старый публикатор получает чистый локальный checkout
  на SHA вершины `release/4.2`. Он действительно проверяет два merge и
  связи PR с `main`, публикует тег и Release, после установки пишет
  Deployment и его статус. В сценарии `wrong_checkout` локальный HEAD
  взят с другой вершины `main`. Проверка HEAD останавливает тот же
  публикатор до записи и SSH.
- В `install_ready` стартует тот же уже опубликованный Release, а запись
  Deployment ещё отсутствует. В `resume` этот же Release уже установлен
  и имеет Deployment без статуса. Runner повторяет приёмку и очистку,
  затем записывает один статус.
- Runner выполняет обычный `release_production`, настоящий публикатор,
  выбор Release и CI, проверку ZIP и чтение/запись Deployment. Контроллер
  выполняет обычный `deploy-prod` с настоящим поиском Release и CI,
  проверкой аннотированного тега, policy и Deployments при подготовке и
  перед переключением. Git читает локальные объекты, контроллер создаёт
  временную SQLite-копию, а HTTP-клиенты выполняют разбор ответов фикстуры.
- Доставка SSH, Docker/systemd, системное переключение SQLite, проверка
  готового runtime и удаление старой БД подменены локальными результатами.
  Команды приёмки и очистки запускают штатный CLI и отдают отдельные
  отчёты. В `resume` эти команды имеют нулевой HTTP-расход. При отказе на
  другом SHA команды VPS не запускались. Фактические запросы и время
  выкладки проверяются отдельно при эксплуатационной приёмке.

## Сравнить расход после исправления PATCH

Повторный локальный замер на Windows и Python 3.12.10 использует тот же
PATCH, две пары слитых PR, 16 Deployments со статусом `success`, 16
предыдущих выпусков и одну миграцию. Запустите те же команды в checkout
с исправлением. Runner работает из отдельного shallow checkout `main`.
Фикстура через Git проверяет, что у runner отсутствует объект кандидата.
В модели GitHub и VPS есть полная история кандидата и обе пары PR.

| Сценарий | Место | GET API до → после | POST API после | GET базы после | Страницы после | Ошибки после | GET хранилища ZIP после |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Публикация и установка | runner | 282 → 265 | 5 | 60 | 93 | 1 | 2 |
| Публикация и установка | VPS | 57 → 57 | 0 | 40 | 37 | 0 | 0 |
| Установка готового Release | runner | 38 → 38 | 2 | 0 | 8 | 0 | 0 |
| Установка готового Release | VPS | 57 → 57 | 0 | 40 | 37 | 0 | 0 |
| Продолжение после установки | runner | 32 → 32 | 1 | 0 | 7 | 0 | 0 |
| Продолжение после установки | VPS | 0 → 0 | 0 | 0 | 0 | 0 | 0 |

При публикации runner отправил на 17 GET API меньше. Запросы страниц
сократились со 105 до 93. До создания Release runner запрашивает
двух родителей каждого merge одним GET на SHA и каталог миграций кандидата
одним GET. Чтения workflow, списка запусков и jobs подтверждённой попытки
выполняются по одному при подготовке, перед тегом и после создания ref.
Установка отдельно подтверждает закреплённую попытку опубликованного
Release.

Сценарий `wrong_sha` передаёт SHA `main` как кандидата и останавливается
после 3 GET без записи и SSH. Исторический `wrong_checkout` передавал
верный SHA кандидата, но запускался с checkout `main` и останавливался
после 2 GET. Интеграция также подтверждает остановку до записи при сдвиге
ветки во время проверки, неполном ответе о родителях, неверной связи PR,
CI другого коммита и неуспешном обязательном job. Ручная публикация
проходит после проверки чистого checkout точного кандидата.

Суммарное время HTTP первой публикации составило 173,05 мс на runner
и 4,57 мс на VPS. Полное время сценариев составило 5,68 с, 1,93 с,
0,61 с и 0,08 с соответственно. Это наблюдения одного прогона.
При сравнении расходов используйте число запросов.

## Подготовить измерение штатного пути v2 на этапе 5

1. Возьмите те же две пары PR, одну миграцию, shallow checkout runner из `main` и точный Release. Для обычного v2-пути подготовьте принятую базу **v2** и две истории на 16 и 1000 Deployment при одном и том же кандидате. Оставьте 16 прежних Release в обоих случаях: дополнительные Deployment меняют только историю установок. Для первой установки поверх истории v1 проведите отдельный прогон. Однократная сверка всех v1 под блокировкой выполняется перед резервированием и перед выдачей права первого POST.
2. Запускайте `release_production.main()` и ограниченный `deploy_prod.main()` с `--attempt`. Сохраните транспортный счётчик отдельно для runner и VPS. Старый стенд `_ControllerFixture` имитирует legacy-приёмку: для v2 нужны запись исходной базы до кандидата, ключ исходного и нового run, ответы Actions по каждому run/attempt, GraphQL и REST текущих записей, root-журнал с правами POST и привязанный к нему переход контроллера. Допускается моделировать контейнеры и удаление на временной БД. В `_ControllerFixture.execute` возвращайте для `deployment-attempt.json` реальный сохранённый JSON, а для `github-read-token` и `compatibility-policy.sha` их отдельные значения фикстуры. Оставьте настоящие проверки Release, обеих пар PR, допуска VPS, D17/D18 и обработку HTTP.
3. Отделите REST GET и GraphQL query как чтения. Read-only запрос к `/graphql` физически использует POST. Отдельно считайте записи REST на создание Deployment и его статусов; включите записи тегов и Release в общий расход runner. Старая сводка `_summary` считает только GET в фазе `deployment_base`. Для полной картины сверяйте результат с маршрутом каждого запроса на локальном транспорте. В частности, прямые проверки D17 и актуальности D18 могут выполняться при публикации и в команде VPS, а запросы Release/тега/CI входят в общую стоимость.
4. Для `publish`, `install_ready`, `resume` и отказа на другом SHA сохраняйте все HTTP-отчёты, число постраничных запросов, ошибки, ZIP после redirect и полное время сценария. Сравните фактические записи транспорта с суммой отчётов. Для свежего установленного кандидата ожидаются одна запись D18, один `in_progress` и один `success`. Возврат и потерю ответа измеряйте отдельными сценариями. До включения писателя проверьте [эксплуатационные условия и матрицу обрывов](RECOVERY.md).
