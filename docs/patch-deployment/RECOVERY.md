# Продолжить попытку Deployment v2

Эта процедура применяется после включения писателя v2. Сначала найдите исходный run и его attempt в Actions. Сверяйте GitHub с контроллером по [контракту чтения](READERS.md) и соблюдайте [порядок доступа к VPS](../PRODUCTION.md). Журнал принадлежит root и расположен рядом с `state.json` под именем `deployment-attempt.json`.

## Продолжить из Actions

1. Для нового выпуска используйте режим `release`. После публикации runner резервирует на VPS исходный ключ `run_id:run_attempt`. В журнале сохраняются полная ссылка на принятую базу, фактическая приёмка, SHA контроллера и владелец. После D18 контроллер записывает его числовой ID.
2. При обрыве дождитесь окончания конкретного run/attempt. Запустите `resume` с теми же версией и SHA и укажите исходный ключ в `source_attempt`. Пример номера — `12001:1`. Новый запуск получает владение только после подтверждения GitHub, что предыдущий владелец завершён. Этот порядок подходит и до выдачи первого права POST.
3. Если POST уже отразился в GitHub, runner сверяет последнюю попытку по полному payload и текущему доверенному статусу. После потери ответа на установку контроллер проверяет durable этап. Для незавершённого перехода со своим ключом и D18 он использует существующий recovery. При подтверждённом кандидате завершает сохранённое намерение очистки и повторяет приёмку того же runtime. При подтверждённом старом выпуске, поколении и миграции записывает failure с прямой ссылкой на D17.
4. Если попытка закрыта и ещё остаётся последней, тот же `resume` повторно удостоверяет итог. Установка и завершённое удаление SQLite выполняются один раз. Если GitHub принял success, но затем изменились runtime или статус, контроллер оставит выпуск для разбора.

## Разобрать отказ записи

Для каждого POST контроллер сохраняет разрешение до отправки. Общий этап `finish` принадлежит одному терминальному статусу. Остановка между выдачей разрешения и отправкой внешне может выглядеть так же, как потерянный ответ GitHub.

- При таймауте сначала используйте обычный `resume`. Если запись появилась, он подтвердит её по ID, автору и текущему состоянию. Если новая запись ещё не видна, сохраните исключение других писателей. Отсутствия строки в списке после таймаута недостаточно для повторной отправки.
- После подтверждённого отказа GitHub (например, HTTP 422 непосредственно на POST) проверьте причину и устраните её. При неопределённом результате потребуется независимое подтверждение, что GitHub окончательно отклонил запрос либо оператор установил, что запрос вообще не отправлялся. До получения такого подтверждения оставьте резервацию открытой. Проверяйте именно запрос последней выдачи разрешения данного этапа.
- В согласованное окно оператор проверяет завершение последнего владельца, реквизиты журнала, текущие D17/D18, статус и фактическое состояние VPS. После доказанного неисполнения запустите через ручной административный вход `sudo -n /usr/local/sbin/deploy-prod VERSION --reconcile-rejected-post SHA KEY SNAPSHOT ACTION`. Подставьте точные значения из журнала. Для `ACTION` допустимы `create`, `in_progress` или `finish`. Контроллер перепроверяет базу или предшествующий статус под lock и снимает только последнее намерение. Новый `resume` повторит соответствующий шаг. Закрытый SSH-вход runner этой команды не предоставляет.
- До выдачи права `create` оператор также может отменить резервацию этой командой с `ACTION=cancel`. После выдачи права сначала требуется отдельная сверка спорного запроса. Команда отмены проверяет отсутствие D18 этой попытки и сохранность базового runtime. При частичном выпуске продолжайте открытую попытку по её ключу. При повреждении состояния, degraded или работе прежнего образа на новом поколении потребуется эксплуатационный разбор. Файлы журнала, selector, backup и SQLite вручную не менять.

После ошибки systemd-финализации со штатными признаками forward recovery владелец может в согласованное окно выполнить `sudo -n /usr/local/sbin/deploy-prod VERSION --recover-attempt-forward SHA KEY SNAPSHOT`. К этому моменту прежний runner должен закончить работу. Контроллер проверяет точные D18, образ, выбранную БД и сохранённые контейнеры, прежде чем продолжить штатное восстановление. Затем возобновите исходный D18 через Actions. Остальные degraded-состояния по-прежнему требуют индивидуального разбора.

## Подготовить эксплуатационную проверку

На этапе 5 проверить реальные права VPS на чтение `GET /actions/runs/{run_id}/attempts/{run_attempt}`, включая текущий и завершённый запуски, а также политику и права всех [читателей](READERS.md). Проверить изолированные импорты snapshot и зафиксировать его SHA в переменной окружения GitHub `PRODUCTION_CONTROLLER_SHA`. Для выделенного ключа v2 настроить `restrict,command="/usr/bin/python3 -I /usr/local/lib/compadre-assistant-deploy/deploy/attempt-ssh.py"` и ограниченный sudo штатного wrapper. В согласованное окно перекрыть прежние независимые пути записи до первого D18.

Оставленная без настройки переменная `PRODUCTION_DEPLOYMENT_WRITER` выбирает v1. После проверки закреплённого читателя v2 на runner, VPS и в CI, отдельного ключа и точного snapshot включение `v2` разрешает открытия. Значение `resume-only` закрывает новые выпуски до публикации и сохраняет возможность завершить открытый D18. С момента появления первой попытки v2 сохраняйте читатель v2 и исключение конкурирующих писателей.

## Сверить проверку обрывов

Локальный стенд запускает обычные `release_production` и команды контроллера с временным журналом. Системную установку, очистку и ответы GitHub моделирует фикстура. На Ubuntu 24.04 дополнительно проверены реальный межпроцессный `flock`, сохранение приватной резервации после освобождения lock и автономный импорт проверенного Git-снимка. Эти проверки не обращались к production. [Сценарии runner и контроллера](../../tests/test_deploy_attempt.py) · [Сценарии GitHub POST](../../tests/test_deployment_writer.py)

| Где прервалась попытка | Что проверено при повторе |
| --- | --- |
| После создания тега, до Release | Занятое имя блокирует публикацию до D18. [Проверки публикатора](../../tests/test_publish_release.py) |
| После создания D18 без статуса | Другой run с исходным ключом продолжает тот же Deployment. |
| После записи `in_progress`, до старта VPS | Подтверждённое отсутствие намерения установки разрешает ровно один install. |
| После старта или потери ответа установки | Завершённый кандидат проходит приёмку. Неизвестный state сохраняет блокировку. Работа прежнего образа на новом поколении исключает failure с возвратом на D17. |
| После завершившегося возврата | Только совпадающие D17, статус, выпуск, поколение и миграция разрешают закрыть D18 с `failure`. |
| После удаления прежней SQLite | Новый owner сверяет сохранённый runtime и завершение очистки. `unlink` не повторяется. Обрывы внутри очистки проверяет [набор SQLite cleanup](../../tests/test_deploy_cleanup_old.py). |
| После записи `success` или закрытия журнала | Следующий запуск подтверждает тот же числовой статус, runtime и результат. |
| При ручном полном CI из `main` и `release/X.Y` | Другой ожидаемый policy pin и открытый D18 блокируют допуск. Смена статуса между решением caller и проверкой закреплённого harness отменяет устаревшую пару. [Проверка обоих читателей](../../tests/test_deployment_reader_v2.py) |

Для переключения закрепите читатель v2 в версии `scripts/full_ci_controller.py` и импортируемого им `deployment_acceptance.py` во всех ветках, запускающих полный CI. Внешний `COMPATIBILITY_POLICY_SHA` должен указывать на проверенный commit с читателем v2 в независимом harness. Тот же policy pin требуется на VPS. После ротации вызовите `main-full.yml` и `release-full.yml` с точными `expected_sha` и `expected_policy_sha` и проверьте источник harness, `accepted-baseline` и evidence. Сценарий v1 остаётся допустимым до первой записи v2. [Контракт читателей и результаты прежних проверок](READERS.md)

На Ubuntu 24.04 с Python 3.12.3 из ровно `1c5e3df6f3d1465b147bf735f9622016b437db5f` собран архив из 75 файлов (SHA256 `38b53d467a64674daab4ac6ab88a5ff21553deaea086150ce238f88d27413882`). Проверены manifest, режимы и root-владение распакованных файлов, изолированные импорты и CLI вне checkout. Для отдельно собранного исторического snapshot `6de377cf402483c32faa63b805f6420df434fe70` тот же вызов с `--attempt` отказал при разборе аргументов до создания каталога состояния. При установке на этапе 5 сверьте SHA выбранного для эксплуатации коммита и digest его собственного архива.
