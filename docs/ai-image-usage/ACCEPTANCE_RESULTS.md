## Подготовить тестовое окружение

При завершении локального шага 14.11.2026 в worktree не было `.env`.
Ниже сохранён способ запуска с выделенными тестовыми ботами. Для шага 2
владелец согласовал проверку на VPS со штатными ботами на время остановки
штатного сервиса.
[Протокол проверки на VPS](#согласованная-проверка-на-vps).

1. В корне выбранного checkout записать SHA через `git rev-parse HEAD`.
   Выбрать проектный Python по правилам [AGENTS.md](../../AGENTS.md#рабочий-порядок).
   Для нового окружения установить зависимости по
   [инструкции](../SETUP.md#разработка-без-docker).
2. Скопировать `.env.example` в локальный `.env` и заполнить
   `TELEGRAM_BOT_TOKEN`, `VK_BOT_TOKEN`, `VK_GROUP_ID`, `ASK_BASE_URL`,
   `ASK_API_KEY`, `ASK_MODEL` параметрами выделенного окружения.
   Включить `ENABLED_CHANNELS=telegram,vk` и `ENABLED_CAPABILITIES=ask,admin`.
   `ADMIN_TRUSTED_APP_USER_IDS` сначала оставить пустой. Для проверки
   отчёта заполнить `ADMIN_TIMEWEB_API_TOKEN`, `ADMIN_TIMEWEB_KEY_ID` и
   проверить `ADMIN_TIMEWEB_CURRENCY` по
   [настройке источника](../SETUP.md#подключить-статистику-timeweb).
   Запросы Ask и OCR направить через тот же выделенный ключ.
   Использовать новый путь `DATABASE_PATH`, например
   `data/ai-image-usage-acceptance-01.db`. Перед миграцией проверить, что этот
   файл ещё не существует, и что процессы не унаследовали одноимённые
   переменные окружения с другими настройками. Секреты оставить в локальном
   окружении.
3. Перед стартом подтвердить доступ к обоим тестовым ботам и отсутствие
   другого polling на тех же ботах. Выполнить из корня checkout команды ниже
   с выбранным `$python`, который содержит явный путь к `python.exe`.
   Если путь базы отличается от примера, передать фактический `DATABASE_PATH`
   как аргумент миграции. Для проверки доставки запустить каждому боту свой
   процесс в отдельном терминале с этой же конфигурацией и SQLite.

   ```powershell
   & $python -m compadre_assistant --migrate --database-path data/ai-image-usage-acceptance-01.db
   & $python -m compadre_assistant --healthcheck --channels telegram,vk
   # В отдельных терминалах
   & $python -m compadre_assistant --telegram-bot
   & $python -m compadre_assistant --vk-bot
   ```

4. Зарегистрировать доверенный тестовый профиль в личном чате, привязать
   второй канал и сверить внутренний ID обеих identities
   [запросом в режиме чтения](../OPERATIONS.md#проверить-внутренний-id-владельца).
   Зарегистрировать отдельный обычный профиль. Указать проверенный
   внутренний ID доверенного профиля в `ADMIN_TRUSTED_APP_USER_IDS` и
   перезапустить оба тестовых процесса. Для проверки отзыва очистить список,
   перезапустить их снова и проверить сохранённый режим и старую кнопку.

### Подготовка и проверка запуска

1. Собрать `git archive` из выбранного для проверки точного SHA. Посчитать SHA-256,
   передать архив по SCP и сверить SHA-256 на VPS до распаковки. Распаковать
   в новый тестовый каталог и записать идентификатор собранного образа.
   Сверить соответствие образа источнику и отдельно зафиксировать digest
   любого временного файла ограждения входящих событий.
2. Выбрать уникальное имя Compose проекта и отдельное имя тестового образа.
   Использовать абсолютные пути к тестовому Compose-файлу и отдельной
   конфигурации. Настроить оба контейнера на один bind mount тестового
   каталога и один `DATABASE_PATH` внутри контейнеров. Подставить нужные
   настройки каналов и Ask на VPS, сохранив конфигурацию в приватном
   окружении оператора. До старта сверить по проекту и mount, что контейнеры
   используют свежую тестовую БД. Штатные SQLite, selector и backup остаются
   вне тестового проекта.
3. Перед polling повторно сверить, что штатный unit остановлен и контейнеры
   со штатными токенами не работают. Применить миграции к тестовой SQLite и
   выполнить healthcheck обоих каналов. Проверить допуск согласованных
   личных адресов для обычного сообщения, фото и callback до любых
   ответов и загрузок. Адреса и содержимое отброшенных событий в журнал
   приёмки не заносить.
4. После старта сверить оба контейнера по имени тестового проекта и image ID,
   их состояния, признаки polling, отсутствие конфликта polling и стартовый
   счётчик общей SQLite. Зафиксировать модель Ask и состояние подключения
   источника Timeweb без вывода секретов. Сообщить владельцу, когда можно перейти
   к пользовательским действиям.
5. Владелец регистрирует тестовый профиль и связывает два личных канала
   по [командам привязки](../RUN.md#13-посмотреть-доступные-команды). Оператор
   сверяет внутренний ID в тестовой SQLite и меняет тестовую настройку Admin
   при проверке допуска и отзыва. Владелец отправляет команды и тестовое
   фото по матрице ниже, сообщает подтверждённые ответы и результаты нажатия
   кнопок. Отдельный обычный профиль применяется для отрицательной проверки
   после согласования его личного адреса.
6. После успешной проверки сверить имя проекта, контейнеры и путь SQLite.
   Остановить и удалить контейнеры тестового проекта, затем удалить его
   тестовую SQLite и её sidecar-файлы. Проверить отсутствие этих ресурсов и
   записать результат. Штатный сервис остаётся остановленным до указания
   пользователя.

## Проверить наблюдения Ask в новой SQLite

Снимать счётчики до и после каждого последовательного вызова в согласованных
личных чатах. После фоновой записи каждый запрос к модели по вопросу или фото
даёт одну строку. Ожидание ввода, отмена, чтение отчёта и отказ до обращения
к модели оставляют число строк прежним. Запрос выполнять к новой тестовой базе
через соединение SQLite URI с `mode=ro`.

```sql
SELECT COUNT(*) AS total,
       COUNT(tokens_json) AS with_token_counters,
       MAX(started_at_us) AS last_started_utc_us
FROM ask_usage;
```

Число строк в базе фиксирует запись учёта. Отказы без вызова модели
дополнительно сверяются с проверками маршрута в автономных тестах.

### Истечение ожидания в VK (5.2)

Через обработчик входящих VK с временной SQLite, управляемыми часами и
подменой VK API проверили ожидание вопроса и фото. До десяти минут
бот молчит. При истечении срока он один раз присылает сообщение с
командой повтора и возвращает нижнее меню режима ИИ.

Сбой доставки повторяется с тем же `random_id`. Отмена, смена ожидания,
удаление профиля и входящее сообщение, опередившее фоновый проход,
исключают устаревшее уведомление. Фоновый проход VK не обрабатывает
ожидание Telegram. Локально прошли 170 тестов. Проверка с живым VK
входит в следующий шаг приёмки.

### Публикация меню только с сообщением в VK (5.3)

Через обработчики каналов с временной SQLite и подменой API проверили,
что запуск, фоновая сверка и освобождение чата после недоставленной
квитанции не создают исходящего сообщения VK. После освобождения чата
ответ на `/help` возвращает нижнее меню. После отключения ИИ из
привязанного Telegram старые кнопки VK остаются видимыми до ответа
в VK. Нажатие `/ask` объясняет, что возможность выключена, предлагает
`/enable ask` и убирает `/ask` из нижнего меню.

справки и ожидающего ввода. В том числе проверили обновление меню
Telegram и уведомление VK об истечении ожидания. Проверка живых чатов
остаётся на шаге 5.4.
