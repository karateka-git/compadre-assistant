# План этапа 6. Приёмка и завершение документации

Этап проверяет режимы ИИ и администрирования в личных чатах Telegram и VK,
фиксирует результаты и сохраняет действующие сценарии в постоянной
документации. Правила функций описаны в [требованиях](REQUIREMENTS.md), порядок
проверок и выпуска — в [инструкции запуска](../RUN.md#проверка-изменения-кода)
и [маршруте выпуска](../RELEASES.md#маршрут-выпуска).

## 1. Подготовить протокол и завершить локальную проверку

**Статус.** Выполнено в `587cec1`. Коммиты и результаты локальных проверок, подготовка окружения и матрица по обоим каналам записаны в [протоколе приёмки](ACCEPTANCE_RESULTS.md).

- Записать проверенный коммит, окружение, команды и результаты в протокол
  приёмки в этой папке. На `081489d` уже прошёл полный `unittest discover`
  (1348 тестов, 3 пропуска), проверки миграции с `v3.2.0`, три автономных
  smoke, синтетические Compose config и CLI healthcheck. Сверить изменения
  после этого SHA и повторить проверки затронутого кода и конфигурации.
- Сверить с кодом постоянные разделы
  [архитектуры](../ARCHITECTURE.md#границы-модулей),
  [правил сообщений](../USER_MESSAGES.md#выбрать-ответ-по-состоянию-чата),
  [настройки](../SETUP.md#настроить-режим-администрирования),
  [запуска](../RUN.md#задать-вопрос-в-режиме-ии) и [карты кода](../CODE_MAP.md).
  Уточнить найденные расхождения в командах, справке, меню и кнопках.
  Проверить на схемах маршрут фото, профильный доступ и общий источник учёта.
- Подготовить матрицу живых сценариев из шага 2 с отдельными результатами
  для обоих каналов и инструкцию запуска на изолированной тестовой SQLite.
  Отметить доступность тестовых ботов и профилей. На момент составления
  плана в worktree нет `.env`, отдельные тестовые боты и доступ к ним
  не подтверждены. Записать, что требуется для начала живой проверки, и
  продолжить подготовку протокола и документации с доступными данными.

**Готово, когда** зафиксированы результаты локальных проверок для указанного
SHA, актуальные инструкции и матрица живой проверки со статусом окружения.

## 2. Проверить в живых личных чатах Telegram и VK

**Статус.** Ожидает выделенного тестового окружения. Параметры тестовых ботов и доступ к их личным чатам пока не подтверждены. [Подготовка окружения](ACCEPTANCE_RESULTS.md#подготовить-тестовое-окружение).

Для этого прогона пользователь согласовал временный запуск на VPS со
штатными Telegram-ботом и VK-сообществом. Обоих ботов штатной версии
остановили. Тестовый запуск готовится в отдельном Docker Compose проекте
из архива `081489ddc3788f768ac3836fd128c8dc4cc935e6`, с новой общей
SQLite и допуском только согласованных личных адресов. Штатный сервис
возобновляется по отдельному указанию пользователя.
[Порядок запуска и фактические наблюдения](ACCEPTANCE_RESULTS.md#согласованная-проверка-на-vps).

Перед запуском зафиксировать проверку SHA архива, образа, проекта, mount
тестовой БД и фильтра входящих личных событий. После старта зафиксировать
наблюдаемые состояния каналов, использованные модель и тариф. Владелец
проверяет доверенный профиль в двух привязанных личных чатах; для отрицательной
проверки использует отдельный обычный профиль, когда доступ к нему подтверждён.
Операционные токены, внешние ID и секреты в протокол не вносить.

| Сценарий в каждом канале | Наблюдаемый результат |
| --- | --- |
| Состояние после `/exit`, затем `/ask <вопрос>` | Бот предлагает войти через `/ai`. Обращения к модели нет. |
| `/ai`, затем прямой и пошаговый `/ask` | Ответ приходит в исходный чат. Режим сохраняется. Вход в одном канале не открывает режим в другом. |
| Справка, меню, кнопка и ручная команда | Команды соответствуют режиму. Старую кнопку после выхода обработчик отклоняет. |
| Фото в `/ai` без ожидания | Бот предлагает `/get_text_from_image`. Обращения к модели нет. |
| `/get_text_from_image`, затем синтетическое фото с известным многострочным текстом | Текст приходит в исходный чат. Сверены строки, порядок и внешний вид в реальном клиенте. |
| Ожидание, `/cancel`, затем фото | Бот предлагает начать сценарий заново. Обращения к модели нет. |
| `/llm_costs` вне `/admin`, затем вход доверенного профиля | Вне режима отчёт не выдаётся. В режиме доступны ручная команда и кнопка. |
| `/llm_costs`, альтернативный и ошибочный пояс | Отчёт содержит сутки, месяц, год, выбранный пояс и отдельные счётчики неизвестной стоимости. Ошибочный пояс получает подсказку. |
| Обычный профиль и отзыв доступа доверенному профилю | Вход и команда отклоняются. После запуска с обновлённым списком режим скрывается из меню, сохранённый режим и старая кнопка отчёт не открывают. |
| Общий учёт Telegram и VK | Последовательно выполнить вопрос и распознавание из обоих каналов. После фоновой записи ответы отчёта в обоих чатах отражают одну историю SQLite. |

Для проверки общей истории выполнить действия по одному и сопоставить интервалы
времени и изменение числа сохранённых обращений в тестовой базе. Это позволяет
проверить запись и тогда, когда сумма округляется до нуля в отчёте. Записать
ожидание, наблюдение и результат каждого сценария. Не присваивать результату
живой проверки статус по тестам с подставными клиентами.

После успешной проверки сверить границы ресурсов тестового проекта и
удалить его контейнеры и тестовый файл SQLite с sidecar-файлами по
согласованию пользователя. Записать результат очистки в протокол.

**Готово, когда** результаты живых сценариев записаны для обоих каналов и
подтверждено, что обращения обоих каналов отражаются в общем отчёте.

## 3. Выпустить изменение и записать эксплуатационную приёмку

**Статус.** Ожидает выполнения.

- Подготовить сведения для PR и описание проверок. После явного согласия на
  `git push` провести PR по [маршруту выпуска](../RELEASES.md#маршрут-выпуска).
  Записать фактические PR, SHA и подтверждение полного CI для выпускаемого SHA.
- После согласования выпуска и окна работ прочитать
  [правила доступа к VPS](../PRODUCTION.md#ограничения-для-работы-с-vps) и
  применить [порядок установки](../RELEASES.md#5-установить-опубликованный-релиз).
  Настройку владельца выполнить по
  [действующей инструкции](../OPERATIONS.md#изменить-список-доверенных-профилей).
- Сверить Release, установленный SHA, Deployment и техническую приёмку по
  [эксплуатационной инструкции](../OPERATIONS.md#установить-выпуск-и-записать-deployment).
  Записать подтверждение владельца по работе ИИ и отчёта в обоих каналах
  после установки. Указать фактически проверенные сценарии и ограничения.

**Готово, когда** запись содержит версию, SHA, подтверждённый Deployment и
результаты эксплуатационной приёмки двух каналов.

## 4. Перенести результаты и завершить работу с веткой

**Статус.** Ожидает выполнения.

- Перенести действующие правила, сценарии и ограничения в постоянные
  документы. Сохранить результат приёмки в эксплуатационной документации
  в формате, принятом в проекте, и проверить ссылки.
- После слияния изменений и завершения приёмки удалить эту папку отдельным
  завершающим изменением. После удаления закрыть связанный пункт бэклога,
  если он был заведён.
- После слияния всех PR выполнить порядок завершения задачи из
  [AGENTS.md](../../AGENTS.md#рабочий-порядок). Проверить чистые рабочие
  копии, обновить основную ветку только быстрым переходом вперёд и архивировать
  worktree с проверкой использования локальных веток.

**Готово, когда** постоянные документы содержат действующие правила и
результаты, временная папка удалена, а рабочая ветка закрыта по правилам проекта.
