## План проверки development-сборки через ботов

Продумать, как проверять изменения текущей ветки через реальные Telegram и VK,
не затрагивая действующие production-процессы и данные. Сравнить локальный запуск
и отдельный стенд на VPS. Для VPS определить изоляцию Compose-проектов, образов,
`.env`, SQLite-файлов, bot credentials и тестового GitHub vault. Учесть ресурсы
сервера, различия сетевого доступа, обновление схемы development-БД и очистку
тестовых данных. Один и тот же бот не должен одновременно обслуживаться двумя
версиями приложения.

Составить воспроизводимый ручной сценарий для регистрации, связи TG/VK, режимов
чатов, подключения vault, анализа статьи и подтверждённой записи. Отдельно
определить, какие проверки остаются автономными, какие требуют внешних API и
какие действия могут изменить тестовый repository.

Критерии готовности: выбран способ запуска development-сборки; описаны
конфигурация, порядок запуска и остановки, проверочные сценарии и безопасный
возврат к исходному состоянию. Production-БД и действующие боты не участвуют в
проверке без отдельного решения.

## Просмотр сохранённых статей через бота

Добавить в возможность Obsidian команду для просмотра своих сохранённых статей
в Telegram и VK. Показывать ID, название или URL, текущий статус обработки и
наличие готового анализа. Предусмотреть постраничный вывод, чтобы длинный
список помещался в сообщения каналов. Статьи других пользователей не должны
попадать в ответ.

Пользователь должен иметь возможность узнать ID после ошибки анализа и затем
повторить обработку без доступа к SQLite.

Критерии готовности: пользователь находит статью и её статус через бота,
получает нужный ID для повторной обработки; пустой список и ошибки отображаются
понятно, а данные другого пользователя недоступны.

## Разделить повторный анализ и обновление статьи

Сейчас `/reanalyze <ID статьи>` заново скачивает страницу, извлекает текст и
запускает LLM-анализ. Разделить это на два понятных пользователю действия:
повторить анализ уже сохранённого текста без сетевой загрузки статьи и обновить
текст с сайта с последующим анализом. Определить ясные названия команд и
обновить `/help` и ответы бота.

Повтор анализа должен помогать после временной ошибки LLM, не меняя сохранённый
текст. Обновление должно использовать актуальную страницу и сохранять прежние
данные при неудачной загрузке. Оба действия должны проверять принадлежность
статьи пользователю и не запускаться одновременно для одной статьи.

Критерии готовности: пользователь может выбрать нужное действие по ID статьи;
повтор анализа не скачивает страницу, обновление загружает её заново, а справка
точно описывает разницу.

## Разобрать сбои и возобновление semantic index

При первой синхронизации production vault индекс остановился на 128 из 641
chunks после HTTP 400 от embedding API. Повторный `/github_sync` сохранил уже
готовые vectors и довёл покрытие сначала до 320, затем до 641 из 641. Отдельный
диагностический запрос к ранее сбойному пакету прошёл успешно, поэтому причина
прежнего HTTP 400 не установлена. Разобрать такие прерывистые ошибки и решить,
когда нужен ограниченный автоматический retry, а когда вмешательство пользователя.

Добавить безопасную диагностику ответа провайдера: структурированные код,
тип и параметр ошибки, HTTP status, request ID, номер и размер пакета,
длительность и результат повторов. Не записывать raw response, текст заметок,
embeddings или credentials. Проверить устойчивость к повторному сбою одного
пакета и сохранение checkpoints без повторной оплаты уже успешных пакетов.
Уточнить сообщение бота: различать работу, остановку из-за ошибки и завершённый
индекс; при остановке объяснять, как повторить `/github_sync`.

Критерии готовности: причина отказа определяется из безопасных метаданных
или явно фиксируется как неизвестная; временная ошибка обрабатывается по
ограниченной политике повторов, постоянная не вызывает бесконечных запросов;
пользователь видит состояние и дальнейшее действие, уже сохранённые vectors
не теряются.

## Подтверждать начало `/github_sync` сразу

Сейчас при долгой проверке vault и построении embeddings команда `/github_sync`
не присылает ответ до завершения. Отправлять короткое подтверждение начала
операции в исходный чат, а итог синхронизации или ошибку — отдельным сообщением.
Определить поведение повторной команды во время незавершённой синхронизации и
сохранить изоляцию чатов Telegram/VK.

Критерии готовности: пользователь сразу видит, что `/github_sync` принят;
долгая операция завершается одним понятным итогом или ошибкой, а повторные
команды не запускают конфликтующие синхронизации.

Критерии готовности: ассистент использует относящийся к текущему диалогу
контекст без смешения пользователей; пользователь управляет сохранённой
историей и сведениями о себе; объём передаваемого контекста ограничен.

## Потоковая выдача ответа Ask

Сейчас `/ask` подтверждает приём вопроса, ждёт полного ответа модели и затем
отправляет его одним или несколькими сообщениями. Рассмотреть streaming как
возможное расширение: показывать текст по мере генерации ответа моделью.

Определить поддержку streaming у выбранного API и возможности Telegram/VK:
обновление уже отправленного сообщения или отправку последовательных частей,
ограничения частоты и длины сообщений. Продумать, что увидит пользователь при
обрыве потока и как сохранить порядок частей без смешения параллельных запросов.

Критерии готовности: длинный ответ появляется постепенно в исходном чате,
завершение и ошибка отображаются понятно, а действующие ограничения длины и
изоляция запросов сохраняются.

## Переключение профиля Ask без пересоздания сервисов

Сейчас Ask читает `ASK_*` и создаёт API-клиент при запуске каждого процесса.
Изменение серверного `.env` не влияет на работающие Telegram и VK контейнеры;
обычный `docker compose restart` также не перечитывает `env_file`. Добавить
управляемую загрузку профиля из доступного во время работы источника и
переключение провайдера, модели или ключа без пересоздания контейнеров.

Сначала проверить новый профиль и доступность API, затем согласованно
переключить оба процесса на новый клиент. Новые вопросы должны использовать
новый профиль, уже начатые — завершаться на прежнем; закрывать старый клиент
только после их завершения. При ошибке проверки оставить действующий профиль.
Определить безопасный способ обновления секрета и наблюдения за состоянием
обоих процессов без вывода ключей в сообщения или журналы.

Критерии готовности: профиль Ask меняется без пересоздания Telegram/VK
контейнеров и без потери выполняемых ответов; оба процесса подтверждают одну
версию профиля; неудачное обновление не нарушает работу Ask.

## LLM-маршрутизация и выполнение последовательностей действий

Реестр возможностей и явная команда `/ask` реализованы в
[roadmap](ASSISTANT_REBIRTH_ROADMAP.md). Автоматическая маршрутизация остаётся
отдельной задачей и не входит в одноразовый Ask.

Научить ассистента выбирать возможность по запросу на естественном языке,
разбивать составную задачу на шаги и, когда это действительно нужно, выполнять
последовательность tool calls через типизированные интерфейсы возможностей.
Определить границы доступных действий, проверку аргументов, лимиты числа шагов
и времени выполнения, обработку ошибок и порядок подтверждения действий,
изменяющих внешние данные. Обязательную проверку GitHub SHA и подтверждение
изменения Obsidian сохранить внутри его возможности.

Критерии готовности: обычный запрос выбирает подходящую возможность;
составная задача выполняется в пределах заданных ограничений; ошибочный или
неоднозначный выбор не приводит к записи во внешние данные без подтверждения.

## Идемпотентная обработка входящих событий в ядре

Вернуться к задаче после [перехода к модульному ассистенту](ASSISTANT_REBIRTH_ROADMAP.md).
Гарантировать на уровне `core`, что повторная доставка одного события из канала
не запускает соответствующую возможность повторно. Это относится ко всем
возможностям; особенно заметна цена повторов для платных LLM-запросов и
операций, изменяющих внешние данные.

Определить устойчивый ключ события для Telegram и VK, атомарное сохранение
состояния до передачи события в возможность и координацию между процессами.
При повторной доставке учитывать состояния «в работе», «завершено» и
«результат неизвестен»; при возможности повторно выдавать сохранённый ответ.
Хранилище обработки событий не должно превращаться в память диалога для LLM.

Сбой после внешнего вызова, но до сохранения результата нельзя автоматически
считать ни успехом, ни неудачей. Не запускать возможность повторно вслепую:
определить сверку результата либо применение idempotency key, если внешняя
система его поддерживает. Внутренние гарантии Obsidian для GitHub write-back
сохраняются независимо от общего механизма.

Критерии готовности: одно событие передаётся возможности не более одного раза
при повторной доставке до, во время и после обработки, включая перезапуск
процесса; конкурирующие Telegram/VK-процессы не выполняют его параллельно;
неизвестный результат не приводит к автоматическому повтору внешнего действия.

## Внешняя PostgreSQL для Timeweb App Platform

Текущий production-вариант использует SQLite на постоянном диске обычной VM.
Вернуться к этой задаче после решения перейти на Timeweb App Platform с
автодеплоем из GitHub: эта платформа пересоздаёт контейнер при деплое и не
поддерживает Compose volumes.

Будущая работа:

- перенести SQLite-схему, repositories и запросы на внешнюю управляемую
  PostgreSQL;
- адаптировать FTS, hybrid retrieval и транзакции к PostgreSQL;
- передавать параметры подключения к БД через переменные окружения App Platform;
- хранить PEM GitHub App в переменной окружения и создавать временный файл
  ключа при запуске контейнера.

Критерии готовности:

- данные переживают redeploy App Platform;
- автодеплой из GitHub не требует ручного восстановления БД;
- Telegram, VK и GitHub write-back работают с PostgreSQL.

## Обновление VPS без прерывания обработки сообщений

Сейчас `docker compose up -d --build` пересоздаёт контейнеры Telegram и VK.
Сборка образа проходит при работающих старых контейнерах, но при замене
polling-процессов возможна пауза и прерывание обработки текущего сообщения.
Сначала измерить длительность паузы при обычном деплое и проверить, что
происходит с сообщениями и статьями, полученными до и во время перезапуска.

После измерений реализовать управляемую передачу приёма сообщений: новый
экземпляр готовится до остановки старого, старый завершает начатую обработку,
а Telegram/VK polling переключается так, чтобы одновременно работал только
один получатель каждого канала. Учесть повторную доставку, незавершённые
операции с SQLite и GitHub write-back, проверку готовности и откат при неудачном
запуске нового экземпляра. При необходимости добавить очередь или отдельный
режим запуска без polling; конкретный механизм выбрать по результатам замеров.

Критерии готовности: при обновлении нет потерянных или дважды применённых
сообщений, начатая обработка завершается либо безопасно возобновляется, а
переключение каждого канала происходит только после проверки нового экземпляра.

## Codex automation для фонового ревью статей и Obsidian

Необязательное расширение reactive workflow после MVP. Пользователь продолжает
получать анализ и предложение сразу после отправки ссылки; automation в будущем
добавит обработку очереди статей по расписанию.

Цель: дать Codex возможность периодически выполнять интеллектуальное ревью
сохранённых статей и Obsidian.

Шаги:

1. Описать входной contract для automation:
   - где находится проект;
   - как получить доступ к SQLite;
   - как получить доступ к GitHub vault;
   - как отправлять или ставить в очередь ответы бота.
2. Описать статусы статей для automation:
   - new;
   - analyzed;
   - needs_obsidian_review;
   - reviewed;
   - failed.
3. Добавить outbound queue или internal send-message API.
4. Создать Codex automation для периодического ревью.
5. Automation flow:
   - прочитать pending articles;
   - обновить Obsidian index через тот же application use case Этапа 10, не
     вызывая `document_chunker` или SQLite adapters напрямую;
   - найти похожие заметки;
   - создать recommendation;
   - поставить результат в очередь или отправить;
   - обновить статус.

Критерии готовности:

- Automation может обработать хотя бы одну pending article.
- Recommendation появляется в SQLite.
- Пользователь получает recommendation в чате или может её запросить.
- Бот отвечает за transport, automation отвечает за периодическую intelligence.

## FAISS или отдельная vector database

Текущий hybrid retrieval использует FTS5 и линейный cosine scan float32 vectors
в SQLite. Измерить число chunks, p50/p95 latency и память на реальном крупном
vault. Переходить на FAISS либо отдельную vector database только при доказанном
узком месте; существующие application ports должны позволить заменить vector
adapter без изменения review workflow. До измерений это не часть Этапа 10.

## A/B-сравнение embedding-моделей на реальном vault

Сравнить парные Yandex `text-embeddings-v2-doc` и
`text-embeddings-v2-query` с `openai/text-embedding-3-large` на одном
поколении chunks и наборе из 20–30 реальных вопросов к пользовательскому vault.
До теста вручную зафиксировать ожидаемые заметки, затем измерить Recall@3,
Recall@5 и MRR, отдельно разобрать русские запросы, смешанные русский/английский
технические термины и близкие по теме заметки. Учитывать качество, latency,
стоимость переиндексации и размер vectors. Менять production-пару только с
полным пересчётом embeddings; chunks и FTS5 при этом не перестраивать.

Перед началом сравнения повторно оценить его целесообразность: прямой
OpenAI-compatible, нативный REST и gRPC API Yandex принимают только один текст на
embedding-запрос, тогда как текущая OpenAI-модель поддерживает batch. Для этого
проекта отсутствие настоящего batch — значительный эксплуатационный минус
Yandex: массовая индексация создаёт по одному HTTP-запросу на каждый chunk и
требует отдельного bounded concurrency. Не переходить на Yandex только из-за

## Оценить необходимость хеша URL

Сейчас исходный URL хранится в `source_url`, а защита от дубликатов выполняется ограничением `UNIQUE` для `normalized_url`. Перед добавлением отдельного URL-хеша проверить, даёт ли он измеримую пользу для размера базы или скорости поиска. Не добавлять его без подтверждённой необходимости.
