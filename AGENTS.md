# AGENTS.md

Этот файл описывает правила взаимодействия пользователя с Codex при работе над проектом. Он не относится к runtime-логике приложения, но должен учитываться при планировании, редактировании, коммитах, push и дальнейшей разработке.

## Обязательные правила

1. Не выполнять `git push` без явного согласия пользователя.
2. `git commit` можно выполнять самостоятельно, если изменения логически завершены.
3. Сообщения коммитов писать на русском языке.
4. После каждого `git push`, выполненного с явного согласия пользователя, перечитывать этот файл как дополнительный контроль правил.
5. Непосредственно перед началом каждой отдельной задачи, затрагивающей исходный код, полностью перечитывать этот файл. Серия связанных изменений в рамках одного непрерывного шага считается одной задачей и не требует повторного чтения перед каждым файлом.

## Правила написания кода

- Новый и изменяемый публичный Python-код сопровождать docstrings по аналогии с JavaDoc/KotlinDoc.
- Для docstrings использовать Google style и соблюдать общие рекомендации PEP 257.
- Docstring должен объяснять назначение класса, функции или метода. Для нетривиального интерфейса также описывать аргументы, возвращаемое значение и ожидаемые исключения.
- Значения enum, статусы и другие неочевидные константы сопровождать краткими комментариями, объясняющими их смысл.
- Сложные участки реализации комментировать там, где важно объяснить причину решения, ограничение или неочевидное поведение.
- Не добавлять комментарии, которые только дословно пересказывают очевидную операцию кода.
- Комментарии и docstrings в коде этого проекта писать на русском языке, сохраняя английские имена идентификаторов и общепринятые технические термины.

## Архитектурные правила

- Основная единица организации — модуль: общее ядро (`core`) или подключаемая возможность (`capabilities`). Общая ответственность принадлежит ядру, предметная ответственность — соответствующей возможности.
- Внутри модуля придерживаться слоёв `domain`, `data`, `presentation`. `domain` хранит модели, правила, use cases и ports/protocols. `data` хранит реализации внешних зависимостей: SQLite, HTTP-клиенты, LLM-клиенты, чтение конфигурации, извлечение текста через сторонние библиотеки. `presentation` хранит входы, команды, обработчики и представление ответов этого модуля.
- Адаптеры каналов Telegram/VK и CLI отделены от `presentation` конкретных возможностей. Они преобразуют события и ответы канала в общие контракты и обратно, не содержат сценариев Obsidian или других возможностей.
- Для каждого конкретного чата канала хранить отдельный активный режим. После обработки общих команд ядро передаёт сообщение presentation выбранной возможности без анализа ссылок, подтверждений и другого предметного содержания. Предметные правила обычного текста принадлежат возможности.
- Направление зависимостей внутри модуля: `presentation` вызывает use cases из `domain`, `data` реализует ports из `domain`. `domain` не зависит от `data`, `presentation`, SDK, SQL и конфигурации окружения. Чистые слои не зависят от конкретных реализаций внешних зависимостей.
- Ядро не импортирует конкретные возможности и не зависит от их внутренних моделей или сценариев. Возможности взаимодействуют с ядром и друг с другом только через явно определённые публичные контракты; прямой доступ к внутренним таблицам, repositories и реализациям другого модуля запрещён.
- Каждая возможность владеет своими данными: таблицами, DTO, mapper-функциями и repositories. Общее подключение к SQLite и общий порядок инициализации схемы допустимы; отключение возможности не удаляет её данные.
- Для хранения в БД или другом data-источнике заводить отдельные data-модели, если данные проходят через `data`-слой. Не использовать SQL-строки, ORM/driver records или другие структуры хранения как domain-модели напрямую.
- Если data-модель является техническим дубликатом domain-модели для переноса данных, называть её в формате `NameDto`, например `ArticleDto` для `Article`.
- Для DTO допускаются nullable-поля, если часть значений появляется только после сохранения или приходит не из каждого data-источника, например `id`, `created_at`, `updated_at`.
- Между data-моделями и domain-моделями использовать явные mapper-функции или mapper-классы внутри `data`-слоя.
- Domain-модели должны описывать смысл проекта, а data-модели должны описывать форму хранения или внешний формат конкретного источника.
- Composition root находится вне `domain`: он собирает конкретные реализации ports и явно регистрирует включённые возможности в ядре. Сборка возможности может находиться в её `bootstrap.py`; детали сборки не должны протекать в чистые слои. Автоматический поиск плагинов не требуется.
- Классы, реализующие port/protocol другого слоя, должны явно наследоваться от соответствующего `Protocol`, если это не создаёт циклических зависимостей или технических ограничений.

## Рабочий порядок

- Перед действиями с Git проверять статус рабочей копии.
- Перед задачей, затрагивающей production VPS, прочитать docs/PRODUCTION.md и следовать его правилам доступа и безопасности.
- Коммиты можно делать без отдельного подтверждения, но push всегда требует явного согласия пользователя.
- Во время refactor-этапов не оставлять legacy-wrapper, старые публичные функции или совместимые обходные пути только ради старых тестов, если пользователь явно разрешил переход на новый контракт. В таком случае переписывать callers и тесты на новый API, а старый путь удалять.
- Если правило из этого файла конфликтует с текущим планом, сначала уточнить действие у пользователя.

## Development-БД

Правила пересоздания ниже временные и действуют только на этапе разработки.
После завершения этого этапа разрешение на удаление БД без подтверждения
утрачивает силу: изменения схемы должны сохранять данные через миграции.
Удаление БД за пределами этапа разработки требует отдельного явного разрешения
пользователя.

- Пока проект находится в разработке, менять схему непосредственно в
  `compadre_assistant/core/data/sqlite/migrations/0001_initial_schema.sql`; накопительные
  миграции и сохранение совместимости промежуточных схем не нужны.
- Если перед новым запуском существующая БД не соответствует изменённой схеме,
  остановить использующие её процессы и удалить `data/app.db`, а также
  `data/app.db-wal` и `data/app.db-shm`, если они остались. При запуске приложение
  создаст базу заново. Пользователь заранее разрешил такое пересоздание;
  отдельное подтверждение для него не требуется.
- Данные development-БД, включая подключение vault и индексы, можно потерять
  при таком пересоздании; перенос и временная копия БД не требуются.
- Обычные изменения строк БД или исходного кода без изменения схемы не являются
  причиной очистки. Скрипты запуска сами несовместимость схемы не определяют.
- Удалять только файлы SQLite, а не каталог `data/`: в нём также находится PEM.

## Команды пользователя для Codex

- Если пользователь пишет `запусти проект в дебаг`, выполнить `.\scripts\open-dev-start.cmd debug` из корня проекта. Команда должна открыть отдельное окно PowerShell, выставить `APP_DEBUG=true` только для этого запуска и оставить окно открытым.
- Если пользователь пишет `запусти проект`, выполнить `.\scripts\open-dev-start.cmd` из корня проекта. Команда должна открыть отдельное окно PowerShell и оставить его открытым.
- Если пользователь пишет `проверь healthcheck`, выполнить `.\scripts\open-check-health.cmd` из корня проекта. Команда должна открыть отдельное окно PowerShell и оставить его открытым.
- Если пользователь пишет `проверь pipeline`, выполнить `.\scripts\open-check-pipeline.cmd` из корня проекта. Команда должна открыть отдельное окно PowerShell и оставить его открытым.
- Если пользователь пишет `проверь всё`, выполнить `.\scripts\open-check-all.cmd` из корня проекта. Команда должна открыть отдельное окно PowerShell и оставить его открытым.
- Если пользователь пишет `проверь ссылку <URL>`, выполнить `.\scripts\open-process-url.cmd "<URL>"` из корня проекта. Команда должна открыть отдельное окно PowerShell и оставить его открытым.
- Если пользователь пишет `проверь ссылку` без URL, использовать URL по умолчанию: `https://habr.com/ru/articles/198682/`.
- Если пользователь явно просит выполнить проверку без отдельного окна, запускать соответствующий `.ps1`-скрипт в текущей Codex-консоли.
